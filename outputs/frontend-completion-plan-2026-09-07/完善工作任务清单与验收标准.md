## 4. 每项共同适用的完工与验收要求

### 4.1 完工标准：开发负责人交付什么

1. 对源码发现先复现：成立缺陷先写能在修复前失败的行为用例；不成立的给反证，不盲改。新增功能先明确API和状态契约。优先复用现有实现，不引入未经请求的新依赖。
2. 任务范围内页面、表单/弹窗、忙态、空态、失败、重试、返回、刷新和角色控制完整；涉及写入时核对幂等、归属、版本及持久化。纯复制/筛选等本地操作不生造后端。
3. 相关接口类型、文档、配置说明、主账本和证据关联同步；已发布迁移只追加，数据变化有回滚说明。
4. 专项测试、类型/格式/lint及完整相关门禁通过；自审差异和秘密扫描。提交按中文Lore协议说明意图、验证与缺口。
5. 交付候选SHA、变更文件、简化点、剩余风险和回滚路径。代码完工可先登记，缺真实供应商证据不能标REAL_CHAIN_VERIFIED。纯验收任务则交付实际证据和结论。

### 4.2 验收标准：如何客观判定通过

1. 按每条用例记录角色/脱敏账号、前置数据、操作步骤、预期结果；执行后填写实际结果、证据、执行人/时间/SHA。当前96条全部未执行。
2. 请求操作核对实际方法/路径/关键参数及返回；写入、版本、任务、账务再核对相关记录。不能只看成功toast、Mock回调或接口路径存在。
3. 交互附同版本截图/录屏，API附脱敏请求/响应和关联ID，自动化附命令、退出码和日志。失败、权限、重复点击、返回/刷新、过期与迟到响应按下文具体用例验证。
4. 替代服务/隔离测试数据与真实服务证据分开。真实验收还需供应商回执、取回产物、播放/解码与内部账务；授权范围、预算和真实发布/发码在动作前确认。
5. 按阻塞层级签署状态：本期AUTOMATED_VERIFIED用例全通过才签自动化验收；适用的真实用例全通过才签REAL_CHAIN_VERIFIED。任务最终验收要求本期所有适用层级通过；尚缺真实证据时保持待真实验收。待确认/暂缓任务标“不阻塞本期”，纳入范围时启用其指定层级；不适用须写依据，不用旧测试全绿销新流程。

### 4.3 门禁和证据规则

开发期只跑受影响专项。全量门禁以正式TXX/PR为单位，收尾按仓库要求执行一次（候选改动或失败修复后的必要重跑除外），不是机械地每个FP都跑一遍；FP-00先交付FP→TXX→分支→PR映射；其中已包含后端全量pytest，避免再单独重复。PG fixture独占；必要构建、Rust、依赖审计和客户浏览器E2E另核对真实CI结果。

```sh
scripts/pg-fixture.sh start
npm run check
scripts/pg-fixture.sh stop
```

这是后续执行要求，本轮只编计划，没有执行以上门禁。上一轮945前端/76后端专项只是旧基线，不能用来销项新改动。

验收证据实施时按主账本§14登记到既有docs/evidence范围，具体文件名按映射确认。CSV预留实际结果、证据链接、执行人、时间和候选SHA，不预填通过。

**未确认处理**：只读盘点和修复方案可交付；不删除、不批量覆盖、不付费重生成。
