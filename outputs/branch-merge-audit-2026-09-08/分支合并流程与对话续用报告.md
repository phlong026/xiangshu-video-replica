# 分支合并流程与对话续用报告

日期：2026-09-08。范围：本地 41 个分支、25 个工作树、GitHub 4 个开放 PR、仓库 CI 和 Codex 任务目录。状态：审计与流程建议完成，尚未执行分支合并。

## 1. 结论

建议执行：冻结交付快照 → 去重和依赖评审 → 独立工作树整理待合入改动 → 冲突处理与复审 → 本地验证 → PR 评审及三门禁 CI → 按顺序 squash merge → main 验证 → 对话环境交接 → 最后清理。

当前已经存在文本冲突和数据库迁移分叉，无法保证完全不发生冲突。可落实的目标是：冲突在独立环境中解决，未提交代码不丢失，每项有效改动有明确去向，失败候选不进入 main，后续开发从已验证的主线出发。

“所有分支完成处理”的验收口径：每个分支记录为已通过 PR 落地、被其他分支覆盖且核验完毕，或明确保留/暂缓并说明原因。备份历史、运维档案、尚未确定的产品功能应保留，不能为了减少分支数量而直接并入产品。

本报告不修改业务代码、已有文档、任何分支引用、工作树索引或 PR；不启停 PG、不运行全量测试、不调用真实付费服务。合并预演使用 `git merge-tree`，生成对象隔离在系统临时目录，未写入仓库对象库。

## 6. 推荐合并顺序

下面是基于提交关系和当前业务记录的候选顺序；迁移发布状态核实和独有改动评审是执行前置条件。

1. **保护来源和 WIP。** 在独立集成工作树操作，指定一个合并负责人和一个本地 PG 测试负责人。为每条来源记录 HEAD、分叉点、提交范围、WIP 归属和对话目录。交付快照固定后，新开发可在独立任务分支继续，新增提交排入下一批；共享文件、迁移和账本的集成写入串行，不混进正在验收的候选。保存本地 main 的历史引用/归档和已提交快照；WIP 按所属任务完成提交或做可恢复的私有备份。Git tag/bundle 不包含未提交文件，必须分别处理，且不把密钥/运行环境放进公开提交。
2. **小任务与已存在 PR。** 依次评审 #93、修复并验证 #94、评审 #95 的固定 `985ef46`。每次合入后刷新 main 并重新检查下一项。#95 不借用本地同名分支直接推送。
3. **收回本地 main 的 110 个提交。** 将 `aab5099` 保存为只读来源，列出迁移/计费基础、管理后台、素材与口播基础、独立创作、复刻/替换、统计与文档的任务边界及依赖。按唯一任务账本组织小 PR；不默认把 692 个文件一次压成一个未经分项评审的大 PR。已有 merge commit 可能包含冲突修复，提取时比较最终树，不能只挑非 merge 提交而漏掉修复。遇到确实不可拆的原子变更，明确共同任务边界及回滚方式后再安排。

## 7. 每个任务的完整门禁

### 7.1 预审与生成可审差异

- 记录 `source HEAD`、源基线、已覆盖提交、目标 main SHA、工作树路径和责任任务；原开发工作树保持可追溯。
- 独立评审需求、实现、测试、迁移、API/OpenAPI、角色权限、幂等计费、队列、分页与关键外部调用的异常/超时行为。对已有安全与账务实现的不同版本逐项合并，不采用整文件 ours/theirs。
- 使用独立候选分支，以最新 origin/main 为正式 PR 基线。分支名使用仓库规定的任务命名；新的通用集成辅助分支可用 `codex/` 前缀。基线变更时重新审查差异。
- 优先提取经过映射的任务提交/净改动；多父 merge commit、重命名迁移、同文件多任务交叉修改需单独人工可读审查。生成文件在对应源 schema 确定后重新生成，并核对差异。

### 7.2 本地验证

先对受影响行为跑专项；冲突解决产生新逻辑时补必要回归。任务收尾由唯一 PG 负责人启动 fixture，服务端 Ruff/format/mypy 后，在仓库根目录执行一次 `npm run check`。

实际根脚本含：变更秘密扫描、客户端检查、E2E 静态检查、Rust fmt/check、服务端 Ruff/format/mypy、服务端全量 pytest。不要再另跑一遍服务端全量，更不能让其他工作树同时使用或停掉同一个 PG fixture。只有测试负责人确认无人使用后才停止 fixture。

涉及迁移的候选还须检查 Alembic heads/history、空库升级、已发布版本升级，以及存在历史分叉时的兼容升级路径；回滚和再升级只在可丢弃测试数据库演练。确认 API/OpenAPI 与客户端生成类型一致。

PG 套件 skip、失败或环境错误均需明确记录，不能作为所要求 PG 门禁通过的证据。没有代码更改或新的疑点时不重复全量；发生修复、基线前移、失败或迁移调整后，相应验证必须重做。

### 7.3 PR、CI 与最终评审

完成本地自审、验证和中文 Lore 提交后推送候选分支，再创建/更新 PR 到 main。PR 写明具体问题、最终行为、任务覆盖、迁移/回滚和测试缺口；不把旧聊天里的“通过”当成当前结果。PR 也可用 Draft 承载评审，但三门禁是否运行由真实 base/HEAD 和 workflow 决定。

三个必须通过的检查名：`Secret scan`、`Linux quality gate`、`Windows Tauri and NSIS`。Linux CI 还覆盖客户浏览器 E2E、Rust tests、web build 和 npm audit；Windows 覆盖内部/customer NSIS 构建。以对应最终候选和最新 base 组合的结果为准，旧 HEAD 的全绿不能用于更新后的分支。

PR 评论必须实际修复并逐条复核；重大修改、冲突解决、权限或迁移变化后重新评审。不得用强推共享分支、管理员绕过或取消失败检查来获取“全绿”。合并前再次比对已批准 HEAD，确保其没有被其他会话更新。

### 7.4 串行合入及异常处理

一次只合入一个 PR，使用 squash；等待该 main SHA 的 push CI 通过后才放行下一项。main 失败则暂停队列，定位是本次回归、组合错误还是环境故障，修复/回滚并恢复绿灯。

回滚方案随 PR 准备：代码优先通过 revert PR；涉及 schema、数据回填或外部副作用时评估后续依赖，不能假设一次 git revert 就能回滚数据库。追加兼容迁移、数据库备份/恢复演练与真实发布属于独立验证边界。

### 7.5 全部结束的验收

- 每项有效改动都有源提交/WIP → PR → squash SHA 的映射；重复、暂缓、归档都有明确理由。
- 最终 main 的 CI 成功，迁移图与升级路径通过验证；任务账本和证据账本同状态，不把专项测试升级为真实链路完成。
- 角色切换、激活/会话、人物/声音/素材、文案/草稿、复刻/替换/独立生成、计费队列/恢复、归档预览、后台/统计和获准的发布流程完成组合回归。
- 本地正式 main 与远端一致；开发分支从这个已验证基线产生。
- 三处 WIP 均已提交、迁移到后续任务或明确保留；旧对话的工作目录已交接。
- 存在暂缓任务时，报告具体剩余项，不宣称全部功能已落地。

## 8. squash 后的正确同步方式

squash 生成新的提交，原分支提交可能不再是远端 main 的祖先。后续分支的 PR 不会必然自动缩小，继续在旧分支叠加开发容易再次带入已经落地的内容。[GitHub 合并策略说明](https://docs.github.com/en/pull-requests/reference/pull-request-merges)

因此：

1. 保存合并前源 HEAD、旧基线和每次 PR 的覆盖范围，后续审计使用不可变 SHA，不能把会移动的 `main` 名称当作旧边界。
2. 合并后的后续任务优先从最新 origin/main 新建分支，迁移经过核对的独有改动；只有明确提交区间、merge 拓扑和重复补丁后才使用 `rebase --onto`。
3. 不对共享/在用旧分支做未经协调的历史改写，不直接 `rebase origin/main` 重放整个旧集成历史，不将旧分支整棵树覆盖新 main。
4. 本地 main 的 110 提交历史先保存归档。全部有效内容已落地、未提交内容已保护、没有工作树占用时，可将旧本地 main 改名保留，再从 origin/main 建立干净跟踪分支；无需把 `reset --hard` 当作必经步骤。
5. 最终验收采用覆盖清单、净差异与行为验证；`git branch --merged` / `--no-merged` 只作祖先关系证据，不作为 squash 后的唯一删除依据。

## 9. 原对话窗口能否继续使用

可以继续沟通，Git 合并本身不删除聊天历史。代码环境必须重新核对：

| 原任务环境 | 合并后的影响 | 续用方法 |
|---|---|---|
| 多个对话共享同一个 local 目录 | 它们看到的是该目录当下的文件和当前分支；其他窗口切分支会影响它们 | 讨论可继续；代码写入串行，先重新确认路径/HEAD/未提交内容 |
| 独立 worktree | 仍保留自己的 checkout；主线合并不会自动刷新它 | 旧内容用于追溯；继续开发前从最新 main 建立新任务分支并只迁移剩余改动 |
| 手动删除了 worktree | 聊天可保留，但原代码目录不可访问 | 先恢复或重新关联有效工作目录；不要假定自动切回主目录 |
| Codex 管理的 worktree 被应用清理 | 官方文档说明会保存快照并在重新打开任务时提供恢复选项 | 使用应用恢复/交接能力；不要把该承诺推广到任意手工创建或删除的 `/private/tmp` 工作树 |

官方说明工作树隔离、Handoff 和删除后的历史/恢复行为，见 [Codex Worktrees](https://developers.openai.com/codex/app/worktrees/)。使用 Handoff 能移动任务环境，但不等于自动整合最新 main；忽略文件、数据库、依赖和运行服务仍须单独核对。

本次 `list_threads` 返回的前 50 个任务中，有 14 个任务的 cwd 指向当前主目录。例如「0907 ｜ 盘点前端页面与后端实现」和「0907 ｜ 梳理文案工坊业务闭环」均如此。标题或聊天主题不证明其绑定独立分支；元数据也不排除某次命令显式操作另一工作树。后续执行前以真实命令的工作目录为准。

在旧窗口继续代码任务时，可先给出这段交接说明：

> 该任务的原分支已通过 PR 合入 main。请先只读核对实际工作目录、当前分支、HEAD、未提交修改、最新 origin/main 和对应合并记录，并读取最新任务账本。保留旧对话作为历史背景；后续修复从最新 main 的新分支开始，仅迁移未落地的改动，避免重复实现或覆盖已有修复。

不要求删除旧对话或重新解释全部历史。完成任务可保留用于追溯；新功能建立新的任务边界。若使用同一旧对话继续实现，应先完成环境和基线交接，再写代码。
