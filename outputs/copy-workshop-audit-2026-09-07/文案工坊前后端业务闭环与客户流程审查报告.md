## 1. 结论

**文案工坊目前属于“基础能力已经存在，面向客户的完整业务闭环仍未完成”。不能认定前端所有功能都已与后端接通，也不宜将当前顺序作为最佳客户操作流程。**

这不是纯展示页面：云草稿、我的文案存储、项目脚本版本、AI 改写任务、ASR 任务及数字人口播任务都有实际后端实现。不过，页面按钮、任务执行器和下游消费的数据之间存在断点：

1. **客户 PostgreSQL 模式的标准 Worker 未接入音频提文案消费分支。** 入队成功不代表会执行，这是最优先修复项。
2. **爆款详情“提取文案”只准备媒体并跳页，没有提交转写，也没有正确替换整套来源上下文。** 新来源可能与旧项目、旧终稿混在一起。
3. **“按 IP 二创”打开旧分析工作区，未直接提交当前工坊文案与 IP。** 该分析入口还没有将 `identityId` 传给实际改写 Hook，后端已具备的 IP 快照能力没有通过此入口完整使用。
4. **“确认终稿”先把本地状态置为成功，云保存和项目脚本同步另行执行。** 无镜头卡的纯 ASR 项目不能完成项目脚本发布；页面确认状态与项目可用脚本不是同一件事。
5. **“保存版本”实际覆盖同一条文案，不是历史版本管理；套用旧文案又未恢复来源及 IP。**
6. **工坊终稿进入视频复刻后，生成请求仍会取拆解原稿作为脚本输入。** 保留在页面状态中的人工终稿不等于最终被生成链消费。
7. **异步结果、任务恢复和回到上一步不完整。** 转写迟到可能污染新草稿；ASR 超时提示去任务中心，但任务中心没有 ASR 项目。

最接近闭环的客户路径是：**直接编辑文案→选择人物→确认→进入数字人口播→选择可用声音/分身→报价并提交**。这条路径不必依赖来源视频或镜头卡，但云保存可靠性、内容限制提示、真实服务及任务返工仍需补足。

本次专项测试共 **365 passed，0 failed，0 skipped**：前端 314，后端 51。这是相关文件中的专项用例总数，非 365 个独立工坊验收场景。通过项主要是模拟接口与独立 SQLite 测试，不能覆盖上述 PostgreSQL Worker 入口、真实付费 Provider 和跨模块整链问题。本次未给出人为加权的“总体完成率”。

## 2. 审查方法与判定口径

按客户操作顺序检查：页面控件→事件处理→前端 API→后端路由/权限→领域逻辑→数据库→Worker→外部调用→结果回填→下游读取。对上下游状态分别核对 `projectId`、`sourceId`、`sourceAssetId`、`script.id/text/original/version/confirmed`、`ipId`、`returnTo`。

| 标记 | 含义 |
| --- | --- |
| 已实现 | 对应源码链存在；若只针对局部能力，不延伸到完整客户链路 |
| 部分实现 | 有实际处理，但缺接线、前提、数据交接或失败恢复 |
| 仅跳转/展示 | 当前控件只改变页面或展示数据，没有执行它名称所暗示的业务 |
| 未接入 | 当前入口没有目标业务调用；不等于仓库其他页面完全没有此能力 |
| 运行依赖待验收 | 需要真实配置、媒体、供应商或客户 PostgreSQL 环境才能验证 |

下文 `[F1]` 等链接定位源码文件及起始位置，紧随的数字为本次快照的具体行号。辅助备忘保存更细的追踪和复现命令。旧报告仅用作检查线索，完成度以当前源码为准。

### 来源切换的已复现错误

在当前 `patchStudioDraft` 上执行“项目 A＋资产 A＋已确认稿 A，仅改 `sourceId=viral-B`”：结果仍保留 `projectId=A`、`sourceAssetId=A`、稿 A 和 `confirmed=true`。这与爆款详情当前调用完全对应。页面可以显示 B 来源，却继续携带 A 的终稿与项目。复现记录见 `flow-audit-notes.md`。

另一个问题：上传 ASR 成功回填将 `sourceId` 写为 `projectId`，但工坊来源条的 `findSource` 只在资产/爆款列表按 ID 查找，因而可能显示“尚未选择来源视频”。这主要是标识符语义错配，不代表上传资产一定丢失。[F2] 883–885；[F1] 87–105。

## 5. 后端按调用顺序检查

### 5.1 云草稿与我的文案

1. `[B1] studio_draft_routes`：6 类读写删除路由均存在；读接口使用登录身份，写接口使用 `BusinessDbDep.write()`。不是假接口。
2. `[B2] studio_drafts`：按 user_id 隔离；工作草稿单用户单 kind upsert；payload 上限 512000 字节；revision 递增；保存文案非空校验、文字上限 100000；同 script_id 覆盖；列表上限 50。保存拒绝 auditor。
3. `[M1] 067_studio_drafts`：两个表及唯一索引存在；用户删除级联；payload 为 JSON 文本的兼容存储。实际迁移编号是 **067**，不能照旧设计文档里的 058/059 重建。
4. 这些表是工作草稿及复用文案域，独立于项目 script 版本，隔离方向合理。缺口在前端成功状态、版本语义、上下文映射与可靠恢复。
5. last-write-wins 是现有合同，revision 未用于客户端乐观锁。它不足以解决同页自动保存、确认保存并行请求乱序；此为需补实验的风险，不在本报告中冒充已发生的数据事故。

### 5.2 音频转写

1. `[B5] script_from_audio_routes`：POST 项目提取返回 202；可按任务 ID 或项目 latest 查询；读写均检查项目访问，写入走会话写事务。
2. `[B6] script_from_audio`：验证项目、来源资产归属及角色，按 project+idempotency key 保存任务；存在 PENDING/RUNNING/成功/失败/不确定状态，持久化原始请求和结果。此处未充分校验资产媒体类型/大小，不能说已完成视频输入的全部校验。
3. 处理链为存储读视频→ffmpeg/ffprobe 抽音频→临时上传及可访问 URL→ASR→结果写 `result_json`→清理临时音频。**ASR 结果没有直接写项目 scripts，这是合理隔离，不是缺少落库。**
4. `[B7] asr`：Fun-ASR 短音频同步/长音频异步适配存在；测试用 StubTransport，不证明真实识别质量。配置缺失会抛 `AsrProviderError`，但入队路由没有转换成客户业务错误，最终可能得到通用 500；不能把“内部抛出错误”当作“客户能明确理解错误”。ffmpeg、签名媒体可访问性、供应商配置均需运行验收。
5. `[B8] generation_worker`：SQLite 主循环接入音频任务领取/执行；PG 主循环没有对应分支。生产要求 PG，故 **当前代码缺少生产任务消费者**。这不是“缺密钥”的问题，先补代码再谈真服务联调。
6. 恢复/并发机制弱于已有改写域：活跃任务先查后插但没有对应活跃唯一约束；完成/失败更新未按领取者及状态做条件保护。旧执行者迟到写回可以覆盖恢复后的状态，详见后端备忘。新增 PG 消费时必须一起验证，避免把队列入口补上后引入重复执行。
7. 长音频供应商 task_id 只存在于局部变量，没有写数据库。进程内同步轮询，未为 ASR 续租；慢请求可能超过 20 分钟租约。发出供应商请求前的抽音准备阶段已经标记 provider_started，而部分网络/轮询超时又被归为普通 FAILED，故“确实失败”“已受理待取回”“尚未调用模型”的恢复语义不一致。
8. 临时对象在正常结束的 finally 中尝试删除，失败只告警，没有复删任务；任务表的 audio_object_key 未被业务写入，进程崩溃后无法靠它找回清理。源码定义的 2GB 上限未参与执行，处理读取完整视频 bytes，会增加大文件内存压力。ASR 只保存全文/时长，未交付设计提及的词级时间戳；语言元数据固定 zh，不能推定已有准确多语言标识或可编辑字幕时间轴。

### 5.3 AI 改写与 IP 画像

1. `[B3] generation_routes`：项目改写路由、单任务读取、按项目/IP 取 latest 已实现。请求包含 text、可选 identity_id、幂等键；没有独立 studio-draft 改写入口。
2. `[B4] script_rewrite`：验证文本、项目访问和人物归属；冻结 IP 画像快照/hash/revision；任务入库；活跃任务与重放保护；Worker 调用文本模型并保存结果。PG Worker **有**改写任务分支，不能和 ASR 缺失混说。
3. IP 快照覆盖名称、身份、服务范围、目标受众、表达方式；提示词约束保留核心信息、节奏、口语化、同语言、新开头及避免过度照搬。选 IP 时还要求不虚构身份、经历、案例、资质、数据、效果保证或服务承诺。
4. 上述内容是提示词要求，并非输出事实核验。没有生成后的相似度/事实/字数±20%/目标时长自动验收；缺少客户可填写的目标时长、具体受众任务、营销目的等工坊输入。
5. 结果校验偏弱：模型返回 `content=null` 可经字符串转换成为 `"None"`；`finish_reason=length` 截断稿也未被拒绝，后端隔离复现已确认。固定 2048 输出 token 与允许 20000 字符输入还存在长稿不完整风险。
6. 工坊按钮接入 `[F8] LiveWorkspacePanel` 时没有传当前稿/IP；`[F9] AnalysisWorkspace` 调 `[F10] useGenerationDrafts` 没传 identityId。**后端支持 IP 改写，不代表此页面入口已支持。**

### 5.4 确认稿与生成模块

1. `[B3] POST /projects/{id}/scripts`→`[B9] create_script_version`：必须有本项目最新且未 stale 的 shot_card_version_id；正文非空；保存全文、字数、预估口播时长、镜头映射、审计记录。
2. 这条项目脚本依赖适用于视频复刻。纯文字/纯 ASR 数字人口播没有天然镜头卡，不应要求客户先做视觉分析才可确认文案。
3. `[B11] oral_routes`→oral 领域：接收最终 `script_text`，验证人物/分身/声音归属、资产就绪及声音确认，保存任务并衔接现有计费。这里的确认是声音资产确认，服务端不校验工坊 confirmed。当前工坊→口播取的是 `state.draft.script.text`，这点正确。
4. 口播任务**已经保存 script_text 正文快照**，但请求没有绑定工坊的服务端不可变终稿版本；客户端的 scriptId/version 未作为终稿版本凭证写入此请求。现有“已确认”是界面工作流状态，不能作为服务端已确认版本的证据。若产品只要求用户点击确认，未必需要增加新审批系统；需要补齐的是版本关联及利用已存正文返回工坊的映射。
5. 视频复刻 `[F1] sendGeneration` 用拆解 originalScript/镜头 spoken_text 构造脚本；`[F3] runReplicaGeneration` 再创建项目脚本并编译。未消费工坊已编辑正文，详见下节。

### 5.5 已有能力的验证边界

鉴权、租户隔离、服务端密钥存储和任务日志均有现有基础，不应因新页面断链就推断整个后端没做。当前专项使用开发身份/SQLite；新增文案路由没有纳入已检查的客户 fencing 参数化名单，仍应补客户会话失效的 PG 验证。ASR/改写的外部用量成本及面向客户的收费/配额未形成此工坊可见闭环；旧 C7 决策明确收费另行确认，不能自行设价，也不能对客户承诺无限免费。

**复刻用错稿的精确链：** `[F1]` 508–549 保留同项目人工编辑稿，只证明内存没被覆盖；到 849–858 创建 `scriptFallback` 时却不读 `state.draft.script.text`；`[F3]` 1121–1129 将 fallback 保存为新项目 script 后编译。因而“页面保留我的修改”的专项测试可以通过，同时真正的生成仍使用另一份稿。

**确认终稿的两种语义应拆清楚：** 客户确认可用于 TTS 的口播稿，不必有镜头卡；若选择视频复刻，再执行“将终稿适配/发布到该项目的分镜脚本”。当前前端把第二步当作第一步的软副作用，导致正常口播准备也可能出现项目同步失败提示。

## 8. 从客户视角，推荐的业务步骤

这是结合当前模块职责提出的流程建议，尚未改变已冻结业务规格或实施代码。

### 8.1 新写/粘贴文字的客户

**进入工坊→新建或继续草稿→输入/粘贴原文→可选人物 IP→可选 AI 改写→人工修改→保存并确认终稿→选择用途。**

不要求先上传视频、创建分镜或选择数字人分身。客户已经有稿时，来源只需标注“直接输入”。人物 IP 在需要风格化改写时选择；普通稿可以先编辑，去口播前再选择发言人物。AI 改写是辅助，不应成为必须步骤。

### 8.2 从视频获得文案的客户

**上传/选爆款/选素材→确认来源→后台提取→核对转写原文→选择 IP 与本次表达目的→改写/编辑→确认终稿→选择用途。**

视频有可用音轨就走 ASR，不必先做视觉分镜。先保存来源资产及任务 ID，再进入显示进度的工坊；允许离页，完成后可恢复。链接解析失败、无音轨、视频不可访问、服务未配置，应给出具体下一步，如上传文件、手工粘贴或重试原任务。

### 8.3 文案用于数字人口播

**已保存的终稿→发言人物→可用声音/分身→预计时长与实际报价→提交→任务结果→预览→保存/发布。**

工坊不负责绑定全部音视频配置，也不直接启动付费成片。若口播页换了人物，明确提示自我介绍可能不匹配，允许一键回工坊检查；回来仍是原创作，不丢声音/分身以外的有效输入。

### 8.4 文案用于视频复刻

**终稿→选择/确认来源项目→拆解并确认分镜→把终稿映射到镜头→确认人物/首帧与视觉 Prompt→报价生成。**

分镜依赖应放在这一分支。若客户只改口播、不改画面，也应在生成前明确显示“使用终稿 Vn”，并能核对被编译的文本。源分析原稿不应静默覆盖客户终稿。

### 8.5 从已有任务返工

**打开原任务→复制该任务的文案及配置为新草稿→修改→撤销确认→再次确认→新任务。**

原任务结果、原脚本快照保持可追溯；新稿与当前正在编辑的另一篇作品分开。失败/不确定的原任务恢复与“用同样素材再创作”是不同动作，不能混用以免重复请求外部服务。

### 8.6 建议统一的页面状态

页面应让客户看清四件事：**现在处理哪份来源、当前文本是否已保存、是否是已确认终稿、下一步会使用哪一版。**

建议的可见状态为“空白/待提取→提取中→待核对→编辑中→保存中→已保存待确认→已确认→已送往某创作”；失败保留原稿并提供重试。确认只针对本稿内容与人物语境；项目分镜发布另有状态。不要用一个布尔 confirmed 同时暗示“用户看过”“云端落库”“项目已绑定”“可生产生成”。
