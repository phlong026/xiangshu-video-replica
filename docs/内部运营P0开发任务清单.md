# 内部运营 P0 开发任务清单

> 版本：P0.1
>
> 整理日期：2026-08-19
>
> 状态：实施中
>
> 唯一架构依据：`docs/内部运营与ZPay计费管理文档-P0.md`
>
> 规则：本清单只覆盖内部 P0；客户销售价、公开注册和完整运营后台进入后续版本

---

## 0. 开发纪律

1. 新功能先写失败测试，再实现通过。
2. 复用现有 FastAPI、React/Vite、Worker、Alembic、COS、cryptography 和 SettingsRepository。
3. 不新增支付微服务、Node 服务、React-admin、PostgreSQL、Redis、Scheduler 或完整计费平台。
4. 所有金额使用整数分，所有条数使用整数。
5. ZPay 密钥不得进入客户端、响应、日志、测试快照或 Git。
6. 真实支付必须单独取得授权；自动化测试只能使用固定签名样本和 Fake 回调。
7. 完成报告区分“代码存在、自动化通过、真实 ZPay 已验收”。

## P0-1：冻结规则与数据迁移

- [x] 在服务端设置中增加内部基础价 1000 分、最低充值 10000 分、充值步长 1000 分。
- [x] 增加 `internal_access_tokens`、`wallets`、`wallet_transactions`、`recharge_orders` 迁移及 downgrade。
- [x] 为订单号、ZPay 订单号、充值入账、任务冻结和任务终态增加数据库唯一约束。

- [x] 订单保存 `INTERNAL`、内部基础价、实际收费价、最低充值和充值步长快照。

- [x] 业务 API 使用内部 Bearer Token，云端关闭开发身份头和固定桌面用户旁路。

出口门：

- [x] Alembic upgrade/downgrade 通过。
- [x] 负余额、重复订单号和重复终态均被数据库拒绝。

- [x] 原始内部令牌只在签发时出现一次，撤销后立即 401。

## P0-2：ZPay 签名与订单创建

- [x] 用 Python 标准库实现独立 ZPay 签名函数。
- [x] 增加官方排序、空值排除、不编码后签名和小写 MD5 测试。
- [x] 新增 `POST /api/recharge-orders`。
- [x] 请求体只接受整数 `amount_fen`；服务端校验 100 元起、10 元步长，不接受客户端条数和价格。
- [x] 生成不超过 32 位、仅含数字的唯一商户订单号。
- [x] 返回页面跳转支付所需的签名表单参数。
- [x] ZPay 网关地址只允许来自部署配置和允许列表。
- [x] `notify_url`、`return_url` 从公开基础域名派生且不带查询参数；商品名称明确体现条数充值用途。

出口门：

- [x] API 传入 10000、11000、20000 分创建成功；9900、10100 和非整数分失败。
- [x] 伪造条数、价格、商户号和回调地址不生效。
- [x] Node Demo 不作为运行依赖。

## P0-3：回调、幂等入账与查单

- [x] 新增 `GET /api/payments/zpay/notify`。
- [x] 验证签名、`pid`、订单号、金额和 `TRADE_SUCCESS`。
- [x] 在一个事务内更新订单、插入 `CHARGE`、更新钱包。
- [x] 成功或已处理订单在 5 秒内返回纯文本 `success`。
- [x] 回调事务中禁止外部查单、COS/Provider 调用和大对象日志写入。
- [x] 回调使用短数据库等待预算；SQLite 锁未及时取得时不返回 `success`，等待 ZPay 重试。
- [x] 重复回调、并发回调和金额冲突均有回归测试。
- [x] 新增只展示、不入账的 `return_url` 页面。
- [x] 新增订单状态查询和管理端手动 ZPay 查单。
- [x] 主动查单复用同一个入账服务函数。
- [x] 外部请求设置超时并做脱敏错误日志。
- [x] 未支付订单的 ZPay 订单号使用数据库 `NULL`，不使用空字符串。

出口门：

- [x] 一个订单无论回调多少次都只增加一次条数。
- [x] 错签名、错金额、错商户号和非成功状态均不入账。
- [x] 直接访问返回页不会改变余额。

出口门：

- [x] 所有成功、失败、取消和重试路径都有账务测试。
