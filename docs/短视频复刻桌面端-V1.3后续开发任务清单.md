## 0. 使用规则

### 0.1 状态标记

| 标记 | 含义 |
| --- | --- |
| `[x]` | 已完成，且证据路径已填写 |
| `[~]` | 代码或局部 UI 已存在，但未达到本任务验收标准 |
| `[ ]` | 未开始或无可验证实现 |
| `[!]` | 依赖真实账号、外部资料、Windows 机器、证书或业务签字 |

不得只因接口、组件、测试文件或打包配置存在就勾选任务。每项必须满足本清单中的退出标准。

### 0.2 开发纪律

每个子任务按以下顺序执行：

1. 写一个失败的回归/契约测试；
2. 用最小改动实现；
3. 跑目标测试；
4. 跑相关 lint、类型、格式、构建和安全检查；
5. 查看完整 diff，确认没有覆盖他人未提交改动；
6. 一个逻辑变更一个中文 Lore 提交。

数据库迁移必须可逆；人物历史版本、项目快照和资产引用不得通过破坏性迁移重写。

### 1.2 不能视为已完成

| 缺口 | 直接证据 | 影响 |
| --- | --- | --- |
| 人物身份四层模型不存在 | `003_characters.py` 只有 `characters.reference_asset_ids_json` | 无法表达真人、人设、版本和资产审核 |
| 多视角人物资产生产不存在 | 无 CharacterImageProvider、生成任务、审核/发布 API | 不能从一张真人图建立角色包 |

| 一级导航不完整 | 当前只有“项目、设置” | 人物库、新建复刻、任务记录不是独立可达入口 |
| 主流程未贯通 | `App.tsx` 只直接串到上传/分析；后续能力散落在组件/API | 员工无法完成完整生产闭环 |
| 客户端缺脚本/Prompt/批次创建调用 | 手写 `api.ts` 没有对应创建函数 | 只能后端或测试发起生成 |

| 通用 retry 端点不改变任务状态 | `rbac_routes.py` 只审计并返回 accepted | 失败任务无法从该入口真实重试 |
| 真实 Provider 模板未填 | `真实Provider验收记录模板.md` 仍为 SOURCE_PENDING | 不能标记 PROVIDER_VERIFIED |
| Windows 检查项未填 | `Windows内测与运维手册.md` 第 8 节 | 不能标记 WINDOWS_VERIFIED |

## 14. 推荐实施顺序

第一开发增量只做人物资产纵向切片，不同时重构现有 H3 后端：

1. P0-00-01：保护当前工作树并建立功能分支；
2. P0-00-02：先写人物领域 API/迁移失败测试；
3. P0-01：完成四层人物模型和旧数据兼容迁移；
4. P0-02：打通真人源图上传、授权、人设和版本；
5. P0-03：FakeCharacterImageProvider、7 视角、审核、发布、匹配；
6. P0-04：人物库桌面端；
7. P0-05/P0-06：复用现有后端完成项目、Prompt、批次和结果 UI；
8. P0-07：桌面 FakeProvider E2E；
9. P0-08：真实 Provider；
10. P0-09/P0-10：Windows 和内部发布。

可并行但不得越过依赖：

- 后端人物模型与前端五入口 Shell 可并行；
- CharacterImageProvider 真实选型可与 FakeProvider 实现并行；
- Windows 构建环境准备可提前，但实机验收必须使用通过 Gate 1/2 的同一提交；
- Provider 证据收集不能替代本地契约测试，反之亦然。
