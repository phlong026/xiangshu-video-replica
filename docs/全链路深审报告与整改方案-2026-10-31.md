## 一、总体结论

**资金安全主链路质量很高**：充值结算内核（单一 `confirm_recharge_payment` 三入口共用 + 三层应用
幂等 + 三层数据库唯一约束）、扣费原子性（行锁 + 条件 UPDATE + 列 CHECK 三重）、报价快照锁定与
触发器防改写、IDOR 全谱系 404 掩蔽 + 拒绝审计、SQL 纪律（113 处 f-string SQL 全部溯源到白名单/
常量/占位符，无可达注入点）、会话 fencing（每请求查库行锁重比五元组）均属高水准。

**真实风险集中在四类**：

| 维度 | 核心问题 | 最高级别 |
| --- | --- | --- |
| 业务逻辑（资损） | 批级付费重生成绕过全部门禁；人物域重复付费调用；Metaso 缺秒数积分无限期冻结 | **P0×1** |
| 支付系统 | 掉单恢复与对账完备性弱（"不重复记账"极强、"不漏记账"缺发现手段） | P1×1 |
| 并发 | 3 套租约机器过期即 FAILED+可重试（用户重试与原 worker 双执行/双付费）；async 路由同步 SQL 阻塞事件循环；请求级连接持有 | P1×6 |
| 安全 | 无 P0/P1 漏洞；API Key scope 白名单外默认放行、子账号权限 fail-open 属横向收敛不足 | P2×2 |

计数：**P0×1，P1×13，P2×30，P3×30+**（分级标准：P0 资损/安全漏洞/数据损坏；P1 正确性缺陷/
竞态/体验断裂；P2 质量与收敛不足；P3 建议项）。

## 二、支付系统

### 2.1 健康度结论

结算内核无 P0/P1 资损路径：验签常量时间、金额三方核对整数分、并发重复回调被"订单行锁 + PAID
早退 + 条件 UPDATE"与"交易号部分唯一 + CHARGE 每单唯一 + 幂等键唯一"六层兜底；充值到账同
savepoint 事务、钱包原子自增带 int4 溢出护栏；退款以 credit-lot 不变量 + 模糊账拒绝转人工 + 钱包
非负 CHECK 三层防穿仓（审计未能构造出穿仓路径）。

### 2.2 发现

**[P1] 已支付/CLOSED 订单失去全部补单入口（ZPay 无扫单 + sync 拒 CLOSED + 扫单只看 PENDING）**
`payment_routes.py:401-410`（人工 sync 在 PAID 早退后 `status != "PENDING"` → 409）、
`zpay_payments.py:161-164`（扫单谓词固定 PENDING）、`zpay_payments.py:458-472`（结算例程本就
接受 PENDING/CLOSED 入账——路由守卫比内核更严，本末倒置）、maintenance 单元只有 native 两个
脚本。后果：ZPay 丢单（回调丢失且网关重试耗尽）无任何自动兜底；微信侧 reconcile 瞬时失败被
skip 后紧跟 close 置 CLOSED，此后三入口全部放弃，仅剩 ~24h 网关重试一条腿。
**修复**：sync 放开到 CLOSED+窗口内；为 zpay 增加对等的 stale-PENDING 扫单并入 maintenance；
close 跳过"上轮 reconcile 刚 skip"的单。

**[P2] 对账口径发现不了两类账差** `control_routes.py:2639-2673`：①`CHARGE.available_delta ≠
recharge_orders.credits`（多记/少记积分但钱包同步改）不可见；②无面向网关的对账，PENDING 只计数
不分账龄。**修复**：加第四类 `charge_amount_mismatch` + PENDING 账龄分段 + 对账快照定时落库。

**[P2] 套餐权益授予失败被静默吞掉** `zpay_payments.py:528-542` 仅 logger.error，资金照常提交，
"人工补授"无任何队列/告警承接。**修复**：同事务插运营队列行或走 alert_delivery。

**[P2] 支付回调端点无速率限制** `payment_routes.py:208-285`：每个到达的 notify 都做配置读取 +
Fernet 解密 + MD5/RSA 验签，微信验签失败路径可触发最长 10s 平台证书下载占线程池。
**修复**：验签失败来源套 `consume_rate_limit`；商户配置短 TTL 进程内缓存。

**[P3]×5**：内部通道下单无幂等封套（`recharge_routes.py:427-487`）；zpay 取码外呼后不复核订单
状态（:900-953，微信分支有）；manual sync 在请求事务内外呼 3s（`payment_routes.py:437-449`）；
WalletPanel 金额换算浮点路线（`WalletPanel.tsx:127-141`，客户侧已修）；submitPaymentForm 双份
实现且 `rel=noopener` 对 form 无效。

## 三、业务逻辑（计费 × 生成 × 人物 × 采集）

### 3.1 [P0] 批级付费重生成对进行中批次无终态门禁 → 双份生成 + 双份扣费（已人工复核确认）

`generation.py:2712-2918`（`regenerate_generation_batch`）vs 任务级 `generation.py:3014-3114`：

- 批级 SELECT 源任务**不过滤状态**（:2756-2776 无 status 列），对每个源任务插 PENDING 替代 +
  `_reserve_generation_credit` 全额新预扣（:2850-2892），**全程不写 `superseded_by_task_id`**
  （该 CAS 写入只存在于任务级 :3103-3105）。
- 任务级有完整门禁：`SOURCE_TASK_ALREADY_SUPERSEDED` 检查 + `require_task_paid_regeneration_state`
  （:3360-3389）+ CAS supersede。
- 端点 `POST /generation-batches/{id}/regenerate`（`generation_routes.py:729-766`）只做 ACL。
- 后果：对 RUNNING/SUBMISSION_UNCERTAIN 批次调批级重生成 → 旧任务继续跑（旧预扣冻结）+ 新任务
  再次付费提交，同 prompt 双份生成、钱包双份占用。`available_actions` 的 UI 约束可被 API 直达绕过。

**修复**：批级入口逐任务复用 `require_task_paid_regeneration_state` + 与任务级相同的 CAS supersede
写入；SUBMISSION_UNCERTAIN 源任务先强制 RECONCILE。

### 3.2 [P1] Metaso 成功但不回传秒数 → 货已交付、钱无限期冻结

`generation.py:7624-7632`（`_metaso_output_seconds` 缺失返回 None）→ `:6068` →
`internal_billing.py:720-730`（usage 为 None 显式跳过结算保持 PENDING）→
`usage_billing.py:749-751`（自动对账只挑 `actual_output_seconds IS NOT NULL`）→ 唯一出口是管理端
人工补秒数（`billing_evidence.py:42-50`）。**修复**：无上游秒数时回退用建批冻结的 `billed_seconds`
先行 SETTLE（多退少补），或自动进 T40 队列 + 告警；至少在批次 credits 上向客户解释"已交付待结算"。

### 3.3 [P1] replica_prompt 计费无任何 reconcile 兜底 → 预扣永久滞留

入队计费挂 `service="analysis"` + replica 任务 id（`replica_prompt.py:206-208`），但
`usage_billing.py:575-587/755-777` 的兜底扫描表清单**没有 replica_prompt_tasks**，
`_reconcile_table_for("analysis")` 只映射 analysis_tasks；T40 队列 LEFT JOIN 清单
（`billing_reconciliation.py:161-167`）同样缺失；而 `acquire_replica_prompt_task` 的过期回收
（:239-253）直接置 FAILED **不调用 finish_source**。进程崩溃即预扣滞留且无人可见。
**修复**：reconcile 与映射表补 replica_prompt_tasks（FAILED/CANCELLED→units=0，SUCCEEDED→units=1）；
acquire 中断路径同事务补 `finish_source(cancelled=True)`。

### 3.4 [P1×2] 人物五视图生成轨道的重复付费窗口

① **租约 120s < 供应商调用超时 240s 且无续租**（`character_image_generation.py:59,477-479,492-507`
vs `first_frames.py:548-552` 注释自证"edit 常需 1-3 分钟"）：正常慢调用在 120s 处过期被另一 worker
再次认领并发起第二次付费调用；原 worker 完成后 CAS 失败丢弃结果。
② **结果未知的传输失败被标 retriable 自动重试**（`character_image_provider.py:116-122` →
`character_image_generation.py:947-954`，超时/连接中断/5xx 全部 retriable，最多 3 次付费调用），
违反全局纪律（`image_tasks.py:86-97`"结果未知绝不自动重试"；`simple_character.py:3692-3707`
同类失败落 UNCERTAIN）。
**修复**：租约提到 ≥ 传输超时 + 余量并按 `renew_image_task_lease` 模式续租；仅 429（未受理）映射
retriable，超时/5xx 落终态或 UNCERTAIN。

### 4.2 事件循环与连接占用（基础设施）

**[P1] async def 路由内直接执行同步 psycopg SQL，阻塞事件循环**：`simple_character_routes.py:286-340,
839-900`（两个 generate 路由，且第二个 `with db.write():` 块**跨 await 持有池连接**；客户生产有

`material_routes.py:153-192`（put_local_material，含 200MB 级 body 的同步处理）。仓内已有正确范式
（`payment_routes.py:258-280` 线程池注释、simple_character 的 `_prepare_simple_character_upload` 用
run_in_threadpool）——三组是漏网。**修复**：改 `def` 路由或包 run_in_threadpool；410 拒绝改全环境。

**[P1] `get_database` 把池连接+事务绑定到整个请求生命周期**（`auth.py:30-63` yield 依赖）：
①`idle_in_transaction_session_timeout=60s` 会在请求中途 >60s 无 SQL 时掐线（慢上传/证书下载路径），
teardown 提交失败；②默认 POOL_MAX=8/进程 vs anyio 40 线程池，突发时排队 30s 后 PoolTimeout 级联；
③compose 容量注释只核算连接总数未核算请求并发。**修复**：依赖内鉴权后即释放连接、路由内按需再开
事务；容量文档加"并发请求 ≤ ΣPOOL_MAX"约束；慢路径显式豁免 idle-in-txn。

**[P2/P3]**：worker `--concurrency` 不校验池上限（仅 docstring 约定）；nginx `client_max_body_size 2g`
远大于应用预算 200MB/600MB；无 HSTS/nosniff 等安全响应头；非客户生产环境 `alembic upgrade head`
仍可静默落 SQLite 默认库（`migrations/env.py:58` 仅客户生产拒绝）；PITR 工具链完整但 staging 恢复
演练无记录证据（README 自认 T38 未到 STAGING_VERIFIED）；`backup.py:5-7` 头注释指向不存在的
systemd 单元；容器内 pg_hba `local all trust`；maintenance.timer 注释与实际备份时间漂移。

## 五、安全

**无 P0/P1 漏洞。** SQL 注入无可达点（113 处 f-string 全部白名单/常量/占位符；LIMIT/OFFSET 统一
clamp 参数化）；路径穿越闭环（`_safe_key` 双重校验 + 上传扩展名白名单）；命令注入零（无 shell=True，
subprocess 全列表形式）；反序列化/压缩包零暴露；前端零 dangerouslySetInnerHTML；IDOR 全谱系 404
