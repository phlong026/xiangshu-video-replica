## 1. 结论

M1 的核心交付质量达标：T07 的 SQLite→PG 导入对账是全表重算而非抽样、写者围栏与只读快照证据链完整、失败单事务回滚；T08 的 8 条条件 CHECK 全部下沉数据库且测试以原生 INSERT 直击 PG；T09 的 per-operator 会话、一次性凭据、CSRF/RBAC 设计正确。基线静态检查与迁移链实机演练全部通过（见 §2）。

阶段不能直接通过，原因有两类：

1. **`_lifespan` 缺数据库模式 fail-closed 校验**（H1）：DB-08 出口门明文要求"bootstrap 与 lifespan 双重 fail-closed"，但 lifespan 侧只校验密钥/身份类，SQLite 类拒绝只剩 bootstrap 单点；直接 `uvicorn app.main:app` 启动时客户生产 + SQLite 组合不会被拦截。该缺口由两个独立子评审同时命中，且删除 `main.py:63-65` 三行后全部测试仍绿（无回归锁定）。
2. **对账器错误码 8/17 无直接触发测试**（H2）：对账器是导入 commit 的最后闸门，其自身拒绝逻辑的回归保护弱于被其对账的业务表，资金类不变量（钱包不平、CHARGE 无 PAID、RESERVE 无终态）缺"构造坏数据 → 必须以该码失败回滚"的用例。

M0 评审的 C1/H1–H4/M1–M9/LOW 全部确认修复（§6），包括本轮补验的 M6（pg-fixture.sh test 路径）与 LOW-3（venv Python 3.12.12 已对齐）。

## 3. HIGH — 阻断项

### H1. 客户生产 SQLite 类 fail-closed 未覆盖 API 进程直接启动路径，且无测试锁定

**位置**：`server/app/main.py:57-66`（`_lifespan`）对照 `server/app/db_pg.py:130-152`（`validate_customer_production`）

```python
# main.py — lifespan 仅调用密钥/身份类校验
assert_customer_production_security()   # 不检查数据库模式
# validate_customer_production()（拒绝 SQLite/缺 DSN/DB_PATH 残留）
# 只在 bootstrap.main() 与 generation_worker 中调用
```

- 打包 launcher 先跑 `python -m app.bootstrap`（`client/src-tauri/resources/start-backend.sh:23-26`）可拦截；但服务端客户生产以 systemd/容器直接 `uvicorn app.main:app` 启动时（launcher 第 37 行即为该形态），`VIDEO_REPLICA_CUSTOMER_PRODUCTION=true` + `VIDEO_REPLICA_DATABASE_URL=sqlite:///...` 的组合会让 API 在 SQLite 车道照常启动，健康检查照常返回 ok，与 Worker 的显式拒启形成不对称——正是 DB-06"禁止双写"要防的静默双库分裂形态。
- **双重 fail-closed 无测试锁定**：39 个 admin 会话用例直接调 `assert_customer_production_security`，无任何用例以违规 env 启动真实 `app.main.app`（`TestClient(app)` 上下文即触发 lifespan）；删除 `main.py:63-65` 三行，全部测试仍绿。
- **证据声明偏差**：`T09-EVIDENCE.md:59`"SQLite/missing-DSN rejection was already delivered by T05"技术上准确（对 bootstrap 路径），但与 §12.1"SQLite…均拒绝启动客户生产"的完整意图有差距。

**修复方案**：

1. `_lifespan` 启动段补 `validate_customer_production(resolve_database_config())`，与 bootstrap 侧完全对齐；
2. 补一条"违规 env 下 `TestClient(app.main.app)` 启动即抛 RuntimeError"的回归锁；
3. T09-EVIDENCE 措辞同步修正。

### H2. 对账器 17 个 mismatch 错误码中 8 个无测试，资金类不变量缺直接触发用例

**位置**：`server/scripts/reconcile_customer_billing.py`（错误码枚举）、`server/tests/test_sqlite_to_postgres.py`

- `sqlite_to_postgres.py → _issue_summary(issues)` 按错误码分型拒绝（`asset_reference_orphan`、`asset_reference_json_invalid`、`database reconciliation failed` 等）；台账 `docs/0822flash评审汇总.md` 记录 17 个错误码中 8 个无测试（含资金不变量）。本轮重读 T08/T13 两轮补丁确认：新增测试均为 schema/PG_ONLY_TABLES/head 断言适配，未新增针对钱包余额不平、CHARGE 无 PAID 订单、RESERVE 无终态配对等资金类码的"构造 → 触发 → 拒绝"用例。
- 对账器是导入 commit 的最后闸门（`migrate_snapshot` 在单事务内 commit 前全量复核，不一致即 `MigrationReconciliationError`）；其自身拒绝逻辑的回归保护弱于被其对账的业务表，未来重构可能无声放宽不变量。

**修复方案**：为每个 mismatch 码补一条表驱动用例（`fail_after_table` 注入模式已具备），断言导入以该码失败并整体回滚。

## 7. 做得对的部分（不建议返工）

- **T07 快照链是真只读、真全量**：`mode=ro&immutable=1` + `PRAGMA query_only` + WAL/journal 边车三查 + 文件头 18/19 字节拒绝 WAL 模式 + `BEGIN IMMEDIATE`（timeout=0）写者围栏贯穿哈希-复制-复核全程 + `PRAGMA data_version` 前后比对 + 快照 0600/O_EXCL/硬链接无覆盖发布。
- **对账是全表重算而非抽样**：无序多重集摘要（count/sum/xor/平方和 mod 2^256）对行序稳定且对重复行敏感；钱包余额 SQL 聚合重算、每 PAID 订单恰一 CHARGE、RESERVE 终态配对、资产引用逐元素校验（`json_each`/`jsonb_array_elements_text`），全部在 commit 前同一事务内复核。
- **误写生产库的多层防线**：advisory xact lock、Alembic head 双侧 parity、未验证 FK 拒绝、空库或仅种子否则拒绝合并、PG-only 表必须为空；失败原子回滚 + `already_reconciled` 幂等重跑。
- **T08 约束数据库级且测试直击 SQL**：12 组非法形状全部原生 INSERT 断言 PG 拒绝（绕过一切应用层）；降级守卫（客户行存在即拒绝 + 空账本对称还原 022）有专项测试；T13 的 activation_code 订单形状与 026 全部 8 条 CHECK 精确兼容。
- **T09 一次性凭据的构造性保证**：nonce 的 SHA-256 直接作 `admin_sessions` 主键，重放依赖数据库唯一约束而非应用层标志位，并发出示至多一次成功；行永不删除，撤销只置 `revoked_at`；签名与 CSRF 均 `hmac.compare_digest`（等长摘要比较）；每请求 JOIN users 重验即时失效；PG 不可用 503，绝不借用 legacy token。
- **迁移链完整性**（本轮实机）：001→032 单头无分叉，upgrade/downgrade/re-upgrade 三段演练通过；M0-C1 教训在 025–032 全部新迁移中无复发（PG-only 早退 + `postgresql_where` 模式统一）。
