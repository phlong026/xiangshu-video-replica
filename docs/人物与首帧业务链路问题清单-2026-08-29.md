# 人物与首帧业务链路问题清单（已逐项校核并修复）

- 日期：2026-08-29
- 分支：`codex/customer-admin-production-session`
- 范围：上传 → 拆解 → 镜头/口播稿 → 源画面 → 人物库 → 人物参考 → 人物置换首帧 → 编译/锁定 Prompt → 建批 → worker → 出片
- 方法：静态代码走读 + 前后端专项回归测试；真实 provider 未重复调用，避免额外费用。
- 用途：记录逐项校核与修复结果。付费端点配额/计费（3.2）按 2026-08-29 用户明确要求保持原样。

## 0. 链路现状总览

四个付费 provider 调用，工程成熟度不一致：

| 环节 | 触发方式 | 任务持久化 | 幂等/去重 | 计费 | 失败可见性 |
|---|---|---|---|---|---|
| 拆解（Gemini） | 202 + 轮询 `analysis_tasks` | 有（表 + worker + 租约） | 有（活跃唯一索引） | 无 | 状态可查、可重试 |
| 五视图拼合图（gpt-image） | 202 + 轮询 `character_sheet_tasks` | 有（表 + worker + 租约） | 有（请求 hash + 活跃唯一索引） | 无（按要求未改） | 状态可恢复；生产 provider 失败显式失败 |
| 人物置换首帧（gpt-image） | 202 + 轮询 `first_frame_tasks` | 有（表 + worker + 租约） | 有（请求 hash + 活跃唯一索引） | 无（按要求未改） | 状态可恢复；不确定提交显式保留 |
| 视频生成（Metaso H3） | 建批 + worker 状态机 | 有（租约 + 归档重试） | 有（idempotency_key + hash） | 有（reserve/settle/release） | SUBMISSION_UNCERTAIN 人工对账 |

补充事实：`character_generation_tasks` 表与 worker 分支已存在（`server/app/character_image_generation.py:463,562`，老七视图流程），新的极简人物流程绕过它走了同步路。异步基础设施不缺。

## P0-1 两个以上付费调用不计费、不限流

- [x] 已校核

**现象**：拆解、首帧、拼合图、AI 改写文案四个付费第三方调用全部不扣费、不预留、无配额；限流器不覆盖这些端点。用户可无限点「重新生成候选首帧」「重新生成多视图」。

**证据**
- `server/app/generation.py:1431` — `reserve_internal_billing` 的唯一业务调用点，位于建视频批次路径。
- `server/app/security_rate_limit.py:82-94` — 限流维度只有 activate_ip / activate_code / login_ip / login_account / admin_exchange_ip。
- `server/app/first_frames.py`、`server/app/simple_character.py`、`server/app/analysis.py`、`server/app/script_rewrite.py` 中无 wallet/credit/billing 引用。

**校核步骤**
```bash
grep -rn "reserve_internal_billing" server/app/*.py
grep -rn "wallet\|credit\|billing" server/app/first_frames.py server/app/simple_character.py server/app/analysis.py server/app/script_rewrite.py
grep -rn "consume_rate_limit" server/app/*.py | grep -v security_rate_limit.py
```
预期：第一条只命中 `generation.py`；第二、三条对上述文件无命中。

**影响**：客户版按次卖视频，图像/分析成本无上限地落在平台侧，且无速率闸门可用于止损。

**处置**：批次 3.2（最小方案 per-user 每日配额 + 复用 `consume_rate_limit`；完整方案按成本折算扣 credit）。

**校核结论**：确认原问题存在。按用户明确要求，本轮不修改付费端点配额、价格、扣费或限流策略；该风险保留并在发布说明中单列。

## P0-2 首帧与拼合图无幂等，超时重试导致双份成本与脏数据

- [x] 已校核

**现象**
- 首帧：客户端 300s 中止，服务端最坏 240s×2 次 ≈ 480s。前端报「生成失败」，服务端跑完照常落库；用户重试 = 第二次付费调用 + 第二个候选版本。
- 拼合图：重试会创建全新的 identity + persona + version，人物库出现两个同名人物，两次都算成功。

**证据**
- `client/src/api.ts:11` — `ANALYSIS_TIMEOUT_MS = 300_000`。
- `client/src/api.ts:2563-2564` — AbortController 仅绑超时，不绑组件生命周期。
- `client/src/api.ts:1931-1943` — `generateFirstFrames` 使用该预算。
- `server/app/first_frames.py:190` — `UrllibApilioTransport(timeout_seconds=240.0)`。
- `server/app/first_frames.py:1188-1219` — `edit_once_with_retry` 最多 2 次尝试。
- `server/app/first_frame_routes.py:119-160` — 无 idempotency key，无任务表。
- `server/app/simple_character.py:235-237` — 每次调用生成新的 identity_id / persona_id / version_id。
- 对照组：`server/app/analysis_routes.py:346` 复用 PENDING/RUNNING 任务；`server/migrations/versions/045_async_analysis_tasks.py:89-96` 活跃唯一索引；`server/app/generation.py:1539-1560` 建批 idempotency_key + request_hash。

**校核步骤**
1. 读上述三处超时常量，确认 300 < 240×2。
2. `grep -rn "idempotency" server/app/first_frame_routes.py server/app/simple_character_routes.py` → 预期无命中。
3. 真实环境复现（会产生费用）：人物库连续上传同一张图两次，或在首帧生成中途刷新页面后再次点击生成，检查 `versions` 表 `first_frame_candidates` 版本数与 `person_identities` 行数。

**影响**：重复扣供应商费用；人物库脏数据；首帧出现用户没预期的「幽灵版本」。

**处置**：批次 2（任务表 + 活跃唯一索引天然幂等）；批次 1.3/1.4 为止血。

**校核结论**：确认原问题存在，已由批次 2 的持久化异步任务、请求 hash 与活跃唯一索引根治；页面刷新、重启和响应丢失均可恢复同一任务。

## P0-4 拼合图与首帧不是异步流程（离开页面即丢反馈）

- [x] 已校核

**现象**：人物库上传/重新生成多视图时切走页面，进度卡消失且结果不再回填；返回后若任务尚未完成，界面什么都没有。首帧虽有前端内存托管，但刷新或重启即失效。

**证据**
- `client/src/App.tsx:381` — `page === "characters" ? <CharacterLibrary/> : null`，切页面即卸载。
- `client/src/CharacterLibrary.tsx:79-80` — `pendingCharacter` 为组件本地 state。
- `client/src/SimpleCharacterUpload.tsx:48-95` — 请求 promise 存在局部闭包，无 module 级托管。
- `client/src/CharacterLibrary.tsx:294-311` — `handleRegenerate` 同样在组件内 await。
- `client/src/FirstFrameSelection.tsx:26-49` — 首帧有 module 级 `pendingFirstFrameGenerations`，注释已写明「不是跨应用重启的持久任务」。
- `server/app/simple_character_routes.py:126-177`、`:221-279` — 服务端为一次长请求跑完全流程。

**校核步骤**
1. 人物库上传一张图，10 秒后切到「项目」页，再切回「人物库」：进度卡应消失。
2. 等待 3 分钟后手动刷新人物库：新人物应出现（证明数据未丢，丢的是 UI 反馈）。
3. 首帧生成中途切页面再回来：应能重新挂接并显示结果；刷新整个应用后再回来则不能。

**影响**：用户认为「生成的内容消失了」；重复提交概率高（与 P0-2 叠加）。

**处置**：批次 2。

**校核结论**：确认原问题存在，已修复。两类图像生成均持久化为服务端任务并由 worker 执行，前端通过最新任务接口恢复进度和终态，不再依赖组件或模块内 Promise。

## P2-1 幂等键复用可能把用户永久卡住

- [x] 已校核

**现象**：建批已在服务端成功但响应未到达前端时，用户修改文案后重试会命中同 key + 不同 hash，服务端返回 409 `IDEMPOTENCY_CONFLICT`，此后任何重试都失败，只能退出重进详情页。

**证据**
- `client/src/ProjectDetailFlow.tsx:96` — `idempotencyKeyRef` 在组件挂载期内固定。
- `client/src/ProjectDetailFlow.tsx:395-410` — 仅在为空时生成，成功后不清空。
- `server/app/generation.py:1539-1548` — request_hash 不一致时抛 `IDEMPOTENCY_CONFLICT`。
- `client/src/api.ts:2312-2313` — 409 被映射为「上游内容已变化，请重新确认后再试」，提示与真实原因不符。

**校核步骤**：代码走读即可确认；实测需要构造响应丢失，可用 devtools 断网模拟。

**影响**：窄场景但用户无法自行恢复，且错误提示误导。

**处置**：批次 4.3。
