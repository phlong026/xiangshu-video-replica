- 发布基线：`a05d349`（PR #79，生产已运行）

## 原子发布顺序

四个工作包在代码审查时保持分组，但生产上作为一个原子发布单元。顺序如下：

1. 构建候选镜像并完成全量 CI，不触发真实 Provider。
2. 备份生产 compose、当前镜像标识和数据库迁移版本。
3. 单实例执行 `alembic upgrade head`，确认 head 为
   `046_async_image_tasks`；迁移只新增表和索引，旧应用可继续运行。
4. 逐台滚动 API，验证 `/live`、`/ready` 和任务查询接口。
5. 逐个滚动 Worker，观察领取、租约、失败终态和现有视频任务不回归。
6. 最后切换静态前端，执行人物库、项目详情、首帧恢复和源画面取帧冒烟。
7. 保留上一生产镜像；发生应用问题时回滚镜像但保留 046 表，不执行有数据风险的
   数据库 downgrade。

## 发布门禁

- 前端：Biome、TypeScript、Vitest 全绿。
- 服务端：Ruff、格式检查、mypy 全绿。
- 专项：人物、首帧、源画面、账务对账、HA 合同全绿。
- PostgreSQL 16：空库 upgrade/downgrade/re-upgrade 和 046 表/索引验证全绿。
- 全仓 `npm run check` 全绿后才允许推送 PR。
- PR CI 全绿并完成合并后，才允许生产迁移和滚动发布。
- 生产发布后检查 API、Worker、数据库 head、页面静态资源和错误日志。

## 已知保留风险

- 拆解、人物拼合图、首帧和 AI 文案改写的独立配额/计费尚未纳入本次发布。
  这是已确认并明确排除的业务决策，不得在发布说明中标成已解决。
- 自动化不会重复调用真实图像 Provider。上线后只做一条受控业务冒烟，并观察任务
  持久化和终态；真实费用和内容质量结果单独留证。
