## 5. 文件级开发顺序

### 5.1 后端优先

1. 迁移和 PostgreSQL 基础。
2. 激活码批次和首次激活。
3. 设备绑定和 session 状态。
4. 客户认证和幂等层。
5. 管理端控制 API。
6. 公平队列改造。

### 5.2 前端随后

1. 客户激活页。
2. 第二设备配对与冲突页。
3. session 失效和切换提示。
4. 管理端激活码、客户、设备和会话页。

### 5.3 持续并行验证

1. 从第一个行为变更起同步补失败测试、回归测试和文档，不在开发末期集中补齐。
2. 从 T03 起持续执行安全扫描；认证、账务和并发变更在每个任务关闭前独立评审。
3. PostgreSQL 基座可运行后逐步增加多实例 smoke test，T36 再完成类生产拓扑验收。
4. API 变更同提交更新 OpenAPI 和生成类型；E2E 随竖切逐层从 Fake 扩展到 staging/真实链路。

## 6. 需要修改的调用关系

| 现有调用 | 改造后 |
| --- | --- |
| `getCurrentUser()` | 区分内部控制面用户与客户 session 用户 |
| `setInternalAccessToken()` | 客户端不再作为主登录方式 |
| `SESSION_EXPIRED_EVENT` | 客户 session 失效统一事件，名称可保留但语义升级 |
| `getControlAccounts()` | 补充客户激活码、设备、会话、审计查询 |
| `syncControlRechargeOrder()` | 保留给 ZPay 续充和补偿，不处理激活码首充 |
| `acquire_generation_task_lease()` | 改为按 `user_id` 调度，不按全局 FIFO |

## 7. 代码提交粒度建议

每个提交只解决一个闭环，不要把大重构揉在一起：

1. `postgres` 迁移基础。
2. 激活码批次和表结构。
3. 首次激活事务。
4. 设备和会话。
5. 客户前端。
6. 管理前端。
7. 公平队列。
8. 部署与验证。

每个闭环都要能单独回滚、单独测试、单独解释。
