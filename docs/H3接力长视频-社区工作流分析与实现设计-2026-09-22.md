# H3 接力长视频：社区工作流分析与实现设计（2026-09-22）

> 定位：`docs/长视频生成方案研究-2026-09-22.md` 的配套实现设计。研究文档回答"做什么、为什么"，本文回答两件事：
> 1. H3 社区（ComfyUI 生态）的"首尾帧自动接力"工作流到底怎么做的、哪些机制能搬到我们的 API 路线；
> 2. 在我们现有代码里落地的最小改动集（含"延续式提示词"编译器落地——本轮对既有判断有一处修正）。

---

## 一、结论速览

1. 社区有两条互补路线，解决的是不同层的问题：
   - **编排层**：`ethanfel/ComfyUI-MiniMaxH3-Context-Loop`——一个可复用采样图 + 场景计划（Production Plan）+ 逐场景渲染 + 场景级检查点 + 审核门 + 延迟组装 + 崩溃恢复。**这一层与我们的服务端架构同构，可完整复刻，是社区最有价值的部分。**
   - **采样层**：`seitanism/ComfyUI-H3-Motion-Context-MultiRef`（Context-Loop 的前身）——在 **latent 空间**做"连续帧锚定 + 音频时间线延续 + 跨轮次 Latent 保存"，让运动和声音在接缝处"真正延续"。
2. **采样层依赖本地开源权重、直接操纵采样过程，API 黑盒无法移植。** 这是像素空间接力路线的固有上限，必须诚实承认；我们能做的是把"尾帧接力 + 延续式提示词"做到像素路线的最优，并在音频与多帧上下文两处用替代方案补位。
3. **重大修正（对上一轮研究结论）**：上一轮写"编译器需新增承接语字段"——经本轮代码核对，**字段已存在**：`opening_action`（开场衔接）的输入、门禁、编译、持久化全链路现成（`generation.py:242`、`h3_prompts.py:143,156-159,255-258`、`PromptEditor.tsx:150-204`）。真正的缺口不在编译器，而在**编排层**：承接语的生产与传递机制。
4. 我们的接力链本质 = **I2VA 链**（每段首帧 = 上段尾帧），逐段复用现有 batch/task/计费/恢复管线；净新增只有编排层（`generation_sequences` 系列）。
5. 社区的"审核门 + 单段重生成"是一等公民（不是事后补丁）——印证我们"段级可恢复、单段重试不连坐"的设计；社区"运行中可追加场景 / 从指定检查点续跑"值得直接吸收。

## 二、社区工作流拆解

### 2.1 Context-Loop：一个采样图跑完整片

**产品结构**（README 原文要点，2026-08 起迭代至 0.6.11）：

- **Production Plan（场景计划）**：场景列编辑器，每场景独立 prompt + 参数 + 覆盖项；`run_name` 标识一个制作项目；运行目录 `output/h3_chains/<run_name>/`，成片在 `final/`。
- **逐场景渲染（内存安全）**："Only the current scene enters the sampler"——同一时刻只有当前场景进采样器；Loop End 负责推进到下一场景，或把 manifest 交给 Assemble。**整片不在内存里驻留，逐段渲染、逐段落盘。**
- **场景级检查点**：每场景生成后落 checkpoint；支持回滚、重做、候选对比（compare takes）；resume 时**拒绝不兼容的生成参数变更**（改了模型/参数就拒绝续跑，防止拼接出不同源的段）。
- **Review Gate（审核门）**：每场景生成后停住，用户可 `approve / retry / reroll / approve & stop`；最后一段批准后 Assemble 写最终 MP4。**审核门是流程中枢，不是附属功能。**
- **Context Builder（上下文构建器）**：从多个已保存场景窗口**组合画面上下文**（可选帧重分区与边界控制）；**音频默认跟随前继场景**（可解锁为独立选择）。这是它在采样层做"连续"的接口。
- **资产复用**：Project Asset Carousel（项目资产轮播）+ Tagged references（标签化参考）；Review Gate 可"抓帧存资产"（`Capture frame…` → Carousel，复用标签生成编号 take，不覆盖原资产）。**段间一致性靠恒定资产，而不是靠模型运气。**
- **崩溃安全与幂等**：manifest 完整性校验、防止重复入队、stale-response 保护、场景日志（scene journal）、取消安全保存；PNG 序列 + 音频并行导出。
- **运行中追加**：最后一段批准前可追加场景，`Approve & continue` 在当前段完成后从第一个新增段续跑（复用已保存检查点）。

### 2.2 Motion Context：latent 空间的音视频延续

- 三个机制关键词：**Motion Context 连续帧锚定**（多帧上下文，不是单帧）、**音频时间线延续**（音频 latent 跟着画面一起延续）、**跨轮次 Latent 保存**（每轮的 latent 状态持久化，下一轮复用；也支撑 latent upscale 与"不重渲染重组装"）。
- 采样层数学：feathered AV continuity（羽化边界的音视频连续）、fractional video/audio denoise-mask 校正、DeRoPE（跨轮次位置编码对齐）——**全部发生在模型内部或 latent 上**。
- 社区对像素空间拼接的批评（教学视频原话口径）："普通的视频延长方式是在像素空间强行拼接，不仅极易失真穿帮，更无法让声音持续延续。"
- 言下之意：**像素空间接力的两个固有弱点 = 接缝失真 + 声音无法延续。** 我们的 API 路线正落在这两个弱点上——设计里必须分别给缓解（尾帧接力 + 承接语降失真；统一音轨/音频提示词收敛降声音跳变）。

### 2.3 机制对照：哪些能搬、哪些不能

| 社区机制 | 依赖 | API 可用 | 我们的等效 |
| --- | --- | --- | --- |
| 逐场景渲染 + 场景级检查点 | 编排层 | ✅ 完整可搬 | 段级任务 + 尾帧检查点（§4.2/4.4） |
| Review Gate（approve/retry/reroll） | 编排层 | ✅ 完整可搬 | 段级审核门（AUTO/MANUAL，§4.6） |
| Assemble（manifest→MP4，不重渲染） | 编排层 + FFmpeg | ✅ 完整可搬 | 段清单快照 + concat（§4.9） |
| resume 拒绝不兼容参数变更 | 编排层 | ✅ | 序列 plan_snapshot 比对（§4.8） |
| 资产复用（Carousel/tag/抓帧） | 编排层 | ✅ | 人物库/素材库 + 尾帧入库（§4.4） |
| 运行中追加场景 / 检查点续跑 | 编排层 | ✅ | 段计划确认后追加 + 序列 resume（§4.3） |
| Context Builder 多窗口画面上下文 | 采样条件注入 | ❌（API 只收单张首帧） | 单帧尾帧 + 可选参考图/参考视频（段级分配） |
| 连续帧锚定（多帧上下文） | latent | ❌ | 不可移植：单帧尾帧信息量天然更少 |
| 音频时间线延续 | latent | ❌ | 统一音轨 / 段原声拼接 / 音频提示词收敛（§4.7） |
| 跨轮次 Latent 保存 | 本地权重 | ❌ | 不可移植；我们保存的是"段产物 + 尾帧资产" |

### 2.4 社区方案给我们的三个直接增益

1. **编排结构被验证**：场景计划 → 逐段 → 检查点 → 审核门 → 组装，与我们研究文档 §6 的 `generation_sequences` 形态几乎一比一，落地信心提高。
2. **接缝质量的诚实预期被校准**：社区在 latent 层做延续才敢称"seamless"；我们在像素层接力，预期应是"可接受接缝 + 支撑叙事连贯"，而不是"无缝"。评审口径、用户预期管理都要按此设定。
3. **"恒定资产"是跨段一致性的主力**：社区的 tag/Carousel 与我们的人物库/素材库同构——常规段用尾帧接力，关键段用参考图锁人（Ref2VA），两条腿走路。

## 三、项目实现设计

### 3.1 概念映射（社区 → 我们）

| 社区概念 | 我们的实体 | 现状 |
| --- | --- | --- |
| Production Plan / run_name | `generation_sequences` + 段计划快照 | 新增（研究文档 §6.1） |
| Scene | `generation_sequence_segments`（一段 = 一个 4–15s 生成单元） | 新增 |
| Scene sampling graph | 现有 generation batch/task（每段一个） | **复用** |
| Scene checkpoint | 段的产物 + `tail_frame_asset_id` + attempt 记录 | 新增字段，产物复用资产库 |
| Review Gate | 段状态 `REVIEW` + 审核动作 | 新增（状态机扩展） |
| Context Builder（画面） | 上段尾帧资产（单帧）+ 可选参考资产 | **复用**（首帧/参考机制现成） |
| Context Builder（音频） | 段原声拼接 / 统一音轨（决策项） | 待决策 |
| Assemble / manifest | 段清单快照 + FFmpeg concat | 复用工具链，新增编排 |
| Carousel / tagged assets | 人物库、素材库、尾帧资产 | **复用** |
| Capture frame | 尾帧抽取（`extract_generated_video_frames`） | **复用** |

### 3.2 数据模型（最小增量）

**`generation_sequences`**（序列）：`id`、`project_id`、`created_by_user_id`、`mode`（`replica` / `independent`）、`source_asset_id`、`status`、`segment_count`、`plan_snapshot`（段计划 + 拼接参数 + 计费快照，JSON）、`final_asset_id`、`idempotency_key`、时间戳。

**`generation_sequence_segments`**（段）：`id`、`sequence_id`、`index`、`status`、`prompt_snapshot`（含 `opening_action` 承接语）、`first_frame_asset_id`、`out_frame_asset_id`（可选，场收尾用）、`tail_frame_asset_id`（生成后回填）、`task_id`（挂现有生成任务）、`attempt`、`error_code`、时间戳。

- **检查点不需要独立表**：`tail_frame_asset_id` + 段状态 + attempt 就是检查点；尾帧资产按 `segment_id + attempt` 命名（重试产生新资产、不覆盖旧资产，可追溯、可回滚对比）。
- 状态机：序列 `DRAFT → CONFIRMED → RUNNING → REVIEW → STITCHING → ARCHIVING → COMPLETED`（异常分支 `FAILED` / `CANCELLED`）；段 = 复用任务六态 + `REVIEW` / `REJECTED` / `SUPERSEDED`（上游重试后未开跑的段自动换新尾帧；已开跑的段标记需人工确认）。
- 计费不变：每段一个现有按秒计费任务；序列层只做汇总报价与明细（研究文档 §5.5）。

### 3.3 段执行流程（时序）

1. **提交序列**：段 0 以用户选定首帧（或源视频开场帧）建任务；`opening_action` 为空（首段无需承接）。
2. **段完成**：worker 复用 `extract_generated_video_frames`（`generation.py:7205`）抽尾帧 → 走现有资产入库（COS，HTTPS 直链）→ **先持久化** `tail_frame_asset_id` → 再推进序列指针（与 `provider_task_id` 先持久化同款原则）。
3. **审核门**：MANUAL 模式停在 `REVIEW`（桌面端通知）；approve 后段 N+1 入队，其 `first_frame_asset_id` = 段 N 的尾帧资产。
4. **单段重试不连坐**：retry 只重跑该段（attempt+1）；成功后新尾帧覆盖指针；下游**未开跑**的段自动使用新尾帧，**已开跑**的段标记 `SUPERSEDED` 待人工决断（保留旧成果，不自动删）。
5. **收尾与组装**：最后一段完成（可选 FL2VA 指定结束画面）→ 段清单快照 → concat → 归档 → `final_asset_id`。
6. **运行中追加**：`CONFIRMED` 状态下可追加段（借鉴社区 `Approve & continue`）；已进入 STITCHING 后追加需显式回退。

### 3.4 尾帧契约（第 2 轮识别的四个坑，逐一给出落法）

| 坑 | 落法 |
| --- | --- |
| 稳定帧抽取 | 复用 `extract_generated_video_frames`（ffmpeg/ffprobe，已有质检链路）；默认取末帧，场收尾可指定偏移取稳定帧 |
| COS HTTPS 直链 | 复用现有资产入库路径；H3 请求 `image_url` 只认 HTTPS 直链 |
| 持久化与指针 | 尾帧入库即写段记录（先持久化后推进）；重试不改写历史 attempt 的尾帧指针 |
| 抽取失败降级 | ffmpeg 缺失/视频损坏时，段标记 `TAIL_FRAME_UNAVAILABLE`：允许人工从成片选帧（复用首帧置换的选帧能力）或整段重试，不阻塞序列 |

### 3.5 延续式提示词落地（回应"细化编译器改动点"）

**结论修正**：不需要新字段。`opening_action` 就是承接语的载体，且语义天然吻合——它是"首帧不是视频开头时，如何从该画面开始"的说明；接力段的首帧是上段尾帧，语义完全一致。

> 承接语的具体写法（三件事模型、五要素、四类段模板、六种反例、五问自检）见专题：`docs/H3接力长视频-延续性提示词设计-2026-09-22.md`。注意一个既有编译器行为：写了 `opening_action` 后首镜头的"动作"行不再输出，承接语因此是"承接 + 首动作"的复合职责。

- **字段与链路（全部现成）**：`GenerationBatchRequest.opening_action`（`generation.py:242`，max 1000 字）→ `compile_replica_final_text(opening_action=…)`（`generation.py:1372`）→ 写入第 1 个镜头（`h3_prompts.py:255-258`：`用户确认的开场衔接：…`）→ 随任务 payload 持久化（`generation.py:1409`）。
- **门禁（现成 + 一处扩展）**：现有 `FIRST_FRAME_ALIGNMENT_REQUIRED`（`h3_prompts.py:156-159`）：`source_frame_time > 0.25` 或未知时必填承接语。接力段的首帧**不来自源视频时间轴**（来自上游段尾帧），`source_frame_time` 语义不适用——门禁需增加第二种触发：**首帧来源 = 上游段尾帧时，承接语必填**（填"如何从上一段结尾继续"）。
- **承接语的生产（这才是真缺口，编排层做）**：
  - P0 人工：序列页逐段填写；编辑器控件与门禁文案（`PromptEditor.tsx:150-156,196-204`）直接复用，文案改为"该首帧来自上一段结尾，请说明如何继续"。
  - P1 半自动：段计划维护"本段结束状态"摘要（分镜动作/镜头落幅的自然语言），系统据此生成承接语候选，用户确认后写入。
  - P2 智能：把上段 prompt + 上段尾帧图交给 H3-Context-IR（¥0.05/次，`056_operation_cost_rates`）或视频分析（看末段成片生成客观承接语）——付费调用，按现有 operation cost 记账。
- **与参考图的关系**：Ref2VA 与首尾帧同请求互斥（`independent.py:219-226`、`prompt_context.py:64-67` 已校验）→ 段级分配：常规段 A（首帧接力），关键段 C（参考锁定）；"首帧 + 参考同请求混合"仍列探针项。

### 3.6 审核门（吸收社区 Review Gate，两档）

- **MANUAL（P0 默认）**：每段生成后停住，桌面端通知；`approve / retry / reroll`。最稳，也把"审片按拼接后时长"的失真问题前置到段级（研究文档 §4.3 失败模式 4）。
- **AUTO_CONTINUE（P1）**：连续跑，但在**场边界必停**（"场"= 3–5 个连续单元，研究文档 §5.3）；对长片（60s+）这是体验与安全的平衡点。
- 审核内容模板化：人物/环境/色调是否漂移 + **承接语是否符合实际尾帧**（看图改字，比改整段 prompt 便宜）。

### 3.7 音频策略（诚实面对不可移植项）

社区靠 latent 音频延续解决"接缝处声音中断/换光影"；API 做不到，三档替代：

1. **P0**：段原声直接拼——最便宜、最快，接受声场跳变（切点落在"场"边界时最自然）。
2. **P1**：统一音轨——配音/音乐铺底，H3 原声降为氛围或丢弃；与管理研究文档 §9 待决策 3 一致。
3. **P2**：段级音频提示词收敛（同环境声/同配乐描述）——仅缓解，不根治。
- 验证手段现成：拼接后用现有 `h3_audio_quality` 质检（生成链路已有）。

### 3.8 恢复、幂等、参数兼容

- **段级恢复**：复用现有六态恢复（worker 重启按段状态续跑）；序列层只按 `task_id` 查询，不重复建任务。
- **序列幂等**：`idempotency_key` + plan_snapshot 的 `request_hash`（沿用 `generation_batches` 模式，迁移 009）；同 key 重复提交返回既有序列。
- **参数兼容校验**（社区同款语义）：resume 时比对新旧 plan_snapshot 的生成参数（模型/分辨率/ratio/时长/参考资产），不兼容则拒绝续跑并提示重建序列——防止拼接出不同源的段。
- **上游变更传播**：段重试成功后，下游未跑段自动换尾帧；已跑段标记 `SUPERSEDED`，由用户确认是否级联重跑（默认不自动跑，省钱）。

### 3.9 组装

- `manifest` = 段清单（index、task_id、产物资产、尾帧指针、attempt）+ 顺序 + 拼接参数快照；**组装不重渲染**（社区同款），可重复执行、可换拼接参数重拼。
- 拼接用现有 FFmpeg 工具链（`media_tools.py`）；组装后归档走现有资产入库；成片进素材库/下载（Tauri `video_downloads.rs` 复用）。

## 四、分期与验证

- **V1 探针先行（不变）**：① Apilio 对 60–180s 长源的拆解形态（全案最不确定）；② 两段真实 H3 首尾帧接力（付费探针，需授权）+ "首帧 + 参考图混合"可行性；③ 拼接参数一致性实测。
- **P0 最小闭环**：复刻长源 → 拆解 → 段计划确认 → 串行 I2VA 接力（人工承接语，MANUAL 审核门）→ 拼接归档。验收对着"像素路线可接受接缝"的预期。
- **P1**：AUTO_CONTINUE + 场边界必停、承接语半自动、序列报价明细、上游变更传播规则。
- **P2**：智能承接语（Context-IR/视频分析）、统一音轨、场结构优化（连接性镜头静帧+缓推降本）、2K 策略落地。
