# 长视频生成方案研究（基于 MiniMax H3 · 桌面端）

> 日期：2026-09-22　性质：研究/方案（无代码改动，未认领开发任务）
> 结论口径：本文只给方案与证据，不声明任何能力已实现；涉及真实付费探针的验证项均标注"待授权"。

## 一、结论速览

1. **H3 官方没有"视频延长/续写"类 API**（已核对 platform.minimax.io 全量接口索引，见 §3）。长视频在 H3 上**只有一条工程路径**：把长片切成 ≤15 秒的生成单元，逐段生成后拼接。"接力"质量决定成片质量。
2. 本项目当前对源视频是 **15 秒硬上限**（`server/app/media.py:44` `MAX_DURATION_SECONDS = 15.0`，波及导入、拆解、参考素材三处），这就是"长视频"需求的根源。最近的 #184 提交（链接解析被 15 秒上限误拦）说明这条边界已在持续摩擦。
3. 推荐落地方案：**片段链引擎（Segment Chain）**——拆解层把长源切成复刻单元 → 生成层逐段调用 H3（**尾帧接力**保连续，人物库参考图锁一致性，段内用 `[Shot N]` 多镜头压缩段数）→ 合成层用服务端既有 FFmpeg 工具链无损拼接 + COS 归档。
4. 该方案**零新供应商、零新模型**，复用现有批次管线（公平队列 / 六态状态机 / provider_task_id 先持久化 / 按秒计费 / 对账恢复），新增面集中在"序列编排实体 + 段间接力 + 拼接归档"三件事。
5. 桌面端（Tauri）定位：**做"复刻专用长片流水线"，不做通用剪辑器**（延续 `docs/短视频复刻桌面端开发说明.md` §2.3 的排除项）。与剪映 Hub 的差异是垂直化：上传爆款 → 自动拆解 → 接力生成 → 一键成片，用户不需要学剪辑。
6. 成本基线（官方 paygo）：768P $0.08/秒、2K $0.13/秒。**长片直接 2K 生成比"768P 生成 + 逐段 2K 再生"更便宜**（0.13 < 0.08+0.10），见 §5.5。

## 二、问题定义与现状基线

### 2.1 "长视频"在业务里的确切含义

乡墅赛道的爆款素材（口播、探房、工地进度、客户见证）典型时长 **30–180 秒**；数字人口播成片常在 60–180 秒。而当前系统全链路按"4–15 秒"设计，用户拿到 60 秒爆款时只有两个选择：手动裁剪成 4 段分别复刻（4 次割裂的生成，成品无法自动拼成一条），或放弃。长视频方案要回答的就是：**让一条 60–180 秒的源素材，产出同等时长的复刻成片，且画面/人物/场景跨段连续**。

### 2.2 15 秒边界的分布（放开时必须同步动的面）

| 层级 | 位置 | 现状 |
|---|---|---|
| 后端常量 | `server/app/media.py:43-44` | `MIN_DURATION_SECONDS = 4.0` / `MAX_DURATION_SECONDS = 15.0` |
| 导入 | `server/app/viral_import_routes.py:258-262` | 超 15 秒 422 `VIRAL_LINK_DURATION_EXCEEDED`，文案"请截取 15 秒以内片段后重试" |
| 拆解 | `server/app/analysis_routes.py:679-685` | 超 15 秒 422 `ANALYSIS_DURATION_EXCEEDED` |
| 独立创作参考素材 | `server/app/independent.py:425-430` | 参考视频/音频累计 ≤15 秒 |
| 生成契约 | `server/app/generation.py:1527-1531` | `output_duration_seconds` 兜底 `min(15, …)`；`independent.py:84` `ge=4, le=15` |
| 前端 | `client/src/studio/CreationPages.tsx:3407-3418, 1235-1237` | 上传前探测拦截 + `normalizeCustomerDuration` 夹紧到 15 |

### 2.3 已有的"长视频基石"（不需要重建的部分）

- **H3 协议构造就绪**：`h3_prompts.py` 已支持 T2VA / I2VA / L2VA / **FL2VA（首尾帧）** / Ref2VA 的提示词结构；`first_frame_asset_id`、`last_frame_asset_id` 字段已存在；官方多镜头标记 `[Shot N] At MM:SS.mmm` 已在编译器中实现（`h3_prompts.py:228-254`）。
- **任务管线就绪**：`generation_batches` → `generation_tasks` 六态状态机（PENDING→SUBMITTING→QUEUED→RUNNING→ARCHIVING→COMPLETED）、`provider_task_id` 先持久化后轮询、公平队列、按秒计费（RESERVE/SETTLE/RELEASE）、对账恢复。
- **媒体工具链就绪（服务端 FFmpeg 全家桶）**：`extract_generated_video_frames`（抽帧，带 `-ss`）、`normalize_generated_video`（几何归一）、`h3_audio_quality`（音频质检）、`FFmpegSceneBoundaryDetector`（场景边界检测）、`material_thumbs.py`（首帧缩略图）、`extract_audio`。
- **COS 与素材体系就绪**：生成结果归档、15 分钟签名直链、素材库五分支视图、人物库参考图资产。
- **Tauri 端就绪**：`client/src-tauri/src/video_downloads.rs`（用户批准目录、下载进度、断点、打开文件夹）、凭据保险库。

**缺口恰好三件事**：① 无"片段序列"编排实体（现有 batch 是"同一请求 × N 条变体"，不是"N 个不同请求串成一条片"）；② 无段间接力（尾帧抽取 → 下一段首帧）；③ 无拼接与长片归档表达。

## 三、H3 官方能力边界（核对结论，2026-09-22）

已核对 `platform.minimax.io` 视频相关全量接口（含 llms.txt 索引）：

| 能力 | 结论 | 对本方案的意义 |
|---|---|---|
| 单次时长 | **4–15 秒整数**（H3）；H3 Max 5–15 秒 | 硬边界，长片必须分段 |
| 模式 | T2V / I2V（首帧、尾帧、首+尾）/ Ref2VA（图≤9、视频≤3 段共≤15s、音频≤3 段共≤15s、合计≤12 件） | **FL2VA 与 Ref2VA 是接力的两根支柱** |
| 多镜头 | Prompt 内 `[Shot N] At MM:SS.mmm` 原生支持 | 15 秒内承载 2–3 个镜头，压缩段数 |
| 延长/续写 | **不存在**（无 extend API） | 只能自建"分段+接力"，与可灵/Veo 的官方延长不同 |
| H3-Context-IR | 多模态上下文 → 结构化增强 prompt（异步） | 长片整片剧本可先做一次 IR 提升一致性 |
| Video Regeneration | 768P 源视频 → 2K（≤15 秒的单条） | 长片逐段再生不经济（见 §5.5） |
| 输出 | 768P / 2K，自带立体声音频，无 seed 参数 | **无 seed ⇒ 段间随机性不可控 ⇒ 接力是唯一的连续性保障** |
| 定价 | 768P $0.08/s，2K $0.13/s | 成本测算基线 |

另注：H3 官方产品侧（hailuoai.video）有"全能参考"工作流；官方还有 Video Agent 模板化生成接口（预置模板 + 素材填充），与本方案的"片段链"是两条路线，可作为后续"模板化长片"的备选，不在本期范围。

### 4.1 对标总表

### 4.2 归纳：同行做长视频的五条共性

1. **分镜先行**：长片不是"一条长 prompt"，而是"脚本 → 分镜 → 逐段提示词 → 逐段生成"。编排粒度和生成粒度都是段。
2. **段间接口是"帧"**：首尾帧/关键帧桥接是跨平台的通用段间契约（Flow Frames、可灵首尾帧、剪映分镜参考图、H3 自身 FL2VA）。
3. **参考素材锁一致性**：人物/场景靠参考资产（图≤9）而非文字描述，跨段复用。
4. **一键成片 + 再精修**：先自动拼接给结果（剪映"预览成片"、可灵续写），再提供局部修改（重 roll、局部编辑、延长）。**用户要的是"成片"，不是"素材堆"**。
5. **生成与后期不换场**：剪映 Hub 的最大信号是打通"生成→剪辑"。我们的替代品不是剪映，但"生成完即预览成片、可一键下载"必须是闭环。

### 4.3 段间衔接专题：同行做法深度调研（2026 年 2–9 月）

> 本节回答用户问题：**"两段视频怎么接"同行到底怎么解**。调研对象为最近几个月发布/更新的产品与 2026 年学术前沿。

**（1）行业基准事实（Runway 官方长视频指南，2026-09-11）**

- 没有任何模型能单次生成连续长片——**10 分钟视频 = 60–100 个独立短生成拼接**，"这是全行业现状，不是某一平台的限制"；
- 衔接不靠"单段生成得更好"，而是靠一个**四层系统解法**（见下）；
- Runway 把"尾帧接力"（last-frame technique）称为**收益最大的一招**："生成镜头 1，取它的最后一帧，用该帧 + 延续式提示词生成镜头 2，如此重复"。

**（2）衔接的四层解法矩阵（2026 主流产品全景）**

| 层 | 具体做法 | 代表产品 | 效果与局限 |
|---|---|---|---|
| **规划层** | 连续性表（每镜头记录：时长/地点/主体/动作/机位/参考图 + **上一镜头结束时的朝向与位置**）+ 主文档四锁定（角色/地点/视觉风格/前后关系）+ **延续式提示词**（描述上一段结束在哪里，而不是重写全新描述） | Runway 官方指南、Flova（多智能体导演） | 成本最低收益最大；前提是"先规划后生成" |
| **帧接口层** | 尾帧→首帧接力（last-frame technique）；或一次给首尾帧（FL2VA / Veo Frames to Video 直接生成过渡段） | **Runway（明确推荐）**、Google Flow、可灵首尾帧、海螺官方（"首尾帧+全能参考"组合） | 像素级衔接最自然；**串行生成（慢）**；跨场景硬切时不该用 |
| **参考接口层** | 角色/场景参考图每段复用；角色类参考视频锁主体（可灵 3–8s）；**音色锚点**（Flova 给每个有台词角色单独建音色）；镜头直接从"角色元素图"生成、不走关键帧 | 可灵全能参考、Flova+Seedance 2.5、Runway References | 锁"身份"不锁"像素"；与帧接口互补；音频一致性首次被产品化（Flova） |
| **模型内层** | native multi-shot（一次生成多镜头、角色跨帧稳定）；记忆机制（动态记忆库/离散关键帧/事件记忆） | Seedance 2.0/2.5（LTX Studio 已集成）、学术：VideoMemory、OneStory（CVPR 2026）、Captain Cinema（ICLR 2026）、EventBank-G（ICML 2026） | 行业最前沿；依赖模型内建，闭源 API 不可定制；**H3 的 `[Shot N]` 是本层的"段内版"** |

**（3）Runway 六种断裂模式与修复（逐条对照我们的方案）**

| 断裂模式 | 现象 | 同行修复 | 我们的对应 |
|---|---|---|---|
| 人物漂移 | 同一人物逐镜变脸/发/衣 | 角色参考图注入每一段 | 人物库参考图（机制 C） |
| 环境漂移 | 房间/场景逐镜微变 | 场景参考图全集复用 | 场景资产（需补：长片级场景快照） |
| 动作不连续 | 段 2 接不上段 1 结尾 | **延续式提示词**（描述前段结束状态） | 复用 `opening_action` 字段（已现成，见配套实现设计 §3.5） |
| 镜头语言不一致 | 一段手持、一段广告片质感 | 统一视觉风格短语逐段重复 | 编译器已有 style_keys 机制（复用） |
| 提示词过载 | 一段塞多个叙事节拍 | 每段单一主行动 | 单元级编译（天然满足） |
| 切换不兼容 | 各自都好但剪在一起不对 | 规划景别递进（广→中→特写） | 分镜卡的镜头序列规划 |

**（4）长视频特有的四个失败模式（Runway 口径，全部与我们的段计划有关）**

1. **AI 填充镜头**：模型自行发明无意义过渡画面 ⇒ 每段必须有明确目的（我们的分镜卡天然满足，但段间不能留"空白让 AI 填"）；
2. **质量波动**：某些段明显比其它段差 ⇒ **重生成弱段而不是全收**（对应我们的"单段重生成"能力）；
3. **单段堆太长**：单次生成要维持复杂动作越久越不可靠 ⇒ **保持单段短而简单，长度用序列构建**（直接支持我们 15 秒分段的策略）；
4. **审片失真**：2 秒看不出问题、在成片里出现 8 秒就明显 ⇒ **按拼接后的实际时长审每段**，不能只看片段预览。

**（5）成本与节奏技巧（Runway 官方建议，可直接引入段计划）**

- 不是每一秒都要同等制作价值：**两个动态场景之间的连接性时刻，用静帧 + 缓推/微缩放（Ken Burns）代替全 AI 生成**——省钱且节奏更好（"全片同一强度会让人看得很累"）；
- 对我们的映射：段计划里标记"高价值动镜头"（生成）与"连接性镜头"（静帧动效），前者用 H3，后者服务端 FFmpeg 即可完成。

**（6）H3 同源生态的做法（官方与社区）**

- **海螺官方**（h3-open 生态页）：推荐"**首尾帧 + 全能参考**"组合工作流，官方定位就是解决"跨段人物一致性"；
- **社区（ComfyUI 生态，仅作参考、明确排除于本项目路线）**：已有"长视频循环流：文生+首尾帧自动接力"、"Motion Context 连续帧 + 跨轮次 Latent 保存"等节点方案——从另一侧印证了"帧接力"是 H3 上跨段的唯一可行抓手（无 extend、无 seed）；
- **Sora 2 已于 2026-04 停用**：其 Storyboard（时间线提示）路线退场，行业共识转向"规划 + 逐段 + 帧/参考接口 + 记忆"。

**（7）对我们的六条直接启示（已吸收进方案）**

1. 尾帧接力必须配**延续式提示词**——载体字段已现成（`opening_action`），缺口在编排层（见配套实现设计 §3.5）；
2. **单序列 3–5 段最稳**（Runway 口径）⇒ 我们的单元切分要引入"场"：一场 3–5 段，场间不硬接尾帧（§5.3 已补）；
3. 规划层字段可直接映射到分镜卡：地点/主体/动作/机位/参考图 + "上段结束状态"；
4. 连接性镜头用静帧动效降本（§5.3 已补）；
5. 审片按拼接后的实际时长进行（2 秒看不出、在成片里待 8 秒就明显），弱段果断重生成、不将就；
6. 前沿（native multi-shot + 记忆机制）短期不可得，我们的等效替代：段内 `[Shot N]` + "前序分镜摘要注入下一段 prompt"（可用 H3-Context-IR 辅助，列为 P2）。

## 五、方案设计：片段链引擎（Segment Chain）

### 5.1 总体架构（三层）

```
长源素材（≤180s，上传/链接导入）
        │  ① 拆解层（复用 Apilio 分析 + FFmpegSceneBoundaryDetector）
        ▼
复刻单元 [U1 | U2 | U3 | … | Un]   每单元 4–15s，按分镜自然边界切，段内可多镜头
        │  ② 生成层（串行接力，复用现有 worker/队列/计费）
        ▼
H3 段结果 mp4 × n（768P/2K，自带音频）
        │  ③ 合成层（服务端 FFmpeg，复用 media_tools 工具链）
        ▼
长片成片（拼接 → 校验 → COS 归档 → 任务中心/素材库可见 → 桌面端下载）
```

### 5.2 段间接力三机制（按优先级组合使用）

**机制 A：尾帧接力（主，像素级连续）**
- 上段生成成功归档后，worker 用 `extract_generated_video_frames` 抽**最后一帧**（`-sseof` 定位，规避过渡黑帧），上传 COS 生成直链；
- 该帧作为下一段的 `first_frame`（`h3_prompts.py` 的 I2VA/FL2VA 通道已就绪），下一段首帧 = 上一段尾帧 ⇒ 视觉无缝；
- **必须与"延续式提示词"成对使用**（Runway 口径的 last-frame technique）：下一段的 prompt 不重写全新描述，而是描述"从当前画面继续"——载体即现成的 `opening_action` 字段（输入→门禁→编译→持久化全链路已就绪，`h3_prompts.py:143,255-258`）；缺口在编排层：承接语的生产与传递（P0 人工 → P2 Context-IR 生成），见配套实现设计 §3.5；
- 成本：一次抽帧 + 一次小图上传，可忽略；延迟：段间 +10–20 秒。
- 约束：段数 N 意味着**串行生成**（总耗时 ≈ Σ 单段耗时，见 §6.4）；任何一段失败只需重跑该段及其后继（尾帧依赖链）。

**机制 B：Ref2VA 上下文继承（辅，锁人物/场景/影调）**
- 把上一段结果视频（≤15s）作为 `reference_video` 传入下一段，同时携带人物库参考图；
- 官方约束：参考视频 ≤3 段、总时长 ≤15s、混合 ≤12 件 ⇒ 只能带"最近一段"，不能累积；且 **R2V 与首尾帧互斥**（`independent.py` 已实现互斥校验）——所以 B 与 A 不能同时用于同一段，**按段二选一**；
- 推荐分配：跨场景切换处（人物/场景需要重新锚定）用 B；同场景延续用 A。

**机制 C：人物库参考图（恒定基线）**
- 复刻流已有"从人物库选择角色版本 + 推荐身体/脸部参考图"的资产管线，长片全程共享同一人物版本即可，跨段身份漂移的第一道防线；
- 注意项目现状：**R2V（reference_image）与首尾帧在同一请求内互斥**（`validate_h3_request` 已实现显式互斥校验）。因此段级分配是"二选一"：常规段用 A（首帧接力），需要重新锚定人物/场景的关键段用 B/C（参考锁人）。"首帧 + 参考图同请求混合"是否可行，列为 V2 探针的附带验证项（官方 v2 文档未明确禁止混合，但项目按互斥处理）。

> 关键工程结论：**H3 无 seed** ⇒ 不能指望"同 prompt 两次生成长得像"。连续性只有两种来源：上一段的真实尾帧（A），或参考资产（B/C）。这是与本地 SD 生态（可固定 seed）最大的架构差异，也是"必须做接力"的硬理由。

### 5.3 单元切分策略

- **优先按分镜自然边界切**：`FFmpegSceneBoundaryDetector` + 拆解结果的 `shot_mappings` 时间轴已有；每单元取 4–15 秒整数（对齐契约 `ge=4 le=15`）；
- **引入"场"两级结构**（吸收 Runway 经验：单序列 3–5 段最稳）：
  - 场 = 3–5 个连续单元（同地点/同人物/连续动作）→ **场内用尾帧接力**（像素级连续）；
  - 场与场之间（换场景/换时空/硬切设计点）→ **不接尾帧**，用人物/场景参考图锁人 + 新场景首帧（可由 Apilio 生成或选源片对应帧）开场，切点即剪辑点；
  - 60 秒片 ≈ 1–2 场；120–180 秒片 ≈ 2–4 场。
- **段内多镜头**：一个 15 秒单元用 `[Shot N]` 承载 2–3 个镜头（如"工地全景→工头特写→材料细节"），既省成本又得到自然的镜头节奏——这是当前编译器已支持但未在长片场景利用的能力；
- **连接性镜头降本**（Runway 官方技巧）：场间过渡/氛围铺陈等"低动态"时刻，可在段计划中标记为静帧 + 缓推（FFmpeg 生成，不走 H3），既省钱又优化全片节奏；
- **首尾折叠**：60 秒源 ⇒ 4×15s 或 5×12s；180 秒源 ⇒ 12–15 段（成本见 §5.5）；
- 与"时间轴压缩"门禁（`TIMELINE_CONFIRMATION_REQUIRED`）的关系：单元级独立编译，逐段对齐源时间段，不改现有复刻门禁语义。

### 5.4 合成层（拼接与后处理）

- **归一化**：每段先过 `normalize_generated_video`（统一分辨率/帧率/编码几何），H3 同参数输出下此步大部分是校验；
- **拼接**：FFmpeg concat demuxer 顺序拼接（编码参数一致时 `-c copy` 无损），输出单条 mp4；
- **校验**：`ffprobe` 总时长 ≈ Σ 段时长（容差内），音频流存在性检查（复用 `h3_audio_quality` 思路）；
- **转场（P1 可选）**：默认硬切；可选 0.3 秒交叉溶解（需重编码，成本可控）；
- **音频策略（P0 决策点）**：H3 每段自带音频，硬拼会得到"每段独立的环境声"；口播/剧情长片建议 **P1 引入统一配音轨**（项目已有 Hifly 口播、ASR 转写、文案体系），P0 先接受原声拼接并在 UI 明示；
- **归档**：成片作为新的素材对象（长片类型）入 COS + 素材库 + 任务中心，桌面端直接下载（Tauri 已有下载通道）。

### 5.5 成本测算（官方 paygo，768P $0.08/s、2K $0.13/s）

| 成片时长 | 段数（15s/段） | 768P 成本 | 2K 成本 |
|---|---|---|---|
| 30s | 2 | $2.4 | $3.9 |
| 60s | 4 | $4.8 | $7.8 |
| 120s | 8 | $9.6 | $15.6 |
| 180s | 12 | $14.4 | $23.4 |

- **2K 路径选择**：768P 生成 + 逐段 2K Regeneration（第三方报价 $0.10/s 口径）= $0.18/s，**贵于直接 2K 生成 $0.13/s** ⇒ 长片果断直接 2K，或整片保持 768P 降低试错成本后再对**通过审核的段**升级 2K（单段重生成视角）；
- 拼接/抽帧/上传为自有算力 + 极小对象存储流量，不产生供应商费用；计费仍按"段 × 秒"逐段 RESERVE/SETTLE，用户对"这条 60 秒片要花 4 段的钱"必须在提交前可见（复用现有视频分支报价弹窗）。

## 六、数据模型与管线设计（贴合现有架构）

### 6.1 编排实体（最小新增）

推荐：新增 **`generation_sequences`**（长片序列）一张表 + `generation_batches.sequence_id`（nullable）一个外键，**不改既有 batch/task 语义**：

- `generation_sequences`：id、project_id、created_by_user_id、source_asset_id（长源）、status、segment_count、拼接参数快照（目标分辨率/总时长）、final_asset_id（成片）、idempotency_key、created_at/updated_at；
- 每段 = 一个现有 batch（`creation_kind='sequence_segment'`，`sequence_id` 指向序列、`segment_index` 序号）；
- 段级一切复用：公平队列、六态状态机、provider_task_id 恢复、按秒计费；**只新增序列级状态**：
  `DRAFT → SEGMENTING → GENERATING → STITCHING → ARCHIVING → COMPLETED`（+ FAILED/CANCELLED，段级失败可单段重试）。
- 兼容红线：不引入 ORM、不引入新框架、不双写；新表按 PG-only 规范登记 `reconcile_customer_billing` 白名单（若涉及计费科目）。

### 6.2 接口面（沿用现有路由风格）

- `POST /api/sequences`（幂等建序列：长源资产 + 目标时长/分辨率）→ 返回段计划（供用户确认/微调）；
- `POST /api/sequences/{id}/start`：确认段计划后启动（逐段预备 + 计费预留）；
- `GET /api/sequences/{id}`：序列状态 + 段列表（段级复用现有任务详情字段）；
- `POST /api/sequences/{id}/segments/{n}/regenerate`：**单段重生成**（对齐剪映"局部编辑"心智），成功后仅重拼；
- 列表/取消/下载复用 generation 端点模式（`require_batch_access` 的序列版助手）。

### 6.3 接力与拼接的 worker 流程（段与段之间）

1. 段 n 生成成功 → 归档 → 若 n < N：抽尾帧 → 上传 COS → 写段 n+1 的首帧引用（同事务提交，保证崩溃可恢复）；
2. 段 n 失败 → 序列进入 `GENERATING` 内的失败态，**不自动连坐**，用户可单段重试或改参后继续（失败不改尾帧指针，沿用段 n-1 尾帧）；
3. 全部段完成 → `STITCHING`：按 index 拼接 → `ffprobe` 校验 → `ARCHIVING`：成片入 COS + 素材库 → `COMPLETED`。

### 6.4 时间预期（桌面端长任务设计的前提）

单段 15s H3 生成的真实耗时以 V2 探针实测为准（经验估计 3–10 分钟/段；代码口径为上界保护：生产 H3 轮询上限 2 小时，`generation.py:161-166`）。串行接力 ⇒ **60 秒长片 ≈ 15–45 分钟量级，180 秒 ≈ 45–120 分钟量级**（估数，探针后校准）。这正是桌面端（本地长任务、系统通知、断点续传、关窗不中断服务端任务）优于网页标签页的场景，也是"分段串行"必须配套进度可视化 + 允许用户离场的原因。

## 七、桌面端（Tauri）体验设计

### 7.1 明确不做（延续既有边界）

- 不做通用非线性时间线编辑器（`docs/短视频复刻桌面端开发说明.md` §2.3 已排除）；
- 不做 ComfyUI 式本地节点编排/本地模型推理（本次用户明确排除，也符合"PG 唯一真源 + 云端供应商"架构）；
- 不在桌面端做视频合成（拼接在服务端，保证一致性与可归档；桌面端只负责下载/预览）。

### 7.2 要做（差异化 = 垂直复刻流水线）

| 视图 | 内容 | 复用 |
|---|---|---|
| 段计划确认 | 拆解后展示"将生成 N 段"：每段源码时间轴、镜头数、费用明细，可合并/拆分/调段长 | 拆解结果、报价弹窗 |
| 长片生成台 | 段卡片列表：段 n/N 状态（六态映射）、首帧缩略、进度、失败单段重试 | TaskRecordsPanel、进度视图、缩略图 |
| 成片预览 | 拼接完成即播（COS 直链），支持下载到用户目录 | video_downloads（已有） |
| 素材沉淀 | 成片自动入素材库"我的成片"，段结果可单独取用 | 素材库五分支 |

### 7.3 与剪映 Hub 的关系

剪映做的是"通用生成+通用剪辑"；我们做"爆款复刻垂直流水线"：**源素材决定拆解计划，拆解计划决定段，段接力自动生成，成片自动拼**。用户不需要拖时间线。长期（P2）可评估"导出剪映草稿工程（draft_content.json）"让专业用户进剪映精修——把剪映当下游，而不是竞争同一个界面。

## 八、分期实施建议

**前置技术验证（P0 的 gate，付费探针与真实验证，需人工授权）：**
- V1：Apilio 分析（拆解）对 60–180 秒长源的支持形态——单次输入 or 分段分析后合并分镜时间轴（**这是全案最不确定的一环**，直接决定拆解层工作量）；
- V2：H3 FL2VA 真实付费探针 2 段（验证尾帧→首帧接力的真实连续性质量与"段缝合处"观感）；
- V3：H3 输出拼接参数一致性实测（是否 `-c copy` 直拼，还是要统一重编码）。

**P0（复刻流长源支持，最小可用）**：放开 media.py 15 秒上限（分场景：仅"长片模式"入口放开，普通复刻流维持 4–15s 不动，避免影响既有验收）；拆解分段 → 串行接力生成 → 拼接 → 归档 → 任务中心展示"N 段长片"。技术载体：`generation_sequences` + 段级 batch 复用。

**P1（编排与体验）**：段计划确认 UI、段卡片生成台、单段重生成、成片下载/入素材库、报价明细（段 × 秒）、失败单段重试。

**P2（增强）**：统一配音轨与音画对齐（接 Hifly/ASR 体系）、转场、关键帧先行的"快速模式"（并行生成 + FL2VA 桥接，牺牲像素级连续换速度）、2K 升级策略、剪映工程导出评估。

**风险清单**：
1. 接力连续性（人物漂移/色调跳变）——缓解：尾帧接力为主 + 参考图恒定 + 探针实测判定；**无 seed 是架构级约束，不可通过参数绕过**；
2. 成本失控（长片单价高）——缓解：提交前段级报价 + 段试跑（先 768P 后 2K？注意 §5.5 结论：逐段再生不经济，必要时只对"审核通过的段"重生成 2K）；
3. 串行时长（小时级长任务）——缓解：桌面端长任务体验（通知/离场/断点），段级可恢复；
4. 拆解 provider 长视频能力不确定——缓解：V1 探针先行，必要时降采样/分段分析；
5. 放开 15 秒上限牵连面大——缓解：新入口隔离（长片模式），不触碰既有 4–15s 验收口径。

## 九、待决策问题（提交用户拍板）

1. **业务载体**：长视频放进"复刻流"（放开长源上限）还是"视频生成独立创作"新增"长片模式"？倾向：**两个入口共享同一片段链引擎，P0 先落复刻流**（痛点最真）。
