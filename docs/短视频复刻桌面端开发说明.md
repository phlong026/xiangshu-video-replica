## 0. 文档治理与完成口径

### 0.1 文档优先级

发生冲突时按以下顺序执行：

1. 本文档：唯一产品、技术和验收规范；
2. V1.3 后续开发任务清单：唯一任务状态与 Gate 证据来源；
3. 共享对话需求对比与范围决议：解释需求来源和冲突裁决；
4. V1.2 开发计划、旧剩余清单和历史评审：只作历史参考。

任何旧文档不得覆盖本文档的 P0 边界，也不得用历史测试数量替代当前 checkout 的验证结果。

### 0.2 完成等级

统一使用以下状态，禁止把不同等级混报：

~~~text
DOCUMENTED
  → CODE_PRESENT
  → LOCALLY_VERIFIED
  → DESKTOP_E2E_VERIFIED
  → PROVIDER_VERIFIED
  → WINDOWS_VERIFIED
  → READY_FOR_INTERNAL_RELEASE
~~~

- `CODE_PRESENT`：代码存在，不代表流程可用；
- `LOCALLY_VERIFIED`：单元/集成/FakeProvider 通过，不代表真实供应商可用；
- `DESKTOP_E2E_VERIFIED`：从桌面端新建人物到下载结果的本地纵向闭环通过；
- `PROVIDER_VERIFIED`：真实账号最小链路和脱敏证据通过；
- `WINDOWS_VERIFIED`：新构建安装包完成 Windows 实机安装、升级、卸载和恢复；
- `READY_FOR_INTERNAL_RELEASE`：前述 Gate 全部通过，并完成 10–20 个真实项目试跑和业务签字。

### 0.3 V1.3 相对 V1.2 的核心修正

V1.2 已覆盖“使用现成人物参考图”的人物库，但没有覆盖共享对话中明确的“从一张真人照片生产可复用多视角角色资产包”。V1.3 将以下能力恢复为 P0：

- 真人身份、角色人设、角色版本和人物资产四层模型；
- 真人源图上传、质量检查和肖像授权；
- 多视角人物资产生成、单张重生成和人工审核；
- 角色版本发布、冻结、归档和历史追溯；
- 根据起始帧朝向/景别自动选择参考资产并保存选择快照；
- 人物资产生产的 FakeProvider、真实 Provider 和桌面 E2E。

V1.3 不重写已经落地的 Tauri、FastAPI、SQLite、存储、Gemini、首帧、Prompt、H3 和任务编排基础。

## 1. 项目结论

首版不是一个“逐镜头生成并拼接”的剪辑工具，而是一条完整的视频复刻工作流：

1. 用户上传一条参考视频。
2. 系统把原视频拆成可编辑的结构化镜头卡片。
3. 管理员从一张已授权真人源图建立人物身份，创建角色人设和不可变版本，生成并审核多视角人物资产包。
4. 系统从原视频开头的候选画面中选出清晰起始帧。
5. 用户从人物库选择一个已发布角色版本；系统按起始帧朝向和景别推荐身体参考图与脸部参考图，用户可改选。
6. 绘图模型在保留构图、姿态、场景的前提下完成人物置换，生成新的首帧图。
7. 系统把镜头卡片、口播稿、人物映射编译为一条可编辑、可保存、可追溯的 H3 Prompt。
8. Prompt 与首帧图一起提交 MiniMax H3 图生视频接口，一次生成一条 4–15 秒完整视频。
9. 用户输入本项目本批次生成数量 N；系统在安全上限内创建 N 个独立 H3 任务。
10. 生成后页面持续显示批次进度条、状态计数和单任务阶段，完成一个结果就立即展示、预览和允许下载。

关键边界：

- P0 只开放图生视频，不开放文生视频和多对象参考。
- P0 的 H3 请求只包含 Prompt 与 first_frame，不把参考音频、参考视频或 reference_image 混入同一请求。
- 角色一致性先在首帧生成阶段完成，H3 负责让该首帧运动起来。
- 人物资产生产发生在 H3 之前；H3 不接收人物多视角参考图。
- P0 的“动态数量”仅指同一项目、同一输入快照生成 N 个候选，不包含跨项目批量生产。
- P0 直接保留 H3 图生视频结果中的原生音轨，不实现独立音频上传、声音克隆、TTS、音轨替换、混音或口型同步。
- 原口播稿或自定义口播稿只作为 H3 Prompt 的生成意图，不承诺逐字复现或跨视频固定音色。
- P0 数据库固定使用 SQLite。

## 2. 阶段规划

### 2.1 第一阶段：P0

P0 只采用图生视频，目标是让内部员工稳定完成：

> 创建并发布角色资产包 → 上传参考视频 → 自动拆解 → 选择角色版本与参考视角 → 生成人物置换首帧 → 编辑并保存 Prompt → 输入生成数量 → 查看实时进度 → 对比、下载

P0 必须实现：

- Windows 桌面端登录与内部权限；
- 项目管理；
- 参考视频上传与对象存储；
- Gemini 3.1 Pro Preview 视频拆解；
- 第三方视觉模型适配入口；
- 结构化镜头卡片查看、编辑、保存和版本记录；
- 真人身份、肖像授权和源图质量检查；
- 角色人设、角色版本和不可变发布快照；
- 单图生成多视角人物资产、人工审核、单张重生成、发布和回滚；
- 人物资产的默认 COS 存储与稳定对象 Key；
- 按起始帧朝向/景别自动匹配人物参考资产并允许人工改选；
- 原始清晰帧自动推荐和人工改选；
- GPT Image 2 与 Nano Banana Pro 2K 首帧生成功能；
- 原口播稿自动提取；
- 自定义口播稿；
- 口播稿与镜头时间自动匹配；
- H3 Prompt 自动编译、编辑、保存、锁定和版本记录；
- MiniMax H3 图生视频；
- 直接使用 H3 成片原生音轨，不做二次音频处理；
- 生成数量由员工输入，服务端按管理员配置的单批次安全上限校验；
- 批次生成进度条、状态计数和单任务阶段；
- 任务状态、错误、结果归档与下载；
- 腾讯云 COS 默认存储；
- 阿里云 OSS 可切换支持；
- SQLite 数据库、自动备份与恢复；
- 后台设置与连接测试；
- 操作日志和最小成本记录。

### 2.2 第二阶段：P1

P1 在 P0 稳定后加入：

- 文生视频；
- 多对象参考；
- 参考图片、参考视频、参考音频的对象编排；
- H3 Context IR 可选能力；
- 更完整的声音克隆、TTS 和音画后期链路；
- 批量项目、模板和团队审核能力。

P1 必须遵守 H3 输入互斥规则：

- first_frame / last_frame 与 reference_image / reference_video / reference_audio 不得混用；
- 多对象参考不是“带首帧的增强版图生视频”，而是另一种请求模式；
- P1 的文生视频和多对象参考复用 P0 核心数据结构；未来若加入高级音频能力，应使用独立模块和迁移，不在 P0 预埋声音字段。

### 2.3 不进入当前范围

- 逐镜头分别调用 H3 后自动拼接；
- 专业非线性时间线编辑器；
- 对外开放注册、支付、会员、积分商城；
- 自动发布到抖音、视频号等平台；
- 未经授权的人脸或声音克隆；
- 独立音频上传、声音库、Voice Clone、TTS、音轨替换、混音和口型同步；
- 承诺逐字对白、帧级口型同步或 100% 人物一致；
- 未经实测直接切换供应商模型别名。

### 3.1 流程门禁

只有同时满足以下条件，才能点击“开始生成”：

- 参考视频上传完成；
- 视频拆解成功或已由人工补全；
- 已选择一个状态为 PUBLISHED 且授权有效的角色版本；
- 角色版本已拥有 P0 必需的已审核人物资产；
- 人物参考资产匹配结果已由用户确认；
- 至少确认一张首帧图；
- Prompt 已保存且状态为已锁定；
- 口播稿已确认；
- H3 与对象存储连接测试通过；
- H3 任务查询/结果获取接口已经过真实环境验证。

## 4. 软件功能结构

### 4.1 一级导航

保持简单，只保留五个入口：

1. 项目
2. 新建复刻
3. 人物库
4. 任务记录
5. 设置

### 4.2 项目

每个项目保存：

- 项目名称；
- 创建人、创建时间和最后修改时间；
- 参考视频；
- 分析版本；
- 镜头卡片版本；
- 人物映射；
- 首帧候选与最终选择；
- 口播稿版本；
- Prompt 版本；
- 生成批次与所有子任务；
- 结果、审核结论和错误记录。

支持的操作：

- 新建；
- 继续编辑；
- 复制项目；
- 归档；
- 删除业务数据；
- 查看审计记录。

删除按企业数据策略执行；已产生的安全审计记录不随项目直接物理删除。

### 4.3 新建复刻

页面采用单页分步工作台：

1. 上传参考视频
2. 拆解视频
3. 选择已发布角色版本
4. 选择起始帧
5. 匹配并确认人物参考资产
6. 生成并确认人物置换首帧
7. 确认口播稿
8. 编辑并锁定 Prompt
9. 设置数量并生成
10. 预览、下载或再次生成

任何自动结果都允许人工修订。系统不得在重新分析时覆盖员工已经保存的人工版本。

### 4.4 人物库

人物库不是“参考图路径列表”，而是人物身份资产的生产、审核和发布系统。

#### 4.4.1 业务对象

~~~text
PersonIdentity（真人身份）
  └── CharacterPersona（角色人设）
        └── CharacterVersion（不可变角色版本）
              ├── CharacterAsset（源图/多视角资产）
              └── CharacterAssetReview（审核记录）
~~~

- `PersonIdentity`：真实自然人及其肖像授权，不包含具体职业服装；
- `CharacterPersona`：同一真人在某一职业、服装、场景和表达风格下的人设；
- `CharacterVersion`：一次可复现的人物资产生产结果，发布后不可修改；
- `CharacterAsset`：源图、生成原图或已批准参考图；
- `CharacterAssetReview`：自动检查和人工审核的独立记录。

示例：

~~~text
真人身份：荣哥
  ├── 人设：企业 AI 落地顾问
  │     └── V1：深色商务休闲服
  └── 人设：乡墅项目管理专家
        └── V1：工程马甲 + 安全帽
~~~

项目只引用 `CharacterVersion`，不得只引用会继续变化的 PersonIdentity 或 CharacterPersona。

#### 4.4.2 真人身份创建

管理员执行：

1. 填写真人姓名或内部显示名；
2. 上传肖像授权附件，记录授权范围和有效期；
3. 上传一张清晰、单人、无遮挡的真人源照片；
4. 系统完成格式、尺寸、单人、人脸可见度、清晰度和水印检查；
5. 源图进入私有 COS/OSS，数据库保存 object_key、SHA256 和授权关系；
6. 人工确认后身份状态变为 ACTIVE。

源照片失败时必须给出具体原因，不得进入多视角生成。授权过期或撤销后禁止新项目使用，但历史项目保留冻结快照和审计证据。

#### 4.4.3 角色人设与版本

角色人设包含：

- 人设名称、职业定位和使用场景；
- 年龄感、发型、体型等允许保持的身份特征；
- 服装、配饰、妆容和默认背景；
- 正向描述和禁止项；
- 使用范围和默认绘图模型策略。

创建版本时冻结：

- 真人源图 asset_id 和 SHA256；
- 人设字段快照；
- 生成 Provider、模型名和参数；
- Prompt 模板版本和内容哈希；
- 必需视角集合；
- 创建人和创建时间。

角色版本状态：

~~~text
DRAFT → GENERATING → REVIEWING → PUBLISHED → ARCHIVED
                   ↘ FAILED
~~~

只有 PUBLISHED 版本可被新项目选择。重新生成人设时创建新版本，不覆盖旧版本。

#### 4.4.4 P0 多视角资产集

每个可发布版本至少包含以下 7 类已批准资产：

| view_type | 业务含义 | 主要用途 |
| --- | --- | --- |
| `FRONT_FACE` | 正面脸部 | 身份细节参考 |
| `FRONT_HALF` | 正面半身 | 中近景身体与服装参考 |
| `FRONT_FULL` | 正面全身 | 正面全身姿态参考 |
| `LEFT_45` | 左 45° | 左转人物首帧 |
| `RIGHT_45` | 右 45° | 右转人物首帧 |
| `LEFT_SIDE` | 左侧面 | 明显左侧面镜头 |
| `RIGHT_SIDE` | 右侧面 | 明显右侧面镜头 |

每类允许生成多个候选，但发布版本必须为每个 view_type 选择一个 `approved_asset_id`。P0 不训练 LoRA 或身份适配器。

#### 4.4.5 多视角生成

多视角生成使用独立 `CharacterImageProvider` 契约，不把供应商参数写入人物业务层。P0 可以复用已接入的 GPT Image 2 或 Nano Banana 编辑能力，但必须通过真实人物 Golden Sample 后才能选为默认 Provider。

流程：

~~~text
源图 + 人设快照 + 目标 view_type
  → 生成 1–N 个候选
  → 自动质量检查
  → 人工审核
  → 单张批准/驳回/重生成
  → 全部必需视角通过
  → 发布角色版本
~~~

生成任务必须保存请求快照、Provider、模型、耗时、费用、错误和输出资产；失败只重试目标视角，不重建整个版本。

#### 4.4.6 人物资产审核

自动检查与人工审核至少覆盖：

- 是否仍为同一人物；
- 五官、脸型、年龄感和肤色是否明显漂移；
- 身材和身体比例是否稳定；
- 同一角色版本的服装和配饰是否统一；
- view_type 标记与实际角度是否一致；
- 是否存在多人、肢体异常、截断、拼图、文字或水印；
- 是否足够清晰且适合图片编辑模型使用。

自动分数只用于提示，**人工批准是 P0 发布硬门禁**。每次批准、驳回、原因和操作者均写审计记录。

#### 4.4.7 项目引用与自动匹配

项目选择一个已发布角色版本后，系统根据选定起始帧的：

- 人物朝向；
- 景别；
- 人脸可见度；
- 身体完整度；

推荐 1 张身体/服装参考图和 1 张脸部参考图，最多允许补充到 4 张。用户可以改选。系统必须保存：

- 角色版本 ID；
- 候选资产 ID；
- 自动推荐理由；
- 用户最终选择；
- 选择时的人物版本快照。

首帧生成和后续重生成都使用这份不可变选择快照，角色库后来发布新版本不得改变历史结果。

#### 4.4.8 COS/OSS 对象键

推荐对象结构：

~~~text
users/{user_id}/identities/{identity_id}/source/{asset_id}.{ext}
users/{user_id}/personas/{persona_id}/versions/{version_id}/generated/{view_type}/{asset_id}.png
users/{user_id}/personas/{persona_id}/versions/{version_id}/approved/{view_type}/{asset_id}.png
projects/{project_id}/character-reference-selection/{selection_id}.json
~~~

数据库保存稳定对象键，不保存长期签名 URL。任何第三方访问 URL 均在调用前按最短可用时长临时签发。

P0 只要求一个项目选择一个主角。多人映射放到 P1。

最小权限角色：

- employee：创建和操作自己或所属团队的项目，使用已授权的人物，生成和下载结果；
- admin：管理员工与团队、人物身份、肖像授权、角色资产审核/发布、Provider 和存储配置；
- auditor：只读查看审计、授权和任务证据，不得修改配置或生成内容。

项目、素材、人物、下载 URL 均执行资源级权限校验。知道 asset_id、version_id 或 project_id 不代表拥有访问权限。

### 4.5 任务记录

展示：

- 批次与子任务；
- 状态；
- 使用模型；
- 时长、分辨率与生成数量；
- 提交人；
- 供应商 task_id；
- 创建、开始和完成时间；
- 估算费用与实际费用（供应商能返回时）；
- 批次进度条与“已完成/总数”；
- 待提交、排队、生成中、归档中、成功、失败、需处理的数量；
- 每个子任务的当前阶段和耗时；
- 错误摘要；
- 重试、下载和从当前版本再次生成。

## 5. 参考视频上传与对象存储

### 5.1 为什么必须使用对象存储

P0 需要对象存储，不能只依赖桌面端把文件直接塞进各模型接口：

- H3 和 Gemini 需要可以访问的素材 URL；
- 视频拆解、抽帧、首帧、生成结果需要跨任务复用；
- H3 是异步任务，桌面端关闭后任务仍需继续；
- 结果要被企业侧归档，不能长期依赖供应商临时 URL；
- 大文件直传对象存储可以避免业务服务成为上传带宽瓶颈。

绘图接口采用 multipart/form-data 时，由服务端从对象存储流式读取后转发，不把云存储永久密钥下发到桌面端。

### 5.2 存储策略

- 默认：腾讯云 COS；
- 可选：阿里云 OSS；
- 存储适配器统一实现 put、getSignedUrl、head、copy、delete；
- 桶默认私有；
- 对外模型只使用短期签名 GET URL；
- 默认签名有效期 2 小时，可由部署配置调整；
- 失败重试前重新生成签名 URL；
- H3 成功后立即把结果复制回企业对象存储。

对象路径建议：

~~~text
projects/{project_id}/source/
projects/{project_id}/frames/raw/
projects/{project_id}/frames/generated/
projects/{project_id}/analysis/
projects/{project_id}/prompts/
projects/{project_id}/outputs/{batch_id}/
characters/{character_id}/references/
characters/{character_id}/authorization/
~~~

### 5.3 上传流程

1. 桌面端向业务服务申请预签名上传地址。
2. 桌面端直传 COS/OSS。
3. 上传完成后回调业务服务。
4. 服务端执行文件头校验、媒体探测和元数据落库。
5. 校验成功后自动启动视频拆解。

“前端文件上传时进行视频拆解”的准确含义是：上传完成后由前端自动触发后端分析任务，不是在桌面端保存 Gemini 密钥或直接调用第三方模型。

### 5.4 P0 文件限制

- 视频容器：MP4、MOV；
- 视频编码：优先 H.264/H.265；
- 参考视频时长：4–15 秒；
- 单文件：不超过 50 MB；
- 无法解析、损坏或超限时，在调用付费模型前拦截；
- 非标准视频先由 FFmpeg 转为标准分析副本，原文件保留。

- 默认 Gemini；
- 管理员启停与测试。

P0 只在代码层保留 ThirdPartyVisionAdapter 接口。通用 Provider 名称、请求格式和任意模型配置通过 feature flag 隐藏，待 P1 再开放，避免首版做成通用模型平台。

## 7. 结构化镜头卡片与 Prompt 编辑器

### 7.1 双层编辑

系统同时提供：

- 结构化镜头卡片编辑；
- 最终 H3 Prompt 文本编辑。

镜头卡片是可理解的数据层，Prompt 是实际提交层。用户可以编辑任一层，但必须明确同步方式：

- 修改镜头卡片后，点击“重新编译 Prompt”；
- 如果 Prompt 已被人工编辑，重新编译时先展示差异；
- 只有用户确认后才能生成新 Prompt 版本；
- 已锁定版本永不被自动覆盖。

### 7.2 Prompt 编译模板

Prompt 按以下顺序组成：

1. 输出目标：完整时长、画幅、风格。
2. 首帧延续：从已确认首帧自然开始。
3. 时间线：按镜头卡片时间段描述动作、镜头、场景和转场。
4. 人物约束：保持首帧人物身份、服装和外观连续。
5. 口播语义意图：原稿或自定义稿对应时间段，供 H3 自动生成原生音频。
6. 画面文字。
7. 环境音、音乐和音效。
8. 避免项：身份突变、额外人物、肢体异常、画面闪烁等。

示例结构：

~~~text
生成一条 15 秒、9:16、写实短视频，从提供的首帧自然开始。

[0.0–3.2s] 人物近景，保持首帧人物身份和服装，镜头轻微推进……
[3.2–8.0s] ……
[8.0–15.0s] ……

口播意图：……
环境音与音乐：……
保持人物脸部、发型、服装和场景连续；不要增加无关人物，不要改变字幕内容。
~~~

### 7.3 Prompt 状态

~~~text
DRAFT → SAVED → LOCKED → USED
~~~

- DRAFT：自动生成或正在编辑；
- SAVED：已保存，可继续修改；
- LOCKED：生成前锁定；
- USED：已经用于至少一个任务。

生成任务必须保存 Prompt 快照，而不是只保存对当前 Prompt 的引用。

### 7.4 系统 Prompt 模板追溯

P0 必须对以下模板进行版本化和哈希记录：

- Gemini 视频分析模板；
- 多视角人物资产生成模板；
- 人物置换首帧模板；
- H3 Prompt Compiler 模板与过滤规则。

每次外部调用或编译结果保存 `template_type`、`template_version`、`template_hash` 和实际输入快照。P0 可以把模板作为后端受控配置维护，但不得只在代码中留下无法追溯的自由字符串。

管理员可视化编辑、审批和回滚模板属于 P1；P0 设置页只需只读展示当前启用版本和哈希。

## 8. 原始清晰帧与人物置换首帧

### 8.1 原始帧选择

服务端在参考视频开头 0–3 秒内抽取候选帧。若首镜头短于 3 秒，以首镜头范围为准。

候选帧评分：

- 清晰度；
- 曝光；
- 运动模糊；
- 人脸可见度；
- 遮挡程度；
- 与镜头卡推荐时间的一致性；
- 构图完整度。

系统推荐 3 张，员工可以：

- 接受推荐；
- 切换候选；
- 输入时间点重新截帧；
- 上传自选首帧。

### 8.2 人物置换输入

绘图模型输入：

- 原始清晰帧；
- 已发布角色版本；
- 自动推荐并经用户确认的人物库 1–4 张参考图；
- 角色人设和版本快照；
- 保留项；
- 替换项；
- 目标画幅和输出规格。

默认使用一张与起始帧景别/朝向最接近的身体参考图和一张 `FRONT_FACE` 身份参考图。系统不得把角色版本中的所有图片无差别提交给绘图模型，也不得在未记录选择快照的情况下静默换图。

首帧提示词必须表达：

> 保留原图的镜头位置、人物姿态、动作、场景、构图、道具、光线与色调，只将原人物身份替换为角色库人物；保持自然皮肤、正确肢体和真实透视；不得增加或删除主体。

### 8.3 绘图模型选择

| 模型 | 用途 | P0 默认建议 | 接口 |
| --- | --- | --- | --- |
| GPT Image 2 | 高质量编辑与人物置换 | 复杂改图备选 | POST /v1/images/edits |
| Nano Banana Pro 2K | 多图参考、比例控制、2K 输出 | 9:16 首帧默认 | POST /v1/images/edits |

两者都通过 Apilio 调用。P0 使用编辑接口，不使用纯文生图接口作为人物置换主路径。

### 8.4 首帧审核

员工必须在提交 H3 前确认：

- 是目标人物；
- 姿态和构图与原视频一致；
- 手部、面部和肢体无明显异常；
- 场景、道具和文字未被意外改变；
- 画幅正确；
- 图片能够正常从对象存储签名 URL 访问。

确认后的图片生成不可变资产版本。

首帧版本必须同时记录 `character_version_id` 和 `character_reference_selection_id`。角色资产被归档或发布新版本后，历史首帧仍使用当时冻结的引用和快照。

## 9. 口播稿、画面匹配与 H3 原生音频

### 9.1 口播稿来源

支持两种来源：

1. 原视频口播稿：由视频拆解自动提取；
2. 自定义口播稿：员工输入或粘贴。

每次修改都形成新版本，保留：

- 全文；
- 来源；
- 字数；
- 预计朗读时长；
- 创建人；
- 与镜头匹配结果。

### 9.2 自动匹配

系统按镜头卡时间和语义，把口播稿拆到各镜头：

- 优先保持完整语义句；
- 不跨越不合理的镜头边界；
- 每段保存目标开始和结束时间；
- 显示预计语速；
- 超出目标时长时提供“压缩稿”建议；
- 不自动删除用户文本，必须由用户确认。

### 9.3 P0 原生音频规则

P0 的唯一音频来源是 H3 图生视频返回 MP4 中的原生音轨。产品不提供任何独立音频能力。

固定规则：

- 不上传参考音频；
- 不调用 Voice Clone、TTS/T2A 或其他声音 API；
- 不保存 voice_id 或声音角色；
- 不提供音色、语速、音调、音乐、混音或音轨替换设置；
- 不拆分、导出或重新合成音轨；
- 下载和归档 H3 返回的完整 MP4，保留其原生音轨；
- 原口播稿或自定义口播稿通过 Prompt 传入 H3，只用于引导生成；
- 不承诺逐字复现、同一人物跨视频固定音色或帧级口型同步。

Provider 验收只检查：

- H3 返回的 MP4 是否包含可播放音轨；
- 音轨与视频时长是否基本一致；
- 是否存在静音、严重爆音或文件损坏。

如果真实任务没有音轨或音轨不可播放，外部任务状态仍按实际结果保存，结果质检增加 AUDIO_QUALITY_FAILED，允许员工重新生成；P0 不启动额外音频补救流程。

## 10. 动态生成数量与任务进度

### 10.1 用户设置生成数量

生成数量不再使用固定选项。员工通过数字输入框或步进器输入本批次数量 N。

规则：

- N 必须是正整数；
- 默认值为 1；
- 最大值由管理员配置 max_generation_count_per_batch；
- 页面必须显示当前允许范围；
- 超过上限时前端即时提示，服务端仍做最终校验；
- 提交前显示“本次将创建 N 个付费 H3 任务”；
- 如果能够取得单价，显示预计总费用；不能取得时明确标记“费用以供应商实际账单为准”；
- 批次提交后 quantity 不可修改；需要其他数量时创建新批次；
- 不把某个固定数字写入客户端或业务规则。

### 10.2 批次与子任务

实现规则：

- 创建一个 generation_batch；
- generation_mode 在 P0 固定为 I2V，字段从 P0 起就存在；
- 在同一事务中创建 N 条 generation_task；
- 每个任务独立调用一次 H3；
- 每个任务拥有独立 task_id、状态、错误、费用和结果；
- 所有任务使用同一份首帧、Prompt、脚本和参数快照；
- Worker 按 max_concurrent_h3_tasks 控制并发，其余任务保持 PENDING；
- 某个子任务失败不影响其他子任务；
- 只允许对失败子任务重试；
- 防止重复点击：前端提交 idempotency_key，服务端在有效期内去重；
- idempotency_key 只防止业务端重复点击，不等于供应商已支持请求幂等；
- 如果创建请求超时且本地没有拿到 provider_task_id，任务进入 SUBMISSION_UNCERTAIN，禁止自动重提，避免重复付费；
- 只有获得供应商请求级幂等能力，或经人工核对确认上次未创建，才允许从 SUBMISSION_UNCERTAIN 重试；
- 不虚构 seed 参数，模型随机性由供应商控制。

### 10.3 批次进度条

生成页面和任务记录页面都必须显示批次进度条：

- 主文案：已完成 terminal_count / total_count；
- 百分比：floor(terminal_count / total_count × 100)；
- 状态计数：待提交、提交中、排队中、生成中、归档中、成功、失败、需处理；
- 结果卡片随单个任务完成逐个出现，不等待整批完成；
- 全部任务终态后进度为 100%；
- 混合成功和失败时显示“已完成，部分失败”；
- 存在 SUBMISSION_UNCERTAIN 时显示“需要管理员处理”，不能伪装成失败或自动完成。
- 用户重试一个已失败任务时，该任务重新进入非终态，进度百分比可以下降；页面必须显示“失败任务已重新生成”，避免用户误以为进度异常。

terminal_count 的计算规则：

- status=FAILED 或 CANCELLED；
- 或 status=SUCCEEDED 且 archive_status=ARCHIVED。

SUBMISSION_UNCERTAIN、PENDING、SUBMITTING、QUEUED、RUNNING、ARCHIVING 和 ARCHIVE_FAILED 不计入 terminal_count。

### 10.4 单任务进度展示

METASO 当前文档没有提供 0–100 的实时生成百分比，因此 P0 不显示虚假精确值。

每个子任务按阶段展示：

~~~text
等待提交 → 正在提交 → 供应商排队 → 正在生成 → 正在归档 → 已完成
~~~

- PENDING、SUBMITTING、ARCHIVING 显示阶段进度；
- QUEUED、RUNNING 使用动态等待条并显示已耗时；
- SUCCEEDED 且已归档显示 100%；
- FAILED 显示失败原因和重试入口；
- SUBMISSION_UNCERTAIN 显示需人工处理；
- 只有供应商未来明确返回 progress 字段时，才显示供应商百分比。

### 10.5 进度刷新

P0 使用简单轮询：

- 桌面端每 2 秒调用 GET /api/generation-batches/{id}；
- 批次全部终态后停止轮询；
- 页面进入后台时可降低频率；
- 连续网络失败使用退避并显示“连接中断，任务仍在服务端运行”；
- 重新打开桌面端或进入任务记录时立即恢复查询；
- 进度以服务端 SQLite 状态为准，不依赖客户端内存；
- P0 不引入 WebSocket 或 SSE。

## 11. 外部 API 集成规范

### 11.1 证据等级

文档中的供应商字段分为三类：

| 标记 | 含义 | 开发规则 |
| --- | --- | --- |
| CONFIRMED | 已从当前供应商页面或官方文档核对 | 可实现 |
| PROVIDER_TEST_REQUIRED | 文档存在，但模型组或别名需账号实测 | 适配器实现后必须连接测试 |
| SOURCE_PENDING | 当前没有明确接口说明 | 不得猜测，不得宣称完成 |

### 11.2 通用安全规则

- 所有第三方 API 只由服务端调用；
- API Key 不写入客户端包、日志、数据库明文或示例；
- 设置页只显示掩码和最后四位；
- 服务端使用操作系统密钥服务或 KMS 加密保存；
- HTTP 客户端设置连接、读取和总超时；
- 外部调用记录 provider、model、latency、status_code、request_id 和脱敏错误；
- 不记录原始 Authorization 头；
- 429、5xx 使用指数退避；4xx 参数错误不盲目重试；
- 任何付费“真实模型测试”必须在按钮旁提示可能产生费用。

### 11.3 Apilio 公共配置

Apilio 的三个模型共用：

- Base URL：默认 https://api.apilio.ai；
- 鉴权：Authorization: Bearer {{APILIO_API_KEY}}；
- API Key：一个必填项；
- 默认模型名由系统内置，不要求普通管理员填写；
- 每个启用模型分别做可用性测试。

默认 Key 可同时服务 GPT Image 2、Nano Banana 与 Gemini；若不同模型组使用不同令牌分组，设置页必须允许管理员在同一 Apilio 卡片中额外保存 `Gemini 视频分析 API Key`。图像编辑始终使用默认 Key，Gemini 优先使用专用 Key；两者均只可加密保存在后端，绝不下发到桌面端。

桌面端不提供 Apilio Base URL 输入项，视频拆解请求固定发送到 `https://api.apilio.ai`，避免遗留配置或误填地址接收 Bearer Key。

~~~bash
            "type": "text",

~~~

实施注意：

### 11.7 METASO MiniMax H3：图生视频

创建接口状态：CONFIRMED。

~~~bash
curl --request POST \
  --url https://metaso.cn/api/minimax/v2/video_generation \
  --header 'Authorization: Bearer {{METASO_API_KEY}}' \
  --header 'Content-Type: application/json' \
  --data '{
    "model": "MiniMax-H3",
    "content": [
      {
        "type": "text",
        "text": "{{LOCKED_H3_PROMPT}}"
      },
      {
        "type": "image_url",
        "image_url": {
          "url": "{{SIGNED_FIRST_FRAME_URL}}"
        },
        "role": "first_frame"
      }
    ],
    "resolution": "{{OUTPUT_RESOLUTION}}",
    "duration": {{OUTPUT_DURATION_SECONDS}},
    "ratio": "adaptive"
  }'
~~~

成功响应：

~~~json
{
  "task_id": "424010985738629"
}
~~~

已确认规则：

- model 为 MiniMax-H3；
- content 至少包含非空 text；
- 首帧放在 image_url 项中，role 为 first_frame；
- 界面分辨率为 768P 或 2K；调用 METASO 时将内部 `768P` 映射为已实测的请求值 `768`，`2K` 原样传递；
- duration 为 4–15 的整数；
- 图生视频 ratio 使用 adaptive；
- 200 返回 task_id；
- 页面列出 400、401、402、422、429、500；
- METASO 页面提示示例只是替换 API Host，能力语义以 MiniMax 官方文档为准；
- IR Context 是供应商控制台可选优化项，可能单独计费，不作为 P0 业务 API 必填字段。

输出时长规则：

- output_duration_seconds 默认取 floor(source_duration_seconds + 0.5)，再限制在 4–15；
- 用户可以覆盖，但只能选择 4–15 的整数；
- 生成批次创建后不可修改；
- 实际值写入 GenerationInputSnapshot；
- 页面明确区分“参考视频原始时长”和“H3 输出时长”。

错误映射：

| HTTP | 内部错误 | 处理 |
| --- | --- | --- |
| 400/422 | PROVIDER_VALIDATION_FAILED | 不自动重试，展示脱敏字段错误 |
| 401 | PROVIDER_AUTH_FAILED | 禁用生成并提示管理员 |
| 402 | PROVIDER_BALANCE_REQUIRED | 提示余额或额度不足 |
| 429 | PROVIDER_RATE_LIMITED | 指数退避并进入队列 |
| 500 | PROVIDER_TEMPORARY_FAILURE | 有上限重试 |

### 11.8 H3 查询与结果下载门禁

2026-08-14 已取得脱敏的真实创建响应和查询响应样本；当前适配器使用以下业务接口：

~~~text
POST https://metaso.cn/api/minimax/v2/video_generation
GET  https://metaso.cn/api/minimax/v2/query/video_generation?task_id={provider_task_id}
~~~

创建返回 `{ "task_id": "..." }`。查询响应为 `{ "items": [...], "total": N }`，即使携带 `task_id` 也可能带回账号下其他任务；应用必须在 `items` 中精确筛选同一 `id`，不得取第一条。当前查询 URL、列表筛选和成功结果解析已有代码/样本支撑，但 Gate 2 仍需用同一真实账号完成“请求 URL → 响应 → 下载 → 归档”的可复现脱敏记录。

成功项含 `content.url` 临时 HTTPS 下载地址。Worker 只在内存中使用它下载后立即归档至当前 COS/OSS；不写入任务、版本、日志或客户端响应。真实闭环为“创建 → 查询列表并筛选 → 下载临时结果 → 归档”。

归档前应用使用本机 `ffprobe` 检查结果是否存在音频流；无音轨或无法检查时任务保留视频结果，但标记 `AUDIO_QUALITY_FAILED`，不得把“供应商宣称原生音频”当作质量通过证据。

当前 METASO 通道已确认不支持取消和回调，P0 不实现这两项。仍为 SOURCE_PENDING 的是供应商失败状态全集、临时结果 URL 时效和完整创建/查询/下载/归档证据；不能凭成功样本推断失败字段。

H3Provider 最小接口：

~~~text
createImageToVideo(request) -> providerTaskId
queryTask(providerTaskId) -> normalizedStatus + resultUrl?
~~~

~~~mermaid
flowchart LR
    A["Windows 桌面端<br/>Tauri 2 + React + TypeScript"] --> B["内部业务 API<br/>FastAPI"]
    B --> C["SQLite<br/>WAL 模式"]
    B --> D["腾讯 COS / 阿里 OSS"]

    B --> F["Vision Provider"]

    F --> K["Apilio Gemini 3.1 Pro"]
    G --> L["Apilio GPT Image 2 / Nano Banana"]
    H --> M["METASO MiniMax H3"]
~~~

### 13.1 客户端

- Tauri 2；
- React + TypeScript；
- 负责上传、预览、编辑和状态展示；
- 不直接保存或调用第三方 API Key；
- 不承担耗时视频分析；
- 自动保存草稿；
- Windows x64 安装包，内部签名分发。

### 13.2 服务端

- FastAPI；
- SQLite；
- FFmpeg/ffprobe；
- Provider Adapter；
- 异步 Worker；
- 任务轮询器；
- 加密配置；
- 审计日志。

P0 不引入复杂微服务。业务 API 与 Worker 可在同一代码仓库、不同进程运行。

SQLite 运行规则：

- 数据库文件默认位于服务端本地数据目录，例如 data/app.db；
- 启用 WAL、foreign_keys 和 busy_timeout；
- 使用 Alembic 管理数据库版本；
- SQLite 文件只能放本机磁盘，禁止放在 COS、OSS、NAS 或网络共享目录；
- P0 只部署一个业务服务节点和一个 Worker 进程；
- Worker 可以异步处理多个外部任务，但数据库写入使用短事务并保持串行可控；
- 任务租约通过带条件的原子 UPDATE 获取，不依赖 SELECT FOR UPDATE；
- 数据库备份使用 SQLite Backup API 或 VACUUM INTO，不在运行时直接复制数据库文件；
- 每日自动备份，并定期执行恢复演练；
- 桌面端不直接访问 SQLite 文件，只调用内部业务 API。

SQLite 适用于当前内部员工、低并发 P0。若以后出现多节点部署或持续高写入并发，再单独立项评估数据库迁移，不在 P0 预先实现。

### 13.3 异步任务

需要异步化：

- 媒体转码和抽帧；
- Gemini 分析；
- 首帧绘图；
- H3 创建与查询；
- 结果下载和归档。

推荐使用 SQLite 任务表加单个 Worker 进程的简单方案。只有在并发量证明需要时再引入专用消息队列。

## 16. 状态机

### 16.1 项目状态

~~~text
DRAFT
UPLOADING
ANALYZING
EDITING
READY_TO_GENERATE
GENERATING
COMPLETED
ARCHIVED
~~~

### 16.2 人物身份与角色版本状态

PersonIdentity：

~~~text
DRAFT → ACTIVE → EXPIRED / REVOKED → ARCHIVED
~~~

- ACTIVE：源图和授权已确认，可创建角色版本；
- EXPIRED / REVOKED：禁止新项目使用，不删除历史证据；
- ARCHIVED：从默认列表隐藏，历史项目仍可追溯。

CharacterVersion：

~~~text
DRAFT → GENERATING → REVIEWING → PUBLISHED → ARCHIVED
                   ↘ FAILED
~~~

- GENERATING：至少一个必需视角正在生成；
- REVIEWING：候选已生成，等待人工审核或单张重生成；
- PUBLISHED：每个必需 view_type 都有一个已批准资产，版本不可变；
- FAILED：生成流程失败但版本和证据保留，可显式重试；
- ARCHIVED：不允许新项目选择，历史项目引用不失效。

### 16.3 批次状态

~~~text
CREATED
RUNNING
NEEDS_ATTENTION
COMPLETED
COMPLETED_WITH_FAILURES
~~~

- CREATED：子任务已创建，尚未开始提交；
- RUNNING：至少一个子任务仍在正常处理；
- NEEDS_ATTENTION：至少一个子任务处于 SUBMISSION_UNCERTAIN；
- COMPLETED：全部任务终态且没有失败；
- COMPLETED_WITH_FAILURES：全部任务终态且存在 FAILED 或 CANCELLED。

批次状态由子任务聚合计算；进度达到 100% 时只能是 COMPLETED 或 COMPLETED_WITH_FAILURES。

### 16.4 外部任务状态

~~~text
PENDING
SUBMITTING
SUBMISSION_UNCERTAIN
QUEUED
RUNNING
ARCHIVING
SUCCEEDED
FAILED
CANCELLED
~~~

供应商状态必须映射到内部状态，不能把供应商原始字符串直接作为业务契约。

archive_status 独立为：

~~~text
NOT_STARTED
DOWNLOADING
ARCHIVED
ARCHIVE_FAILED
~~~

只有外部任务成功且 archive_status=ARCHIVED，业务结果才算可交付。

SUBMISSION_UNCERTAIN 是付费保护状态：表示请求可能已被供应商接收，但本地没有 task_id。该状态不进入自动重试队列，只能在供应商明确支持请求幂等或管理员完成核对后处理。

### 16.5 结果质检状态

quality_status：

~~~text
NOT_REVIEWED
PASSED
FAILED
~~~

quality_issue_codes 可以包含 AUDIO_QUALITY_FAILED、CHARACTER_DRIFT、FRAME_ARTIFACT、TEXT_ERROR 等。AUDIO_QUALITY_FAILED 只表示 H3 原生成片的音轨质检不通过，不触发 TTS、混音或其他音频任务。

### 16.6 可恢复性

- 桌面端关闭不影响服务端任务；
- Worker 重启后能从任务表恢复；
- SUBMITTING 超时先查询幂等记录，再决定是否重提；
- H3 成功但结果归档失败时进入 ARCHIVE_FAILED，可只重试下载；
- 原始供应商响应脱敏后保留。

- 错误响应；
- 签名 URL 时效；
- H3 返回 MP4 的原生音轨。

真实 Provider 验收只运行预算受控的最小成功链路和供应商能够确定触发的少量错误，不要求靠随机失败验证状态机。真实测试使用最小素材并记录费用。不得在仓库、截图、日志或工单中保留完整密钥。

## 19. P0 验收标准

### 19.1 功能验收

- 管理员能够从一张真人源图创建身份、角色人设和版本；
- 系统能够生成 P0 规定的 7 类多视角人物资产；
- 管理员能够逐张批准、驳回和重生成，只有完整合格版本才能发布；
- 新项目只能选择授权有效且已发布的角色版本；
- 历史项目永久引用当时的角色版本和参考资产选择快照；
- 内部员工能够从新建项目完成到预览、下载结果；
- 镜头卡片可编辑、保存、重新打开；
- Prompt 可编辑、保存、锁定、追溯；
- 人物置换首帧必须由用户确认；
- 人物参考资产自动匹配结果必须可解释、可人工改选并可追溯；
- 原稿和自定义稿均可使用；
- 员工可以输入任意合法正整数数量，不使用固定 4 条选项；
- 服务端按 max_generation_count_per_batch 拦截超限数量；
- quantity=N 时准确创建 N 个独立任务；
- 生成页面和任务记录页面都显示批次进度条；
- 任务记录按项目自动列出批次和结果，不要求员工手工输入 Batch ID；
- 进度、状态计数和任务列表在重开桌面端后保持一致；
- 混合成功/失败批次最终显示 100% 和“部分失败”；
- 腾讯 COS 可用；
- 切换到 OSS 后主流程不改；
- SQLite 重启后数据、任务和版本完整；
- SQLite 备份可以恢复；
- 任务失败有明确原因和安全重试；
- H3 结果保存到企业存储并保留原生音轨。

### 19.2 质量验收

以人工质检为准，记录：

- 同一角色版本 7 类人物资产的身份一致性；
- 人物资产的角度、景别、服装、肢体、清晰度和水印检查；
- 镜头结构相似度；
- 人物身份连续性；
- 首帧与原构图一致性；
- 动作和镜头运动符合度；
- 口播与画面的语义匹配；
- H3 原生音轨是否存在且可播放；
- 是否有明显肢体、闪烁、字幕或音频问题。

P0 不设未经数据验证的“90% 相似度”宣传指标。先用 10–20 个内部样本建立基线，再决定量化阈值。

### 19.3 安全验收

- 客户端包内无第三方密钥；
- 数据库无密钥明文；
- 日志不含 Authorization；
- 私有桶和短期 URL 生效；
- 肖像授权可追溯；
- 授权过期或撤销后不能创建新角色版本或用于新项目；
- 真人源图、生成原图和已批准资产均执行对象级权限校验；
- 权限和审计有效；
- 密钥轮换后旧密钥失效；
- 删除策略经过验证；
- SQLite 文件不位于网络共享目录，备份与恢复经过验证。

## 20. 风险与未决项

| 风险/未决项 | 当前状态 | 处理 |
| --- | --- | --- |
| METASO 查询请求 URL 和失败状态全集仍缺完整真实证据 | 阻断完整 Provider 验收 | 使用真实账号补齐脱敏证据；取消/回调已确认不支持，不开发虚假能力 |
| 用户提供的 METASO 示例密钥已暴露在对话/截图 | 高风险 | 立即吊销并创建新密钥 |
| 多视角人物资产默认 Provider/模型尚未通过 Golden Sample | 阻断人物真实闭环 | 建立 CharacterImageProvider 契约，实测 GPT Image 2/Nano Banana 后选择默认实现 |
| 机器相似度分数不能可靠替代人物审核 | 已接受的 P0 边界 | 自动分数只提示；人工批准是角色版本发布硬门禁 |
| 旧 `characters.reference_asset_ids_json` 与新四层人物模型不一致 | 数据迁移风险 | 可逆迁移、兼容 API、升级/降级和历史项目回归测试 |
| 桌面端后端能力未贯通 | 当前主要产品缺口 | 以 DESKTOP_E2E_VERIFIED 为 Gate 1，不再用后端 E2E 代替桌面 E2E |
| Nano Banana 模型页与通用示例别名不同 | 待实测 | 不静默降级，连接测试后固化 |
| Apilio json_schema 在当前 Gemini 模型组的支持 | 待实测 | 不支持则退到 json_object + 应用校验 |
| H3 原生人声无法锁定音色或逐字口播 | 已接受的 P0 边界 | 允许重新生成，不增加独立音频链路 |
| H3 结果无音轨或音轨损坏 | Provider 输出风险 | 标记 AUDIO_QUALITY_FAILED 并重新生成 |
| 精确口型同步 | P0 明确不实现 | 不增加音频或口型供应商 |
| 图片置换后人物仍可能漂移 | 模型风险 | 多候选 + 人工首帧审核 + 结果质检 |
| 价格与可用模型随供应商变化 | 动态信息 | 不把网页价格写成业务常量 |
| 临时 URL 过期 | 可控 | 任务前生成，失败重试时刷新 |

## 21. P1 扩展设计

### 21.1 文生视频

只提交 text，允许设置 ratio。复用 Prompt 版本、批次和任务体系，不进入首帧流程。

### 21.2 多对象参考

支持 reference_image、reference_video、reference_audio。对象卡定义：

- 对象名称；
- 类型；
- 素材；
- Prompt 中的引用名；
- 角色/物体/动作/声音用途；
- 优先级。

多对象参考请求不得带 first_frame 或 last_frame。

### 21.3 迁移要求

- P0 数据库实体不重建；
- 复用 P0 已存在的 generation_mode，只扩展 T2V、R2V 枚举；
- Provider Adapter 增加 createTextToVideo 与 createReferenceToVideo；
- 设置页按已启用能力逐步显示；
- P1 上线前重新核对当时供应商 API。

### 21.4 Prompt 模板管理与规模化生产

P1 可增加：

- 管理员可视化编辑、审批、灰度、回滚 Gemini/人物/首帧/H3 模板；
- 模板效果评测和 Golden Sample 对比；
- 跨项目批量创建、模板批量套用和无人值守队列；
- 团队审核、发布和质量统计。

这些能力不得反向放宽 P0 的模板快照、人物授权和人工审核门禁。

## 最终产品契约

P0 的完成定义不是“能发出一个 H3 请求”，而是：

> 管理员可以从一张已授权真人源图创建人物身份和角色人设，生成、审核并发布包含 7 类必需多视角资产的不可变角色版本；员工可以在 Windows 桌面端选择该角色版本，上传参考视频，得到可编辑的结构化拆解，确认起始帧和人物参考资产匹配，生成并确认人物置换首帧，编辑和保存口播稿及 H3 Prompt，在系统安全上限内输入本批次生成数量 N，查看实时进度并逐个预览、下载结果；历史项目永久引用当时的角色、Prompt 和生成输入快照；最终 MP4 可追溯、可归档、可下载且保留 H3 原生音轨；P0 不提供独立音频或跨项目批量生产；业务数据使用 SQLite 保存；所有第三方密钥和素材访问满足企业安全要求，人物/图片/视频 Provider 均经过真实账号验证，并通过新构建 Windows 安装包的实机验收。
