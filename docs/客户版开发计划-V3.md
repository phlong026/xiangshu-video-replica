# 客户版开发计划 V3

> 版本：V3.0
>
> 状态：`READY_AFTER_USER_CONFIRMATION`，尚未开始业务开发
>
> 执行任务：`docs/客户版任务清单-V3.md`
>
> 验收规格：`docs/客户版测试与验收规格-V3.md`

## 1. 计划结论

这不是在现有系统上补几个页面。本轮扫描到当前运行层有 33 个模块直接依赖 `sqlite3`，并且认证、任务领取、控制面和部署都以单机为前提。客户版必须先完成 PostgreSQL 运行迁移，再建设激活码、设备/session、公平队列和多实例；最终数量以 T04/DB-02 行级清单为准。

42 个任务的基础工程量约为 **95–165 人日**；按风险预留后建议按 **110–185 人日**管理。真实服务器开通、域名/证书、付费 ZPay/Provider 验收和灰度观察时间另算，不计入纯开发人日。

推荐配置为：2 名后端（其中 1 名偏 DB/账务）、1 名前端/Tauri、1 名 QA 自动化、1 名 OPS/安全按阶段投入。该配置下，达到类生产 staging 的合理目标是 **8–12 周**；真实链路和 10/100 码灰度取决于外部授权与观察窗。

## 2. 资源场景

| 场景 | 人员 | 预计节奏 | 主要风险 |
| --- | --- | --- | --- |
| 推荐 | 2 后端 + 1 前端/Tauri + 1 QA + 0.5–1 OPS/安全 | 8–12 周到 staging，之后真实链路/灰度 | 协调成本可控，关键车道有人复核 |
| 紧凑 | 1 后端 + 1 前端 + QA/OPS 兼职 | 12–18 周 | PostgreSQL、session、队列串行，安全测试易后置 |
| 单人全栈 | 1 人 | 22–34 周 | 高风险代码缺少独立 reviewer，不推荐直接生产化 |

排期只能在 T02 回归基线和 T04 SQLite 迁移清单完成后重新校准；在此之前不承诺固定上线日期。

## 3. 并行开发车道

### 车道 A：数据库、迁移与账务

- 任务：T02–T14、T22–T23。
- 负责人：DB/后端 + 账务 reviewer。
- 产物：PG runtime、Alembic、导入对账、一账户一码、首充一次、ZPay 续充。
- 阻塞关系：所有客户功能的主前置。

### 车道 B：设备、认证与 session

- 任务：T15–T21。
- 负责人：后端 + 安全 reviewer。
- 产物：两槽、配对、租约、409、显式 switch、epoch fencing。
- 阻塞关系：依赖 T13；完成 T20 后前端才能做真实联调。

### 车道 C：Worker、公平队列与性能

- 任务：T24–T27。
- 负责人：后端/性能 + DB reviewer。
- 产物：按用户轮转、多 Worker 无重复、崩溃恢复、压测证据。
- 阻塞关系：可在车道 B 后半程并行，但必须基于 PG。

### 车道 D：客户前端、Tauri 与管理端

- 任务：T28–T34。
- 负责人：前端/Tauri + QA。
- 产物：激活、配对、冲突、切换、设备管理、管理后台、E2E。
- 并行方式：API 模型冻结后可先用 mock 写失败组件测试；不得用 mock 结果替代真实双 API E2E。

### 车道 E：安全、部署和发布验证

- 任务：T35–T42。
- 负责人：QA、OPS、安全、Verifier。
- 产物：类生产、监控、备份/PITR、故障演练、真实链路、灰度和 Go/No-Go。
- 运行方式：从 T03 起参与，不允许在开发结束后才补安全和部署。

## 4. 阶段与里程碑

### M0：开发基线（建议第 1 周）

范围：T01–T04。

出口门：

- V3 规格、开发设计、任务清单一致；
- 当前 P0 全量回归有新鲜证据；
- PostgreSQL 16 fixture 可运行；
- 当前扫描到的 33 个 SQLite 依赖模块和迁移风险被逐行登记。

### M1：PostgreSQL 可运行基座（建议第 2–4 周）

范围：T05–T09。

出口门：

- API、Worker 和 Alembic 在 PG 上运行；
- 空库 upgrade/downgrade 通过；
- SQLite 导入、对账和回滚窗口演练通过；
- per-operator admin session/CSRF 可追溯真实 actor；客户生产配置为 SQLite/local/dev identity/单管理员映射时 fail-closed。

这一阶段禁止开放客户流量，也不做“PG 与 SQLite 双写”。

### M2：激活码与首次充值（建议第 4–6 周）

范围：T10–T15。

出口门：

- 管理端可批量生成、发放、暂停、作废和受控导出；
- 100 并发同一码只产生一个 user/wallet/activation/order/CHARGE/session；
- 响应丢失可恢复同一设备和 session 凭据；
- 数据库、日志、错误、普通 CSV 无激活码明文。

### M3：两设备与单在线（建议第 6–8 周）

范围：T16–T23。

出口门：

- 最多两个当前有效设备槽，解绑后可审计化替换；
- 第一设备在线时第二设备普通登录 100 次全部 409；
- 显式切换后旧设备全部 API/heartbeat 401；
- 旧请求迟到进入业务事务时被 fencing；
- 后续 ZPay/后台加款不改变码、设备和并发。

### M4：公平队列、客户端和管理端（建议第 7–10 周，可并行）

范围：T24–T34。

出口门：

- A1000/B100/C10 按用户轮转，每用户默认运行 1；
- 四 Worker 无重复领取和重复付费；
- 客户激活、第二设备、冲突、切换、续充 E2E 通过；
- 管理端批次、客户、设备、session、审计可操作且 actor 真实。

### M5：类生产 staging（建议第 10–12 周）

范围：T35–T39。

出口门：

- 双 API、至少四 Worker、PG HA、私有 COS、LB/TLS；
- API/Worker kill、PG failover、COS/ZPay/Provider 临时失败演练通过；
- 备份/PITR 可恢复并核对激活、账务和 session epoch；
- 认证、账务、并发专项审查无 Critical/High。

### M6：真实链路与灰度（外部窗口）

范围：T40–T42。

顺序：真实最低额 ZPay、COS、Provider -> 10 个客户码 -> 100 个客户码 -> Go/No-Go。

任何阶段出现重复入账、双在线、旧设备写入成功、跨用户访问或账本不一致，立即停止扩大并执行对应回滚点。

## 5. 关键路径与不可错误并行项

关键路径：

```text
PG 全量运行迁移
  -> 首次激活原子事务
  -> 两设备与单在线 session
  -> 全业务写 fencing
  -> 客户 E2E
  -> 多实例 staging
  -> 故障与真实链路
  -> 灰度
```

禁止错误并行：

- T13 不能在 T08/T10 数据约束未完成前实现；
- T20 switch 不能在 T19 基础租约状态机未通过前实现；
- T21 不能只批量替换 dependency，必须逐写路由验证事务内 fencing；
- T25 公平队列不能在 SQLite 上先实现再“以后迁移”；
- T36 staging 不能用单 API/单 Worker 健康检查冒充多实例；
- T40 真实付费和 Provider 提交必须获得人工授权。

## 6. 每周工作节奏

### 周初

- 选择已满足依赖的任务；
- 明确 owner/reviewer、失败测试、回滚点；
- 冻结本周 API/migration 变更，不临时扩充产品范围。

### 每个任务关闭前

- 读取完整 diff；
- 跑目标测试、静态检查和安全扫描；
- 保存 SHA、命令、通过数、未测试项；
- 认证/账务/并发由独立 reviewer 审查；
- 按中文 Lore 协议提交。

### 周末门禁

- 只按证据更新任务状态；
- 区分本地自动化、staging、真实外部链路；
- 未过阶段出口门时，下周继续修复，不带病进入下一生产化阶段。

## 7. 分支与提交策略

- 大车道使用 `feat/customer-v3-*` 独立分支；数据库、认证、队列、前端避免在一个长分支混做。
- 每个 Alembic revision 单独提交，迁移与对应测试同提交；存量导入脚本再单独提交。
- 公共 API 先提交模型/失败测试，再提交实现，再生成 OpenAPI 前端类型。
- 不 force-push 共享分支；通过 PR 和必需检查进入集成分支。
- 每个提交标题使用中文意图，正文记录约束、拒绝方案、测试与未测试项。

## 8. 质量门

| Gate | 必须通过 |
| --- | --- |
| G0 任务就绪 | 依赖完成、文件范围明确、失败测试和回滚点明确 |
| G1 本地代码 | Ruff/format/mypy、Biome/TypeScript/Vitest、目标 PG 测试通过 |
| G2 集成 | PG migration、并发、E2E、OpenAPI 无漂移 |
| G3 安全 | secret、认证、IDOR、CSRF、CORS/Host、账务、并发审查 |
| G4 staging | 双 API、四 Worker、PG HA、COS、故障演练 |
| G5 真实链路 | 经授权的 ZPay/COS/Provider 证据绑定发布 SHA |
| G6 生产 | 10/100 码灰度、监控、备份、回滚、值班、业务批准 |

## 9. 回滚点

| 回滚点 | 时机 | 处理 |
| --- | --- | --- |
| R0 | PG 适配前 | 保留现有内部 P0 release/tag，不覆盖其数据 |
| R1 | PG 导入后未开放客户 | 停止新服务，恢复旧 P0；PG 作为未开放影子库 |
| R2 | staging 激活码 | 删除 staging 测试数据或恢复快照；不影响生产 |
| R3 | 10 码灰度 | 暂停发码和新充值、强制下线灰度账户、逐笔对账 |
| R4 | 100 码灰度 | 停止扩大、冻结风险写入、恢复稳定发布、按账务规则补偿 |

已确认的 CHARGE 和账务流水不能靠数据库回滚静默删除；退款/补账必须走审计化业务单据。

## 10. 主要风险储备

- PostgreSQL 迁移面超过初步估计：优先缩小当期功能，不跳过全量 PG 回归。
- 设备凭据安全存储方案需要新依赖：单独做威胁模型和依赖审查，不在 UI 提交中顺带加入。
- Provider 请求不支持幂等：保留 `SUBMISSION_UNCERTAIN` 与人工核验，不自动重复付费 POST。
- 心跳造成 PG 热点：先以 30/90 秒和索引压测，只有证据不足才新增 Redis ADR。
- 管理端 actor 不真实：禁止用统一环境变量管理员进入客户生产。

## 11. 开发完成后的交付物

- 代码、Alembic、OpenAPI 和生成类型；
- SQLite -> PG 导入与对账报告；
- 单元、PG 集成、E2E、安全、性能和故障演练报告；
- 客户端 macOS/Windows 凭据持久化与重启验收；
- 多实例部署、监控、备份、回滚和值班手册；
- 真实 ZPay/COS/Provider 证据；
- 10/100 码灰度和最终 Go/No-Go 记录。

## 12. 开发启动建议

第一批只启动 T02–T06：回归基线、PG fixture、SQLite 差异清单、连接/迁移基座。该批关闭前不并行编写首次激活业务逻辑，以免在错误事务模型上返工。
