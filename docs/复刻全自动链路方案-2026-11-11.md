## 1. 背景与目标

现状：一键复刻自动化只覆盖素材供给段（导入建项目），复刻页三段式（拆解→首帧置换→文案与生成）全部需要用户手动推进，最终生成与付费还要跳转 AI 视频创作页。

目标：新增一条**全自动复刻链路**，与现有手动链路并存：

- 用户发起一次 → 系统自动完成 导入 → 拆解 → script 版本桥接 → 首帧候选与选定 → 提示词编译；
- 在**确认点**暂停，向用户展示提示词、首帧、文案终稿与三栏费用明细（已结算 / 仍预占 / 新增生成费用）；
- 用户单次确认（绑定报价凭证与产物指纹）→ 原子完成 锁提示词 + 建批次 + 资金预占 → 自动跑完生成 → 交付；
- 用户放弃 → 任务终止，已产出成果保留在项目里，可转手动链路继续编辑。

### 非目标

- 不做无人值守自动扣费（确认点是资金闸门，刻意保留——2026-11-11 拍板）。
- 不做运营管理后台批量生产线。
- 不改手动链路任何交互与口径。
- 不新增计费项：各环节费用完全沿用现有计费目录（`billing_catalog.py`），自动链路只做串联与预估汇总展示。

## 3. 架构：`replica_pipeline_tasks` 编排器

### 3.1 数据模型（r1#7/#12 重写：类型、租约、幂等作用域、FK 策略）

关联 ID 一律沿用现有 `text` 类型（现有 users/projects/任务表主键即 text，uuid 类型会产生不匹配）：

```sql
CREATE TABLE replica_pipeline_tasks (
    id               text PRIMARY KEY,          -- 与现有任务 id 同型（uuid 文本）
    owner_user_id    text NOT NULL,             -- 沿用 text，不建 FK 强引用（删除策略见下）
    project_id       text NOT NULL,
    platform         text NOT NULL,
    video_id         text NOT NULL,
    request_hash     text NOT NULL,             -- 发起参数指纹（策略+规格），重试一致性校验
    status           text NOT NULL CHECK (status IN (
                       'ENQUEUED','IMPORTING','ANALYZING','SCRIPT_VERSIONING',
                       'FIRST_FRAMING','COMPOSING','AWAIT_CONFIRM',
                       'GENERATING',
                       'NEEDS_REVIEW','NEEDS_REVIEW_SETTLED',
                       'DRAINING',
                       'DELIVERED','DELIVERED_PARTIAL','FAILED','CANCELLED','EXPIRED')),
    -- NEEDS_REVIEW       子任务未全部收口（存在待提交/运行中/未收口预占/提交未知），
    --                    占用在途约束、禁止接受部分成果与重生成受理（r3#3）；
    --                    轮询「仅观察收口」自动迁 SETTLED（r4#1）
    -- NEEDS_REVIEW_SETTLED 全部子任务已收口，释放在途约束，允许两类显式动作
    -- DRAINING           撤销推进权后的「收口中」（r4#2）：FAILED/CANCELLED 已判定但
    --                    运行中子任务/未收口预占尚未结清——继续占用在途约束，
    --                    无任何付费推进；全部收口后迁对应终态（FAILED/CANCELLED）释放。
    --                    撤销推进权（不再触发新阶段）与释放在途资格（允许新任务）是两件事
    stage            text NOT NULL,             -- 精确断点（含失败阶段）
    stage_retry_no   integer NOT NULL DEFAULT 0, -- 业务重试序号（操作键派生用，r2#3；
                                                 -- 确定性失败后才原子递增，不用租约 attempt 代替）
    character_version_id text,                   -- 发起时选定并冻结的人物版本（r2#2）
    suspended_at     timestamptz,               -- 当前挂起时段起点（总开关挂起，r3#6）
    suspended_seconds_total integer NOT NULL DEFAULT 0, -- 历史挂起累计秒数；恢复时累加
                                                 -- 期限判定统一用「有效运行时长」，
                                                 -- 见 §3.2 期限适用范围表
    idempotency_key  text NOT NULL,             -- 用户作用域：'{owner_user_id}:{客户端键}'
    -- 租约字段（复用 task_lease 语义的列形态）
    locked_by        text,
    locked_until     timestamptz,
    attempt          integer NOT NULL DEFAULT 0,
    next_poll_at     timestamptz NOT NULL,      -- 等待期调度键：到期才可被领取（r1#9）
    -- 各阶段产物引用（可空；sub_* 另存操作键，见 3.3）
    project_fingerprint  text,                  -- 复用判断指纹（r1#11）
    import_task_id   text,
    analysis_task_id text,
    script_version_id text,
    first_frame_task_id text,
    prompt_version_id text,
    batch_id         text,
    quote_token      text,                      -- AWAIT_CONFIRM 冻结的报价凭证
    quote_snapshot   jsonb,                     -- 金额上限、档位、数量、总秒数、产物指纹
    stage_detail     jsonb,                     -- 失败原因、重试线索、策略快照
    created_at timestamptz NOT NULL DEFAULT now(),
    updated_at timestamptz NOT NULL DEFAULT now(),
    confirmed_at timestamptz,
    finished_at  timestamptz,
    UNIQUE(idempotency_key)
);
CREATE INDEX ix_replica_pipeline_poll ON replica_pipeline_tasks(next_poll_at)
    WHERE status IN ('ENQUEUED','IMPORTING','ANALYZING','SCRIPT_VERSIONING',
                     'FIRST_FRAMING','COMPOSING','GENERATING',
                     'NEEDS_REVIEW','NEEDS_REVIEW_SETTLED','DRAINING');
    -- 可调度状态白名单（r3#7 + r4#1/#2 + r7#3）：
    -- NEEDS_REVIEW / DRAINING 为「仅观察收口」模式：领取后只做收口检查与
    -- →SETTLED / →终态迁移，无任何付费动作（r4#1/#2）；
    -- NEEDS_REVIEW_SETTLED 为「仅产物恢复观察」模式：只消费免费恢复事件
    -- 重判 DELIVERED，不触发重生成（重生成须用户显式受理，r7#3）。
    -- AWAIT_CONFIRM 由独立过期扫描驱动；
    -- 领取查询使用同一谓词，且排除 suspended_at IS NOT NULL 的行（r4#4：
    -- 挂起行只被可重入的恢复事务驱动，不被普通领取抢跑）。
-- 每用户单在途：数据库级约束（r1#13，应用层先查再建不可依赖）。
-- 谓词 = 「后台付费敞口未收口」（r3#3 + r4#2：NEEDS_REVIEW 时子任务可能仍在运行并
-- 继续付费提交；DRAINING 的运行中子任务同样未收口——撤销推进权 ≠ 释放在途资格）。
CREATE UNIQUE INDEX uq_replica_pipeline_active_user
    ON replica_pipeline_tasks(owner_user_id)
    WHERE status IN ('ENQUEUED','IMPORTING','ANALYZING','SCRIPT_VERSIONING',
                     'FIRST_FRAMING','COMPOSING','AWAIT_CONFIRM','GENERATING',
                     'NEEDS_REVIEW','DRAINING');
-- 每项目单在途（同谓词）
CREATE UNIQUE INDEX uq_replica_pipeline_active_project
    ON replica_pipeline_tasks(project_id)
    WHERE status IN ('ENQUEUED','IMPORTING','ANALYZING','SCRIPT_VERSIONING',
                     'FIRST_FRAMING','COMPOSING','AWAIT_CONFIRM','GENERATING',
                     'NEEDS_REVIEW','DRAINING');
```

- **FK 删除策略**（r1#7）：`project_id`/`owner_user_id` 不建数据库级 FK 强引用，改为应用层归属校验 + 项目删除路径显式级联取消在途 pipeline（禁止「删项目无声抹掉资金授权与审计」——pipeline 行保留，置 CANCELLED 并在 `stage_detail` 记录 project_deleted）。
- **幂等语义**（r1#12）：幂等键用户作用域 + 客户端生成；`request_hash` 记录发起参数。同键**永远重放原尝试**（含终态），绝不复活；EXPIRED 后重新发起走**新键新尝试**，显式指向原 pipeline/project 并重新报价，旧 `quote_snapshot` 仅留档。
- 租约字段仅承载编排任务自身的领取（`locked_by/locked_until/attempt`），`attempt` 用于拒绝旧 worker 迟到提交（r1#8）。

### 3.2 状态机（r1#10 补充生成域结果映射）

```
ENQUEUED → IMPORTING → ANALYZING → SCRIPT_VERSIONING → FIRST_FRAMING
         → COMPOSING → AWAIT_CONFIRM → GENERATING
         → DELIVERED / DELIVERED_PARTIAL / NEEDS_REVIEW
任意在途态 --撤销事件（接管/删除/期限判定）--> DRAINING -->（收口观察）FAILED / CANCELLED
挂起不是独立状态：行级属性 suspended_at，可叠加于任意在途态与 DRAINING（r5#2）
```

**完整状态转换表**（16 态统一口径，r5#7；DDL、状态图、轮询白名单、两个唯一索引谓词均以此表为准）：

| 从 | 事件 | 到 | 说明 |
| --- | --- | --- | --- |
| ENQUEUED | worker 领取 | IMPORTING | |
| IMPORTING | 导入完成 / 失败 | ANALYZING / FAILED\* | \*未收口一律经 DRAINING（见下） |
| ANALYZING | 拆解完成 / 失败 | SCRIPT_VERSIONING / FAILED\* | |
| SCRIPT_VERSIONING | script 就绪 / 失败 | FIRST_FRAMING / FAILED\* | 确定性写库 |
| FIRST_FRAMING | 候选选定 / 失败 | COMPOSING / FAILED\* | |
| COMPOSING | 编译+报价冻结 / 冲突或失败 | AWAIT_CONFIRM / FAILED\* | 冲突码入 stage_detail |
| AWAIT_CONFIRM | 确认事务 | GENERATING | §4.2 单事务 |
| AWAIT_CONFIRM | 放弃 / 72h 扫描 | CANCELLED\* / EXPIRED | EXPIRED 仅此入口 |
| GENERATING | 收口 × 可交付矩阵（r6#4） | 见下 | 按「是否收口 × 是否全部可交付」四象限判定 |
| GENERATING | 全收口 × 名额全覆盖可交付 | DELIVERED | §3.2.1 判定 |
| GENERATING | 全收口 × 未全覆盖可交付 | NEEDS_REVIEW | 等人工选择 |
| GENERATING | 全收口 × 全覆盖不可交付（归档/规范化失败） | NEEDS_REVIEW_SETTLED | stage_detail 标记交付产物失败；**产物恢复观察**（§3.2.1，免费恢复自动重判 DELIVERED）或对不可交付名额付费重生成/转手动 |
| GENERATING | 全收口 × 未覆盖不可交付（含全部失败且预占结清，0 名额覆盖） | NEEDS_REVIEW_SETTLED | 无效结果集合；重生成/放弃/转手动 |
| GENERATING | 未收口（任一象限） | NEEDS_REVIEW | 提交未知=行属性 uncertain，冻结在 GENERATING |
| NEEDS_REVIEW | 观察收口：重算名额覆盖 | DELIVERED 或 NEEDS_REVIEW_SETTLED | **r5#1：全覆盖可交付直接 DELIVERED**（对账成功/归档恢复场景） |
| NEEDS_REVIEW_SETTLED | 重生成受理事务 | GENERATING | §5.1.1；唯一索引裁决资格 |
| NEEDS_REVIEW_SETTLED | 接受部分成果（非空且满足规格对应可交付谓词的有效结果集合，r7#3/r10#1） | DELIVERED_PARTIAL | |
| NEEDS_REVIEW_SETTLED | 产物恢复观察：免费恢复完成且全部可交付 | DELIVERED | 观察轮询驱动，无付费动作（r7#3；SETTLED 在轮询白名单中仅为本出口与收口确认，不触发重生成） |

重生成批次完成的出口统一走 **GENERATING 行**（重生成受理已把 pipeline 迁入 GENERATING，`SETTLED→重生成完成` 不可达，r7#4）。
| NEEDS_REVIEW_SETTLED | 转手动 | CANCELLED\* | |
| 任意在途态/DRAINING 前态 | 撤销事件 | DRAINING | 统一撤销事务（r5#2），见 §5.3 |
| DRAINING | 收口观察 | FAILED / CANCELLED | 对应撤销事件的原语义 |

- \* 号规则：**迁 FAILED/CANCELLED 前若仍有运行中子任务/未收口预占，一律先落 DRAINING**；子任务全部收口且预占结清后由观察轮询迁终态。已在 DRAINING 后挂起的（§5.3），清挂起屏障后仍可被观察轮询驱动（无付费动作）。
- **三个独立状态集合（r8#4 明确，全部为 DDL CHECK 的子集）**：
  - **轮询白名单**（可调度，§3.1 索引谓词）：推进态 7 个（ENQUEUED、IMPORTING、ANALYZING、SCRIPT_VERSIONING、FIRST_FRAMING、COMPOSING、GENERATING）+ NEEDS_REVIEW + NEEDS_REVIEW_SETTLED + DRAINING（后三者为仅观察模式，无付费动作）；
  - **在途约束集合**（唯一索引谓词）：轮询白名单 + AWAIT_CONFIRM，**减去** NEEDS_REVIEW_SETTLED（已收口无敞口）——即「后台付费敞口未收口」的精确表达；
  - **独立过期扫描集合**：仅 AWAIT_CONFIRM（72h 确认期限）。
  三者交集与差集均有明确业务含义，DDL/状态图/谓词注释三处以本表为准。

### 3.2.1 交付判定：以「交付名额」为业务单位（r3#1/#2 统一口径）

**交付单位不是镜头**：批次按 `quantity` 创建 N 条生成任务，每条任务持有相同的完整提示词快照与完整输出时长（`generation.py:2624-2655`）——一条任务 = 一个**交付名额**。费用三栏、确认卡、界面与验收断言的数量口径统一为「交付名额（原始任务数）」，全文不再使用「镜头数」表达交付数量。

- **原始交付名额集合** = 首次授权批次创建的全部任务；
- **有效结果** = 名额自身 SUCCEEDED，或其替代链（`superseded_by_task_id`，`generation.py:998`）末端 SUCCEEDED 的任务——**每条替代链最多贡献一个有效结果**；
- **DELIVERED 谓词（r7#4 统一，充要）**：**全部子任务收口且无提交未知 ＋ 有效结果覆盖全部交付名额 ＋ 全部有效产物可交付**。三条件缺一不可，全文（转换表、§5.1、§7、§9 断言）以此为准。**不要求原批次状态为 `SUCCEEDED`**——实测原失败名额即使已有成功替代，原批次仍停在 `COMPLETED_WITH_FAILURES`（`batch_status`/`calculate_progress`），按原批次状态判定会永久阻断交付；
- **「可交付」判据（r8#1 明确，可执行）**：自动档固定 768P，生成任务成功后经 `finalize_generation_direct_result` 落 `SUCCEEDED + DIRECT`（成片直链）——**`SUCCEEDED + DIRECT（直链就绪）即为可交付**，与 AI 视频创作页现有交付形态一致；归档与规范化是 2K 特定规格的可选增强，**不在自动档交付路径上**（无需调用人工归档接口）。因此正常自动档全链路中「产物恢复观察」分支不应触发，仅作为未来规格扩展的安全网保留；§9 验收补「全 DIRECT 交付不依赖人工归档接口」用例；
- **名额覆盖 ≠ 可交付（r7#3 区分 + r9#1 谓词统一）**：两个正交计数——`covered`（有效结果覆盖的名额数）与 `deliverable`（有效产物满足**规格对应可交付谓词**的名额数；**768P 自动档的可交付谓词 = `SUCCEEDED + DIRECT`，不含任何规范化前提**——`finalize_generation_direct_result` 不执行规范化且 `result_asset_id=NULL`，按规范化计数会把正常 DIRECT 成果误判不可交付）。全文（含部分交付）统一按此谓词计算：接受部分成果（DELIVERED_PARTIAL）要求 `deliverable` 集合**非空**且其中全部满足该谓词；§9 补「DIRECT 成功与失败混合时接受部分成果」断言；
- **产物恢复观察（r7#3 + r8#1 收窄）**：仅当未来自动档扩展到依赖免费后处理的规格时才会触发（768P 交付全 DIRECT，见上）。机制：pipeline 落 `NEEDS_REVIEW_SETTLED` 时注册产物恢复观察，`NEEDS_REVIEW_SETTLED` 纳入观察轮询白名单（仅产物恢复观察，无任何付费动作）——归档/规范化免费恢复完成后，观察轮询重算 `deliverable`，全部可交付 → 直接迁 `DELIVERED`（无需人工、不重复付费）；**后处理的执行者、幂等键与有界恢复出口在规格扩展时随该规格一并设计**（r8#1：768P 自动档无此依赖，不为它预造规范化通道）；恢复不可能成功（永久失败）→ 用户可选对**这些名额付费重生成**（见 §5.1）或转手动。
- 用户在 NEEDS_REVIEW_SETTLED 明确接受部分成果 → `DELIVERED_PARTIAL`（有效结果未覆盖全部名额但产物可交付）。

### 3.2.2 待核对双态与收口（r3#3）

| 状态 | 进入条件 | 约束占用 | 允许的动作 |
| --- | --- | --- | --- |
| `NEEDS_REVIEW` | 批次返回 `NEEDS_ATTENTION`/`COMPLETED_WITH_FAILURES`，或收口前的不确定结果（uncertain 冻结除外） | **占用**（子任务可能仍在运行并继续付费提交） | 父编排无付费推进，但**既有授权内剩余排队子任务照常提交至收口**（§6 许可谓词允许，r6#3）；观察轮询每次领取重算名额覆盖：全覆盖且可交付 → 直接 `DELIVERED`（对账成功/归档恢复场景，不经人工，r5#1）；未全覆盖且已收口 → `NEEDS_REVIEW_SETTLED` |
| `NEEDS_REVIEW_SETTLED` | 全部子任务到达终态、预占全部收口、无提交未知 | **释放** | 接受部分成果 / 重生成受理 / 转手动 |

- **提交未知（SUBMISSION_UNCERTAIN）**：pipeline 冻结在当前阶段并置 `stage_detail.uncertain=true`，禁止一切新的付费提交（含新发起与重生成受理），直至对账器给出确定性结果（沿用现有生成域对账机制）。
- **AWAIT_CONFIRM 不占执行槽**：租约已释放，由 `next_poll_at` 之外的独立过期扫描驱动（§3.3）。

### 3.2.3 期限适用范围（r3#6：挂起计时完整落地）

有效运行时长 = `now() - created_at - suspended_seconds_total - (挂起中 ? now()-suspended_at : 0)`。

| 期限 | 计时口径 |
| --- | --- |
| 执行期限（24h 到 AWAIT_CONFIRM） | 排除挂起时长 |
| 无进展期限（30 分钟/阶段） | 排除挂起时长 |
| 每阶段重试预算（2 次） | 挂起不消耗次数 |
| AWAIT_CONFIRM 确认期限（72h） | **恒定计时，不排除挂起**；总开关关闭期间确认接口同样拒绝（挂起=一切付费动作不发生），重开后在剩余期限内可确认，过期按 EXPIRED 走重发起 |
| 报价凭证有效期（300s） | 恒定，与一切无关（`quote_contracts.py`） |
| 过期扫描 | 挂起中的 pipeline 不做 EXPIRED 判定与任何推进动作 |

### 3.3 驱动方式：轮询推进 + 有界调度（r1#8/#9 重写）

编排任务复用 generation worker 池领取，但**等待期与执行期的租约语义明确分离**：

- **领取条件**：`next_poll_at <= now()` 且未持有租约且 `suspended_at IS NULL`（r4#4：挂起行不参与普通领取，只被恢复事务驱动）。领取时 `attempt += 1` 并短事务推进。NEEDS_REVIEW/DRAINING 在轮询集合中为**仅观察模式**：只做收口检查与状态迁移（→SETTLED / →终态），无任何付费动作（r4#1/#2）。
- **等待子任务时**：置好下一次 `next_poll_at`（有上限退避：30s 起步、翻倍、封顶 5 分钟），**立即释放租约**——等待期不持有租约、不心跳续租。修正 r1#9 指出的「释放后照常心跳」矛盾：等待期唯一动作是到期后重新变得可领取。
- **副作用恰好一次 + 业务重试**（r1#8 + r2#3）：每阶段入队使用操作键 **`pipeline:{id}:{stage}:{stage_retry_no}`** + 请求指纹。注意各子任务域的幂等重放语义不同——首帧任务对同一幂等键**直接重放旧任务（含失败终态）**（`image_tasks.py:354`），因此固定键无法实现自动重试：`stage_retry_no` 是**业务重试序号**，崩溃恢复复用同一序号（找回在途任务），只有子任务到达**确定性失败终态**且重试预算未耗尽时才原子递增序号、以新键重新入队；禁止用租约 `attempt` 兼做业务重试计数。子任务受理与引用回填（`import_task_id` 等）在**同一事务**完成；无法同事务的域按操作键找回。所有推进/完成写入校验 `attempt` 与 `locked_by`，拒绝失租 worker 的迟到提交。
- **逐域恢复规则**（r1#8）：导入/拆解/首帧各自的租约过期恢复行为不同，编排器不假设子任务必然到达终态——
  - 子任务在位（有 id）：按该域既有过期恢复语义等待；
  - 子任务无 id 且操作键无产物：阶段入队从未成功，重新入队；
  - 子任务无 id 但操作键有产物：按操作键找回引用。
- **有界退出**（r1#9）：
  - **执行期限**：整条 pipeline 自发起起 24h 未到 AWAIT_CONFIRM → FAILED(原因=执行超时)；
  - **无进展期限**：同阶段连续无进展超阈值（如 30 分钟无状态变化）→ FAILED；
  - **重试预算**：每阶段自动重试上限 2 次（计入发起时披露的有界授权），超限 FAILED；
  - **AWAIT_CONFIRM 过期**：由**独立过期扫描**（worker 池外的定时任务，复用现有定时任务模式）驱动，72h → EXPIRED。等待确认不占执行槽、不阻塞子任务。
- COMPOSING 由编排任务自身完成（进程内调用与 `/prompts/compile` 相同的确定性编译函数，无收费）。

## 4. 确认点设计（资金闸门，r1#1/#2/#3 重写）

### 4.1 授权凭据绑定（r1#1 P0 闭环）

进入 AWAIT_CONFIRM 时调用现有报价契约（`generation_price_quote`）取得**报价凭证**（`quote_token`，300 秒有效期）并冻结 `quote_snapshot`：金额上限、档位、任务数量、总秒数、产物指纹（prompt_version_id、first_frame 资产、script_version_id、规格）。

**确认请求必须携带**：`quote_token` + 客户端所见的金额上限 + 产物指纹。服务端逐项比对：

- 报价过期（>300s）→ 422 要求前端重新拉取报价并重新展示（不是自动续价）；
- 产物指纹不匹配（用户看过 A 稿确认的是 B 稿）→ 422 重新展示；
- 金额上限不符 → 422。

前端确认卡倒计时 300s，过期即置灰并提示重新核价。**任何变化都拒绝并重新展示，绝不静默按新价授权。**

### 4.2 原子提交边界（r1#2 闭环）

确认动作为**单一事务**（会话 fencing 保护，参照现有登录/计费域纪律），**锁序遵循 §6 全局顺序（r8#2：先项目后 pipeline，与撤销事务同向，消除「确认持 pipeline 等项目、撤销持项目等 pipeline」的死锁）**：

```
BEGIN;
  非锁定读项目标识（不做 UPDATE 前置假设）;
  SELECT ... FOR UPDATE projects 行;          -- 全局锁序第一位
  SELECT ... FOR UPDATE pipeline 行;           -- 持锁重验 project_id 关联未被改
  校验 status=AWAIT_CONFIRM（confirm/cancel/expire 同一把行锁 + 数据库时钟判过期）;
  validate_quote（token、金额、指纹）;
  require_generation_duration_available（再次校验）;
  锁定 prompt version;
  创建 generation batch（批次键固定派生自 pipeline id，幂等）;
  资金预占（生成档位全额预估）;
  回填 batch_id、status=GENERATING、confirmed_at;
COMMIT;
```

领取、恢复、确认、重生成、删除五类事务全部按此顺序（r8#2）；§9 并发测试增加「确认/重生成 与 撤销」交错场景。

- 建批次后崩溃：事务回滚或提交是原子的，重放确认（同幂等键）返回既有结果，**不因后来涨价误报失败**；
- 不同幂等键的并发确认：行锁串行化，第二个看到状态已迁移直接返回既有结果；
- confirm / cancel / expire 竞争：同一行锁 + 数据库时间裁决，先到先得。

### 4.3 费用三栏披露（r1#3 闭环）

确认卡费用区固定三栏：

1. **已结算**：确认点前已实际结算的预处理费用（拆解、首帧已交付用量）；
2. **仍预占**：预处理环节尚在预占未结算的部分（含失败待释放的预占——失败与未执行预占**必须释放**，只有既有结算规则认定的**已交付用量**才不退）；
3. **本次新增**：生成报价（档位 × 秒数 × 数量），即本次授权标的。

发起弹层（§7）同步披露：预处理环节会产生 1-2 类费用、候选数量与重试次数上限、生成前还有一次确认。「已产生费用不退」表述限定为「已交付用量不退」。

## 5. 失败出口与人工接管（r1#10/#11 重写）

### 5.1 生成域结果映射

| 批次/任务终态 | pipeline 状态 | 后续动作 |
| --- | --- | --- |
| 全部子任务收口且无提交未知 ＋ 名额全覆盖 ＋ 全部有效产物可交付（三条件充要，原批次可能停在 `COMPLETED_WITH_FAILURES`） | DELIVERED | 成片直链交付 |
| `COMPLETED_WITH_FAILURES` 或 `NEEDS_ATTENTION` | NEEDS_REVIEW →（子任务全部收口后）NEEDS_REVIEW_SETTLED | 收口前仅查看；收口后可选〔对**未覆盖或有效结果不可交付**的名额付费重生成（重新授权）〕〔接受部分成果（非空且满足规格对应可交付谓词的有效结果集合）→ DELIVERED_PARTIAL〕〔转手动〕 |
| 重生成批次完成（pipeline 已在 GENERATING） | 归并后按 §3.2.1 三条件充要谓词判定 | **全部收口且无未知＋名额全覆盖＋全部有效产物可交付（DIRECT）→ DELIVERED**（原失败任务保持终态不变，不修改历史）；未满足 → 按收口状态落 NEEDS_REVIEW / NEEDS_REVIEW_SETTLED（r8#4：与转换表同源，不单写全覆盖出口） |
| 提交未知（UNCERTAIN） | 冻结在当前阶段 + uncertain 标记 | 等对账器确定性结果；禁止一切新付费提交 |
| 用户取消批次 | CANCELLED | 按既有取消/退款口径 |

### 5.1.1 重生成受理事务（r3#4：重新取得在途资格的边界）

从 `NEEDS_REVIEW_SETTLED` 发起重生成（`POST .../replica-pipelines/{id}/regenerate`，携带新报价 token + 指纹）：

```
BEGIN;
  非锁定读项目标识;
  SELECT ... FOR UPDATE projects 行;          -- 全局锁序第一位（r8#2）
  SELECT ... FOR UPDATE pipeline 行;           -- 持锁重验关联与状态
  校验 status=NEEDS_REVIEW_SETTLED 且无提交未知;
  validate_quote（新报价、名额范围、金额上限）;
  迁入 GENERATING —— 此写触发 uq_replica_pipeline_active_* 唯一索引：
    若用户/项目已另发新任务占用资格 → 唯一冲突回滚，409 拒绝（预占未发生）;
  钱包敞口复查（§6 上限）;
  原子停止被替代名额旧任务的恢复资格（r8#3，见下）;
  创建替代批次（任务挂接原名额 superseded_by）+ 资金预占;
COMMIT;
```

资格冲突在预占前被唯一索引拒绝，无副作用。重生成与首次确认共用同一套 fencing 事务形态（§4.2）。

**重生成范围含「有效结果不可交付」的名额（r7#3）**：此类名额（如 `ARCHIVE_FAILED`）现有单任务口径 `require_task_paid_regeneration_state` 会拒绝受理——自动链路**不调该函数**，改走替代批次挂接（新任务挂 `superseded_by_task_id` 到原名额），授权校验走本节事务（报价覆盖指定名额清单）。这些名额不占 §4.2 首次授权的「未覆盖名额」范围；首次授权仅约束原批次，重生成永远独立授权。

**替代受理必须原子停止旧任务的恢复资格并闭合其状态（r8#3 + r9#2）**：现有公平队列与 FIFO 归档重试的领取条件均未排除已替代任务——若只挂接 `superseded_by_task_id`，旧任务仍会被恢复队列反复领取（置 `SUBMITTING`、完成写入又被 superseded 校验拒绝、租约恢复后再领取），循环占用队列并破坏 SETTLED「全部子任务终态」前提。因此替代受理事务内**持锁（子任务行锁）重验旧任务状态后原子处理**：
- 旧任务处于**终态**（含 `SUCCEEDED/ARCHIVE_FAILED`）→ 标记替代关系即可，终态不再被领取；
- 旧任务**正被免费恢复领取中**（非终态、有活跃租约）→ **拒绝本次替代**（409/可重试错误，提示稍后重试——恢复完成后再替代终态版本），绝不把在途任务强行改写；
- 旧任务**非终态但无活跃租约**（失租遗留的 `SUBMITTING` 等）→ **原子归一为历史终态**（保留既有结算事实，stage_detail 标记 superseded_archive），不再参与领取；
- 此后**领取谓词、过期恢复、迟到完成写入三处统一校验替代链**（带有效 `superseded_by_task_id` 的任务不再被领取；迟到结果仅留档不改变替代链不参与结算）。
§9 测试必须断言：替代成功后整条 pipeline 能**实际到达 DELIVERED**（旧任务无残留非终态）；「免费恢复与付费替代交错」中旧任务不再被领取、迟到结果不改变替代链、计费不重复收口。

- **单在途约束的语义**：谓词 = 后台付费敞口未收口（§3.1）。DELIVERED / DELIVERED_PARTIAL / FAILED / CANCELLED / EXPIRED / NEEDS_REVIEW_SETTLED 均释放；NEEDS_REVIEW 继续占用。

### 5.2 阶段失败（确认点之前）

FAILED(stage, stage_detail)，产物保留；每阶段自动重试计入有界预算（§3.3）。**若仍有运行中子任务/未收口预占，先迁 DRAINING（占用在途约束、撤销推进权），全部收口后落 FAILED 释放**（r4#2）。任务中心失败卡提供〔重试（新尝试、重报价）〕〔转手动编辑〕。

### 5.3 接管协议（r1#11：不做「天然接管」假设）

- **复用判断**：重试/重发起时不按「存在产物即跳过」——按 `project_fingerprint`（来源资产 + 策略配置 + 上游版本链）比对，指纹一致才复用，不一致重建该阶段；
- **统一撤销事务（r5#2）**：接管、项目删除、期限判定的撤销共用**同一个事务形态**（共享父行锁，见恢复锁序）：持锁重读父状态 → 置 `stage_detail.reason`（manual_takeover / project_deleted / deadline_exceeded）→ **未收口一律落 DRAINING**（已收口直接落对应终态）；若行处于挂起（DRAINING+suspended 并存），**同事务内清除挂起屏障**（挂起语义只属于可恢复场景，撤销即不可恢复）、既有 `suspended_pending` 产物**降级为历史产物**、此后观察轮询允许无付费地驱动 DRAINING 收口（正常领取谓词不再被挂起排除——清了 `suspended_at`）、**禁止任何恢复发布**。项目删除路径不再直接写 CANCELLED，改调本事务（r5#2）；
- **接管 = 原子撤销自动推进权**：用户进入复刻页手动编辑该项目时走统一撤销事务（reason=manual_takeover），此后自动链路对该项目的任何推进写入被状态机拒绝；
- **取消边界**：取消父 pipeline 不停止已提交的付费子任务——排队中的按各域取消语义取消并释放预占；运行中/已结算的跑完，产物照常落库；
- **迟到结果隔离（r2#4 + r3#5：区分暂时挂起与永久撤销）**：仅查 pipeline 状态不够——拆解完成会在自己的发布事务里继续发布新 analysis + shot card（`analysis_routes.py:1094`），而项目按版本号取最新、人工脚本据版本链判过期，迟到的自动产物会顶掉人工成果。因此**自动链路驱动的子任务，其发布/完成事务内必须校验推进权**，并按 pipeline 处于哪种「离开可推进状态」分流：
  - **终态 / 被接管**（永久撤销推进权）：产物仍落库但标记为**历史产物**（不进入当前版本链、不参与「取最新」选择），下游阶段不触发；
  - **挂起**（暂时，可恢复）：产物落库并标记 `suspended_pending`（同样不入当前版本链），**但保留操作键到产物的映射**；
- **挂起产物恢复协议（r3#5 + r4#4 屏障 + r5#6 锁序）**：总开关重开后，以**可重入的受保护恢复事务**执行：按操作键找回全部 `suspended_pending` 产物 → 校验归属、版本指纹与推进权 → **幂等发布进当前版本链**（等同该子任务此刻完成）→ 累计挂起时长（`suspended_seconds_total`）→ 清除 `suspended_at` → 重设 `next_poll_at`，**同一事务完成后才开放普通领取**。恢复期间普通领取被 `suspended_at IS NOT NULL` 谓词排除；恢复事务崩溃可直接重入（幂等：已发布产物按操作键识别跳过）。不依赖「同操作键重新入队」，引用找回即可，避免重复付费。
- **共享父行锁与固定锁序（r5#6）**：**子任务完成发布、恢复事务、统一撤销事务、过期裁决四类事务共享 pipeline 父行锁，固定锁序=先父行后子任务**，锁内重读父状态决定发布语义（在途→正常发布；挂起→`suspended_pending`；撤销→历史产物）。堵死「子任务读到父挂起 → 恢复事务查不到其产物、清挂起提交 → 子任务随后才提交 `suspended_pending` 而错过恢复」的竞争——该子任务的提交必须在拿到父行锁后重读状态再定语义，恢复已清挂起则按在途正常发布。恢复事务内**复核确认期限（72h 恒定计时，已过期则转 EXPIRED 而非发布）与挂起代次**（每次挂起/恢复经同一行锁线性化并递增代次，恢复只处理本代次的挂起产物，防止「恢复后再次关闭」窗口的陈旧发布）；
- **验收**：补「挂起期间子任务完成 → 重开恢复 → 产物纳回版本链 → 断点续跑」用例（§9）。
- **确认前完整性校验**：confirm 事务内再校验 prompt/首帧/文案版本链仍属本 pipeline（指纹比对，§4.1），防手动编辑交错后授权错链。

## 6. 权限、并发与敞口（r1#13 重写）

- **每用户单在途**：数据库级部分唯一索引（§3.1），应用层校验仅作友好提示。
- **母子账号/共享钱包**：钱包费用以**钱包维度**设敞口上限（单自动任务费用上限 = 配置项；活跃钱包同时在途自动任务数上限 = 配置项），不只按用户数；子账号功能权限复用现有子账号权限体系，发起/确认/取消/重试各接口逐一校验 owner/project/产物归属。
- **权限撤销**：会话失效或权限变更后，后台编排使用发起时授予的**受限持久授权**（只含本 pipeline 推进所需动作），撤销后禁止新增付费动作；AWAIT_CONFIRM 确认动作要求确认者仍是 owner 本人（活会话）。
- **审计员**拒绝发起（`require_not_auditor`）；review 演示模式不渲染入口。
- **项目删除保护（r2#5）**：现有删除保护只覆盖生成与拆解的部分在途状态（`rbac_routes.py:731`），未覆盖首帧任务与提交未知；且首帧任务随项目级联删除（`046_async_image_tasks.py:63`）会连带销毁结算依据。删除判定扩展为：该项目存在**在途 pipeline、未结算预占、或提交未知子任务**时禁止物理删除（仅允许标记删除），直至全部子任务收口、预占结算或释放；pipeline 行按 §3.1 策略保留审计与授权证据。
- **总开关**：新增独立控制项（§8），语义：关闭 = 一切付费动作不发生——拒绝新发起、后台推进挂起（`suspended_at`，期限适用范围见 §3.2.3）、AWAIT_CONFIRM 的确认接口同样拒绝；重开时执行挂起产物恢复协议（§5.3）后从断点续跑，不中途废弃已扣费工作。
- **提交许可与线性化 fencing（r4#3 + r5#3/#4 + r6#1）**：挂起父编排不足以阻止已入队子任务被独立 worker 领取并调用供应商（如首帧任务在 `generation_worker.py:771/830` 独立领取执行）。r6 指出「签发许可+事后代次复核」仍留有检查-发送窗口（供应商无消费代次的协议）——因此把**新增付费提交的线性化点定义为「发送意图落库」**：

  **worker 付费提交协议（每次首次/重试提交点）**：
  ```
  持父行锁（§5.3 统一锁序，父→子）：
    校验提交许可谓词（见下）；
    在 pipeline 行原子「签发+消费」许可：写入发送意图记录
    （sub_task_id、许可代次、提交点标识）并回填子任务对应域字段；
  COMMIT；
  之后才发起供应商调用——意图已落库的调用按「在途」处理。
  ```

  **提交许可谓词**（持锁内校验）：①父状态 ∈ **允许子任务提交的状态集** = 推进态（ENQUEUED…GENERATING）∪ `NEEDS_REVIEW`（无 uncertain——既有授权内剩余排队任务必须继续提交才能收口，r6#3）；DRAINING 不在集合内：其剩余排队任务走**主动取消退队并释放预占**，再观察收口；②非挂起、非 uncertain、总开关开启（r5#3 三种止付条件）；③归属与授权 fencing 有效。

  **关闭/撤销/挂起/uncertain 的语义**：这些事件持同一父行锁发生——在此之前意图已落库的调用视为**已受理**（继续允许查询/归档/结算/对账，不制造孤儿调用）；之后未落意图的调用永远拿不到许可（新增付费被挡）。不再承诺「已签发未发送即时失效」这种供应商协议不支持的语义。

  **逐域三态证据与恢复动作（r6#2）**（现有域的 `SUBMITTING`/`RUNNING`/`submitted_at` 均不等于供应商已受理，不能直接当受理证据）：

  | 证据状态 | 判定 | 恢复动作 |
  | --- | --- | --- |
  | 无发送意图记录 | **确定未发送** | 可退队：回 PENDING、释放租约、不计费、不耗重试预算 |
  | 发送意图已落库、无供应商回执 | **可能已发送** | 不退队不重发；**按各域既有对账器的「无回执」语义出口**（见下表） |
  | 供应商回执在案 | **已受理** | 正常结算与后续流转 |

  **「可能已发送」的逐域出口映射（r7#1）**——三态表不替代各域对账器，而是对齐它们的既有语义，`intent-only`（意图在、供应商任务不存在）在各域的确定性出口如下；无回执在任何域都**不得**当作确定未发送证据：

  | 域 | 对账器对「无回执/无供应商任务 ID」的既有语义 | 自动链路对该出口的承接 |
  | --- | --- | --- |
  | 首帧（`image_tasks.py` `first_frame_reconcile_decision`） | 判 FAIL 并释放预占 | 承接：按失败出口走重试预算/FAILED；预占释放由对账器完成，编排器不重复释放 |
  | 视频生成（`generation.py` `reconcile_generation_task`） | 无供应商任务 ID → 要求**人工核实** | 承接：置 `uncertain=true` 冻结新付费提交（§3.2.2），在途资格保持占用直至人工核实出结果——intent-only 的**人工核实出口**；核实结果经统一行锁写回，状态机继续 |
  | 拆解（`analysis` 域） | 失败路径置 FAILED 并释放预占 | 承接：FAILED(DRAINING 收口) 或按重试预算重入队 |

  各域的**真实事务边界**（领取/意图落库/回执落库/失租恢复/对账各自所在的 `pg_transaction`）在实施时逐域盘点成表并纳入代码注释；编排器不自行判定「可能已发送」的结算结果，只消费各域对账器的确定性结论。

  三态判定绑定许可代次与子任务 attempt；**全局锁序（r6#2 + r7#2）**覆盖所有涉及多行类型的事务：

  ```
  projects（项目行锁，最前）→ replica_pipeline_tasks（父行）
    → assets → 各任务表行（analysis_tasks / first_frame_tasks / generation_tasks）
    → 计费行（billing_operations / 钱包）
  ```

  - 一切涉及父+子的事务按「父 → 子」固定顺序获取（领取事务同样先父后子，消除与撤销事务的反向等待死锁，r6#2）；
  - **间接入队路径纳入改造清单（r7#2）**：`media.py:persist_upload_completion` 现有顺序是先 `FOR UPDATE assets` 再调用拆解入队——若入队函数内部取项目锁会形成「资产→项目」与「项目→资产」（FK 检查）的环路。改造为：该路径的项目锁**前移到资产锁之前**（函数入口先锁 projects 行），全局顺序不被破坏；实施时逐个盘点所有会触发自动链路子任务入队的入口（上传完成、恢复、重试），同一规则处理；
  - **真库并发测试必须覆盖「上传完成（资产→…→入队）与直接入队交错」**，不能只测两个入队请求（§9）；
  - 手动链路任务无归属标记，零影响（项目行锁对手动入口同样生效但语义不变——只多了一把先取的锁）。
- **归属去重与跨归属互斥（r5#5 + r6#5）**：现有任务域按项目去重复用在途任务（首帧 `image_tasks.py:400-410` 按 `project_id+request_hash`、拆解 `analysis.py:1322-1343` 按同项目素材）——仅新建时附 metadata 仍可能复用无标记的手动任务绕过 fencing，且「先查后建」在自动与手动并发入队时互不可见。因此：①**互斥边界 = 项目行锁**：自动与手动入队入口统一改为**先锁 `projects` 行（FOR UPDATE）再检查+插入**——项目行锁对无归属标记的手动入口同样生效，消除并发窗口（真库并发测试覆盖同时入队，§9）；②自动链路入队去重键纳入 pipeline 归属（request_hash 混入 pipeline_id）保证命中自己；锁内跨归属检查使用**不含归属的素材指纹**（project_id+素材来源，与现有唯一约束列解耦），命中其他归属在途任务 → 拒绝入队并 `FAILED(stage_detail.conflict=task_belonging)`，提示稍后重试或转手动，绝不跨归属复用、也绝不给手动任务反向补标记；③「确定未发送」的退队按上方三态证据表执行；「可能已发送」不退队等对账。

## 9. 测试与验收口径（r1#14 扩充）

**状态机与故障语义**：每阶段 成功推进 / 子任务失败 / 入队后未回填即崩溃（操作键找回）/ 租约失而迟到提交被拒（attempt 校验）/ 无进展超限 FAILED / 执行超时 FAILED / 重试预算耗尽 FAILED / **业务重试序号：同键重放含失败终态的旧任务（`image_tasks.py:354` 语义），确定性失败后递增序号新键重入队，崩溃恢复复用同序号（r2#3）** / **挂起期间期限计时排除挂起时长，重开断点恢复（r2#7）**。

**发起预检**：人物缺失/无权限/参考图不可用 → 收费拆解前拒绝（`MAIN_CHARACTER_NOT_FOUND` 路径，r2#2）；人物版本冻结进 pipeline 后与编译产物指纹一致。
