## 1. 目标

本版要实现的是“一个用户只能有一个激活码、一个激活码最多绑定两台设备、两台设备同一时刻只能一台在线”的客户版方案，同时保持激活码与充值金额直接绑定，不引入套餐体系。

核心目标只有三条：

1. 激活码可以批量生成、发放、激活、绑定用户和设备。
2. 客户登录、第二设备配对、显式切换、heartbeat、被踢下线，全部围绕“单在线会话”运行。
3. 多用户公平排队、多实例部署、高可用与扩容，建立在 PostgreSQL 真源之上，而不是进程内状态。

## 2. 当前实现与目标差距

| 能力 | 当前实现 | 目标状态 |
| --- | --- | --- |
| 客户激活码 | 只有内部充值和钱包，没有客户激活码域 | 新增批次、生成、发放、首次激活、作废、审计 |
| 设备绑定 | 只有内部身份或桌面身份，没有客户设备域 | 1 个激活码最多 2 台当前有效设备 |
| 在线会话 | 没有客户 session lease 和 fencing | 同一时刻只允许 1 台设备在线 |
| 登录冲突 | 当前没有第二设备冲突语义 | 第二设备普通登录返回冲突，可显式切换 |
| 公平队列 | 目前是全局 FIFO 领取 | 按 `user_id` 公平轮转，默认每用户并发 1 |
| 数据库 | 当前是 SQLite WAL 单机 | 生产以 PostgreSQL 为真源 |
| 部署 | 当前是单 API、单 Worker | 多 API、多 Worker、LB、PG HA、私有 COS |

当前可复用的基础主要是钱包、账本、ZPay 充值、已有任务域和部分管理端骨架；客户激活码、设备、会话、公平队列和管理页需要新增或重构。

## 3. 业务规则

### 3.1 激活码

- 一个用户只能有一个主激活码。
- 一个主激活码只能归属一个用户。
- 激活码直接绑定充值金额，不设置套餐。
- 首次激活只入账一次。
- 后续充值走同一个钱包，不允许第二个激活码再次开户或再次入账。

### 3.2 设备

- 一个激活码最多绑定两台当前有效设备。
- 历史绑定记录保留，解绑后只释放当前占用，不删除审计。
- 两台设备同一时刻只能有一台在线。
- 设备凭据和在线 session 需要分层，不能把激活码当作长期 API 凭据。

### 3.3 会话

- 普通登录不允许静默踢掉另一台设备。
- 若另一台设备在线，返回冲突，由用户显式确认切换。
- 显式切换必须是原子操作：先让旧会话失效，再建立新会话。
- heartbeat 负责续租；旧 session 的迟到请求不得复活。

### 3.4 公平队列

- 队列公平单元是 `user_id`，不是设备。
- 默认每用户同时运行 1 个任务。
- 设备切换不改变任务归属，不取消排队中的任务。

### 3.5 多实例与高可用

- 会话、钱包、设备、激活码、队列都必须以 PostgreSQL 为真源。
- API 可以无状态扩容，Worker 通过数据库锁和租约领取任务。
- 所有关键写入都需要幂等键和事务内 fencing。

### 4.2 客户端状态机

```text
未激活
  -> 首次激活成功
激活完成
  -> 绑定设备 1
  -> 设备 1 在线
  -> 设备 2 配对
  -> 设备 2 绑定完成
  -> 普通登录冲突
  -> 显式切换
  -> 设备 1 失效 / 设备 2 在线
  -> heartbeat 续租
  -> logout / timeout / 管理员下线
```

被切换下线时，前端必须把它视为“会话失效”，不能误报为余额不足、网络错误或服务异常。

### 6.3 幂等与冲突

- 首次激活、设备配对、登录、切换、退出都要带幂等键。
- 同一个幂等键 + 同一个请求体必须返回同一结果。
- 同一个幂等键 + 不同请求体必须拒绝。
- 登录冲突要返回可解释的业务码，而不是模糊 500。

## 7. 安全边界

- 激活码不落明文日志、不落前端本地存储、不进 CSV 明文导出。
- 设备凭据使用独立摘要，不复用激活码。
- session token 和 cookie 需要和设备绑定，不能被跨设备复用。
- 管理端所有高风险操作需要真实 actor、原因、幂等键和审计记录。
- 客户端和管理端都要防止把“旧 session 失效”误解释成通用故障。

## 11. 实现级数据库合同

### 11.1 迁移原则

1. 客户生产只运行 PostgreSQL；SQLite 只作为旧 P0 数据导入来源，不做客户生产或多实例测试真源。
2. 本轮扫描到 33 个 `server/app` 运行模块直接依赖 `sqlite3`，迁移必须覆盖连接类型、参数占位符、事务开启、时间函数、行对象和异常类型，不能只修改 `server/app/db.py`；最终数量以 T04/DB-02 行级清单为准。
3. 不双写 SQLite 与 PostgreSQL。切换时进入维护窗，停止写入，导出、导入、对账，随后只开放 PostgreSQL。
4. 历史 Alembic 迁移不直接删除；用后续迁移修正 PostgreSQL 索引和约束，并验证空库 `upgrade head`。
5. 大表收紧约束遵循“先加可空字段 -> 回填 -> 校验 -> 再设非空/唯一”的顺序。

### 11.3 必须由数据库证明的不变量

- `activation_code_activations.code_id UNIQUE` 与 `user_id UNIQUE`；
- 激活首充订单和 CHARGE 均唯一；
- 当前设备槽部分唯一索引：`(activation_code_id, slot_no) WHERE status='BOUND' AND revoked_at IS NULL`；
- 当前设备指纹部分唯一索引，解绑历史行不占槽；
- `customer_session_state.user_id` 为主键且 `activation_code_id` 唯一；
- session epoch 只能递增；
- 管理写幂等键按 actor、canonical route 和 key digest 唯一；
- 任何已确认账务流水不得通过普通业务代码更新或删除。

## 12. 关键事务流程

### 12.1 首次激活

```text
BEGIN
  锁定 customer_idempotency_envelope(operation=activate, key)
  同键不同请求 -> 409 IDEMPOTENCY_CONFLICT
  已有成功信封 -> 解密并返回原 user/device/session

  HMAC 激活码并 SELECT ... FOR UPDATE 锁 code
  校验 ISSUED、未过期、未暂停/作废
  创建服务端随机 username 的 customer user
  创建 wallet
  写 activation_code_activations
  创建 slot 1 device 和独立设备凭据摘要
  创建 provider=activation_code、status=PAID 的充值单
  写唯一 CHARGE 并增加 wallet.available_credits
  把 code 改为 ACTIVE 并绑定 user
  创建 session state，epoch=1，lease=数据库当前时间+90秒
  写资金、安全、session、操作审计
  AEAD 加密设备/session 一次性响应并写幂等信封
COMMIT
```

任何一步失败必须整体回滚。用户名冲突只允许重新生成用户名，不能重跑另一笔独立激活事实。

### 12.2 第二设备绑定

1. 第二设备提交主激活码、候选设备摘要和幂等键；服务端不再次充值。
2. 创建绑定候选设备摘要的一次性配对请求。
3. 第一台当前绑定设备批准；第一设备不可用时由真实管理员核验发放记录后批准。
4. 消费配对请求时锁定 code、当前设备行和配对行，选择空闲 slot 1/2。
5. 两槽已满返回 `DEVICE_SLOTS_FULL`；并发争夺 slot 2 只能有一个事务成功。
6. 设备凭据只返回一次，并由幂等响应信封支持提交后响应恢复。

### 12.3 登录、冲突与切换

```text
锁 customer_session_state(user_id)
无会话或租约已过期 -> 建立当前设备会话
同设备 + 当前有效 session token -> 只续租，不换 token/epoch
同设备丢 session token但设备凭据有效 -> epoch+1，签发新 token
其他设备在线 + 普通 login -> 409 OTHER_DEVICE_ONLINE
其他设备在线 + 显式 switch -> epoch+1，记录旧会话被切换，签发新会话
```

切换事务提交后，旧 token 在所有 API 节点失效。旧设备迟到的 heartbeat/logout 不得修改新会话。

### 12.4 写请求 fencing

认证中间件只负责初步验证。创建项目、上传、创建生成任务、充值、解绑等写操作必须在业务事务内重新比较 `user_id + device_id + session_id + session_epoch + lease`。任何字段已变化都回滚并返回 `SESSION_REPLACED` 或 `SESSION_EXPIRED`。

## 13. API 请求、响应和错误合同

### 13.1 通用请求头

- 会产生状态变化的客户请求：`Idempotency-Key`、`X-Request-Id`；
- 桌面客户：`Authorization: Bearer <session-token>`，原始 token 只存系统安全存储；
- 同源 Web：`HttpOnly + Secure + SameSite` cookie，写请求同时校验 CSRF；
- 管理端：独立 admin session cookie、CSRF、真实 actor；不得复用客户 session。

### 13.2 稳定业务错误

| HTTP | code | 客户端行为 |
| --- | --- | --- |
| 400 | `ACTIVATION_UNAVAILABLE` | 统一提示码不可用，不暴露不存在/过期/作废细节 |
| 409 | `USER_ALREADY_ACTIVATED` | 已有账户不能兑换第二主码 |
| 409 | `IDEMPOTENCY_CONFLICT` | 停止自动重试并上报 request id |
| 409 | `PAIRING_APPROVAL_REQUIRED` | 进入等待第一设备批准页 |
| 409 | `DEVICE_SLOTS_FULL` | 引导先解绑或联系客服 |
| 409 | `OTHER_DEVICE_ONLINE` | 展示脱敏设备名和租约剩余时间，允许显式切换 |
| 401 | `SESSION_EXPIRED` | 清理 session token，保留设备凭据，回登录页 |
| 401 | `SESSION_REPLACED` | 显示已切换至另一设备 |
| 401 | `DEVICE_REVOKED` | 清理全部本设备凭据，进入恢复流程 |
| 429 | `RATE_LIMITED` | 按 `Retry-After` 等待，不循环提交 |

API 模型进入 FastAPI OpenAPI 后，必须重新生成 `client/src/generated/api.ts`，禁止前后端分别维护冲突类型。

## 14. 客户端凭据与 Tauri 改造

当前 `client/src-tauri/src/lib.rs:15-95` 会探测并自动拉起本机 FastAPI。客户云端构建必须将该行为移除或限制在明确的本地开发 feature 中，不能让正式客户包偷偷启动本地业务真源。

需要新增 Tauri 安全桥接：

- 生成并读取稳定的 `device_instance_id`；
- 保存、读取、删除设备凭据和 session token；
- macOS 使用 Keychain，Windows 使用 DPAPI/系统凭据存储；
- JS 侧只接收完成请求所需的短生命周期值，不写 LocalStorage/sessionStorage；
- 安全存储实现方式先做依赖与威胁模型评审，避免未经审查引入插件。

浏览器客户入口只使用同源 HttpOnly cookie。桌面与浏览器的 credential adapter 必须隔离，不能在 `api.ts` 中用一个全局明文变量模拟持久会话。

## 15. 管理端真实操作人方案

首版复用 `users` 的 `admin/auditor` 角色，但新增独立 `admin_sessions`。每个操作员使用自己的短期、一次性交换凭证换取 HttpOnly admin cookie；交换凭证只存摘要并在成功后作废。管理写操作还需要 CSRF、reason、Idempotency-Key 和 request id。

当前 `CONTROL_ADMIN_USER_ID` 只能保留为内部 P0 兼容路径，客户生产启动时必须拒绝用它代表所有操作员。未来如接企业 SSO，只替换 admin session 的签发入口，不改变审计 actor 合同。

## 16. 公平队列实现合同

领取事务必须同时完成：释放可恢复租约、检查全局 Provider 槽位、选择最久未调度且有积压的用户、检查该用户运行数、锁定该用户最早任务、写任务租约、更新 `last_dispatched_at`。候选用户和任务都使用 `FOR UPDATE SKIP LOCKED`。

公平性验收不是“全局 FIFO 更快”，而是：A 排队 1000、B 100、C 10 时，只要三者都符合运行条件，每轮都能获得机会；默认每用户 `running <= 1`。设备切换不修改队列 owner、创建时间或已取得的 Worker 租约。

## 17. 配置与启动阻断

客户生产至少配置：PostgreSQL DSN、公开 origin、可信代理/CORS/Host、code/device/session HMAC 版本化密钥、幂等 AEAD 密钥、30/90 秒租约、私有 COS、ZPay、Provider、admin session 和审计保留期。

出现下列任一项必须拒绝启动：SQLite、生产本地持久资产、开发身份头、缺失关键密钥、非 HTTPS cookie、单一控制管理员映射、未配置可信代理边界。

## 18. 可观测性

必须记录脱敏结构化字段：request id、actor/user、device/session id、epoch、task/order/code mask、operation、result code、latency。禁止记录主激活码、设备 token、session token、ZPay key 和幂等响应明文。

核心指标和告警：

- 激活成功、失败、唯一约束冲突、重复恢复；
- 设备槽占用、配对等待、第三设备拒绝；
- 当前在线、409 冲突、显式切换、旧 epoch 阻断、heartbeat 延迟；
- 每用户队列长度/最大等待/运行数、Provider 槽位、Worker 租约恢复；
- PAID 无 CHARGE、CHARGE 无来源、钱包重算不一致；
- PostgreSQL 连接池、锁等待、慢查询、复制延迟、备份/PITR 状态。

重复入账、双在线、旧设备写入成功、跨用户访问和账本不一致均为 P1 级发布阻断。

## 19. 非目标

- 本期不做套餐、组织共享钱包、一个用户多个主激活码；
- 不用 Redis、Celery、Kubernetes 作为首发前置；
- 不承诺设备指纹能证明物理硬件或自然人唯一；
- 不自动执行真实付费、真实 Provider 提交或生产发布；
- 不在客户功能尚未完成时删除内部 P0 的可回滚发布版本。
