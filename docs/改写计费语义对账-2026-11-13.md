# 改写计费语义对账（M6，2026-11-13）

> 结论：`ConfirmedRewriteResponseError`（供应商已确认受理并返回响应，但响应不可交付）
> 场景下，**客户全额退费，供应商成本仅记在 attempt 层**——本文件把该口径与
> `server/app/script_rewrite.py` 的实现逐点对齐，作为对账与客诉处理的引用依据。

## 一、场景定义

改写链路（`POST /script-rewrite` → `script_rewrite_tasks` → DeepSeek）里，以下
三种「响应已到达但不可交付」的失败都抛 `ConfirmedRewriteResponseError`：

| error_code | 触发 | 客户侧文案 |
| --- | --- | --- |
| `DEEPSEEK_RESPONSE_INVALID` | 响应体解析失败 / 结构缺失 | AI 改写服务返回内容异常，请重试。 |
| `DEEPSEEK_RESPONSE_TRUNCATED` | `finish_reason=length`（输出被截断） | 改写结果超过输出上限，尚未生成完整文案，请缩短原文后重试。 |
| `DEEPSEEK_RESPONSE_EMPTY` | 正文为空 | AI 改写结果为空，请重试。 |

区别于「提交即失败」族（`DEEPSEEK_NETWORK_FAILED` / `_REQUEST_FAILED` 等）：
后者供应商未受理，同样全额退费且**没有** attempt 层成本。

## 二、资金动线（fail_script_rewrite_task）

```
确认受理的响应不可交付（ConfirmedRewriteResponseError）
  ├─ complete_source_attempt(usage=1)      # attempt 层：记供应商成本 1 单位
  └─ finish_source(units=0, succeeded=False)  # 客户结算 0 单位 → 预留全额释放
```

- **客户**：不承担任何费用（账单 0 单位；钱包预留全额返还）。
- **供应商成本**：只出现在 attempt 层（`billing_attempts`，经
  `usage_billing.complete_source_attempt(usage=1)`）与 `external_calls` 流水，
  用于成本核算，**不进入客户账单**。
- **幂等/重试**：任务落 FAILED（`DEEPSEEK_*` 码），客户重新发起是一次新受理、
  新预留；重放同幂等键按既有受理语义处理。

## 三、对账要点

1. 客户账单侧找不到这三类失败的扣费记录是**预期行为**，不是漏单；
   核对成本时到 attempt 层 / external_calls 查。
2. 客诉「改写失败还扣费」的排查顺序：先查 `wallet_transactions`（应无扣费），
   再查任务行 `error_code` 是否属于上表三码。
3. 若未来把「确认受理但不可交付」改为部分计费，必须同步修改本文件、
   `ConfirmedRewriteResponseError` 注释与 `fail_script_rewrite_task` 的结算参数，
   三处一致（M6 的教训就是注释先于实现漂移）。
