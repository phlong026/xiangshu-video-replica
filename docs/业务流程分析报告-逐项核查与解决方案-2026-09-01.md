## 2. §3.2 风险 R1–R9 —— 逐条核查

### ⚠️ R1 —— **现象为真，但初稿把「道次」写反了（本条经二轮修订）**

> **修订说明**：本核查初版判定「R1 不成立、建议删除」。该判定**错误**——它只核到 `media.py` 函数体内层，未上溯路由层的 `with db.write()`。经原报告作者提出异议后重核，结论改为下述分道表述。**按初版执行会误删一个真实的客户道可用性问题。**

报告原文：*「`complete_upload` 把最大 50MB 视频整体读进内存再算 sha256/ffprobe，**且发生在 `with conn:` 事务内部**……SQLite 道长事务持写锁跨外部 I/O」*

实测 `server/app/media.py`：

```python
353:    content = storage.get_object(storage_key)          # ← COS 全量读
354:    metadata = probe_video(probe, content, ...)        # ← ffprobe
355:    validate_duration(metadata.duration_seconds)
356:    content_sha256 = hashlib.sha256(content).hexdigest()
357:
358:    analysis_task: sqlite3.Row | None = None
359:    with conn:                                         # ← 事务从这里才开始
360:        conn.execute("UPDATE assets SET ...")
```

在**函数体这一层**，三段重 I/O 确实都在内层 `with conn:` 之前。但**函数体不是事务边界的全部真相**——必须上溯路由层：

```
media_routes.py:461   with db.write() as (conn, actor):        # ← 包住整个 complete_upload
                          completed = complete_upload(conn, ...)
customer_fence.py:341 BusinessDb.write()  →  客户道走 fenced_pg_transaction
customer_fence.py:183     with pg_transaction(...) as conn:    # ← 事务先开
                              ctx = verify_session_context(...)  # ← 会话行 FOR UPDATE
                              yield conn, ctx                    # ← 之后才执行路由体
customer_auth.py:121      "... WHERE token_digest = ANY(%s) LIMIT 1 FOR UPDATE"
db_portable.py:403    __exit__ 只对 SQLiteBackend 生效；transaction() docstring 明写
                      "PG: no-op — the outer fenced_pg_transaction owns the transaction"
db_pg.py:43           DEFAULT_POOL_MAX = 8
```

**分道结论：**

| 道次 | 事务状态 | 判定 | 严重度 |
|---|---|---|---|
| 内部 SQLite 道 | `db.write()` 只开连接不开事务；353 行前的前置调用全是 SELECT，sqlite3 deferred 事务尚未隐式开启；唯一事务是 `media.py:359` 的 `with conn:`，在 I/O **之后** | 初稿归因的「**SQLite 道**长事务持写锁」**不成立** | **P3**：仅剩 `get_object` 全量 `bytes` + `probe_video` 二次引用 ≈ 2×文件大小的内存峰值 |
| 客户 PG 道 | 围栏事务**已打开**、会话行 `FOR UPDATE` **已持有**，路由体（含 50MB `get_object` + ffprobe）全程在事务内；内层 `with conn:` 是 no-op，不构成第二个事务边界 | 初稿的指控**成立，且后果比初稿描述的更重** | **P2（可用性）**：① 持该客户 `customer_session_state` 行锁 → 同一用户的心跳续租与其他写请求串行排队在其后（90s 租约 / 30s 心跳，慢 COS 读 + ffprobe 有逼近租约到期的现实风险）；② 占用连接池 1 个连接，**池上限仅 8**，并发上传完成直接吃掉连接预算 |

**整改方向随之改变**：不是「纯流式改造」，而是**先把 I/O 挪出围栏事务（P2a），流式作为容量优化跟上（P2b）**。详见 §5.4。

**根因是结构性的，不止 R1 一处**：`db_portable` 门面在 PG 道把内层 `with conn:` / `transaction()` 变成 no-op，导致**读单个业务函数无法判断它是否处在事务内**——事务边界的真相只存在于路由层的 `with db.write()`。本核查初版的误判正是被这一结构骗过。建议在 S3 拆分时补统一约定：执行外部 I/O（COS / provider / ffmpeg）的业务函数必须在 docstring 声明「假定调用时不在事务内」，并在客户道测试中加一条「围栏事务内不得发生外部 I/O」的断言（可用 `psycopg` 连接的 `info.transaction_status` 在 I/O 前探测）。

### 5.4 第三波修订版（P 波）

**P1 worker 空闲退避** —— 采纳，且因 N3（每轮 6 条全表 UPDATE 而非 3 条）**收益高于报告估计**。建议拆两步，第一步就能吃到大部分收益：

1. 把 `mark_expired_active_leases_needing_attention` 从两个 acquire 入口里提出来，改由 worker 主循环**每轮调用一次**（立刻减半开销），或每 N 轮一次
2. 再做 `idle_seconds` 自适应退避 1s→5s

同意报告「不引入 LISTEN/NOTIFY」的判断——理由（SQLite 道行为分叉、与 S2 冲突）成立。

**P2 `complete_upload` 分道整改** —— 🔴 **C1(v2) 后拆为两项，顺序不可颠倒**：

- **P2a（P2，可用性，优先做）· 把重 I/O 挪出客户围栏事务**。当前 `media_routes.py:461` 的 `with db.write()` 覆盖整个 `complete_upload`，使 `get_object` + ffprobe 在客户 PG 道跑在围栏事务内、持会话行 `FOR UPDATE`、占 8 连接池中的 1 个。改法是把 `complete_upload` 拆成 **`probe`（纯外部 I/O，不接 conn）→ `persist`（纯 DB，短事务）** 两段，路由层先探测后开事务：

  ```python
  probed = probe_completed_upload(storage=storage, probe=probe, asset_id=...)  # 事务外
  with db.write() as (conn, actor):                                            # 仅持锁做写
      completed = persist_completed_upload(conn, actor=actor, probed=probed)
  ```

  **围栏语义注意**：权限/归属校验（`require_asset_access`）必须**在事务内重做一次**，probe 段只做 `head_object`/下载/探测，不得成为授权依据。
  护栏：客户道 E2E 上传用例 + 新增一条「围栏事务内不得发生外部 I/O」断言。

- **P2b（P3，容量，跟上即可）· 流式校验**。`storage.get_object` 改分块流式读 + `hashlib.sha256` 增量更新 + spooled 临时文件喂 ffprobe，消除 2×文件大小的内存峰值，两条道同时受益。

原 P2 里的秒传补事务已提到 A5 单独做完。

**P3 `SUBMISSION_UNCERTAIN` 半自动对账** —— 采纳，且这是**运营侧收益最大的一项**。当前 reconcile 唯一入口是手工 HTTP（已核实），随规模线性增长的人工负担是真实的。实施前需用户确认；红线（不改变真实付费提交事实）由「自动 enqueue，但 SETTLE/RELEASE 仍走既有 provider 真状态规则」保证，管理端 `confirm_not_charged` 保留为最终兜底。

**P4 / P5 前端拆分** —— 采纳，但按核查结果**调整拆分粒度**：9 套请求封装（非 4 套）收敛为 1 个参数化 `request()`（差异仅 base / token / CSRF 头）；9 处错误映射（非 5 处）收敛为单一 `errorCatalog.ts`。落地 `customerApi.ts` / `internalBillingApi.ts` 实现文件时，现成的 864 行 `customerApi.test.ts` 就是它的规格说明，可以照测试反向切模块边界。
