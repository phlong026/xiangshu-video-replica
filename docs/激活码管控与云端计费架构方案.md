# 激活码管控与云端计费架构方案（V2 云化改造）

> 方案日期：2026-08-19
> 状态：V1.3 终版复核修订（V1.1 B1-B3/M1-M12 → V1.2 B4-B6/M13-M23 → V1.3 F1-F9 + 三项精简，全部合入，见 §10 修订记录）

## 1. 调研结论：现状与差距

### 1.1 现有架构全景（单机闭环）

```
┌─────────────────────────── 员工 Windows/macOS 单机 ───────────────────────────┐
│                                                                              │
│  Tauri 2 桌面壳 (lib.rs: TCP 探测 127.0.0.1:8000 → 自动拉起 sidecar)         │
│      └── React 19 前端 (api.ts: 默认 http://127.0.0.1:8000，                 │
│                          已支持 VITE_API_BASE_URL 覆盖)                      │
│                                                                              │
│  FastAPI 本地 sidecar (PyInstaller 单目录) + 本地 Worker (generation_worker)  │
│      ├── SQLite (WAL)：users/projects/assets/versions/                       │
│      │     generation_batches/generation_tasks/audit_logs…                   │
│      ├── provider_settings 表：metaso/apilio/cos/deepseek 配置               │
│      │     （Fernet 加密，主密钥存 macOS Keychain / Windows DPAPI）          │
│      └── 安全边界：API 仅限 loopback（非回环 403）、CORS 白名单、             │
│            身份由环境变量 VIDEO_REPLICA_DESKTOP_USER_ID 指定单用户            │
│                                                                              │
│  所有 Provider 调用（Metaso H3 / Apilio Gemini / DeepSeek / COS）            │
│  均从本机发起，密钥永在本机内存与磁盘中                                       │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 密钥与配置现状：为什么本地存储无法支撑计费

已核实全部 6 类 Provider 消耗点均从本地 `SettingsRepository.load_provider_config()` 读取密钥：

| 消耗点 | 代码位置 | Provider | 性质 |
| --- | --- | --- | --- |
| H3 视频生成（I2V） | `generation.py` `MetasoH3Provider` | metaso | **主计费点** |
| 视频拆解分析（分镜） | `analysis_routes.py` | apilio (Gemini) | 高频消耗 |
| 首帧生成/人物置换 | `first_frame_routes.py` | apilio (gpt-image-2) | 按次消耗 |
| 人物库图片生成 | `character_image_generation.py` | apilio (nano-banana-pro-2k) | 按次消耗 |
| 口播稿改写 | `script_rewrite.py` | deepseek | 按次消耗 |
| 视频归档/上传/下载 | `storage.py` | cos (腾讯云) | 按量消耗 |

**核心矛盾**：只要密钥下发到客户端，任何本地计费都可被绕过——客户可从内存或数据库中提取密钥直连 Provider。密钥一旦随安装包分发即失控，且无法吊销（吊销即全部客户端同时失效）。

**由此得出本方案的根基性结论：**

> **"配置集中托管"与"计费管控"是同一件事的两面。要实现按次计费，必须把所有 Provider 调用移到云端执行；密钥永不下发，客户端瘦身为纯 UI + 激活通道。**

### 1.3 生成链路全景与状态机（计费扣点依据）

任务状态机（`generation_tasks.status`，代码实证）：`PENDING → SUBMITTING → QUEUED → RUNNING → ARCHIVING → SUCCEEDED`，异常分支 `FAILED / CANCELLED / SUBMISSION_UNCERTAIN`（提交结果不确定，需对账 `reconcile`）；批次级 `NEEDS_ATTENTION`。

现有链路关键事实：

1. **前端从不直连 Provider**，全部经后端 API —— 云化是"平移"，不是重写。
2. **批次-任务两级模型**：一个批次（`generation_batches`，含 `quantity`）创建 N 个任务（`generation_tasks`），Worker 以 SQLite 租约（`locked_by/locked_until`）领取执行。**租约超时回收已实现**（代码实证）：领任务 SQL 条件为 `locked_until IS NULL OR datetime(locked_until) <= CURRENT_TIMESTAMP`，`GENERATION_LEASE_SECONDS = 600`，Worker 崩溃后任务 10 分钟内自动可被重新领取 —— 多 Worker 部署无孤儿任务风险，此项**无需改造**。
3. **幂等键已内建**：`idempotency_key` 作用域为 **`UNIQUE(created_by_user_id, project_id, idempotency_key)` 三元组**（migration 009 已从用户级收窄至项目级）+ `request_hash` —— 可直接复用为"防重复扣费"的第一道闸。注意此三元组是**业务幂等**域，与 §4.4 的**账务幂等**域（挂 `license_id`）是两套独立命名空间，不可混用。
4. **成本字段现状（勘误）**：`generation_tasks.estimated_cost` 是真实数据库列（migration 001_core 建表即有）；`actual_cost` 在全部 21 条迁移中**均不存在**，需在计费迁移中新增。更关键的是 `estimated_cost` 的**取值不可信**：其来源 `PaidRegenerationRequest.estimated_cost_snapshot` 由客户端请求体传入，服务端仅做 `total/quantity` 除法后落库 —— 因此它是展示口径快照，**不得作为计费依据**（详见 §1.4 与 B6）。任务级可用动作 `RETRY / RECONCILE / CONFIRM_NOT_CHARGED / REGENERATE`（`available_actions`）的语义边界（原地重置 / 管理员确认 / 新建任务付费）由代码 409 守卫强制（`SAFE_PRE_PROVIDER_FAILURE_CODES` / `SUBMISSION_MAY_HAVE_BEEN_CHARGED` / `REQUIRES_PAID_REGENERATION`），§4.5 计费矩阵以此为据，细节以 §4.5 为准，此处不重复展开。
5. **审计完备**：`audit_logs` 覆盖登录、设置变更、批次创建、任务操作全链路。
6. **上传走 COS 预签名直传**（`create_upload_intent`），不经过后端转发 —— 上云后仅需预签名改由云端签发、桶 CORS 增加客户端来源。
7. **全局并发限制**：`runtime_settings.max_concurrent_h3_tasks` 当前是单机全局值 —— 上云后成为全平台共享值，需要按 license 分配公平配额（见 §5.4）。
8. **项目级数据隔离已就绪**：`permissions.py::require_project_access` 已覆盖 projects / analysis / generation / versions 全部项目级路由（通过条件：`actor.role in {admin, auditor}` 或 `row["owner_user_id"] == actor.id`）。多租户改造**不需要重写**这层。但注意该实证范围**不含 assets / characters 路由**——覆盖情况未确认，已列入 §5.6 排查清单（COS 预签名签发是跨租户素材读取的最后闸门）。
9. **但共享域数据无归属维度**（云化的真正缺口）：`person_identities`（人物身份库）在单机是**刻意的全局共享设计** —— `list_person_identities` 执行 `SELECT * FROM person_identities` 无 owner 过滤，employee 仅经 `identity_available_to_employee` 做可用性过滤；`simple_character.py` 中有显式注释 `visibility intentionally matches GET /api/person-identities` 佐证。同时 `character_generation_routes.py` / `character_reference_routes.py` 的 `require_project_access` 调用数为 **0**。单机单用户时这不是问题；**多客户上线后即为跨客户肖像素材泄露**（见 B4 与 §5.6）。

| 资产 | 云化后去向 |

### 2.2 三条铁律（整个方案的security invariant）

1. **密钥永不落地**：metaso/apilio/cos/deepseek 密钥只存在于云端数据库（加密）与云端进程内存。客户端任何层面（前端/本地存储/网络抓包）都拿不到密钥。
2. **余额真源在云端**：客户端展示的余额是缓存快照，本地篡改无意义——扣费校验、冻结、结算全部发生在云端事务内。
3. **执行在云**：所有 Provider 调用由云端 Worker 发起。客户端破解与否，都绕不开云端这一道闸。

### 2.3 一次视频生成的完整数据流（目标态）

```
客户端                        云端 API                     云端 Worker                Provider

  ├──────────────────────────────────────────────►│ 验设备令牌 → 验激活有效      │

  │  ◄── 批次信息 + 最新余额快照 ──────────────────┤                            │
```

## 3. 激活码管控方案

### 3.1 实体模型

```
plans（套餐）           licenses（激活码=授权主体）      devices（设备）         wallets（钱包）
┌──────────────┐   ┌──────────────────────┐   ┌──────────────────┐   ┌──────────────┐
│ id           │◄──│ plan_id              │   │ license_id       │   │ license_id   │
│ 名称          │   │ code(激活码,唯一)     │──►│ device_fingerprint│  │ total(累计)  │
│ 单价(元/条)   │   │ status: UNUSED/      │   │ status: ACTIVE/  │   │ available    │
│ 充值折扣档位   │   │   ACTIVE/DISABLED/   │   │   DISABLED       │   │ reserved     │
│ 赠送次数      │   │   EXPIRED            │   │ machine_info(脱敏)│   │ (冻结中)     │
│ 次数有效期规则 │   │ max_devices(默认1)   │   │ last_heartbeat_at│   │ version(审计)│
│ 默认并发配额   │   │ expires_at(可选)     │   │ activated_at     │   └──────┬───────┘
└──────────────┘   │ created_by_admin_id  │   └──────────────────┘          │
                   │ bound_user_id ────────► 激活时自动创建 user(role=employee)，
                   └──────────────────────┘   与现有 owner_user_id 外键全兼容
                                    wallet_transactions（只追加流水）
                                    ┌───────────────────────────────────────┐
                                    │ CHARGE/RESERVE/SETTLE/RELEASE/   │
                                    │ REFUND/ADJUST/EXPIRE + amount +  │
                                    │ batch_id/task_id+billing_round + │
                                    │ idempotency_key + created_at     │
                                    └───────────────────────────────────────┘
```

设计要点：

- **钱包挂 license 而非 device**：换电脑（换绑）余额不丢；一个码默认绑 1 台设备（`max_devices` 可调），未来一码多机共享钱包有扩展位。
- **激活即建 user**：`licenses.bound_user_id` 指向 `users` 表新记录（role=employee）——现有 `projects.owner_user_id`、`generation_batches.created_by_user_id` 等所有 user 外键**零改动**。
- **计费真源**：钱包余额由流水推导，守恒式为 `total ≡ available + reserved + ΣSETTLE + ΣEXPIRE − ΣREFUND − ΣADJUST`（§4.3/§4.4 有完整增量表）；余额列是缓存，并发一致性由事务行锁保证，日终对账按守恒式重算兑底。

### 3.2 激活码生成与格式

- 格式：`VR-XXXXX-XXXXX-XXXXX-C`（3 组 5 位 Base32 大写 + 1 位校验位），约 75 bit 熵，暴力穷举与碰撞在现实中不可行。
- 生成：管理端批量生成（CSPRNG），支持指定套餐、有效期、备注（客户名）。
- 存储：`licenses.code` 以 Fernet 加密存储（复用现有 `settings.py` 加密栈），管理端可再次查看（运营需要给客户补发码）；同时存 SHA256 哈希列用于激活接口的快速索引。
- 激活接口对同一码的失败尝试限速（每 IP + 每码 10 次/小时），防止撞码。

### 3.3 硬件指纹

Tauri Rust 层采集（不经过 WebView，原始值不出现在前端 JS）：

| 平台 | 主因子 | 辅助因子 |
| --- | --- | --- |
| Windows | `MachineGuid`（HKLM\SOFTWARE\Microsoft\Cryptography） | 主板序列号（Win32_BaseBoard） |
| macOS | `IOPlatformUUID` | `IOPlatformSerialNumber` |

- 指纹 = `SHA256(主因子 + "|" + 辅助因子 + "|" + 服务端全局盐)`，盐为服务端 env 配置的全局固定值（盐只防跨库彩虹表，不承担防伪职责——防伪依赖密钥不出云与设备槽位）；客户端激活后不再复算指纹，无需持久化盐。
- Rust 实现建议：`machine-uid` crate（跨平台 MachineGuid/IOPlatformUUID）+ `sysinfo`（主板序列号），经 Tauri command 暴露给前端仅用于激活请求。
- **指纹漂移容忍**：重装系统（Windows 重装通常保留 MachineGuid 的场景除外）、换主板会导致指纹变化 → 走换绑流程（§3.5），不是自动失败。
- **诚实边界**：纯软件指纹可被虚拟机克隆/注册表复制欺骗。V1 接受该风险（密钥在云端，克隆指纹只能"共享次数"，无法偷密钥，且 `max_devices` 槽位使克隆同一指纹无增益——同指纹重新激活会占满槽位，把真实设备挤出去）。V2 可选 USB 加密狗升级。

### 3.4 激活流程与设备令牌

```
客户端                                云端
  │ POST /api/public/activate                    │
  │  { code, device_fingerprint,                 │
  │    machine_info(脱敏: OS版本/内存档位) }      │
  ├─────────────────────────────────────────────►│ 码有效? 未禁用? 未过期?
  │                                              │ 槽位未满?（或旧指纹换绑已批准）
  │                                              │ 事务: 建 device + 建 wallet（幂等）
  │                                              │       + 建 user → license ACTIVE
  │                                              │       赠送仅首次激活发放；换绑重激活
  │                                              │       跳过 gift CHARGE（幂等冲突不报错）
  │ ◄── device_token + license 快照 ─────────────│
  │     (套餐/余额/过期时间/并发配额)              │
  │
  │ 此后所有请求带 X-Device-Token                 │
```

- **device_token**：随机 256 bit，服务端存哈希；长期有效但服务端可吊销（禁用设备/禁用激活码即时生效）。客户端以 Rust `keyring` crate（或 tauri-plugin-stronghold）保存到 OS 密钥库——语义对齐现有 `local_settings_key.py` 的 Keychain/DPAPI 封装，但该 Python 模块随本地 sidecar 移除，**不可直接复用**。
- **令牌校验中间件**替换现有 `get_current_user` 的 env 身份逻辑：`X-Device-Token → device → license → bound_user_id → users 表`（返回现有 `CurrentUser` 结构，下游路由零改动）。
- **无会话层**：device_token 即凭证，不做"单会话踢下线"（桌面端是单实例常驻应用，会话语义不适用，崩溃重启也不应被旧会话挡住）；一号多开仅由设备槽位（`max_devices`）约束。

### 3.5 设备生命周期与心跳

| 事件 | 行为 |
| --- | --- |
| 心跳 | 客户端每 5 分钟 `POST /api/device/heartbeat`（仅带 device_token，不复算指纹）；服务端更新 `last_heartbeat_at`，可顺带推送"已被禁用/套餐变更"指令 |
| 指纹校验时机 | 仅在激活与换绑时比对指纹（主板序列号在部分 OEM 机读取失败属常态，在线比对会误杀正常客户）；运行期异常由管理端手动锁定设备 |
| 远程禁用 | 管理端禁用 device 或 license → 心跳与下一个 API 请求立即 403 `LICENSE_DISABLED` |
| 换绑 | 管理端解绑旧指纹（码回到 ACTIVE 未绑定态）→ 客户端重新激活；每码换绑次数限 3 次/年（可配置），防"一号传着用" |
| 到期 | license/套餐过期 → API 拒绝新批次，存量任务继续跑完，数据只读；**余额保留在钱包不作废，续费模型见 D14（V1.3）** |

### 3.6 安全边界声明（能防什么 / 不防什么）

| 威胁 | 防护 | 残余风险 |
| --- | --- | --- |
| 提取 API Key 直连 Provider | 密钥不出云 —— **免疫** | 无 |
| 本地改余额/破解客户端计费 | 余额真源在云 —— **免疫** | 无 |
| 一码多机 | 硬件指纹 + 设备槽位（max_devices） | 虚拟机克隆指纹可共享次数（见 §3.3） |
| 激活码泄露被他人抢注 | 首次激活即绑定；可加"激活码+客户姓名后缀"双因子（V1 可选） | 抢在客户前激活（运营可解绑重置） |
| 重放/中间人 | 全站 HTTPS + token 哈希存储 + 请求 nonce | 无（必须强制 HTTPS） |
| 服务端拖库 | 激活码 Fernet 加密、token/指纹哈希、密钥 Fernet | 运营方服务器运维责任 |

## 4. 计费方案

### 4.1 计费对象（V1 范围决策）

| 动作 | V1 | 理由 |
| --- | --- | --- |
| H3 视频生成（`generation-batches` 每条任务） | **按次扣费** | 主成本，用户明确要求"一条视频一个价" |
| 视频拆解 / 首帧 / 人物图 / 口播改写 | 免费（计入套餐定价成本） | 计费粒度太碎伤体验；流水表已预留 `billing_action` 字段，V2 可开差异化计费 |
| 云存储 | 免费（运营成本） | 量小 |

> 计费设计按"动作"建模而非硬编码视频：`wallet_transactions.billing_action ∈ {VIDEO_I2V, IMAGE_GEN, ANALYSIS, SCRIPT_REWRITE}`，V1 只启用 `VIDEO_I2V`，后续开闸零迁移。

**免费不等于无限：免费动作必须有配额闸**（V1.2 新增，M17）。视频拆解走 Apilio Gemini、口播改写走 DeepSeek、首帧与人物图走 Apilio gpt-image / nano-banana——这四类**真实消耗 Provider 成本**却在 V1 完全免费。密钥上云后成本由运营方承担，若无配额，单个客户循环调用拆解即可造成不可控成本敞口（且不触发任何计费告警）。

V1 最小实现（不引入钱包，避免计费粒度过碎伤体验）：

| 闸 | 口径 | 落点 |
| --- | --- | --- |
| 日配额 | 每 license 每自然日：拆解 ≤ 50 次、改写 ≤ 200 次、首帧/人物图 ≤ 200 次（`plans` 表配，套餐可覆写） | 路由入口计数，超限 429 `FREE_QUOTA_EXCEEDED` |
| 频率闸 | 每 license 每分钟 ≤ 10 次免费动作 | 同上，与激活接口限速同一套限流器 |
| 观测 | 免费动作调用量按 license 日聚合进管理端报表 | `audit_logs` 已覆盖，报表侧聚合即可 |

> 阈值取值待运营按实际用量拍板（见 D13）。**"自然日"统一按 Asia/Shanghai 时区切日**（V1.3 明确：按 UTC 切日会让国内客户晚 8 点后跨日重置/提前耗尽配额；服务端计算 date 边界时显式指定该时区，与服务器系统时区无关）。计数表建议直接复用 `audit_logs` 按 `(license_id, action, date)` 聚合，V1 不新建计数表（KISS；量级下 COUNT 查询成本可忽略，M4 压测若成瓶颈再加物化计数）；**前提是 `audit_logs` 需在计费迁移中一并加 `license_id` 冗余列**（V1.3 勘误，F4：现状无此列；虽可经 `users.bound_user_id → licenses` join 推导，但直查列在一码多机与报表场景更稳）。

### 4.2 套餐与定价

- **plan 核心字段**：`unit_price_fen`（单条视频价格，单位分，避免浮点）、充值档位（如充 100 元得 100 条、充 500 元得 550 条）、`gift_credits`（激活赠送）、次数有效期（V1 建议：永久）、`max_concurrent_tasks`（单 license 并发配额，见 §5.4）。
- **充值折算**：管理端录充值（金额 + 套餐）→ `credits = 金额 / unit_price × 档位折扣系数` → CHARGE 流水。价格调整只影响之后的充值，已购次数不贬值。
- **差异化定价（V2 预留）**：`generation_tasks` 已有 `resolution`、`output_duration_seconds`、`model` 字段，价格规则表可按这些维度配单价。**注意实际枚举是 `768P` / `2K`（代码实证），不是 `768P/1080P`** —— 价格规则表的枚举值必须照抄代码，写错即全部匹配落空回落到基准价。V1 只按"条"一口价。

### 4.3 钱包模型

表结构见 §6 DDL（license 主键；total / available / reserved 三列 + 行级非负约束）。两条核心规则：

- **守恒式**（由日终对账兜底，不做行内 CHECK——total 是累计口径，行内表达不了）：`total ≡ available + reserved + ΣSETTLE + ΣEXPIRE − ΣREFUND − ΣADJUST`
- **并发控制**：账务操作一律在事务内锁定 wallet 行（PG: `SELECT ... FOR UPDATE`；SQLite: `BEGIN IMMEDIATE` 已串行化写入）。`version` 不参与并发判定，仅审计/展示。

扣费采用**预冻结-结算（reserve-settle）两阶段**模式，与任务生命周期同构：

### 4.4 流水类型（只追加，禁止 UPDATE/DELETE）

**账务单元 = （任务, 轮次）**：现有 RETRY 是原地重置同一 task 行（可能多轮 FAILED→PENDING→FAILED），账务必须挂在 `(task_id, billing_round)` 而非 `task_id` 上，否则二次结算/二次返还必然撞唯一约束、账务卡死或透支。`generation_tasks` 增加 `billing_round INTEGER NOT NULL DEFAULT 1`：初始 1，每次 RETRY / CONFIRM_NOT_CHARGED 重试 +1；REGENERATE 付费重生成是新任务，billing_round 重新从 1 计。

**账务幂等键必须挂 license 命名空间**（V1.2 修订，B5）：V1.1 的 `UNIQUE(idempotency_key, type)` 是**全局平面命名空间**，而幂等键的实际来源——客户端 `createIdempotencyKey()` 生成的批次键、管理端录入的充值单号、运营侧的重试键——都不保证跨租户唯一。两个 license 撞同一个 key 时，第二个客户的冻结会被静默吞掉（约束拒绝），表现为"提交成功但没扣次数、任务却在跑"，是直接的资损与串账。约束改为：

```
UNIQUE (license_id, idempotency_key, type)
```

并强制前缀规范，使不同来源的键在同一 license 内也不可能碰撞：

| 来源 | 前缀格式 |
| --- | --- |
| 批次创建 | `batch:{batch_id}` |
| RETRY 新轮次 | `retry:{task_id}:{billing_round}` |
| 充值录单 | `recharge:{recharge_order_id}` |
| 激活赠送 | `gift:{license_id}` |
| 到期核销 | `expire:{license_id}:{yyyymm}` |
| 管理端调账 | `adjust:{admin_user_id}:{uuid}` |

> 与 §1.3-3 的业务幂等（`UNIQUE(created_by_user_id, project_id, idempotency_key)`）是**两套独立命名空间**：前者防重复提交批次，后者防重复动账。实现上不得共用同一列或同一校验分支。

| 类型 | 语义 | 触发点 | 关联 | 幂等保障 |
| --- | --- | --- | --- | --- |
| `CHARGE` | 充值/赠送入账 | 管理端录单 / 激活赠送（**仅 license 首次激活**；换绑重激活幂等跳过，V1.3 F6） | recharge_order_id | `UNIQUE(license_id, idempotency_key, type)` |
| `RESERVE` | 冻结（尚未消耗） | 批次创建：**聚合 1 行 amount=N**（挂批次）；RETRY 新轮次：amount=1（挂 task+round） | batch_id / task_id+round | `UNIQUE(license_id, idempotency_key, type)`（`batch:` / `retry:` 前缀） |
| `SETTLE` | 冻结转实扣（消耗） | 任务该 round 进入 SUCCEEDED（且归档终局，见 §4.5） | task_id+round | `UNIQUE(task_id, billing_round, type)` |
| `RELEASE` | 冻结释放（未消耗，退回可用） | FAILED / CANCELLED(未提交) / reconcile 判负 / CONFIRM_NOT_CHARGED / **冻结 TTL 到期** | task_id+round | `UNIQUE(task_id, billing_round, type)` |
| `REFUND` | 已结算资金的善意返还（运营人工） | 管理端对 NEEDS_ATTENTION/客诉退款 | task_id+round | `UNIQUE(task_id, billing_round, type)`（与同 round SETTLE 类型不同不冲突；同类型第二次被挡=防双退） |
| `ADJUST` | 管理员调账（可正可负，必须填理由） | 管理端 | admin_user_id | `UNIQUE(license_id, idempotency_key, type)`（`adjust:` 前缀）+ 审计关联 |
| `EXPIRE` | 次数到期核销（V2 启用有效期时） | 定时任务 | — | `idempotency_key = expire:{license_id}:{yyyymm}` |

**ADJUST 负向调账的硬约束**（V1.2 新增，M23）：ADJUST 是唯一允许 `amount < 0` 的类型，必须在**同一事务内**校验 `balance_available + amount >= 0`，不足则拒绝并返回可调最大额度，**禁止把余额调成负数**。理由：`wallets` 表有 `CHECK (balance_available >= 0)` 行级约束，负向调账越界会直接抛数据库异常而非业务错误，运营端只会看到 500，无法判断该调多少。同时负向 ADJUST 必须填 `reason` 且写 `audit_logs`（与正向同规格）。

各类型对钱包字段的精确增量（§4.3 守恒式的操作定义）：

| 类型 | total | available | reserved |
| --- | --- | --- | --- |
| CHARGE | +a | +a | — |
| RESERVE | — | −a | +a |
| SETTLE | — | — | −a |
| RELEASE | — | +a | −a |
| REFUND | — | +a | — |
| ADJUST | — | ±a | — |
| EXPIRE | — | −a | — |

### 4.5 扣费时序（与现有状态机逐态对齐）

```
POST /generation-batches (quantity=N, idempotency_key)
│
├─ [API 层，单事务]
│   1. 验设备令牌 → license ACTIVE 且未过期
│   2. 事务内锁定 wallet 行（PG 行锁 / SQLite BEGIN IMMEDIATE）
│   3. available >= N ? 不足 → 402 BALANCE_INSUFFICIENT（前端引导充值/联系运营）
│   4. available -= N; reserved += N；写 1 行 RESERVE（amount=N，挂 batch_id，
│      idempotency_key=批次幂等键）——聚合单行，天然兼容 UNIQUE(idempotency_key,type)
│   5. 建批次 + N 个 PENDING 任务（billing_round=1；现有 create_generation_batch 逻辑原样）
│   ※ 幂等：同 idempotency_key 重复提交 → 命中现有幂等分支返回原批次，不重复冻结
│
├─ [Worker 层，随任务状态推进]
│   PENDING → SUBMITTING → 提交 Provider
│       ├─ 提交成功 → QUEUED…RUNNING…ARCHIVING（冻结保持）
│       ├─ 提交失败（terminal）→ RELEASE 当轮（冻结释放回 available）
│       └─ SUBMISSION_UNCERTAIN → 冻结保持，等待现有 reconcile 对账机制裁决
│
└─ [终态账务矩阵]（全部按 (task_id, billing_round) 落账）
    SUCCEEDED              → SETTLE（reserved -= 1）※落点定义见下方"SETTLE 落点"
    FAILED                 → RELEASE（冻结自动全额释放；pre-provider 失败可 RETRY）
    CANCELLED（未提交）     → RELEASE ※取消能力为 V1 新增（现状代码无 CANCELLED 入口，见 D11）
    CANCELLED（已提交）     → 不释放（provider 成本已发生；是否返还按套餐配置）
    SUBMISSION_UNCERTAIN   → 冻结保持；reconcile 成功 → SETTLE；判负 → RELEASE
    CONFIRM_NOT_CHARGED    → RELEASE（仅 SUBMISSION_UNCERTAIN 且无 provider 证据时可用，
                              现有代码语义原样承接）+ 任务回 PENDING，billing_round+1，
                              并与 RETRY 同规立即重新 RESERVE amount=1 挂新轮（V1.3，F2：
                              余额不足则任务挂起并通知，禁止裸奔进新轮——否则该轮 SETTLE
                              会把 reserved 扣成负数或吃掉其他任务的冻结）
    NEEDS_ATTENTION        → 已 SETTLE 不动账；客诉由运营人工 REFUND（善意返还，
                              每 round 至多 1 次，UNIQUE 防双退）
```

**三种重试/重生成机制的计费语义（代码实证边界）**：

| 机制 | 代码现状 | 账务动作 |
| --- | --- | --- |
| `RETRY` 免费原地重试 | UPDATE 同一 task 行回 PENDING；仅 pre-provider 失败或 CONFIRM_NOT_CHARGED 后可用 | 当轮已 RELEASE → 开启新 round：billing_round+1 并重新 RESERVE amount=1（需余额 ≥1，防透支），RETRY 请求的幂等键落 UNIQUE |
| `REGENERATE` 付费重生成 | 新建批次/任务，写 retry_of_task_id，请求体带 payment_confirmation_version | **按新批次正常计费**：RESERVE → SETTLE，无任何减免（AUDIO_QUALITY_FAILED 等已消耗成本的场景由代码强制走这里） |
| 归档重试（ARCHIVE_FAILED） | 现有 `_retry_archive`，无 Provider 调用 | 不动账 |

**为什么冻结点在批次创建而不是提交成功时**：防止"余额 1 条却提交 10 条批次"的透支窗口；冻结失败即拒绝，语义对用户最直观（下单即占额，失败即释放）。

#### SETTLE 落点的精确定义（V1.2 新增，M15）

V1.1 只写"任务 SUCCEEDED → SETTLE"，但代码里 `SUCCEEDED` 与归档是**两个独立维度**：任务可以是 `status='SUCCEEDED'` 且 `archive_status='ARCHIVE_FAILED'`（Provider 已出片已计费，但转存 COS 失败）。此时若不定义清楚，会出现两种错误实现——扣了但用户拿不到片（客诉），或等归档成功才扣、而归档重试永远失败导致该笔永久挂在 `reserved`（占额）。

**规则：SETTLE 挂 `status` 转 `SUCCEEDED` 的那一刻，与 `archive_status` 无关。**

| 场景 | 账务 | 理由 |
| --- | --- | --- |
| `SUCCEEDED` + 归档成功 | SETTLE | 正常路径 |
| `SUCCEEDED` + `ARCHIVE_FAILED` | **同样 SETTLE**（立即，不等归档） | Provider 成本已实际发生；`provider_result_url` 仍在，归档可无限次重试且不调用 Provider（不重复计费） |
| 归档重试最终成功 | 不动账（已 SETTLE） | `UNIQUE(task_id, billing_round, type)` 天然挡住二次落账 |
| 归档重试彻底放弃、用户拿不到成片 | 运营人工 REFUND | 走善意返还通道，不改 SETTLE 语义 |

> 实现锚点：扣费钩子挂在 `generation.py::_store_and_finalize_archive` 的 **status 落 SUCCEEDED 分支**，而非归档成功分支。

#### 冻结 TTL：reserved 必须有兜底出口（V1.2 新增，M14）

V1.1 的 RESERVE 只有"任务进终态"这一条释放路径。但任务卡在非终态是真实存在的（Provider 侧长期 QUEUED 不返回、`SUBMISSION_UNCERTAIN` 对账拿不到裁决、Worker 反复崩溃耗尽重试）。这些情况下 `balance_reserved` 会被永久占用——客户余额显示"有"却下不了单，且守恒式仍然成立（对账不告警），是最难排查的一类资损。

| 项 | 定义 |
| --- | --- |
| TTL 时长 | 任务停留非终态 **24 小时**（`plans` 可覆写；须显著大于 H3 最长生成时间 + reconcile 周期） |
| 扫描 | 日终对账任务顺带扫描：`status NOT IN (终态) AND created_at < now - TTL` |
| 动作 | 强制 `RELEASE` 当轮冻结 + 任务标记 `FAILED`（`failure_code = BILLING_RESERVE_EXPIRED`）+ 批次转 `NEEDS_ATTENTION` + 告警管理端 |
| 防误伤 | 释放前**必须**再查一次 Provider 侧状态（复用现有 `reconcile_submission_uncertain_task`）；查到已出片则走 SETTLE 而非 RELEASE |
| 幂等 | 复用 `UNIQUE(task_id, billing_round, type)`，与正常 RELEASE 同一约束，不会双退 |

> 不新增数据库列：TTL 判定用现有 `generation_tasks.created_at` / `updated_at` 即可（KISS）。

### 4.6 防双扣与对账

1. **物理防双扣/防双退**：`UNIQUE(task_id, billing_round, type)`——同一任务同一轮至多一条 SETTLE、一条 RELEASE、一条 REFUND（三种类型语义正交可共存）；同类型第二次写入被约束拒绝。
2. **批次级对账（V1.3 重写，F1）**：初始冻结（batch 级 1 行 amount=N）与重试冻结（task 级 amount=1）是**两种粒度**，V1.2 的三联等式把两者混写必然误报（首轮无任务级 RESERVE 行，Σ任务轮次行 = 重试次数 ≠ N）。改为三条独立断言，任一不满足 → 批次进人工对账队列：
   - **冻结侧**：每批次恰好一条 batch 级 RESERVE 且 `amount == quantity`；每个非首轮 `(task_id, billing_round)` 恰好一条 amount=1 的任务级 RESERVE（首轮份额由 batch 级行覆盖，无任务级行）；
   - **收尾侧**：每个已终态轮次以恰好一条 SETTLE **或** RELEASE 收尾（唯一性已由约束物理保证，对账验证的是**存在性**——防止漏收尾）；在途轮次不要求；
   - **防多扣**：`Σ该批次 SETTLE.amount ≤ quantity`（含 reconcile 判正的 SETTLE；REGENERATE 是新批次，不计入本批次）。
3. **钱包守恒对账（日终）**：按 §4.3 守恒式 `total ≡ available + reserved + ΣSETTLE + ΣEXPIRE − ΣREFUND − ΣADJUST` 重算比对，漂移即告警（管理端通知 + audit_logs）。
4. **所有资金动作写 audit_logs**（复用现有审计表），充值/调账/退款均强制留痕。
5. **冻结时效对账（V1.2 新增）**：日终扫描超 TTL 仍未收尾的冻结，按 §4.5"冻结 TTL"处置。注意此项**守恒式检不出来**（reserved 占用本身是合法状态），必须独立扫描，否则资损静默累积。
6. **账务幂等键跨租户抽检（V1.2 新增）**：定期校验 `wallet_transactions` 不存在同一 `idempotency_key` 跨 `license_id` 复用的行——若出现，说明前缀规范或约束落地有误（§4.4 B5）。

## 5. 用户端与服务端拆分方案

### 5.1 组件划分

| 组件 | 形态 | 部署 |
| --- | --- | --- |
| **瘦客户端** | 现有 Tauri + React，保留全部工作台 UI | 分发给客户（NSIS/dmg） |
| **云端业务服务** | 现有 `server/app` 整体上云（API + Worker） | VPS，Docker Compose |
| **管控服务** | 新增 `app/license.py / billing.py / control_routes.py` 模块（并入同一 FastAPI，`/api/control/*` 前缀） | 同上 |
| **管理端 Web** | 新增独立 React app（可放 `admin/` 目录，复用现有构建栈） | 同域静态托管（Caddy/Nginx） |

> 管控服务不单独起进程：与业务服务共享数据库和 Provider 适配层，避免双写；用路由前缀 + 鉴权域隔离（管理端 session 令牌 vs 设备令牌两套中间件）。同进程风险的最小缓解：管控路由独立限流、管理端来源 IP 白名单（Caddy 层，运营网络固定时启用）、管控动作审计统一 `control.*` 前缀。

### 5.2 数据归属决策

| 数据 | 归属 | 说明 |
| --- | --- | --- |
| 激活码/设备/钱包/流水 | **云端（新增）** | 计费真源 |
| provider_settings（密钥） | **云端（迁移）** | 从"每台客户机一份"变为"服务器唯一一份" |

| 客户端本地存储 | 仅缓存：登录态、UI 偏好、离线只读快照（可选） | 本地 SQLite 保留为缓存层（V1 可先不做离线快照） |

### 5.3 鉴权改造（关键替换点）

| 现有机制 | 云端目标机制 | 改动位置 |
| --- | --- | --- |
| loopback 中间件（非回环 403） | **删除**，全站 HTTPS | `main.py` |
| `VIDEO_REPLICA_DESKTOP_USER_ID` env 身份 | 设备令牌中间件（token → device → license → user） | `auth.py`（接口不变，换实现） |
| CORS 白名单（127.0.0.1:5173 等） | origins 改云端域名 + Tauri origin；`allow_headers` **必须新增 `X-Device-Token`**（现状仅 `Content-Type, X-Dev-User-Id`，漏配则激活后所有请求预检失败） | `main.py` |
| `X-Dev-User-Id` 开发头 | 云端部署清单**必须不存在** `VIDEO_REPLICA_ALLOW_DEV_IDENTITY_HEADER`（该 env 是唯一开关，误配=任意 HTTP 头冒充任意用户）；bootstrap 启动自检：非 dev 模式检出该变量即拒绝启动 | `auth.py`、`bootstrap.py` |
| RBAC employee/admin/auditor | admin/auditor → 管理端；employee → 设备激活自动创建 | `permissions.py` 原样 |
| （无）单一身份来源 | **双鉴权域分流**：客户端 `X-Device-Token` 与管理端会话令牌是两套凭证，共存于同一 FastAPI 实例 | `auth.py` 新增依赖分层（见下） |

**双鉴权域的分流规则（V1.2 新增，M13）**：现有 `get_current_user` 是全局唯一身份入口（env 单用户），云化后它要同时服务两类调用方，必须显式分域，否则会出现"管理员令牌能打业务 API"或"设备令牌能打管控 API"的越权。

| 依赖 | 接受凭证 | 挂载路由 | 拒绝行为 |
| --- | --- | --- | --- |
| `get_current_device_user()` | 仅 `X-Device-Token` | `/api/*`（业务面） | 无 token 或 token 无效 → 401；license 非 ACTIVE → 403 `LICENSE_DISABLED` |
| `get_current_admin_user()` | 仅管理端会话令牌（Cookie/JWT） | `/api/control/*`（管控面） | 非 admin/auditor → 403 |
| `get_current_user()` | **废弃**，不再直接被路由引用 | — | 保留为上述两者的内部实现细节，返回结构仍是现有 `CurrentUser`，下游业务路由零改动 |

要点：

- 两个依赖**互不回退**。管控令牌打 `/api/*` 必须 401，反之亦然——不做"admin 万能钥匙"，否则管理端一旦被撞库即等于全部客户数据裸奔。
- `users` 表加 `password_hash` 列（迁移，见 §6）；激活自动创建的 employee 用户 `password_hash` 为 NULL，且**登录接口必须显式拒绝 `password_hash IS NULL` 的账号**，防止空密码绕过。
- `permissions.py::require_project_access` 的 `admin/auditor` 放行分支保持不变，但它此时只可能来自管控面依赖，语义自洽。

- 优先做一个共享 fixture（建 plan → 建 license → 激活 → 返回带 `X-Device-Token` 的 client），让绝大多数测试只改夹具引用、不改断言；

### 5.6 租户隔离改造（V1.2 新增，B4 —— M1 的阻塞项）

#### 问题陈述

单机架构下"只有一个用户"，因此代码里有一批**刻意的全局共享设计**。这些设计在单机是正确的，云化后**每一处都变成跨客户数据泄露**。这是 V1.1 完全没有覆盖的缺口，也是本次评审唯一定级为 Blocker 的架构性问题。

代码实证的三类现状：

| 类别 | 现状 | 云化后果 |
| --- | --- | --- |
| **项目级数据**（projects / generation_batches / tasks / analysis / versions） | `require_project_access` 已全覆盖，按 `owner_user_id` 隔离 | ✅ 无需改造，激活建 user 后天然按 license 隔离 |
| **共享域数据**（`person_identities` 人物身份库） | 无 owner 列；`list_person_identities` 执行 `SELECT * FROM person_identities` 无过滤；employee 仅经 `identity_available_to_employee` 做**可用性**过滤而非**归属**过滤。`simple_character.py` 注释 `visibility intentionally matches GET /api/person-identities` 确认是刻意设计 | ❌ **客户 A 能看到并使用客户 B 上传的真人肖像** —— 不只是数据泄露，是肖像权与合规事故 |
| **无归属校验的路由**（`character_generation_routes.py` / `character_reference_routes.py`） | `require_project_access` 调用数为 **0** | ❌ 归属机制未确认，须逐路由排查后补齐或论证其安全性 |
| **素材与人物路由**（`assets` 相关路由 / `characters`，V1.3 补入排查，F8） | 覆盖情况**未实证**——§1.3-8 的实证范围只覆盖 projects / analysis / generation / versions | ⚠️ COS 预签名**签发**路由是跨租户读取素材的最后一道闸，必须实证或补 `require_project_access`；DB 层隔离做完但签发路由裸奔等于白做 |

> 注意区分：`settings_routes.py` 的 `require_project_access` 调用数同样为 0，但它是**正确的**——Provider 配置是全局运营数据，由 `require_role(admin)` 守卫，云化后归管控面。不要误改这一处。

#### 改造方案：可见性分层

`person_identities` 增加归属维度，把"全局共享"拆成"运营公共模板"与"客户私有素材"两层：

```sql
-- person_identities 增列（一条迁移）
ALTER TABLE person_identities ADD COLUMN owner_license_id TEXT REFERENCES licenses(id);
ALTER TABLE person_identities ADD COLUMN is_public_template INTEGER NOT NULL DEFAULT 0;
-- owner_license_id IS NULL AND is_public_template = 1  →  运营维护的公共模板，全客户可见
-- owner_license_id = X                                 →  客户 X 私有，仅 X 可见
CREATE INDEX ix_person_identities_owner ON person_identities (owner_license_id);
```

可见集判定（替换现有无过滤查询）：

| 角色 | 可见集 |
| --- | --- |
| employee（客户端设备身份） | `owner_license_id = 自己的 license` **∪** `is_public_template = 1` |
| admin / auditor（管控面） | 全部（运营需要跨客户排障与内容审核） |

配套规则：

- **写入侧**：客户端上传的人物一律写 `owner_license_id = 当前 license`、`is_public_template = 0`；只有管控面能把某个人物标记为公共模板（且标记动作写 `audit_logs`）。
- **存量迁移**：现有 `person_identities` 全部数据在迁移时标为 `is_public_template = 1`（视为运营预置模板）——内测期数据本就来自运营方，这样处理不破坏现有客户体验；若存量中确有内测客户上传的私有肖像，迁移工具需按 `created_by_user_id` 回填 `owner_license_id`。
- **`character_generation_routes.py` / `character_reference_routes.py`**：逐路由排查，凡是接受 `person_identity_id` 或 `project_id` 入参的，一律补 `require_project_access` 或新增 `require_identity_access`（按上表可见集判定）。
- **钱包/流水路由**：新增的 `/api/wallet/*` 从设计之初就按 `license_id = 当前设备所属 license` 过滤，不复用 `owner_user_id` 路径。

#### 验收标准（M1 的出口条件，必须有自动化测试）

建两个 license（L1 / L2），各自激活、各自建项目与人物，然后断言：

| 用例 | 期望 |
| --- | --- |
| L1 的 token 访问 L2 的 `project_id` | **404**（不是 403 —— 不泄露资源是否存在） |
| L1 的 token 访问 L2 的 `generation_batch_id` / `task_id` | 404 |
| L1 的 token 调 `GET /api/person-identities` | 只含 L1 私有 + 公共模板，**不含 L2 私有** |
| L1 的 token 用 L2 的 `person_identity_id` 发起生成 | 404 / 422，不得成功 |
| L1 的 token 访问 `/api/control/*` | 401 |
| 管控面 admin 令牌访问 `/api/*` | 401 |
| L1 的 token 查钱包/流水 | 只见自己 license 的流水 |

> 这组测试是 B4 与 M13 的共同验收凭据，必须在 M1 完成，**不得延后到 M4**：一旦有第二个客户上线，泄露就已经发生了。

```sql

    expires_at TEXT,
    bound_user_id TEXT REFERENCES users(id),   -- 激活时自动创建 user：
                                               -- username='license_'||code_hash[:8], role='employee'
    remark TEXT,                           -- 客户名等运营备注
    rebind_count INTEGER NOT NULL DEFAULT 0,
    created_by_admin_id TEXT REFERENCES users(id),
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE devices (
    id TEXT PRIMARY KEY,
    license_id TEXT NOT NULL REFERENCES licenses(id),
    device_fingerprint TEXT NOT NULL,      -- SHA256(主因子|辅助因子|全局盐)
    machine_info_redacted TEXT,            -- OS 版本/内存档位（脱敏）
    status TEXT NOT NULL DEFAULT 'ACTIVE'  -- ACTIVE/DISABLED
        CHECK (status IN ('ACTIVE','DISABLED')),
    token_hash TEXT NOT NULL,              -- device_token 的哈希
    last_heartbeat_at TEXT,
    activated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
-- 换绑 = 旧行翻转 DISABLED（tombstone 保留），重新激活插新行；
-- 唯一性只对活跃设备生效（PG 与 SQLite 均支持部分索引）：
CREATE UNIQUE INDEX uq_devices_active_fingerprint
    ON devices (license_id, device_fingerprint) WHERE status = 'ACTIVE';

CREATE TABLE wallets (                      -- 随 license 首次激活幂等创建（INSERT OR IGNORE 语义）；
                                           -- 换绑重激活不得重建（V1.3，F6）
    license_id TEXT PRIMARY KEY REFERENCES licenses(id),
    balance_total INTEGER NOT NULL DEFAULT 0 CHECK (balance_total >= 0),  -- 累计获得口径
    balance_available INTEGER NOT NULL DEFAULT 0 CHECK (balance_available >= 0),
    balance_reserved INTEGER NOT NULL DEFAULT 0 CHECK (balance_reserved >= 0),
    version INTEGER NOT NULL DEFAULT 0,      -- 仅审计/展示，不参与并发判定
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
    -- 不做 available+reserved<=total 的行内 CHECK（total 为累计口径表达不了）；
    -- 守恒由日终对账按 §4.3 守恒式兜底
);

CREATE TABLE wallet_transactions (           -- 只追加，禁止 UPDATE/DELETE
    id TEXT PRIMARY KEY,
    license_id TEXT NOT NULL REFERENCES licenses(id),
    type TEXT NOT NULL CHECK (type IN
        ('CHARGE','RESERVE','SETTLE','RELEASE','REFUND','ADJUST','EXPIRE')),
    billing_action TEXT NOT NULL DEFAULT 'VIDEO_I2V',
    amount INTEGER NOT NULL CHECK (type = 'ADJUST' OR amount > 0),
    -- ADJUST 可为负；负向调账须在事务内校验 available + amount >= 0 后再写（§4.4 M23），
    -- 不依赖 wallets 的 CHECK 兜底（那会抛 500 而非业务错误）
    billing_round INTEGER NOT NULL DEFAULT 1, -- 账务轮次，对齐 generation_tasks.billing_round
    batch_id TEXT,                           -- 批次级 RESERVE 关联
    task_id TEXT,                            -- SETTLE/RELEASE/REFUND 关联
    idempotency_key TEXT,                    -- 前缀规范见 §4.4：batch:/retry:/recharge:/gift:/expire:/adjust:
    reason TEXT,                             -- ADJUST/REFUND 必填
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (task_id, billing_round, type),   -- 物理防双扣/防双退；task_id 为 NULL 的行不参与去重
    UNIQUE (license_id, idempotency_key, type)  -- 账务幂等键挂 license 命名空间（B5）；
                                                -- 全局平面命名空间会导致跨租户撞键静默吞冻结
);

CREATE TABLE recharge_orders (             -- 管理端人工录单（V1 无支付网关）
    id TEXT PRIMARY KEY,
    license_id TEXT NOT NULL REFERENCES licenses(id),
    plan_id TEXT NOT NULL REFERENCES plans(id),
    amount_fen INTEGER NOT NULL CHECK (amount_fen > 0),
    credits INTEGER NOT NULL CHECK (credits > 0),
    external_ref TEXT,                     -- 对公转账/微信收款凭证号
    status TEXT NOT NULL DEFAULT 'CONFIRMED',
    created_by_admin_id TEXT NOT NULL REFERENCES users(id),
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);
-- 防重复录单（V1.3，F3）：幂等键 recharge:{order_id} 防的是同单重放，防不了运营把

CREATE UNIQUE INDEX uq_recharge_orders_ref
    ON recharge_orders (license_id, external_ref) WHERE external_ref IS NOT NULL;

-- users 表迁移（管理端登录凭证，整块新增）:
```

| **M3 管理端后台** | 激活码批量生成/导出/换绑、套餐与定价、充值录单（**同一凭证重复录单被唯一索引拒绝并提示查原单，F3**）、设备管理、Provider 配置托管（Fernet 迁移至云端）、用量/收入报表、**免费动作配额闸与用量报表（M17）**、**per-license 在途任务数报表（M18 前置观测）** | 运营全程不碰数据库即可完成发码→充值→客服换绑；客户端设置页 Provider 表单移除；**免费动作超限返回 429 `FREE_QUOTA_EXCEEDED`**；**管理端可见各 license 的免费动作日用量与在途任务数** |

依赖与顺序依据：M1 是不可绕过的地基（没有云端执行就没有真计费）；M2 依赖 M1 的令牌与批次链路；M3 与 M2 可部分并行（配置托管不依赖钱包）；M4 收尾。

**V1.2 对排期的净影响（必须在报工时量前明确）**：

| 变化 | 里程碑 | 方向 |
| --- | --- | --- |
| 租户隔离改造（B4）从"无"变为 M1 阻塞项 | M1 | **加**——不可延后到 M4，第二个客户上线即已泄露 |
| 测试夹具改造（M16）显性化 | M1 | **加**——原方案隐含为"顺手改"，实为 28 文件量级 |
| 双鉴权域分层（M13） | M1 | 加（小）——`auth.py` 依赖分层，路由侧零改动 |
| 冻结 TTL + SETTLE 落点 + 负向调账（M14/M15/M23） | M2 | 加（中）——均为账务正确性硬需求，无法用运营流程替代 |
| per-license 并发配额（M18）由 M1/M2 推迟到 M4 | M1→M4 | **减**——避开热路径 SQL 早改，M4 有真实数据再校准 |
| Worker 租约超时回收确认已实现（M22） | M1 | **减**——原列为待改造项，实证无需改造 |
| 项目级归属校验确认已覆盖（M22） | M1 | **减**——`require_project_access` 已覆盖 projects/analysis/generation/versions |

净结论：M1 显著变重（隔离 + 夹具 + 分层），M2 中度变重（三项账务正确性），M4 接过 M18。**不要把 M1 的隔离与夹具工作压缩进 M2**——它们是"第二个客户能否上线"的前置条件，不是优化项。
