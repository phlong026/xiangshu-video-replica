# 激活码管控与云端计费架构方案（V2 云化改造）

> 方案日期：2026-08-19
> 状态：架构设计稿（待评审决策，见 §9 待决策清单）
> 关联文档：`docs/服务端分发与自动拉起方案.md`、`docs/Windows内测与运维手册.md`、`docs/短视频复刻桌面端开发说明.md`
> 目标：将 Provider 密钥（API Key / 云存储 / MiniMax-H3）集中到云端管理端，通过激活码实现硬件绑定与套餐关联，按"条"计费、生成一次扣费一次，并完成用户端与服务端的彻底拆分。

## 1. 调研结论：现状与差距

### 1.1 现有架构全景（单机闭环）

```
┌─────────────────────────── 员工 Windows/macOS 单机 ───────────────────────────┐
│                                                                              │
│  Tauri 2 桌面壳 (lib.rs: TCP 探测 127.0.0.1:8000 → 自动拉起 sidecar)         │
│      └── React 19 前端 (api.ts: 默认 http://127.0.0.1:8000，                 │
│                          已支持 VITE_API_BASE_URL 覆盖)                      │
│                                                                              │
│  FastAPI 本地 sidecar (PyInstaller 单目录) + 本地 Worker (generation_worker)  │
│      ├── SQLite (WAL)：users/projects/assets/versions/                       │
│      │     generation_batches/generation_tasks/audit_logs…                   │
│      ├── provider_settings 表：metaso/apilio/cos/deepseek 配置               │
│      │     （Fernet 加密，主密钥存 macOS Keychain / Windows DPAPI）          │
│      └── 安全边界：API 仅限 loopback（非回环 403）、CORS 白名单、             │
│            身份由环境变量 VIDEO_REPLICA_DESKTOP_USER_ID 指定单用户            │
│                                                                              │
│  所有 Provider 调用（Metaso H3 / Apilio Gemini / DeepSeek / COS）            │
│  均从本机发起，密钥永在本机内存与磁盘中                                       │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 1.2 密钥与配置现状：为什么本地存储无法支撑计费

已核实全部 6 类 Provider 消耗点均从本地 `SettingsRepository.load_provider_config()` 读取密钥：

| 消耗点 | 代码位置 | Provider | 性质 |
| --- | --- | --- | --- |
| H3 视频生成（I2V） | `generation.py` `MetasoH3Provider` | metaso | **主计费点** |
| 视频拆解分析（分镜） | `analysis_routes.py` | apilio (Gemini) | 高频消耗 |
| 首帧生成/人物置换 | `first_frame_routes.py` | apilio (gpt-image-2) | 按次消耗 |
| 人物库图片生成 | `character_image_generation.py` | apilio (nano-banana-pro-2k) | 按次消耗 |
| 口播稿改写 | `script_rewrite.py` | deepseek | 按次消耗 |
| 视频归档/上传/下载 | `storage.py` | cos (腾讯云) | 按量消耗 |

**核心矛盾**：只要密钥下发到客户端，任何本地计费都可被绕过——客户可从内存或数据库中提取密钥直连 Provider。密钥一旦随安装包分发即失控，且无法吊销（吊销即全部客户端同时失效）。

**由此得出本方案的根基性结论：**

> **"配置集中托管"与"计费管控"是同一件事的两面。要实现按次计费，必须把所有 Provider 调用移到云端执行；密钥永不下发，客户端瘦身为纯 UI + 激活通道。**

### 1.3 生成链路全景与状态机（计费扣点依据）

任务状态机（`generation_tasks.status`，代码实证）：`PENDING → SUBMITTING → QUEUED → RUNNING → ARCHIVING → SUCCEEDED`，异常分支 `FAILED / CANCELLED / SUBMISSION_UNCERTAIN`（提交结果不确定，需对账 `reconcile`）；批次级 `NEEDS_ATTENTION`。

现有链路关键事实：

1. **前端从不直连 Provider**，全部经后端 API —— 云化是"平移"，不是重写。
2. **批次-任务两级模型**：一个批次（`generation_batches`，含 `quantity`）创建 N 个任务（`generation_tasks`），Worker 以 SQLite 租约（`locked_by/locked_until`）领取执行。
3. **幂等键已内建**：`idempotency_key` 用户级唯一 + `request_hash` —— 可直接复用为"防重复扣费"的第一道闸。
4. **成本字段已预留**：`generation_tasks.estimated_cost / actual_cost`；管理员"确认不计费重试"语义已存在：`billing_confirmation_status = 'CONFIRMED_NOT_CHARGED'` + 审计动作 `generation_task.billing_confirmed_not_charged` —— 计费体系可自然衔接，不是从零开始。
5. **审计完备**：`audit_logs` 覆盖登录、设置变更、批次创建、任务操作全链路。
6. **上传走 COS 预签名直传**（`create_upload_intent`），不经过后端转发 —— 上云后仅需预签名改由云端签发、桶 CORS 增加客户端来源。
7. **全局并发限制**：`runtime_settings.max_concurrent_h3_tasks` 当前是单机全局值 —— 上云后成为全平台共享值，需要按 license 分配公平配额（见 §5.4）。

### 1.4 可复用资产盘点

| 资产 | 云化后去向 |
| --- | --- |
| FastAPI 全部业务路由（projects/analysis/characters/generation…） | 整体上云，改动集中在鉴权与配置源 |
| 任务状态机 + Worker 租约 + 对账（reconcile）机制 | 原样上云，是计费结算的"事实源" |
| `idempotency_key` / `request_hash` | 防重复扣费复用 |
| `estimated_cost/actual_cost`、`billing_confirmation_status` | 计费流水挂接点 |
| RBAC（users.role: employee/admin/auditor） | 管理端鉴权直接复用（admin 进管理台，auditor 只读报表） |
| Fernet 加密配置方案（`settings.py`） | 管理端 Provider 配置托管原样复用，主密钥改服务器环境变量注入 |
| OS 密钥库封装（`local_settings_key.py`：Keychain/DPAPI） | 客户端保存 device_token 复用同一套封装 |
| COS 预签名上传/下载 | 云端签发，桶 CORS 更新即可 |
| `VITE_API_BASE_URL` 前端开关 | 客户端直连云端的现成通道 |
| `backup.py` 备份恢复 | 云端数据库每日备份复用思路 |

### 2.1 三面架构

```
┌───────────────────── 管控面 Control Plane（运营方使用）─────────────────────┐
│  管理端 Web（React，独立前端）                                               │
│  激活码管理 / 套餐与定价 / 充值录单 / 设备管理 / Provider 密钥托管 /        │
│  用量与收入报表 / 管理员账号（复用 users.role=admin/auditor）                │
└──────────────────────────────┬──────────────────────────────────────────────┘
                               │ /api/control/*（账号密码 + Session/JWT）
┌──────────────────────────────┴──────────────────────────────────────────────┐
│                          云端服务（单 VPS 起步，Docker Compose）              │
│  ┌─────────────── 执行面 Data Plane ───────────────┐  ┌── 管控 API ──┐     │
│  │ 现有 server/app 整体上云：                        │  │ license/     │     │
│  │  · 业务 API（/api/*，鉴权改为设备令牌）           │  │ wallet/      │     │
│  │  · Generation Worker（H3 任务执行 + 扣费钩子）    │  │ device/      │     │
│  │  · Provider 适配层（Metaso/Apilio/DeepSeek/COS） │  │ plan/recharge│     │

│  └──────────────────────────────────────────────────┘  PostgreSQL/SQLite     │
└──────────────────────────────┬──────────────────────────────────────────────┘
                               │ HTTPS（设备令牌 X-Device-Token）
┌──────────────────────────────┴──────────────────────────────────────────────┐
│  瘦客户端（Tauri + React，保留全部工作台 UI）                                 │
│  · 激活页（输激活码 → 绑定本机硬件） · 余额/用量展示                          │
│  · 项目/人物库/生成全流程（API 全部指向云端）                                 │

│  · 保留：COS 直传（云端签发预签名）、本地缓存（只读降级用）                    │
└─────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 三条铁律（整个方案的security invariant）

1. **密钥永不落地**：metaso/apilio/cos/deepseek 密钥只存在于云端数据库（加密）与云端进程内存。客户端任何层面（前端/本地存储/网络抓包）都拿不到密钥。
2. **余额真源在云端**：客户端展示的余额是缓存快照，本地篡改无意义——扣费校验、冻结、结算全部发生在云端事务内。
3. **执行在云**：所有 Provider 调用由云端 Worker 发起。客户端破解与否，都绕不开云端这一道闸。

### 2.3 一次视频生成的完整数据流（目标态）

```
客户端                        云端 API                     云端 Worker                Provider
  │  POST /api/projects/{id}/generation-batches  │                            │
  │  (quantity=N, idempotency_key)                │                            │
  ├──────────────────────────────────────────────►│ 验设备令牌 → 验激活有效      │
  │                                               │ 事务：建批次+N任务           │
  │                                               │       钱包冻结 N 次(RESERVE)│
  │  ◄── 批次信息 + 最新余额快照 ──────────────────┤                            │
  │                                               │ 领任务(PENDING→SUBMITTING) │
  │                                               ├───────────────────────────►│ 提交 H3
  │                                               │◄── provider_task_id ───────┤
  │  (轮询 GET 批次详情，与现状一致)               │ QUEUED→RUNNING→ARCHIVING   │
  │                                               │◄───────── 结果 MP4 ─────────┤
  │                                               │ 归档 COS + 质检             │
  │                                               │ SUCCEEDED → SETTLE 扣实    │
  │  ◄── 任务完成 + 余额快照 ─────────────────────┤                            │
```

## 3. 激活码管控方案

### 3.1 实体模型

```
plans（套餐）           licenses（激活码=授权主体）      devices（设备）         wallets（钱包）
┌──────────────┐   ┌──────────────────────┐   ┌──────────────────┐   ┌──────────────┐
│ id           │◄──│ plan_id              │   │ license_id       │   │ license_id   │
│ 名称          │   │ code(激活码,唯一)     │──►│ device_fingerprint│  │ total(累计)  │
│ 单价(元/条)   │   │ status: UNUSED/      │   │ status: ACTIVE/  │   │ available    │
│ 充值折扣档位   │   │   ACTIVE/DISABLED/   │   │   DISABLED       │   │ reserved     │
│ 赠送次数      │   │   EXPIRED            │   │ machine_info(脱敏)│   │ (冻结中)     │
│ 次数有效期规则 │   │ max_devices(默认1)   │   │ last_heartbeat_at│   │ version(乐观)│
│ 默认并发配额   │   │ expires_at(可选)     │   │ activated_at     │   └──────┬───────┘
└──────────────┘   │ created_by_admin_id  │   └──────────────────┘          │
                   │ bound_user_id ────────► 激活时自动创建 user(role=employee)，
                   └──────────────────────┘   与现有 owner_user_id 外键全兼容
                                    wallet_transactions（只追加流水）
                                    ┌───────────────────────────────────────┐
                                    │ CHARGE/RESERVE/SETTLE/REFUND/ADJUST/  │
                                    │ EXPIRE + amount + batch_id/task_id + │
                                    │ idempotency_key + created_at         │
                                    └───────────────────────────────────────┘
```

设计要点：

- **钱包挂 license 而非 device**：换电脑（换绑）余额不丢；一个码默认绑 1 台设备（`max_devices` 可调），未来一码多机共享钱包有扩展位。
- **激活即建 user**：`licenses.bound_user_id` 指向 `users` 表新记录（role=employee）——现有 `projects.owner_user_id`、`generation_batches.created_by_user_id` 等所有 user 外键**零改动**。
- **计费真源**：钱包余额由流水推导（`available = Σ(CHARGE+赠送) - Σ(SETTLE) - Σ(RESERVE 未决) + Σ(REFUND)`），余额列仅为缓存 + 乐观锁版本号。

### 3.2 激活码生成与格式

- 格式：`VR-XXXXX-XXXXX-XXXXX-C`（3 组 5 位 Base32 大写 + 1 位校验位），约 75 bit 熵，暴力穷举与碰撞在现实中不可行。
- 生成：管理端批量生成（CSPRNG），支持指定套餐、有效期、备注（客户名）。
- 存储：`licenses.code` 以 Fernet 加密存储（复用现有 `settings.py` 加密栈），管理端可再次查看（运营需要给客户补发码）；同时存 SHA256 哈希列用于激活接口的快速索引。
- 激活接口对同一码的失败尝试限速（每 IP + 每码 10 次/小时），防止撞码。

### 3.3 硬件指纹

Tauri Rust 层采集（不经过 WebView，原始值不出现在前端 JS）：

| 平台 | 主因子 | 辅助因子 |
| --- | --- | --- |
| Windows | `MachineGuid`（HKLM\SOFTWARE\Microsoft\Cryptography） | 主板序列号（Win32_BaseBoard） |
| macOS | `IOPlatformUUID` | `IOPlatformSerialNumber` |

- 指纹 = `SHA256(主因子 + "|" + 辅助因子 + "|" + 服务端盐)`，盐在激活时由服务端下发（首次握手获取），指纹值本身不落地明文。
- Rust 实现建议：`machine-uid` crate（跨平台 MachineGuid/IOPlatformUUID）+ `sysinfo`（主板序列号），经 Tauri command 暴露给前端仅用于激活请求。
- **指纹漂移容忍**：重装系统（Windows 重装通常保留 MachineGuid 的场景除外）、换主板会导致指纹变化 → 走换绑流程（§3.5），不是自动失败。
- **诚实边界**：纯软件指纹可被虚拟机克隆/注册表复制欺骗。V1 接受该风险（密钥在云端，克隆指纹只能"共享次数"，无法偷密钥，且 `max_devices` 槽位使克隆同一指纹无增益——同一指纹并发会话会被服务端互斥下线）。V2 可选 USB 加密狗升级。

### 3.4 激活流程与设备令牌

```
客户端                                云端
  │ GET /api/public/handshake                    │ ← 下发指纹盐 + 服务端公钥(可选)
  │ ◄────────── salt ────────────────────────────│
  │
  │ POST /api/public/activate                    │
  │  { code, device_fingerprint,                 │
  │    machine_info(脱敏: OS版本/内存档位) }      │
  ├─────────────────────────────────────────────►│ 码有效? 未禁用? 未过期?
  │                                              │ 槽位未满?（或旧指纹换绑已批准）
  │                                              │ 事务: 建 device + 建 user
  │                                              │       绑定 license → ACTIVE
  │                                              │       若套餐含赠送次数 → CHARGE(gift)
  │ ◄── device_token + license 快照 ─────────────│
  │     (套餐/余额/过期时间/并发配额)              │
  │
  │ 此后所有请求带 X-Device-Token                 │
```

- **device_token**：随机 256 bit，服务端存哈希；长期有效但服务端可吊销（禁用设备/禁用激活码即时生效）。客户端用现有 `local_settings_key.py` 的 Keychain/DPAPI 封装保存在 OS 密钥库——**复用已有代码**。
- **令牌校验中间件**替换现有 `get_current_user` 的 env 身份逻辑：`X-Device-Token → device → license → bound_user_id → users 表`（返回现有 `CurrentUser` 结构，下游路由零改动）。
- **并发互斥**：同一 device_token 同时只允许 1 个活跃会话（登录踢下线语义），防一号多开。

### 3.5 设备生命周期与心跳

| 事件 | 行为 |
| --- | --- |
| 心跳 | 客户端每 5 分钟 `POST /api/device/heartbeat`（带指纹哈希）；服务端更新 `last_heartbeat_at`，可顺带推送"已被禁用/套餐变更"指令 |
| 指纹不符 | 心跳指纹与激活指纹不一致 → 403 拉黑该 token，需重新激活或换绑 |
| 远程禁用 | 管理端禁用 device 或 license → 心跳与下一个 API 请求立即 403 `LICENSE_DISABLED` |
| 换绑 | 管理端解绑旧指纹（码回到 ACTIVE 未绑定态）→ 客户端重新激活；每码换绑次数限 3 次/年（可配置），防"一号传着用" |
| 到期 | license/套餐过期 → API 拒绝新批次，存量任务继续跑完，数据只读 |

### 3.6 安全边界声明（能防什么 / 不防什么）

| 威胁 | 防护 | 残余风险 |
| --- | --- | --- |
| 提取 API Key 直连 Provider | 密钥不出云 —— **免疫** | 无 |
| 本地改余额/破解客户端计费 | 余额真源在云 —— **免疫** | 无 |
| 一码多机 | 硬件指纹 + 设备槽位 + 会话互斥 | 虚拟机克隆指纹可共享次数（见 §3.3） |
| 激活码泄露被他人抢注 | 首次激活即绑定；可加"激活码+客户姓名后缀"双因子（V1 可选） | 抢在客户前激活（运营可解绑重置） |
| 重放/中间人 | 全站 HTTPS + token 哈希存储 + 请求 nonce | 无（必须强制 HTTPS） |
| 服务端拖库 | 激活码 Fernet 加密、token/指纹哈希、密钥 Fernet | 运营方服务器运维责任 |

## 4. 计费方案

### 4.1 计费对象（V1 范围决策）

| 动作 | V1 | 理由 |
| --- | --- | --- |
| H3 视频生成（`generation-batches` 每条任务） | **按次扣费** | 主成本，用户明确要求"一条视频一个价" |
| 视频拆解 / 首帧 / 人物图 / 口播改写 | 免费（计入套餐定价成本） | 计费粒度太碎伤体验；流水表已预留 `billing_action` 字段，V2 可开差异化计费 |
| 云存储 | 免费（运营成本） | 量小 |

> 计费设计按"动作"建模而非硬编码视频：`wallet_transactions.billing_action ∈ {VIDEO_I2V, IMAGE_GEN, ANALYSIS, SCRIPT_REWRITE}`，V1 只启用 `VIDEO_I2V`，后续开闸零迁移。

### 4.2 套餐与定价

- **plan 核心字段**：`unit_price_fen`（单条视频价格，单位分，避免浮点）、充值档位（如充 100 元得 100 条、充 500 元得 550 条）、`gift_credits`（激活赠送）、次数有效期（V1 建议：永久）、`max_concurrent_tasks`（单 license 并发配额，见 §5.4）。
- **充值折算**：管理端录充值（金额 + 套餐）→ `credits = 金额 / unit_price × 档位折扣系数` → CHARGE 流水。价格调整只影响之后的充值，已购次数不贬值。
- **差异化定价（V2 预留）**：`generation_tasks` 已有 `resolution`（768P/1080P）、`output_duration_seconds`、`model` 字段，价格规则表可按这些维度配单价（如 1080P = 2 × 基准价）。V1 只按"条"一口价。

### 4.3 钱包模型

```sql
wallets: license_id (PK), balance_total(累计获得), balance_available(可用),
         balance_reserved(冻结中), version(乐观锁), updated_at
不变式: available + reserved <= total   （任何时刻成立）
```

扣费采用**预冻结-结算（reserve-settle）两阶段**模式，与任务生命周期同构：

### 4.4 流水类型（只追加，禁止 UPDATE/DELETE）

| 类型 | 触发点 | 关联 | 幂等保障 |
| --- | --- | --- | --- |
| `CHARGE` | 管理端充值录单 / 激活赠送 | recharge_order_id | 录单号唯一约束 |
| `RESERVE` | 批次创建时冻结 N 次 | batch_id | `idempotency_key`（复用现有批次幂等键！） |
| `SETTLE` | 任务 SUCCEEDED，冻结转实扣 | task_id | **task_id 唯一约束 → 物理防双扣** |
| `REFUND` | 任务 FAILED/CANCELLED/管理员确认不计费 | task_id | task_id + 退款类型唯一 |
| `ADJUST` | 管理员调账（必须填理由，进审计） | admin_user_id | 审计关联 |
| `EXPIRE` | 次数到期核销（V2 若启用有效期） | — | 定时任务幂等 |

### 4.5 扣费时序（与现有状态机逐态对齐）

```
POST /generation-batches (quantity=N, idempotency_key)
│
├─ [API 层，单事务]
│   1. 验设备令牌 → license ACTIVE 且未过期
│   2. SELECT wallet FOR UPDATE（乐观锁 version）
│   3. available >= N ? 不足 → 402 BALANCE_INSUFFICIENT（前端引导充值/联系运营）
│   4. available -= N; reserved += N   （RESERVE N 条流水，挂 batch_id）
│   5. 建批次 + N 个 PENDING 任务（现有 create_generation_batch 逻辑原样）
│   ※ 幂等：同 idempotency_key 重复提交 → 命中现有幂等分支返回原批次，不重复冻结
│
├─ [Worker 层，随任务状态推进]
│   PENDING → SUBMITTING → 提交 Provider
│       ├─ 提交成功 → QUEUED…RUNNING…ARCHIVING（冻结保持）
│       ├─ 提交失败（terminal）→ REFUND 1 次
│       └─ SUBMISSION_UNCERTAIN → 冻结保持，等待现有 reconcile 对账机制裁决
│
└─ [终态结算]
    SUCCEEDED          → SETTLE 1 次（reserved -= 1; total 不变）
    FAILED             → REFUND 1 次（provider 侧失败，全额自动返还）
    CANCELLED（未提交）→ REFUND 1 次
    CANCELLED（已提交）→ 不返还（provider 成本已发生；可按套餐配置）
    NEEDS_ATTENTION    → 默认扣费（视频已生成，成本已发生）
                          管理员"确认不计费" → REFUND（复用现有
                          billing_confirmation_status='CONFIRMED_NOT_CHARGED'
                          + 免费重试链路，语义完全现成）
    SUBMISSION_UNCERTAIN → reconcile 成功 SETTLE / 失败 REFUND
    重试任务（retry_of_task_id）→ CONFIRMED_NOT_CHARGED 分支已声明"不再计费"，
                                   新任务不再产生 RESERVE
```

**为什么冻结点在批次创建而不是提交成功时**：防止"余额 1 条却提交 10 条批次"的透支窗口；冻结失败即拒绝，语义对用户最直观（下单即占额，失败即返还）。

### 4.6 防双扣与对账

1. **物理防双扣**：`wallet_transactions(task_id, type)` 建唯一索引——同一任务永远只能有一条 SETTLE、一条 REFUND。
2. **批次级对账**：`批次 quantity == RESERVE 数 == SETTLE 数 + REFUND 数 + 在途冻结数`，不满足则批次进人工对账队列。
3. **日终对账任务**：`balance_available == Σ流水` 重算比对，漂移即告警（发管理端通知）。
4. **所有资金动作写 audit_logs**（复用现有审计表），充值/调账/退款均强制留痕。

## 6. 云端数据库新增表（DDL 草案）

```sql
CREATE TABLE plans (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    unit_price_fen INTEGER NOT NULL CHECK (unit_price_fen > 0),   -- 单条视频价格（分）
    gift_credits INTEGER NOT NULL DEFAULT 0,                      -- 激活赠送条数
    credits_validity_days INTEGER,                                -- NULL=永久
    max_concurrent_tasks INTEGER NOT NULL DEFAULT 2,              -- 单码并发配额
    discount_tiers_json TEXT NOT NULL DEFAULT '[]',               -- 充值档位折扣
    is_active INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE licenses (
    id TEXT PRIMARY KEY,
    code_encrypted TEXT NOT NULL,          -- Fernet，管理端可再查看
    code_hash TEXT NOT NULL UNIQUE,        -- SHA256(code)，激活接口索引
    plan_id TEXT NOT NULL REFERENCES plans(id),
    status TEXT NOT NULL DEFAULT 'UNUSED'  -- UNUSED/ACTIVE/DISABLED/EXPIRED
        CHECK (status IN ('UNUSED','ACTIVE','DISABLED','EXPIRED')),
    max_devices INTEGER NOT NULL DEFAULT 1,
    expires_at TEXT,
    bound_user_id TEXT REFERENCES users(id),
    remark TEXT,                           -- 客户名等运营备注
    rebind_count INTEGER NOT NULL DEFAULT 0,
    created_by_admin_id TEXT REFERENCES users(id),
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE devices (
    id TEXT PRIMARY KEY,
    license_id TEXT NOT NULL REFERENCES licenses(id),
    device_fingerprint TEXT NOT NULL,      -- salted SHA256
    machine_info_redacted TEXT,            -- OS 版本/内存档位（脱敏）
    status TEXT NOT NULL DEFAULT 'ACTIVE'  -- ACTIVE/DISABLED
        CHECK (status IN ('ACTIVE','DISABLED')),
    token_hash TEXT NOT NULL,              -- device_token 的哈希
    last_heartbeat_at TEXT,
    activated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (license_id, device_fingerprint)
);

CREATE TABLE wallets (
    license_id TEXT PRIMARY KEY REFERENCES licenses(id),
    balance_total INTEGER NOT NULL DEFAULT 0 CHECK (balance_total >= 0),
    balance_available INTEGER NOT NULL DEFAULT 0 CHECK (balance_available >= 0),
    balance_reserved INTEGER NOT NULL DEFAULT 0 CHECK (balance_reserved >= 0),
    version INTEGER NOT NULL DEFAULT 0,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CHECK (balance_available + balance_reserved <= balance_total)
);

CREATE TABLE wallet_transactions (
    id TEXT PRIMARY KEY,
    license_id TEXT NOT NULL REFERENCES licenses(id),
    type TEXT NOT NULL CHECK (type IN
        ('CHARGE','RESERVE','SETTLE','REFUND','ADJUST','EXPIRE')),
    billing_action TEXT NOT NULL DEFAULT 'VIDEO_I2V',
    amount INTEGER NOT NULL,               -- 正数；含义由 type 决定
    batch_id TEXT,                         -- RESERVE 关联
    task_id TEXT,                          -- SETTLE/REFUND 关联
    idempotency_key TEXT,                  -- 充值单号 / 批次幂等键
    reason TEXT,                           -- ADJUST 必填
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE (task_id, type),                -- 物理防双扣
    UNIQUE (idempotency_key, type)
);

CREATE TABLE recharge_orders (             -- 管理端人工录单（V1 无支付网关）
    id TEXT PRIMARY KEY,
    license_id TEXT NOT NULL REFERENCES licenses(id),
    plan_id TEXT NOT NULL REFERENCES plans(id),
    amount_fen INTEGER NOT NULL CHECK (amount_fen > 0),
    credits INTEGER NOT NULL CHECK (credits > 0),
    external_ref TEXT,                     -- 对公转账/微信收款凭证号
    status TEXT NOT NULL DEFAULT 'CONFIRMED',
    created_by_admin_id TEXT NOT NULL REFERENCES users(id),
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- generation_tasks 增列（一条迁移）:
--   license_id TEXT（冗余便于报表/配额过滤）
-- generation_batches 增列:
--   license_id TEXT
```

## 7. 实施路线图

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| **M1 云基座 + 激活闭环**（先行） | server 上云部署（含 PG 迁移或 SQLite 起步）、HTTPS、设备令牌中间件替换 env 身份、激活码表 + 激活/心跳接口、客户端激活页与令牌持久化、删除 loopback | 未激活客户端被拒；激活后全流程（Fake Provider）跑通；云端可禁用设备即时生效 |
| **M2 计费闭环** | wallets/流水表、批次冻结、终态结算/返还、CONFIRMED_NOT_CHARGED 衔接、余额接口与前端展示、充值录单、402 余额不足引导 | 并发提交不透支不双扣；FAILED 自动返还；日终对账零漂移；重试不重复扣费 |
| **M3 管理端后台** | 激活码批量生成/导出/换绑、套餐与定价、充值录单、设备管理、Provider 配置托管（Fernet 迁移至云端）、用量/收入报表 | 运营全程不碰数据库即可完成发码→充值→客服换绑；客户端设置页 Provider 表单移除 |
| **M4 生产加固** | 每 license 并发公平配额、心跳禁用推送、离线降级提示、单实例锁、备份恢复演练、压测（并发批次+Worker）、对账告警 | 10 客户并发压测通过；备份恢复演练通过；对账漂移告警可观测 |

依赖与顺序依据：M1 是不可绕过的地基（没有云端执行就没有真计费）；M2 依赖 M1 的令牌与批次链路；M3 与 M2 可部分并行（配置托管不依赖钱包）；M4 收尾。

## 8. 风险清单

| # | 风险 | 缓解 |
| --- | --- | --- |
| 1 | 云端单点故障 → 全客户不可用 | 每日备份 + 恢复演练（复用 backup.py 思路）；VPS 快照；后续可双机热备 |
