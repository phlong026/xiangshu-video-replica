# 上传时长门禁按场景分流与长视频本地抽音轨设计说明（2026-10-08）

## 需求

1. 上传接口上传超过 15 秒的视频会被拦截。**裁剪爆款（复刻）**仍须控制在 15 秒
   以内；**提取文案**放开 15 秒上限。
2. 大于 15 秒的视频用于提取文案时，客户端先**本地提取音频**，再拿音频去提取
   文案（原片不出本机）。

## 现状（改动前）

- 服务端 `media.py::probe_upload_completion` 在上传完成探测期无条件调用
  `validate_duration`（4–15 秒 + 0.1 秒容差），所有走 `/api/assets/upload-intent`
  的参考视频一律被拦。
- 上传意图已带 `purpose` 字段（`replica`=复刻 / `script`=文案素材），
  `persist_upload_completion` 用它决定是否自动入队视觉分析，但时长门禁没有用它。
- 文案提取链路（`script_from_audio` → ffmpeg 抽音轨 → ASR）自身无 15 秒限制；
  复刻分析入口（`analysis_duration_for_asset`）有独立的 15 秒二次校验。

## 改动总览

### 服务端（`server/app/media.py`）

| 点 | 改动 |
| --- | --- |
| `validate_duration` | 新增 `allow_long` 参数：`script` 只卡 4 秒下限（防损坏文件），放开 15 秒上限；报错文案按场景区分 |
| `probe_upload_completion` | 从 `PreparedUploadCompletion.purpose`（由 DB `metadata_json.upload_purpose` 带出）分流校验 |
| `validate_upload_request` | 改为 (content_type, 后缀) 成对白名单：`replica` 只放 MP4/MOV；`script` 额外放音频（`.m4a/.mp3/.wav/.aac`） |
| intent / persist 的 kind | 音频落 `reference_audio`（`reference_audio` kind 已在生成链路存在），视频仍为 `reference_video` |
| persist 的项目状态 | 仅视频置 `REFERENCE_READY`；文案音频不推进项目状态 |
| `is_project_source_asset`（新） | 上传完成链路认领 intent 资产用，认 `reference_audio`；下游视觉分析/首帧仍用 `is_reference_video_asset` 只认视频 |

复刻场景的时长守护不放松：>15.1 秒的资产在分析入口
`analysis_duration_for_asset` 依旧 422（"超过 15 秒上限，无法拆解"）。

### 桌面端 Rust（`client/src-tauri/src/viral_audio.rs`）

新增 `local_video_extract_audio` 命令：前端把视频字节经 **raw IPC** 直送
（WebView 拿不到本地文件路径；`InvokeBody::Raw` 之外一律 fail-closed），落临时
文件 → 复用既有 `extract_audio`（参数与服务端逐项一致：`-vn -ac 1 -ar 16000
-c:a aac -b:a 32k`）→ 回传音轨字节，临时文件无论成败都清理。ffmpeg 仍取随包
分发资源，缺包报明确错误。

### 前端（`client/src`）

- `viralCache.ts::extractLocalVideoAudio`：File → raw invoke → 包回
  `File（原名.m4a，audio/mp4）`；非桌面端抛错由调用方兜底。
- `MainPages.tsx::handleUploadFile`（首页上传，`purpose="script"`）：
  - `readVideoDuration` ≤ 15.1 秒 → 整片上传（现状，边界与复刻分析上限一致）；
  - > 15.1 秒 → 本地抽轨 → 只传音频（几百 KB）→ `createScriptFromAudioTask`
    消费音频资产；
  - 读不出时长 / 非桌面端 / 抽轨失败 → 回退整片上传（服务端 script 已放开）。
- `api.ts::contentTypeForFile` 扩展音频映射；首页提示文案同步更新。
- 复刻准备页（`CreationPages.tsx`）的本地 4–15 秒预检**保持不变**（复刻场景）。

## 音频/视频是否会进素材库——不会

素材库与这条链路是**两套资产体系**：

| | 素材库（material_routes） | 本链路（assets/upload-intent） |
| --- | --- | --- |
| 归属 | `assets.project_id = NULL`，归入素材组（"参考素材"等），带 title/group/tags | 挂在**项目**下（`project_id` = 上传时创建的项目） |
| 入口 | 素材库页上传、人物/口播参考 | 首页/项目页上传参考视频 |

因此：

- **抽出的音频**：作为该项目的 `reference_audio` 来源资产存在，只服务文案提取
  （script-from-audio 任务的 `source_asset_id`），**不进素材库**。
- **原视频（>15 秒）**：本地抽轨后**根本不上传**，服务端无副本；Web 端兜底路径
  才整片上传（≤50MB），也只落项目资产。
- **转写中间产物**：服务端抽出的临时音轨对象沿用既有生命周期管理（任务级临时
  对象），与素材库无关。

若后续希望音频沉淀进素材库（跨项目复用），那是新需求：素材库上传走
material_routes 且 project_id 为 NULL，需要单独打通"素材资产作为文案提取来源"
的归属校验，当前设计有意不做。

## 测试

- 服务端 `server/tests/test_media_duration_gate.py`（18 例）：时长分流、报错文案
  区分、音频仅 script 放行、(类型, 后缀) 混搭拦截、探测期 script 放行 45s /
  replica 仍拦。
- Rust：`extract_audio_from_bytes` 临时目录清理与 ffmpeg 缺失报错路径。
- 前端 `MainPages.test.tsx`：>15s 抽轨后只传音频且 `purpose="script"`、上传时序
  改造后的会话作废语义；文案断言同步更新。

## 已知边界

- sha256 复用路径（`reuse_owned_completed_upload`）仍只匹配 `reference_video`：
  同一长视频先以 script 上传、再在项目页以 replica 上传时会命中复用，复刻分析
  入口会给出"超过 15 秒上限"的明确报错，属可接受闭环。
- 抽轨判定用前端 `readVideoDuration`（浏览器解码），读不出的文件回退整片上传，
  由服务端 ffprobe 统一裁决。
