# 账号诊断功能：市场调研、方法论与落位方案

> 日期：2026-11-20  
> 需求：用户输入自己的账号主页链接，系统对该账号做多维度分析并给出诊断报告。  
> 本文只做调研与方案，不含代码改动。

---

## 0. 一句话结论

- **产品形态**：不是"再做一个数据看板"，而是"**一次输入 → 100 分体检报告 → 直接衔接到复刻/文案生产**"。这是我们相对新抖/飞瓜/蝉妈妈的差异化：它们止于报告，我们止于产出。
- **落位**：客户侧「创作」组新增一级入口 **账号诊断**，排在「爆款视频」之后；工作台输入区下方加一个轻量次级入口引流。不建议放进「资产」或「分发」。
- **方法论**：开源社区已有一套可直接照搬的成熟 rubric（抖音六维 100 分制 + S/A/B/C 量级自适应基准 + 六类风险预警），比我们自己拍脑袋设计靠谱得多；LLM 只负责"解读与建议"，打分必须用确定性算法。
- **最大约束不在算法，在数据**：纯公开数据拿不到播放量、完播率、粉丝画像。因此 P0 只能做"公开数据体检"（互动口径），要达到新抖级别的深度必须让用户导入创作者后台数据（P1）或走官方授权（P2）。这一点必须在产品文案里说清楚，否则诊断结论会被质疑。

## 1. 市面同类功能方案

### 1.1 国内（抖音/小红书生态）

| 产品 | 定位 | 账号诊断相关能力 | 对我们的启示 |
|---|---|---|---|
| **新抖**（新榜） | 抖音全场景数据 | 达人对比（多账号）、粉丝画像与粉丝趋势、从"粉丝/作品/商品/直播"四方向做商业价值评估 | "四方向 + 画像"是最早被市场接受的信息架构；对比功能是刚需 |
| **蝉妈妈** | 直播电商数据 | 搜账号即可看：近 7/30 天趋势、粉丝活跃时段、作品横向对比（爆款 vs 拖后腿）、粉丝画像（性别/年龄/地域/兴趣）、AI 账号分析 | **"作品横向对比"**是最有价值的单点功能，实现成本低、用户感知强 |
| **飞瓜数据** | 抖音/快手/B站 | 达人分析（追溯近 3 年数据）、粉丝画像、每日涨粉趋势、热榜/涨粉榜、竞品对比 | 涨粉趋势依赖"历史快照"，必须从第一天开始存快照 |
| **抖查查** | 短视频+直播 | 明确提供"诊断与陪跑"服务，覆盖达人/视频/直播/商品多域，支持导出与 API | 诊断可以做成"报告 + 人工陪跑"的服务包 |
| **千瓜** | 小红书 | 千瓜指数 = 达人活跃度 + 创作能力 + 粉丝质量 三维；AI 内容诊断报告 | 指数化（单一分数）比堆指标更易传播 |
| **灰豚数据** | 抖音/快手/小红书 | 自动生成**账号健康度评分**，与竞品多维对标；5 大分析域 | "健康度评分 + 分档评级"是行业通用表达 |

共同特征：**搜索账号 → 总分/评级 → 分维度拆解 → 与同量级或竞品对比 → 优化建议**。没有一家是"只给一堆图表"。

### 1.2 海外（TikTok / YouTube）

| 产品 | 能力结构 | 启示 |
|---|---|---|
| **HypeAuditor** | 免费 TikTok Audit + 付费 35+ 指标；**Audience Quality Score（1–100，由 15 个指标、4 组构成）**；假粉/互赞群/异常增长检测；EMV、报价估算 | "单一可信分数 + 分项解释"是说服力最强的形态；真实性/刷量检测是付费点 |
| **Modash** | 达人发现 + 受众真实性评分 + Shopify 集成 | 诊断和"找达人/投流"可以连成工作流 |
| **vidIQ Channel Audit** | VPH（每小时播放）、互动率、涨粉、观看时长、留存、Top 播放列表/搜索词、**按优先级排列的修复清单**；对比上一周期 | **"优先修复清单"比分数更有行动价值**，我们应该直接抄这个输出结构 |
| **TubeBuddy Health Report** | 近 30 天播放/涨粉、受众人口属性/设备/地域、流量关键词环比 | 环比是诊断的灵魂，没有对照就没有结论 |

### 1.3 市场空位（我们的机会）

1. **"诊断 → 拆解 → 复刻 → 发布 → 再诊断"闭环**：所有竞品都断在报告页，我们天然有后半段生产能力。
2. **报告里的每一条短板都能一键变成任务**：例如"互动率低"→ 打开文案工坊；"爆款集中在单一选题"→ 打开该类爆款列表；"更新频率低"→ 生成排期。
3. **中文语境 + 自有积分体系**：可按次计费（5–10 积分），比竞品年费订阅更轻。

## 2. 开源仓库里的账号诊断方法论

### 2.1 最强参考：redfox-data/redfox-community `douyin-account-diagnosis`

仓库：https://github.com/redfox-data/redfox-community/tree/main/skills/douyin-account-diagnosis  
输入账号昵称/抖音号 → 拉取账号画像 + 近期作品 → 六维打分 → 100 分制四级评级 + 六类风险预警 + 报告。

**六维权重与满分**

| 维度 | 满分 | 权重 | 子项 |
|---|---|---|---|
| 账号基础画像 | 8 | 10% | 头像、简介、地域完整度、抖音号（性别/年龄只展示不计分） |
| 内容生产力 | 15 | 15% | 作品总量、人均获赞、发布频率 |
| 互动健康度 | 30 | 30% | 粉丝获赞比、粉丝互动率、互动结构比、作品均互动 |
| 内容质量 | 20 | 20% | 爆款率、中位/均值偏离、互动稳定性 CV、零互动占比 |
| 内容趋势 | 15 | 15% | 近期趋势、爆款集中度、最新活跃度 |
| 粉丝质量 | 10 | 10% | 粉丝规模、粉丝互动比、获赞/粉丝背离 |

**量级自适应基准（关键设计：同一指标对不同粉丝量要给不同标准）**

| 量级 | 粉丝数 | 互动率 优秀/良好/偏低 | 爆款线（单条赞/粉丝） | 均互动强传播线 | 作品总量高产线 | 人均获赞高效线 |
|---|---|---|---|---|---|---|
| S 超头部 | ≥100万 | 2.0% / 1.2% / 0.6% | 1.0% | 10万 | 150 条 | 200,000 |
| A 头部 | 10万–100万 | 4.0% / 2.5% / 1.2% | 2.0% | 2万 | 600 条 | 15,000 |
| B 腰部 | 1万–10万 | 6.0% / 4.0% / 2.0% | 5.0% | 5000 | 300 条 | 3,000 |
| C 尾部 | <1万 | 8.0% / 5.0% / 2.5% | 10.0% | 1000 | 100 条 | 1,000 |

**评分规则要点**

- 维度归一化分 = 维度得分 ÷ 维度**有效**满分 × 100；综合 = Σ(归一化分 × 权重)，四舍五入取整。
- **有效满分**：样本退化（如 2 条样本时中位数恒等于均值）或 0/0、字段缺失的子项从分母剔除，报告标"(不计入)"；账号确认无作品则按最低档计 0 分且不剔除（"没内容"本身是负面信号）。
- 剔除门槛：中位/均值偏离需 n≥3；爆款集中度/互动稳定性/发布频率需 n≥5；趋势需满 3 天作品 ≥4 条；样本 <5 条输出"数据置信度"提示。
- 评级：85–100 优质 / 70–84 正常 / 50–69 待优化 / <50 风险。
- 趋势类只比较"已发布满 3 天"的作品（避免新作品数据未稳定造成误判）。

**六类风险预警**

| 类型 | 条件 | 等级 |
|---|---|---|
| 僵尸粉 | 粉丝互动率 < 本量级偏低线 且 粉丝 > 5 万 | 高危 |
| 刷量 | 获赞/粉丝 > 100 且 近期互动骤降 | 高危 |
| 衰退 | 近期均互动 < 早期 50%（成熟作品 ≥4 条） | 中危 |
| 限流 | 零互动占比 > 30% | 中危 |
| 断更 | 最新作品距采集 > 14 天 | 中危 |
| 单条依赖 | 最大爆款互动 > 均值 10 倍 | 低危 |

**报告结构**：总结句（昵称+分数+评级）→ 基本信息表 → 六维评分表（核心短板加粗）→ 风险预警 → 关键发现（每条带数据佐证）→ 近期作品明细（可点击）→ 优化建议（按优先级）→ 注明适用基准线。

> 这套 rubric 的工程价值：**全部是公开可得字段**（昵称、简介、粉丝数、获赞总数、作品数、每条点赞/评论/分享/收藏、发布时间），不依赖播放量和粉丝画像——正好匹配我们 P0 的数据条件。

## 3. 我们产品的可行方案

### 3.1 数据源三条路（这是最关键的技术决策）

| 方案 | 能拿到什么 | 成本 | 合规/门槛 | 建议 |
|---|---|---|---|---|
| **A. 公开数据（TikHub）** | 主页资料、粉丝/获赞/作品数、近 20–40 条作品的赞评转藏、发布时间、标题话题 | 约 $0.001/次主页 + 作品列表调用，一次诊断 ≈ 2–4 次调用 ≈ **¥0.02–0.05** | 需已配置 tikhub 供应商；当前 `VIDEO_REPLICA_VIRAL_CLIENT_DISABLED=1` 全局下线，需为诊断单独开开关 | **P0 采用** |
| **B. 用户导入创作者后台数据（Excel/截图）** | 播放量、完播率、涨粉明细、粉丝画像（性别/年龄/地域/兴趣）、流量来源 | 0 增量成本，纯解析 | 用户操作成本高；需适配多种导出格式 | **P1 作为"深度诊断"加分项**（DashPersona 已验证可行） |
| **C. 抖音开放平台 OAuth** | 官方最全、最准 | 需应用资质、用户逐账号授权 | 审核周期长、门槛高 | **P2，不做短期依赖** |

**结论**：P0 用 A 做"公开数据体检"，报告里如实标注"未含播放量/完播率/粉丝画像"。这既是诚实，也是 P1 的转化钩子（"想看更深的？导入后台数据"）。

现有代码可直接复用的部分：
- TikHub 客户端骨架与计费计量：`server/app/viral_tikhub.py`（BEARER、超时、备用通道、`meter_call("viral_data")`），但目前只接了 3 个搜索/详情路径，**没有用户主页与作品列表接口**，需要新增：
  - `GET /api/v1/douyin/web/handler_user_profile?sec_user_id=...`
  - `GET /api/v1/douyin/app/v3/fetch_user_post_videos?sec_user_id=...&max_cursor=0&count=20&sort_type=0`
  - 小红书对应 `xiaohongshu/app_v2/get_user_posted_notes` + 用户信息接口
- 链接解析：`server/app/viral_link.py` 现在只认单条视频链接（`/video/{id}`、`modal_id=`），**账号主页链接 `douyin.com/user/{sec_uid}` 会被判为"没有可用视频"**，需要新增"账号链接 → sec_uid"识别分支（纯字符串解析，不调上游）。
- 任务/计费骨架：`usage_billing.accept_operation` / `finish_source`、`billing_catalog.SERVICES`、worker 轮询（参考 `replica_prompt` 任务族）。
- LLM 结构化输出：沿用 `json_object` + 宽容解析 + 空壳检测（2026-11-20 空壳事故的结论：**不要给顶层宽松 json_schema**）。

### 3.2 诊断指标体系（P0，适配公开数据）

完全采用 2.1 的六维 rubric，只做两处必要调整：

1. **"粉丝质量"降级为代理评估**：无粉丝画像，"粉丝规模/粉丝互动比/获赞粉丝背离"仍可算，但文案必须写"基于公开互动数据的代理指标，非平台粉丝画像"。
2. **刷量/僵尸粉判定加置信度**：公开数据只能给"疑似"，输出为"风险提示"而非结论，并给出判定依据（例如获赞/粉丝 >100 且近 10 条均互动较前 10 条下降 >50%）。

新增两个我们独有的维度（放在报告"关键发现"里，不计入 100 分，避免污染可比性）：
- **赛道与选题结构**：标题/话题标签做 31 类目归类，输出选题占比与"爆款选题 TOP3"。
- **可复刻度**：结合我们已有的视频拆解能力，标注哪几条作品最适合一键复刻（时长、口播/剧情、是否真人出镜）。

### 3.3 产品流程

```
输入账号链接/抖音号
  → 解析 sec_uid（本地正则，不调上游）
  → 拉主页 + 近 20~40 条作品（2~4 次上游调用，10s 内）
  → 确定性打分（纯函数，可单测、可回归）
  → LLM 生成解读与建议（失败可降级为模板文案，不阻塞报告）
  → 报告页：总分 + 评级 + 六维雷达 + 风险卡 + 作品明细 + 优先修复清单
  → 行动按钮：拆解爆款作品 / 生成同类选题文案 / 查看同赛道爆款 / 再诊断（7 天后提醒）
```

**关键交互决策**：
- 首次诊断即时出分（不等 LLM），报告骨架先渲染，解读段落渐进出现。
- 同一账号 24h 内重复诊断走缓存（对齐 TikHub `cache_url` 24h 免费重读），避免重复扣积分。
- 报告永久保存并生成"历史分数曲线"——这是用户留存和二次付费的抓手（新抖/飞瓜的核心粘性也在这里）。

### 3.4 计费与使用门禁（2026-11-20 定案）

**规则**

1. **新用户首单免费**：每个客户账号在整个生命周期内免费 1 次，不论诊断几个账号。
2. **之后必须是付费会员**：判定口径 = 该客户存在一笔 `status='PAID'` 的充值订单，且该订单来自后台配置的充值套餐（`package_id` 非空）并且该套餐**到账积分 > 0**（读冻结的 `package_snapshot_json.credits`，不读当前套餐配置，避免后台改价影响历史判定）。赠送/补偿类 0 元订单不算。
3. **会员每次仍扣积分**：单次消耗 = `account_diagnosis` 计费科目的售价，**由管理员在「价格与套餐 → 逐项成本与售价」后台填写**，默认 8 积分。
4. **第二次使用时**：客户端收到 `ACCOUNT_DIAGNOSIS_MEMBER_REQUIRED` 或 `INSUFFICIENT_CREDITS`，直接弹出充值对话框（复用 `CustomerRechargeDialog`），而不是只跳钱包侧栏。

**判定顺序（服务端，入队前一次性完成）**

```
1. 免费额度未使用 → 原子占用（UPDATE users SET ... WHERE 未使用）→ 放行，扣 0 积分
2. 无付费套餐     → 402 ACCOUNT_DIAGNOSIS_MEMBER_REQUIRED → 前端弹充值
3. 有付费套餐     → accept_operation(account_diagnosis) 扣积分
4. 余额不足       → 402 INSUFFICIENT_CREDITS → 前端弹充值
```

**细节**

| 项 | 规则 |
|---|---|
| 免费额度占用时机 | 入队时原子占用，避免并发双开；任务失败（上游异常）时归还，保证"失败不消耗免费次数" |
| 缓存重读 | 同一账号 24h 内的报告直接返回，不占免费额度、不扣积分 |
| 供应商成本 | 约 ¥0.02–0.05/次（TikHub），毛利充足 |
| 新计费科目 | `account_diagnosis`（provider=tikhub, module=account） |
| 失败策略 | 上游失败全额退回（沿用 `finish_source`）；"账号不存在/私密/无作品"属于有效结果，正常计费 |
| 防刷 | 免费首单按客户计；建议叠加设备/手机号维度限流（桌面端已有设备管理，可复用），否则批量注册可刷免费额度 |
| 并发 | 单客户同时 1 个诊断任务，超出排队 |

### 3.5 字段 → TikHub 接口映射（2026-11-20 核实）

用户已确认"缺字段可直接调 TikHub 对应接口"，据此逐字段核实如下。

**基础链路（走公开接口，普通账号可用）**

| 报告字段 | TikHub 接口 | 价格 | 可靠性 |
|---|---|---|---|
| 昵称/头像/简介/地域/抖音号/粉丝数/获赞总数/作品数 | `GET /api/v1/douyin/web/handler_user_profile?sec_user_id=` | ~$0.001 | 高 |
| 作品列表 + 单条点赞/评论/分享/收藏/时长/发布时间/标题话题 | `GET /api/v1/douyin/app/v3/fetch_user_post_videos?sec_user_id=&max_cursor=0&count=20` | 按次 | 高（count 上限 20，取 2 页） |
| 单条播放量 | `GET /api/v1/douyin/app/v3/fetch_video_statistics` | ~$0.002 | **中**：抖音官方对"他人视频"普遍不返回 `play_count`，可能为 null/0 |
| 批量播放量（≤50 条） | `GET /api/v1/douyin/app/v3/fetch_multi_video_statistics` | ~$0.025 | 同上；能取到的都是有效值，取不到就是 null |

**增强链路（走星图接口，仅覆盖已入驻星图的达人）**

| 报告字段 | TikHub 接口 | 价格 | 前提 |
|---|---|---|---|
| sec_user_id → 星图达人 ID | `GET /api/v1/douyin/xingtu/get_xingtu_kolid_by_sec_user_id` | ~$0.001 | 账号需在星图有收录 |
| 达人基础商业信息 | `GET /api/v1/douyin/xingtu_v2/get_author_base_info?o_author_id=` | ~$0.001 | 同上 |
| **播放量、完播率、互动率**（逐条） | `GET /api/v1/douyin/xingtu_v2/get_author_homepage_videos?o_author_id=`（返回 `watch_cnt` / `finish_rate` / `interact_rate`） | $0.002 | 同上；V1 版同能力 $0.02，不要用 |
| **粉丝画像**（性别/年龄/地域/兴趣/设备） | 星图达人画像接口（同一 `o_author_id` 体系） | 待实测确认路径 | 同上；需 TikHub 账号具备对应端点权限 |

**结论与工程含义**

1. **P0 完全可行**：即使播放量、完播率、粉丝画像全部缺省，六维 rubric 的 30 个子项也能全部计算（它本来就只用粉丝数与互动量做分母）。
2. **"能取就升级"策略**：先调基础链路出报告；若 `get_xingtu_kolid_by_sec_user_id` 命中，再追加星图和画像数据，把"互动健康度/内容质量"的口径从"互动代理"升级为"播放/完播真实口径"，报告标注数据等级（L1 公开 / L2 星图）。
3. **不要串行等**：星图链路失败不能阻塞报告；设计成"基础报告先出，增强字段后到就补，不到就标『未获取』"。
4. **成本**：L1 ≈ 3 次调用（¥0.02 级）；L2 追加 3 次（¥0.03 级），总成本仍在 ¥0.05 以内，8 积分定价毛利充足。
5. **待实测项**：①`fetch_user_post_videos` 返回的 `statistics` 里 `play_count` 实际是否为空；②普通非星图账号调 `get_xingtu_kolid_by_sec_user_id` 的返回形态；③粉丝画像端点的确切路径与权限要求。上线前用 3 个真实账号（头部/腰部/尾部）各跑一次探针并留档。

## 6. 风险与注意事项

1. **数据口径风险（最高）**：公开数据没有播放量，所有"率"都必须用粉丝数或互动量做分母，报告中必须显式注明口径。否则用户会拿它和新抖对比后质疑数据准确性。
2. **平台合规**：只采集公开主页与公开作品；控制频率（单账号单日 ≤3 次）；不存储用户身份信息；报告页注明数据来源与采集时间；遵守平台条款与 robots。
3. **供应商单点**：TikHub 当前处于"爆款线已下线"状态，诊断若依赖它，需明确 SLA 与备用通道（客户端已支持 `backup_base_url`）。建议上线前做一次真实账号的端到端探针，确认 `follower_count / total_favorited / aweme_count` 与作品 `statistics` 字段齐全。
4. **误判成本**：刷量/僵尸粉判定只输出"疑似 + 依据"，不输出定性结论；评分必须附带"本账号适用基准线"与样本量提示。
5. **LLM 不稳定**：解读段落用 `json_object` + 宽容解析 + 空壳检测；LLM 失败时用模板文案兜底，**绝不能让 LLM 失败导致整份报告不可用**。
6. **计费争议**：账号不存在、私密账号、无作品都属于"有效结果"，需在产品文案与退款规则里写明，避免客服争议。
