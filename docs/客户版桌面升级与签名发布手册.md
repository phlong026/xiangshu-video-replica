# 客户版桌面升级与签名发布手册

本手册覆盖 Windows NSIS、macOS Apple Silicon / Intel 的正式制品、启动自动更新和服务器发布。业务 API 的增量部署另见《生产服务器增量部署手册.md》。

## 更新链路

- 客户端界面打开后自动检查更新，未登录也会检查。启动检查失败会短暂等待后重试一次，下一次启动仍会检查。
- 更新入口和弹窗由 `RootApp.tsx` 的 `CustomerShell` 挂载，沿用 `appUpdate.tsx` 和官方 Tauri updater。登录切换、StrictMode 和手动入口共用更新状态，避免重复下载、安装。
- 发现更高版本后显示下载进度，自动下载、验证 minisign 签名并安装。Windows 安装器使用现有 passive 更新方式并重新拉起应用；macOS 替换应用后调用重启命令。
- 检查失败不阻止登录或使用软件。个人中心保留“检查更新”及手动重试入口。浏览器网页不执行桌面更新。
- 当前版本来自安装包的 Tauri/package 元数据；新版本来自 `https://<正式域名>/downloads/customer-cloud/stable.json`。

## 一、信任材料与环境

生产更新公钥固定在 `client/src-tauri/tauri.customer.conf.json`。新的 Mac 构建使用相同公钥；正式构建必须注入真实更新端点，不能把 `staging.example.invalid` 编入交付包。

签名机复用现有 updater 私钥、密码和 Windows Authenticode 证书。私钥只进入签名进程环境，不进入仓库、日志、临时配置或 GitHub Actions。不要每次发版重新生成密钥，否则已安装的 Windows 客户端无法验证新包。

| 环境变量 | 用途 |
| --- | --- |
| `VIDEO_REPLICA_RELEASE_SIGN_THUMBPRINT` | 已安装的 Windows 代码签名证书指纹 |
| `VIDEO_REPLICA_RELEASE_EXPECTED_SIGNER` | 可选，期望证书主题子串 |
| `VITE_API_BASE_URL` | 正式 HTTPS 云端 origin，例如 `https://video.zszhj.cn` |
| `TAURI_SIGNING_PRIVATE_KEY` | 已安全注入的 updater 私钥内容 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 已安全注入的私钥密码 |
| `CARGO_TARGET_DIR` | 可复用的纯 ASCII 构建目录，避免中文路径导致 Windows 原生归档失败 |

Windows 正式构建使用 PowerShell 7（`pwsh`）。既有本机证书的 Authenticode 检查必须为 `Valid`；不能将 CI 的 unsigned Windows 安装器作为正式包。时间戳服务不可用时，脚本已有 `-TimestampUrl ''` 应急选项，发行记录会保留该选择。

macOS 当前采用既有 ad-hoc / 未公证构建方式，须在发行元数据中如实记录；用于自动更新的 minisign 签名与 Apple Developer ID、公证是不同机制。

## 二、版本与源码

从最新 main 创建独立发版 worktree。版本需同步 9 个文件、11 个值：

- 根 `package.json`、`client/package.json`。
- `package-lock.json` 的顶层、`packages[""]`、`packages.client` 三处。
- `client/src-tauri/tauri.conf.json`、`Cargo.toml`、`Cargo.lock` 的桌面项目版本。
- `server/pyproject.toml`、`server/uv.lock` 的 API 项目版本，以及 `server/app/main.py` 的 API 版本。

Windows 和两套 Mac 制品必须来自相同的已提交源码 SHA。构建前提交修改，Windows 正式入口会拒绝有 tracked changes 的源码。发行记录的 `source_sha` 应保留真实构建提交，不得为了匹配 squash SHA 而伪改。

可在 PR CI 等待期间构建同一 head；正式发布前必须确认 CI 已通过且源码已合入 main。若为 squash 合并，再核对构建提交与合并提交的源码树一致。后续若修复了代码，应重新构建受影响制品，不复用旧包。

## 三、Windows 正式构建

入口为 `scripts/release/build-customer-signed-release.ps1`，也可通过 `npm run release:customer` 调用。多行更新日志应直接通过 PowerShell 传入，避免 npm/cmd 参数链截断：

```powershell
$notes = [System.IO.File]::ReadAllText('E:\release-input\notes.txt')
& .\scripts\release\build-customer-signed-release.ps1 `
  -OutputRoot 'E:\release-output\windows' `
  -ReleaseNotes $notes
```

先按上表安全注入签名环境。输出目录为 `<OutputRoot>/customer-cloud/<version>/`，包含：

- Windows `.exe`、`.exe.sig`。
- Windows `stable.json`。
- `SHA256SUMS.txt`、`release-manifest.json`（含真实 `source_sha`、Authenticode 和 updater 信息）。

构建门禁会检查版本、正式 origin、公钥、真实应用二进制中的 updater endpoint、Authenticode 签名及 updater sidecar。安装包和更新签名是两类独立检查。

## 四、Mac 构建与三平台汇总

`Desktop installers` workflow 生成 Apple Silicon、Intel 的 DMG 与 `.app.tar.gz`。正式 Mac 构建覆盖生产 endpoint、公钥及架构信息，CI 不接收 updater 私钥。

通过已认证 GitHub API 获取指定运行、源码 SHA 和 artifact digest；下载制品到独立空目录，核对归档 digest 后再提取。下载地址跳转到其他主机时，不携带 GitHub Authorization。制品只作为数据，不执行归档中的脚本。

在签名机执行发行汇总入口：

```powershell
& .\scripts\release\finalize-customer-release.ps1 `
  -WindowsReleaseDir 'E:\release-output\windows\customer-cloud\2.6.8' `
  -MacArtifactsDir 'E:\release-input\verified-mac-artifacts' `
  -ExpectedCommit '<已核对的40位构建SHA>' `
  -Version '2.6.8' `
  -MacArm64ManifestSha256 '<受信下载记录中的arm64清单SHA256>' `
  -MacX64ManifestSha256 '<受信下载记录中的Intel清单SHA256>' `
  -Origin 'https://video.zszhj.cn' `
  -OutputDir 'E:\release-output\customer-cloud\2.6.8'
```

汇总器复查 Windows 签名、两套 Mac 的来源/版本/架构/端点/公钥和哈希，使用本机既有密钥为 Mac 更新归档生成 `.sig`，并独立进行密码学验签。两个清单 SHA 必须来自已校验的 CI 下载记录，不能把可变提取目录的自报字段作为信任锚。

最终目录平铺 8 个制品：Windows exe/sig，以及每套 Mac 的 DMG、app.tar.gz、app.tar.gz.sig；另有统一 `stable.json`、`release-manifest.json`、`SHA256SUMS.txt`。

统一更新平台键：

| 平台 | 更新制品 | 首装制品 |
| --- | --- | --- |
| `windows-x86_64` | `.exe` | 同一 `.exe` |
| `darwin-aarch64` | Apple Silicon `.app.tar.gz` | 对应 DMG |
| `darwin-x86_64` | Intel `.app.tar.gz` | 对应 DMG |

`stable.json` 的 signature 为对应 `.sig` 的完整 UTF-8 原文，外层必须是无空白的 canonical Base64；不允许附加 LF、CRLF 或前导空格，以匹配客户端严格解码。schemaVersion=2 的发行记录保留旧 Windows 字段，新增三平台映射和受控 assets 列表；SHA256SUMS 覆盖 8 个制品、stable 与发行记录，不包含校验和文件自身。

不要将正式签名目录交给 `prepare-desktop-release.py`；该工具仅处理 `internal-test-unsigned` 预览包。

## 五、服务器发布

真实通道目录为：

```text
/opt/video-replica/app/desktop-releases/customer-cloud
```

nginx 的 `/downloads/customer-cloud/` alias 必须指向该目录，stable 清单应保持不缓存或需重新验证的缓存策略。不要放在 SPA 站点根目录下，业务 rollout 会清空站点根目录。

将完整正式目录上传至服务器隔离 staging，逐文件核对哈希。服务器需要现有 `bash`、Python 3、OpenSSL、flock、curl 和 SHA256 工具；只使用固定的生产公钥验签，不接受发行目录自报公钥作为信任锚：

```bash
deploy/customer-desktop-release.sh \
  --channel-root /opt/video-replica/app/desktop-releases/customer-cloud \
  --public-key '<仓库固定的Tauri生产公钥>' \
  --release-dir /tmp/desktop-release-2.6.8
```

也可显式设置 `VIDEO_REPLICA_DESKTOP_CHANNEL_ROOT` 与 `VIDEO_REPLICA_DESKTOP_UPDATER_PUBLIC_KEY`。`VIDEO_REPLICA_SITE_ROOT` 仅保留旧环境兼容，正式发布应明确指定通道目录。

发布器取得独占锁，校验全平台清单、文件白名单、哈希和签名，将完整新版本目录落位，最后原子切换 `stable.json` 并通过 HTTPS 回读。保留上一份清单及版本制品；同版制品不覆盖。既有 Windows-only 版本仍可验证和回滚。

## 六、验收与回滚

- 受影响的 updater 与登录入口测试通过；完成 PR CI 和合并后 main CI。
- 对比签名机、服务器、公开下载的资产哈希，检查三平台 URL、版本、签名和实际二进制端点。
- 在可用桌面测试环境验证自动检查、下载安装、重启和版本显示；未能执行的操作系统真机项如实记录，不能用 mock 测试代替真实安装结果。
- 单独验证正式公网 health、客户端/管理端 bundle；API 随版本部署时复查资金对账。
- 回滚清单使用相同通道和固定公钥参数：

```bash
deploy/customer-desktop-release.sh \
  --channel-root /opt/video-replica/app/desktop-releases/customer-cloud \
  --public-key '<仓库固定的Tauri生产公钥>' \
  --rollback '<旧版本>'
```

回滚只影响尚未升级的客户端。已升级客户端不会自动降级，故障应发布更高版本修复。不要删除当前版本与回滚所需的旧版本制品。

## 七、旧客户端首次引导

Windows 2.6.6/2.6.7 已有正确更新地址，可收到新版，但首次接收仍受旧程序“登录后、每日一次”的检查时机影响，可通过个人中心手动检查提前升级。

内置占位更新地址、尚无 updater 的旧 Windows，以及本次修复前的 Mac 包，无法仅靠替换服务器清单修正。需要手动安装一次 2.6.8 修复版，此后沿用新版每次启动的自动更新流程。
