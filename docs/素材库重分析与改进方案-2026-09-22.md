## 0. 结论速览

1. 素材库"能用"阶段已完成：统一 API、上传闭环、24/页分页、视频缩略图、批量授权、失败自动重试均已落地（#143/#145/#163）。当前主要矛盾已从"能不能用"转向 **"找得到、管得住、用得快"**。
2. 五个结构性问题（按影响排序）：
   - **分组没有实体**：group 是自由文本 + 逐素材覆盖，没有分组列表/筛选/批量移动，改 20 个素材的分组要点 20 次；
   - **项目维度缺失**：素材库里看不到"哪些素材属于哪个乡墅项目"，而这正是营销团队最强的组织心智；
   - **无批量操作 / 无排序 / 无标签**：素材一多就退化为一条长河；
   - **设计稿已画、代码未实现**：新建分组、排序、网格/列表切换、上传时间、归属人物名（V1.4 审核稿全部已有设计，代码 0 实现）；
   - **与创作流衔接浅**：快捷动作藏在详情面板、切页丢状态、卡片缺时长/时间信息。
3. 同行（字节 Seedance 素材库、Eagle、新榜矩阵通、剪映、扣子）的共性答案：**文件夹 + 标签双体系、多维检索、批量操作、一键调用到创作、AI 自动标引**。建议按 P0（组织与效率）→ P1（结构与衔接）→ P2（智能化与生命周期）三阶段推进，P0 预计 1–2 个任务即可显著改变体验。

**（2026-09-22 追加：§6 显示尺寸与横竖屏、§7 素材云存储上传策略）**

4. **显示尺寸（§6）**：卡片媒体区是固定 140px 视窗，内部一律按 9:16 框渲染后被裁切——**竖屏素材（本产品素材大头）在网格里只显示中段约 37%**，横屏反而基本完整；数据层没有宽高比字段，图片也没有派生缩略图。修复方向：fitContainer 模式去 9:16 依赖（contain + 模糊背景）、图片补缩略图、上传探测补记 `width/height/aspect_ratio`。
5. **云存储（§7，覆盖全站链路）**：14 条上云链路的现状是"输入与派生全自动、结果半自动、采集全量强推"。最大成本在 viral 采集全量预归档（09-19 spec 已立案，目标降 80%）；最大风险在 **H3 结果默认 direct 不归档**（用户不点"保存"可能丢失已付费成果）；另有一键人物 5 份同字节双份冗余、五个写入点绕过内容寻址等可回收项。

## 2. 问题清单（代码证据）

### 2.1 组织体系：分组名存实亡、无标签、项目维度缺失

**P-A1 分组没有实体，只有逐条覆盖的文本。**
`MaterialItem.group` 是字符串（`materials.py:117`），取值 = `group_override`（用户逐条覆盖）或 `base_group`（系统默认：项目素材/我的上传/口播成片/…，`materials.py:649-653`）。因此：
- 列表 API 没有 `group` 筛选参数（`material_routes.py:44-62`），**无法按分组浏览**；
- 没有"新建分组/重命名分组/删除分组"入口，改 20 个素材的分组 = 20 次"选中 → 输入文本 → 保存"（`ContentPages.tsx:2843-2858`）；
- 自由文本无建议、无去重，手打会产生"我的上传 / 我的上传 / 我的上传的"碎片；
- 卡片上的 `分组 · 类型`（`ContentPages.tsx:1780-1782`）不可点击，只是文本。

**P-A2 无标签体系。** `MaterialItem` 无 tags 字段（`materials.py:107-134`）；一个素材只能落在一个分组里。真实场景需要多维度交叉（项目 × 场景类型 × 用途），单分组表达不了"新中式 · 庭院 · 航拍"。

**P-A3 项目维度缺失——最强的用户心智没有落点。**
5 个来源中"项目素材"实为**项目参考视频**（4–15s 参考片，`materials.py:341-346`）；用户上传的工地实拍/房屋照片 `project_id IS NULL`，全部落进"我的上传"（`materials.py:361-365`）。列表 API 无 `project_id` 筛选，详情面板"归属"只显示"人物库"或分组名（`ContentPages.tsx:2732`）。结果：**用户无法回答"这个乡墅项目的素材都在哪"**。

**P-A4 来源筛选是系统视角，不是用户视角。** 下拉选项"我的上传/项目素材/人物素材/口播成片/视频成片"（`ContentPages.tsx:2592-2597`）描述的是技术来源，用户想筛的是"张工的素材""某某项目的素材"这类**对象**。

### 2.2 检索与浏览：无排序、搜索弱、卡片信息缺失

| # | 问题 | 证据 | 用户影响 |
|---|---|---|---|
| P-B1 | 无排序能力（服务端无 sort 参数，前端无排序 UI） | `material_routes.py:44-62`、`materials.py:519-520` | 找不到"刚上传的""最大的"素材 |
| P-B2 | 搜索仅标题、需点击"搜索"按钮提交（非即时）、无结果高亮 | `ContentPages.tsx:2567-2602`、`materials.py:479-481` | 搜"工地"搜不到标签/描述里的内容 |
| P-B3 | 视频瓦片**有封面时不显示时长**（时长角标只在无封面兜底时出现） | `ui.tsx:370-375`、`ContentPages.tsx:2611-2622` | 同款场景多个视频无法快速区分 |
| P-B4 | 卡片不显示创建时间、文件大小（数据均已返回） | `materials.py:123-125`、`AssetCard ContentPages.tsx:1776-1783` | 无法判断素材新旧、无法感知体积 |
| P-B5 | 无网格/列表双视图（设计稿有） | — | 音频、长名称素材在网格里低效 |

### 2.3 整理效率：无批量、上传体验单薄

**P-C1 无多选、无批量操作。** 整个卡片是一个 `<button>`，点击即单选（`ContentPages.tsx:1763-1784`）；没有"选择模式"，无法批量移入分组 / 批量移除 / 批量下载。素材每项目动辄几十条，整理成本 = N 倍。

**P-C2 上传是单文件、无拖拽、分组写死。** `<input type="file">` 无 `multiple`（`ContentPages.tsx:2505-2515`）；无页面级拖拽区；上传固定 `group: "我的上传"`（`ContentPages.tsx:2349-2352`），用户不能在上传时选择目标分组；进度只有一个百分比，不可取消。

**P-C3 去重结果对用户不可见。** 服务端命中相同字节时返回 `upload_required=false` + `reused_from_asset_id`（`materials.py:176-181`），前端 `handleUpload` 完全没有消费这两个字段（`ContentPages.tsx:2345-2380`）——用户重复上传后不知道发生了"复用"，也无法理解为什么没有重新上传流量。

**P-C4 上传无客户端大小/类型预校验**（此前代码审查 C-6 已登记），超限只能等后端 413。

### 2.4 信任与生命周期：移除不可逆、状态语言技术化

| # | 问题 | 证据 | 用户影响 |
|---|---|---|---|
| P-D1 | "从素材库移除"无确认、无回收站、无恢复入口（实为 hide） | `ContentPages.tsx:2413-2444,2872-2881` | 误触即消失，"我的素材丢了" |
| P-D2 | 状态词面向实现：永久保存 / 处理中 / 生成完成，尚未归档 | `ContentPages.tsx:1746-1755,2734-2740` | 用户不关心"归档"，只关心"能不能用" |
| P-D3 | 无云端素材用量（只有本机缓存条） | `ContentPages.tsx:2545-2565` | 按量计费产品里客户无法感知云端占用 |
| P-D4 | 无使用记录（素材被哪些任务/成片引用过） | 无 | 不敢删、重复传，是素材库的通病（同行矩阵通/Seedance 都在解这个问题） |

### 2.5 创作流衔接与状态残留

- **P-E1 快捷使用入口只在右侧详情面板**：必须"先点卡片 → 再看右侧 → 点动作"，网格上没有任何 hover 快捷动作（对标：Seedance"一键调用到创作场景"）。
- **P-E2 切页丢状态**：页面切换是 `switch(page)` 条件渲染（`StudioWorkspace.tsx:2355-2395`），切走再回：筛选、分页、已加载列表、预览签名全部重置并重新请求（09-17 报告 P1-1 未落地）。
- **P-E3 音频口播断头**：素材库"用于音频口播"跳转后无法提交（全景梳理 §7 断点 #3，属另一任务范畴，此处仅登记）。
- **P-E4 direct 结果提示藏在详情面板底部**（`ContentPages.tsx:2882-2884`），用户不理解"尚未归档"意味着什么、什么时候能用。

## 3. 同行做法对标

| 产品 | 关键做法 | 对我们的启示 |
|---|---|---|
| **字节 Seedance 2.0 素材库** | AI 自动识别内容生成**智能标签**（格式/主题/场景）+ 自定义标签体系；关键词/标签/格式/时间多维度检索；素材**一键调用到创作场景**；企业级角色权限 | 标签 + 一键调用是标配；AI 标引是差异化亮点 |
| **Eagle（素材管理标杆）** | **文件夹 + 标签双体系**；**智能文件夹**（保存筛选条件为动态集合）；"显示子文件夹内容"透视视角（宏观↔微观一键切换）；批量操作；AI 整理素材库 | 分组要做"实体"，筛选条件要能保存复用；批量是刚需 |
| **新榜矩阵通（企业新媒体）** | 集中上传 → **按标签分类** → 团队快速检索；解决"素材分散、历史优质素材未沉淀、复用率低" | 与我们客户画像最接近：营销团队要的是"沉淀 + 找得到" |
| **剪映** | 素材库 + 收藏 + 名称搜索 + 本地/云端分层 | 收藏/星标是低成本高感知的功能 |
| **扣子（Coze）视频创作** | "**项目素材**"与"**资产库**"分离：项目内素材服务当前任务，资产库跨项目复用 | 印证 P-A3：项目维度必须有 |
| **火山引擎 IMS / 华栖云（企业级）** | AI 跨模态标引 + 自定义标签库 + 权限体系 | 长期方向；短期先做标签底座 |

**共性结论（5 条）**：① 文件夹 + 标签双组织；② 多维检索（名称/标签/类型/时间）；③ 批量操作；④ 管理与创作打通（一键调用）；⑤ AI 自动标引降低整理成本。我们目前只做到其中 1.5 条。

## 4. 改进方案

### 4.1 设计原则

1. **用户心智优先**：乡墅营销团队的组织单位是"项目"和"场景"（工地/外观/庭院/室内），不是媒体格式。分组与项目维度是第一优先级。
2. **偏好层不动本体**：素材是虚拟视图（5 来源 UNION），分组/标签本质是用户偏好，继续挂在 `studio_material_preferences` 上扩展（已有 `group_override/hidden` 先例），不引入素材本体迁移。
3. **最小增量、复用现有**：不引入 ORM/新表（红线）；列表 API 加参数、批量接口复用现有 owner 校验模式。
4. **渐进式**：P0 只做"组织 + 效率"（1–2 任务）；AI 标引等重投入放 P2，且需先解决计费归属。

### 4.2 P0 —— 组织与效率（预计 1–2 个任务，体验变化最大）

**P0-1 分组轻实体化（推荐轻量方案）**

- 后端：
  - 新增 `GET /api/studio/materials/groups` → `[{name, count}]`（对当前用户可见素材的 `COALESCE(NULLIF(group_override,''), base_group)` 聚合）；
  - 列表 API 增加 `group` 精确筛选参数（WHERE 加计算列条件，不改 UNION）；
  - 新增 `PATCH /api/studio/materials/bulk`：`{material_ids: [≤100], update: {group?, hidden?}}`，逐条校验 owner，返回 `{updated, skipped}`；分组"重命名/删除"由前端组合批量接口实现（本质是批量改文本，无需分组实体表）。
- 前端：
  - 左侧（或筛选行）增加**分组导航**：全部 / 未分组 / 各分组 + 计数；
  - 详情面板分组编辑改为**选择器**（已有分组下拉 + "新建分组"输入），消灭自由文本碎片；
  - 上传流程支持选择目标分组（默认"我的上传"）。
- 不推荐建 `material_groups` 实体表（跨 5 种虚拟来源的映射 + 存量迁移成本高，收益可在 P2 需要分组排序/颜色时再评估）。

**P0-2 批量操作**
- 前端：工具栏增加"整理"模式（进入后卡片可勾选、支持全选本页、跨页累积 Set）；批量条：移入分组 / 移入回收侧（先做隐藏）/ 批量下载（Web 端连续触发或提示；桌面端可评估 ZIP，标注为待定）。
- 后端：`PATCH bulk`（见 P0-1）承载批量改；批量下载复用 resolve（≤100 已有）+ 逐个签名。

**P0-3 排序 + 卡片信息补全**
- 后端：列表 API 增加 `sort`（`created_desc`（默认）/`created_asc`/`title_asc`/`size_desc`）。
- 前端：
  - 排序下拉（"最新上传"等，设计稿已画）；
  - 视频/音频瓦片**常显时长角标**（数据已有，`live.ts:157`；不再与封面互斥）；
  - 卡片 meta 行补创建时间（相对时间："今天/昨天/3 天前"，复用 `formatTaskTime` 风格）；
  - 详情面板补"上传时间 / 文件大小 / 时长"三行（数据均已返回）。

**P0-4 上传增强**
- `<input multiple>` + 顺序上传队列（显示"2/5 上传中"），逐文件独立成败与重试；
- 页面级拖拽上传（拖动高亮整个列表区）；
- 上传前选择目标分组（与 P0-1 联动）；
- 去重提示：`upload_required=false` 时 toast"检测到相同文件，已复用已有素材"；
- 客户端大小预校验（图片 ≤10MB / 视频音频 ≤50MB，与后端 `ALLOWED_UPLOADS` 对齐，`materials.py:61-92`）。

**P0-5 对象筛选与归属显示（项目/人物维度）**
- 列表 API 增加 `person_id`、`project_id` 筛选参数（字段已在 `MaterialItem`，仅缺过滤参数）；
- `MaterialItem` 增加 `person_name` / `project_title`（从既有 CTE 的 `display_name` / `project.name` 派生，`materials.py:309,327`）；
- 详情面板"归属"显示"张工（人物库）/ 某某别墅项目"并可点击跳转；
- 前端来源筛选下拉增加"按人物/按项目"二级选择（数据源复用已加载的人物列表/项目列表）。

### 4.3 P1 —— 结构与衔接

| # | 改动 | 说明 |
|---|---|---|

## 6. 显示尺寸与横竖屏（问题一）

### 6.1 尺寸机制的事实（代码级）

素材卡片媒体区是一个**固定 140px 高的视窗**，而里面渲染的视频/图片各有自己的比例：

1. 卡片网格第一行写死 140px：`grid-template-rows: 140px 24px 18px 22px`（`content.css:341`）；`.content-asset .studio-media` 同为 `height: 140px` + flex 居中（`content.css:367-373`）。
2. 视频/图片统一走 `VideoPreview`（`fitContainer=true`，`ui.tsx:348-377`）；fitContainer 下组件**不写内联比例**（`VideoPreview.tsx:175-186`），由类样式接管：`.video-preview { aspect-ratio: 9/16; width: 100% }`（`video-preview.css:2-12`）。
3. 在 230–300px 宽的卡片里，这个 9:16 框实际高约 373px，垂直居中放进 140px 视窗——**上下溢出部分被卡片 `overflow: hidden` 裁掉**（`content.css:345`）。

结果矩阵（按内容放进 9:16 框后被 140px 视窗裁切推导）：

| 素材比例 | 卡片可见内容 | 详情面板（视频 9:16 框 / 图片自适应） |
|---|---|---|
| 竖屏 9:16（H3 成片、口播成片、手机竖拍） | **只显示中段约 37%**，人物头部/主体常被裁掉 | 完整填满 |
| 横屏 16:9（部分参考视频） | 视频条完整（约 118px 高），上下补模糊背景（有缩略图时） | contain + 上下模糊 |
| 方形 / 竖长图（人物视图、拼合图） | 中段约 42%–66% 可见 | 图片按原始比例自适应（`VideoPreview.tsx:175-186`） |
| 音频 | 波形 + 播放器横条（`ui.tsx:323-341`、`content.css:404-406`） | 同左 |

> 关键点：业务素材大头正是竖屏（H3 生成 2K 9:16 归一化 1440×2560、口播成片 9:16、手机竖拍）——**最常用的素材在网格里显示得最糟**。

### 6.2 三个结构性成因

- **P-F1 媒体框比例写死 9:16，素材方向不定**：现状是"先按 9:16 渲染、再让 140px 视窗裁掉溢出"，没有任何按素材方向适配的逻辑。
- **P-F2 数据层没有宽高比**：素材上传探测只取时长（`materials.py:1092-1106`）；参考视频链路记录 `resolution/fps/aspect_ratio`（`media.py:533-542`）但素材链路没有，`MaterialItem` 也无这些字段。前端只能等缩略图/视频加载后从 `naturalWidth/Height` 得知比例，无法用于首屏布局。
- **P-F3 图片没有派生缩略图**：缩略图只在视频链路生成（`material_thumbs.py:78-92`；`attach_video_thumbnail` 显式跳过非 `video/*`，`materials.py:1179-1180`），图片卡片直接加载原图（≤10MB），影响网格流量与首屏速度。

### 6.3 图片/视频/音频是否都应放进素材库（问题一的第二半）

结论：**三类都保留在素材库，但要按媒体形态分呈现**。依据：

- 三类都有明确去向：图片→"用作原画面 / 用作首帧"（`ContentPages.tsx:2771-2790`）；音频→"用于音频口播"（`ContentPages.tsx:2754-2770`）；视频→复刻参考/发布。服务端 5 来源 CTE 天然统一三类（`materials.py:334-338,354-358`）。
- 音频承担的不只是"素材"：`audio_purpose` 有三种——`voice_clone`（声音克隆样本，5–180s、≤20MB）、`reference`（参考音频 ≤15s）、`oral_audio`（完整口播音频）（`materials.py:267-283,916-917`、`live.ts:1313`）。把音频移出素材库会造成"声音样本在哪"的新断点。
- 但音频与视觉素材的浏览方式不同：卡片 140px 里只有装饰性波形（`ui.tsx:326`），"全部" tab 会把波形卡混进视觉网格。建议：**音频在"全部"中折叠为紧凑横条或默认排除；音频 tab 内用列表（波形 + 时长 + 用途 + 去向按钮）**。

### 6.4 修改方案

**P0（与素材库任务同批做，改动集中在 CSS/组件）**
1. 卡片媒体区**去 9:16 依赖**：给 fitContainer 模式加独立类（如 `.video-preview--fit`），不再应用 `aspect-ratio: 9/16`，改为填满视窗 + 前景 contain + 模糊背景兜底（复用现有 backdrop 能力，`video-preview.css:36-42`）。效果：竖屏素材完整可见（窄列 + 两侧模糊）、横屏完整可见（上下模糊），不再裁切主体。
2. 媒体区高度 140 → 160px（提高竖屏可读性，保持卡片紧凑）。
3. **图片派生缩略图**：复用 `material_thumbs` 模式为 image 生成 `<key>.thumb.jpg`（PNG/JPEG/WebP → 缩放到 ≤480 高），网格用缩略图、详情用原图。
4. 时长角标常显（与既有 §4.2 P0-3 合并）。

**P1（数据层与筛选）**
5. 素材 complete 时记录 `width/height/aspect_ratio`：视频探测已在跑（`inspect_media_bytes`，顺手取宽高）；图片补 PNG/JPEG/WebP 头解析（`character_identity.image_dimensions` 已有 PNG 先例，`character_identity.py:1278+`）；`MaterialItem` 新增对应字段。
6. 列表 API/前端加"方向"筛选（竖屏/横屏/方形，按 aspect_ratio 派生）；媒体区高度可按方向分三档（竖 200 / 方 160 / 横 120）。
7. "全部" tab 音频折叠（见 6.3）。

**P2**
8. 大图预览（完整比例 + 分辨率信息）；列表视图加"分辨率/比例"列；可选瀑布流。

### 6.5 验收口径（§6）

1. 竖屏视频/图卡片主体完整可见、无核心内容裁切；横竖混排各自比例正确；
2. 图片网格走缩略图（单卡数百 KB 级），首屏加载明显改善；
3. 上传后素材带 aspect_ratio（列表 API 可读），"方向"筛选可用；
4. "全部" tab 不再出现视觉卡与波形卡混排。

### 7.2 现状评价

做得对的（保持）：
- 素材库/参考视频：直传 + 内容寻址去重 + orphan 清理（best-effort 删除 + `upload_cleanup` 兜底，`materials.py:1243-1282`、`storage.py:1051-1069`）；
- 缩略图自动派生 + 7 天签名（缓存友好，`material_thumbs.py:28-31`）；
- direct 设计本身是成本聪明的（不复制字节）；口播/首帧/源帧/人物等链路自动归档到位。

四个问题（按成本/风险排序）：

**G1 viral 全量强制预归档（成本最大）**
"采集→全部下原片→写 COS→才发布"（`viral_store.py:83-92`；09-19 spec §2.1 同述）。5–20MB/条、大多数从未被使用；09-19 spec 已把它列为存储/流量成本大头（目标降 80%），设计了桌面端"本地优先 + 按需上云"（Draft，未落地）。云版尚未处理。

**G2 H3 结果不自动归档（客诉风险最大）**
生成成功默认 DIRECT：结果字节留在供应商 URL（`generation.py:5533-5541`），素材库显示"生成完成，尚未归档"（`ContentPages.tsx:2734-2740`），播放依赖供应商链接（`generation_routes.py:798-842`）。风险：① 供应商 URL 时效不可控，用户不点"保存"就可能丢失已付费成果；② direct 素材无服务端缩略图与时长（无本地字节，`material_thumbs` 三个写入点都不覆盖）；③ "direct 与 stored 的可用性差异"对用户不可解释。

**G3 一键人物双份冗余（可立即省约一半）**
`simple_character.py:392-410`：五视图的 `generated` 与 `approved` 用同一份 `content` 各写一个对象——一套人物 12 个对象中 5 份是纯冗余。

**G4 上传通道不统一（长期隐患）**
素材库/参考视频走内容寻址（`content_store`：hash 命名空间 + ref_count + orphan 清理，`content_store.py:100,194`），而人物、首帧、源帧、口播、生成结果直接 `put_object` 各自命名空间（`simple_character.py:358-410`、`first_frames.py:1922`、`source_frames.py:459`、`oral.py:1028`、`generation_routes.py:900`）。后果：同字节跨场景不能复用（同一张图作人物源图 + 参考图 + 首帧 = 3 份）、无统一引用计数（无安全物理回收的基础）、清理口径分散。

**G5 生命周期缺口（治理）**
- 素材库"移除"= hide，无物理回收路径（§2.4 P-D1、§4.4 P2-3）；
- `content_objects.ref_count` 已有但未见自动 GC 的验证；
- 采集对象无 TTL（未发布/长期未使用）；direct 过期任务无清理/提示；注销用户的内容处理未定义。
- 观察项：素材 complete 是"intent 键写入 → 服务端读回 → 写内容寻址终键 → 删 orphan"（`materials.py:1073-1082,1145-1151,1243-1282`、`storage.py:1062-1069`）。正常路径不双份，但服务端要过手一遍字节（读 + 写），50MB 视频意味着服务端流量 ×2。存储层已声明 `copy_object`（`storage.py:156,385,471`），可评估用服务端复制替代重写（注意 local provider 语义）。

### 7.3 修改意见（按素材角色定策略）

原则：**"是否参与生成 / 是否是付费成果"决定上云时机，而不是"是否出现过"**。

| 素材角色 | 代表 | 策略 | 现状 → 目标 |
|---|---|---|---|
| 生成必需输入（H3/Gemini 需公链） | 参考视频/音频/图、人物视图、首帧 | 必须上云 | 已实现，维持 |
| 付费结果产物 | H3 成片、口播成片 | **生成成功即自动归档** | 口播已自动；**H3 需改** |
| 浏览/采集型 | viral 采集视频 | **元数据 + 封面自动上云；原片按需**（复刻/导入时才归档） | 全量强制 → 按需 |
| 派生小对象 | 缩略图、封面 | 自动上云 | 已实现，维持 |
| 能力注册物 | 声音克隆样本 | 上云（生成必需） | 维持，补保留期说明 |

**P0 建议：H3 结果改为自动归档（需拍板，三选一）**
- 方案 A：生成成功即自动归档（下载 → 归一化 → COS），用户零操作；成本全平台承担（可计入生成价）。
- 方案 B（推荐）：**生成成功后由 worker 自动归档**，失败进现有重试队列；同时保留"保存"作为补偿入口。技术上归档链路已幂等可重试（`generation_routes.py:845+`；`generation_worker.py:860-881` 已有 ARCHIVE_FAILED 重试路径），把触发从"用户点击"改为"worker 调度"即可。
- 方案 C：维持 direct + 到期倒计时提示（不推荐，客诉风险最高）。
- 待拍板：① 归档流量/存储是否计入生成计费；② 选 A/B 后"保存"按钮语义（改为"确保归档/重试"）。

**P1 建议**
- 一键人物 approved 复用 generated 对象（同 URI 或走内容寻址）：一套人物 12 → 7 个对象；
- 图片缩略图派生（与 §6 P0-3 同一改动，双重收益：省网格流量 + 提卡片速度）；
- 若 G2 短期不解决，direct 素材至少保留"preview 后抽帧缓存"，补上封面与时长。

**P2 建议**
- 上传通道统一到 `content_store`（新写入点逐步接入）：跨场景去重 + ref_count 驱动的回收（§4.4 P2-3 回收站的技术底座）；
- 生命周期治理：素材物理回收、采集对象 TTL、direct 过期清理、云端用量展示（§4.4 P2-5）；
- 评估 upload complete 用服务端 `copy_object` 替代"读 + 写"，省服务端流量；
- 与 09-19 spec 对齐：云版采集侧采用其"按需归档"原则（原片按复刻需求归档；浏览侧最多保留低码率预览版），避免桌面/云两套策略分裂。

### 7.4 需要拍板的决策

1. H3 归档策略（A/B/C）与归档费用归属；
2. viral 云版按需化范围（是否对"已发布批次"的播放也降级为低码率预览）；
3. 上传通道统一与生命周期治理的排期（P2，建议进 V3 收敛清单评估）。

### 7.5 验收口径（§7）

1. H3：按拍板策略，生成成功后无需用户操作即可在 COS 见到结果对象（或窗口期内自动归档），素材库状态显示正确；
2. viral：新采集批次中"从未被任何客户使用"的视频不再产生原片对象（或按拍板范围），成本可统计下降；
3. 人物：新生成人物的对象数 12 → 7；
4. 通道统一（P2）后：同字节跨模块复用可统计（`content_objects` / 去重指标）。
