## 1. 结论

M4/M5 交付包把队列从 SQLite 全局 FIFO 迁到 PG 公平轮转，并把客户端/管理端从后端契约铺到可用页面，是 V3 交付面最大的一个阶段。队列侧的核心设计全部对得上修订版 ADR：锁序单向 **cursor 行 → task 行**（SKIP LOCKED 双端使用）、空队列用户时间戳推进防钉头、GREATEST 幂等释放、CHECK {0,1} 约束兜底；迁移侧以 append-only 方式处理了已发布 revision 的拓扑问题（030→041，理由与先例写进迁移 docstring）。Worker 侧两阶段 claim/work 事务（M5 后端评审 P1-1）是本阶段最重要的正确性修复——claim 提交后崩溃不再回滚到 PENDING（避免重复付费 POST），而是留给过期清扫器转 `SUBMISSION_UNCERTAIN` 人工对账门；结算恰好一次由"同 round 已终态幂等返回 + SETTLE 必须已归档 + 钱包条件更新 rowcount 校验"三层守卫。前端红线（secret 不进 Web Storage、vault 边界、admin cookie+CSRF、切换二次确认）逐条核实无违犯。全量 1158 pytest / client 513 vitest / 浏览器 E2E 4 用例 / CI 三门全绿。

阶段可以通过，但有两个 MEDIUM 需要收口：worker 入口点的**陈旧注释仍描述 P1-1 修复前的单事务崩溃语义**（M1，运维按注释预期"租约回滚"而实际是 UNCERTAIN 人工门）；`fair_queue_enabled` **没有受审计的启用路径**（M2，ADR §4 定位为灰度观察开关，但管理端 runtime settings 不含该字段，生产只能裸 SQL 翻转、绕过 `runtime_settings.update` 审计）。

## 4. MEDIUM

### M1. `generation_worker.py:236-239` 陈旧注释误述两阶段崩溃语义

**位置**：`server/app/generation_worker.py` `main()` PG 分支注释——"Every task executes in its own fenced transaction, so a crash between the lease and the result write **rolls the lease back** — nothing leaks, nothing double-pays."

- 这段注释描述的是 **M5 后端评审 P1-1 修复前**的单事务设计；现行实现（`run_pg_worker_once` docstring 明确记载）是两阶段：claim 事务**提交** SUBMITTING + 槽位 + 全局计数；崩溃后租约**不回滚**，由 `mark_expired_active_leases_needing_attention` 转 `SUBMISSION_UNCERTAIN`（`LEASE_EXPIRED_NEEDS_ATTENTION`）进入人工对账门。
- 两处叙述互相矛盾，且陈旧的一处在**运行时入口点**——运维排障时按注释预期"任务回 PENDING 重跑"，实际会看到 UNCERTAIN + 需要人工 reconcile，判断依据直接错误。
- 行为本身正确（P1-1 修复的方向就是不让付费调用被静默重发），纯文档缺陷，但位于最高误导价值的位置。

**修复方案**：改写 `main()` 注释为两阶段语义（claim 提交 → 崩溃留 SUBMITTING → 清扫器转 UNCERTAIN 人工门），或直接引用 `run_pg_worker_once` docstring。

### M2. `fair_queue_enabled` 没有受审计的启用路径

**位置**：`server/app/settings_routes.py:38-41`（`RuntimeSettingsRequest` 仅 3 字段，不含 `fair_queue_enabled`）；`server/app/generation.py:3554-3575`（唯一读点）；全仓无任何写点（管理 API / env / deploy 工具均无，仅测试用裸 SQL 翻转）。

- 修订版 ADR §4 把该开关定位为**灰度观察机制**："FALSE keeps the legacy global FIFO so the rollout can be observed before enabling"——T36 staging 验收与生产启用必然要翻它。
- 现状只能 `UPDATE runtime_settings SET fair_queue_enabled = TRUE WHERE id = 1` 裸 SQL：绕过其它 runtime 设置变更都走的 `runtime_settings.update` 审计动作（settings_routes.py:346），无 runbook、无回滚记录、无操作者留痕——与 T09"每个操作可追溯真实 actor"的纪律冲突。
- 不阻塞当前（默认 FALSE + FIFO 是合法运行态），但 T36 前必须收口，否则 staging 启用即是第一次裸 SQL 生产操作。

**修复方案**：`RuntimeSettingsRequest` 增加 `fair_queue_enabled: bool | None`（仅 admin 角色可写、None 表示不变），`save_runtime_settings` 同步 upsert；或在 T36 部署手册中给出带审计登记的受控 SQL 流程（次选）。

## 5. LOW

- **L1 终态写无所有权/被顶替守卫**（`generation.py:2399-2432`）：`UPDATE generation_tasks SET status='SUCCEEDED' ... WHERE id = %s` 不校验 `locked_by`/`superseded_by_task_id`。病理路径：provider 调用超出 600s 租约 → 清扫器转 UNCERTAIN 并释放槽位 → 运维 reconcile RETRY 顶替任务（`superseded_by_task_id` 置位）→ 原_worker 迟到的终态写把已顶替任务改回 SUCCEEDED。无资金风险（UNCERTAIN 不可再领取、仅一次付费 POST、槽位 GREATEST 兜底），但建议加 `AND superseded_by_task_id IS NULL` 防御性守卫（reconcile 入口已有同型检查，终态写对齐即可）。
- **L2 T27-EVIDENCE 迁移目标陈旧**（`docs/evidence/T27-EVIDENCE.md` 头部"alembic upgrade head 到 revision-040"）：030→041 改名后 head 已是 041，测试实际 `command.upgrade(config, "head")`（test_queue_load_10k.py:105）。证据文档该行应更正为 041。
- **L3 里程碑口径分歧**：`docs/客户版开发计划-V3.md` 的 M4 = T24–T34（含队列与全部前端），M5 = T35–T39 staging；团队交付标签把 T25–T27/T34-E2E 称作"M5"。账本（任务清单头部叙事）沿用工作标签。建议在任务清单加一行口径注记，防止后续 M5 评审（计划语义 = staging）与已交付"M5"混淆。

## 7. 做得对的部分（不建议返工）

- **两阶段 claim/work（P1-1）是本阶段的正确性支柱**：付费调用不再可能因"单事务回滚 → 重回 PENDING → 下一 worker 重发"而双花；崩溃语义从"碰运气回滚"变成"确定性 UNCERTAIN + 人工门"。
- **041 的 append-only 拓扑修复（P1-3）处理得当**：不改已发布 revision、理由与 031 先例写入 docstring、冻结的 030 槽位留空并说明——这是迁移纪律的正面教材。
- **RETURNING 驱动的过期清扫（P2-1）**：并发清扫的输家只看到自己 UPDATE 过的行，双审计/双释放竞态从形状上消除。
- **结算恰好一次三层守卫**：同 round 终态幂等返回、SETTLE 强制 SUCCEEDED+ARCHIVED+资产（metaso 另加 cos:// 前缀）、钱包条件更新 + rowcount 校验。
- **T27 压测断言是真的**：EXPLAIN 计划形状断言（索引名 + 无 Seq Scan）、10000 任务恰好一次（per-task claimers==1）、`deadlocks==0`/`pending_locks==0`/`stuck_cursors==0`——不是描述性证据。
