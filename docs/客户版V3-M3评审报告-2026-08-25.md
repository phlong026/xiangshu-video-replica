## 1. 结论

M3 交付的设备槽、第二设备配对、会话租约、显式切换与 session fencing 是 V3 客户车道质量最高的一个阶段。三条主线各有硬设计：四态配对状态机把"一次消费、双批准通道互斥"下沉为数据库形状 CHECK；会话状态机以单行 `FOR UPDATE` 为串行化点，配合 `clock_timestamp()` 锁后判定与 `expected_*` 全字段重比对实现事务内 fencing；`db_portable` 用 fail-closed 翻译器保证 PG-canonical 单一 SQL 源（SES-04"dependency alone never closes the task"红线被如实遵守，`customer_fence.py` 在依赖缺失时拒绝工作）。T23 调账的原子四写、T22 续充的 T14 信封复用与回调幂等均质量扎实。静态门禁、PG16 迁移链实机（001→040 含 037→038→039→040）、M1/M2 全部修复落地验证均通过（§2）。

阶段不能直接通过，原因是**出口门 2 的"100 次全部 409"没有数值级同构测试**（H1）：行为本身正确（单行锁语义完备、2 线程 barrier 锁定单赢家与 409），但出口门明文验收在 M3 区间内没有任何 100 量级证据——T19/T20-EVIDENCE 将进程级并发证明列为"未测试项（PG 行锁语义覆盖，T13 100 并发先例）"，而同仓 T13 已有真 100 线程 barrier 先例（`test_hundred_concurrent_same_code_exactly_one_activation`），补测成本极低。语义论证不能替代出口门验收，这一条必须以同构测试关闭后才能宣称 M3 出口门达成。

其余问题均为账本纪律类（冻结映射表二次漏回填、任务清单状态滞后）与低风险运维观察，不阻塞后续开发。

- T19/T20-EVIDENCE 自认未测试项："多 API 实例同租约/switch 竞态的进程级证明（PG 行锁语义覆盖，同 T13 100 并发先例）"——语义论证成立（`login_session` 单行 `FOR UPDATE` + 谓词锁串行化），但"100 次全部 409"的出口门验收没有可重复、可回归锁定的证据。

## 5. LOW（按主题归并，源条目可追溯至各子评审）

- **`BusinessConnection.commit()/rollback()` 在 PG 车道静默 no-op**（`db_portable.py:315-321`；调用点 `zpay_payments.py:127,188-196`）：PAID 早退路径的 `conn.rollback()` 意图是"放弃事务"，PG 上实际留下一个只读事务并随 `pg_transaction()` 退出提交（只读事务提交无害）；错误路径靠外层 `conn.transaction()` 异常回滚兜底。**设计正确、后果为零**，但接口语义与调用者意图不一致，属易误用面——建议文档注明"PG 车道提交/回滚权威在外层事务容器"，或对 no-op rollback 发一次 warning 日志。
- **zpay 回调钱包自增无 int4 溢出守卫**（`zpay_payments.py:167-175`，对照 T23 `admin_customer_routes.py:446` 有 `available_credits <= 2147483647 - %s`）：多笔续充累计可溢出 → 回调 500 + ZPay 侧重试风暴（不会损坏数据，事务回滚）。单笔受 `INT4_MAX_FEN` 上限，概率极低；建议与 T23 对齐加同一守卫，成本一行。
- **service 层默认时钟为主机钟，依赖路由层传 PG 时钟**（`customer_session_service.py` 默认 `now or server_now_utc()`，`customer_session_routes.py:210-211,325-326` 传 `SELECT now()`）：当前全部调用点正确，但新增调用点若漏传，租约/过期判定漂移到主机钟（SES-01"PG 是唯一可信时钟"的纪律靠调用点自觉维持）。建议 service 层对未传时钟的写路径 fail-closed 或断言。

## 7. 做得对的部分（不建议返工）

- **会话 fencing 三层架构是本阶段最好的设计**：`customer_session_snapshot` 早期门（PG 未配置时返回 None 走内部车道，fail-closed）→ `fenced_pg_transaction` 事务内终审——行锁 + `clock_timestamp()` 锁后判定（`now()` 固定事务开始时间会错误授权等待锁的过期请求，这个细节是实打实的正确性）、`expected_*` 全字段重比对（lease 精确匹配，被拉回即 fence，PR #52 P2 修复）、码/设备状态复查。SES-04 红线被如实遵守：`customer_fence.py` 从未让"依赖存在"替代事务内验证。
- **037/038 配对状态机 DB 级形状强制**：四态各自证明自己的转移列，038 泛化后"双批准列互斥"（`approved_by_device_id`/`approved_by_admin_user_id` 恰好一个）由 CHECK 强制，无半对残留可能；部分唯一索引只锁 PENDING/APPROVED（终端行不阻塞新请求）。
- **T18 `DeferredHTTPWriteError`**：lazy EXPIRED 翻转（写副作用）与幂等层事务冲突的正确解法——快照 409、提交翻转、提交后重抛，同键重放同 409；无副作用分支保持普通 raise（键保持可重试）。先红后绿 13 例 + 重放锁定。
- **`db_portable` fail-closed 翻译器**：单一 PG-canonical SQL 源（无双实现红线）；未识别构造 `raise ValueError`、未闭合字面量 `raise`、参数化 cast 拒绝——翻译器宁可失败不可误译。
- **T23 调账原子四写**：PAID 订单（`provider='admin_adjustment'`）+ CHARGE 流水 + 钱包原子自增（`RETURNING` 溢出守卫）+ 审计行，全部在同一 fenced 事务；金额=credits×unit_price 冻结快照使 PRICE-01 恒成立；int4 溢出 400 拒绝而非 500。
- **T22 续充全套**：T14 信封复用（同键重放密封响应、异请求 409、占用键回滚释放）；回调幂等三保险（PAID 早退零写、`ZPAY_TRADE_ALREADY_BOUND` 防重绑、钱包/订单/流水原子转移）；"续充不变码/设备/并发"出口门 5 有专门测试（PENDING 钱包不变 + 幂等回放 + PG 车道 notify 入账）。
- **时钟纪律**：路由层统一传 PG 时钟、`_server_now` 复用、租约判定 `clock_timestamp()` 锁后取（M2 报告"时钟纪律不统一"的教训在 M3 未复发）。
- **T28 客户端适配**（过界但质量高）：凭据显式传参（无全局明文模拟）、401 三态分发为确定 UI 事件、anti-enumeration 400 不误归 service-unavailable（review P1 修复）、路径参数编码（P3）。
