## 2. 合流方向（已定）

**以远程 main 为基准，把本地 4 个提交移植上去**。理由：

1. 远程 main 是生产部署/发版的现役基准（`ab46e790`=生产基线，2.6.5 发布线），
   种子仓部署方案依赖它；
2. 体量不对称：远程侧 113 提交/300 文件 vs 本地侧 4 提交/4 文件+1 归档目录，
   反向搬运不成立；
3. 本地 4 提交中的三个修复已在生产上单独 patch 过（生产提交 `2d7e079`/`1b91f8a`），
   合流后远程 main 即含等价修复，下次部署无需再 patch。

**红线不变**：本地 main 与远程 main 两条历史严禁 `git merge`；本方案全程不触碰本地 main。

## 3. 执行步骤

### 第 0 步 前置确认

```bash
# 网络恢复标志：fetch 成功且 origin/main 到达 880f3042
git fetch origin main
git rev-parse origin/main   # 期望 880f3042...
```

fetch 持续不通时的替代：`curl -L https://codeload.github.com/phlong026/xiangshu-video-replica/tar.gz/880f3042`
拉内容快照用于门禁预演（见第 4 步备注），推送兜底见第 3 步。

### 第 1 步 防重复检查

远程 113 提交中若已包含本地三修复的等价改动，cherry-pick 会冲突或产生重复。
先确认：

```bash
git log origin/main --oneline -- server/app/media_tools.py server/app/first_frames.py | head -10
git log origin/main --oneline --grep="质检" --grep="转码" | head -10
```

若发现同主题提交，改为树级比对后只移植差异部分。

### 第 2 步 合流分支 + cherry-pick

```bash
git checkout -b feat/sync-release-into-remote-main-20261028 origin/main
git cherry-pick b13914dd 743efb61 bef6539d 7d162359
```

- 预期全部干净落位。若 `media_tools.py` 冲突：远程侧无内容改动，直接
  `git checkout --theirs` 不成立（theirs 是远程版=旧内容），应取**本地版**
  （`git checkout b13914dd -- server/app/media_tools.py`）后 `git add` 续挑。
- cherry-pick 保留原 4 个提交的独立身份与提交信息，历史可读。

### 第 3 步 树级双向校验（内容零丢失断言）

```bash
# 断言 A：合流分支相对远程 main 的差异 = 恰好本地 4 提交的文件集
git diff --name-only origin/main..feat/sync-release-into-remote-main-20261028
#    期望输出 = server/app/first_frames.py、server/app/media_tools.py、
#    server/tests/test_apilio_image_provider.py、server/tests/test_oral_domain.py、
#    前端页面V1.4-完整审核包-2026-09-05/**，不多不少

# 断言 B：4 提交的关键内容在合流树上与发布线一致
git diff 7d162359 feat/sync-release-into-remote-main-20261028 -- server/app/media_tools.py server/app/first_frames.py
#    期望为空（这三个代码文件内容逐字一致）
```

### 第 4 步 门禁（check:full，集成窗口语义）

```bash
npm run check:full
```

已知的本机坑（务必先自检，避免白跑）：

- **ffmpeg 必红 3 用例**：homebrew ffmpeg 8.1.2 缺 libwebp 编码器与 HDR tonemap，
  3 个 pytest 用例本机必红，会卡门禁放行。开跑前 `ffmpeg -encoders | grep webp`
  自检；必红则提前拍板豁免或换 ffmpeg 构建。
- **分片端口互踩**：跑分片前 `docker ps` 查占用，有并行会话夹具则
  `CI_SHARD_BASE_PORT=5701`。
- fetch 仍不通时的降级：用第 0 步 tarball 内容预演门禁后再推送（门禁语义不变，
  对象历史后补）。

### 第 5 步 推送远程 main（FF 快进）

```bash
git push origin feat/sync-release-into-remote-main-20261028:main
```

- 新提交父 = `880f3042` = 远程 main 当前头，**天然快进**，无需 force。
- 若 git 协议仍不通：走 Git Data API 快进兜底（blob→tree→commit→ref，
  2026-10-23 已验证的快照推送法；blob 只需上传 4 提交涉及的新内容，树与
  commit 用 SHA 组装，父提交填 `880f3042`，ref 快进不违反任何纪律）。
- 推送后 `gh api repos/phlong026/xiangshu-video-replica/commits/main` 复核头部落位。

### 第 6 步 收尾治理（与第 5 步解耦，单独拍板）

- **换主线**（此前已提议待拍板）：本地 main 改名
  `archive/main-baseline-20260924`，重建 `main` → `origin/main` 并设跟踪，
  工作区切回 main。此后 ahead/behind 恢复可信。
- **归档已并线分支**：`fix/oral-audio-normalize-tolerance`、
  `deploy-merge-20261009`、`integrate/remediation-20261013`、
  `feat/viral-cohort-sources`、`fix/remediation-batch3-20261013` 内容均已在线上，

  本地 replace 接线引用勿随手清理（push 断链坑的来源，保留无害）。
- **生产侧退役**：下次增量部署基于新 main 后，生产容器内的手工 patch

## 4. 风险与回滚

| 风险 | 缓解 |
| --- | --- |
| cherry-pick 冲突（评估为零，非零即异常） | 按 §3 第 2 步预案取本地版续挑；树级断言 A/B 兜底 |
| 远程 113 提交含同主题修复 | §3 第 1 步防重复检查前置 |
| check:full 本机必红 | ffmpeg 自检前置；豁免需拍板并记录 |
| push 网络失败 | Git Data API 快进兜底（已验证路径） |
| 误触本地 main | 全程在独立分支操作，main 零接触 |

**回滚**：推送前一切操作都在新分支，`git branch -D` 即净；推送后回滚 =
`gh api` 把 main ref 重置回 `880f3042`（快进 push 的逆操作，无 force 语义残留）。

## 5. 验收标准

1. 远程 main 头 = 本地合流分支头（含 4 提交内容），`gh api` 实证；
2. 断言 A/B 全绿；
3. `npm run check:full` 全绿（或豁免项有拍板记录）；
4. 本地 fetch 恢复后 origin/main 与远程一致，后续 ahead/behind 判读可信。
