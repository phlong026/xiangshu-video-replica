# CI 本地化与低频推送工作流方案分析

日期：2026-10-08
背景：GitHub 账号（z7hh2s48ct-cmyk）于 2026-10-08 前后被封禁（fetch/gh api 均返回 403
"Your account is suspended"），初步归因为高频自动化推送与 API 操作被风控识别为
自动化开发账号。本文分析"本地 Docker 门禁 + 本地合并 + 低频推送"方案的可行性，
并给出对标与推荐落地路径。

## 一、根因校准：封号触发点不止"推送频繁"

排查现状后，判断风控触发点大概率是以下组合（按嫌疑排序）：

1. **Git Data API push 兜底**（记忆台账中的 blob→tree→commit→ref 快进方案）：
   用 REST API 逐个创建对象再移动 ref，是教科书级的 bot 写入模式，与正常
   git 协议 push 在平台侧完全可区分。这个方案应永久停用。
2. **gh api 高频轮询**：每次 PR 后轮询 CI 状态、PR 可合并状态，多会话并行时
   轮询次数成倍放大。
3. **多 AI 会话并行的高频 push/PR/comment**：单日上百次远端写操作 + 大量
   元数据 API 调用，即使内容正常，模式也高度自动化。
4. 普通 git 协议 push 本身（SSH/HTTPS smart protocol）：嫌疑最低，正常人类
   开发者一天 push 几十次也不罕见。

**推论：新方案的核心指标不是"门禁挪到本地"，而是"远端写操作降一个数量级 +
彻底消除非典型 API 模式"。** 只把 CI 挪本地、但保留 GitHub PR 流程，风控压力
降不了多少。

## 二、现状盘点：已经具备什么、缺什么

### 已具备（比预想的多）

| 资产 | 状态 |
| --- | --- |
| 本地门禁 `npm run check:static` | ✅ secret 扫描 + Biome/tsc/vitest + e2e lint + cargo fmt/check + ruff/mypy |
| 本地门禁 `npm run check:sharded` | ✅ 上述 + 四分片并行 pytest，每片独立 PG 容器（Docker） |
| 本地门禁 `npm run check` | ✅ 全量 pytest 版本 |
| self-hosted runner 脚本 | ✅ `scripts/ci/self-hosted-runner/`（setup/register/service + VM 预置文档） |
| CI 调度已本地化一半 | ✅ ci.yml（2026-09-10 设计）PR 优先调度 self-hosted runner，hosted 仅降级；路径过滤 + 无关 job 空转短路 |
| AGENTS.md 工程约定 | ✅ 已写明"收尾提交前跑全仓门禁（等价于 CI 的 Linux 质量门）" |

结论：**"本地门禁等价于 CI"这件事已经实现了 80%**，当前 GitHub Actions 的增量
价值主要是：分支保护的 status check 依据、平台无关环境的二次验证、以及少量
本地没有的检查项。

### 本地门禁的缺口（需补齐才能真正等价）

| 缺口 | 现状 | 补齐难度 |
| --- | --- | --- |
| `cargo test`（Rust 单测） | 本地只跑 fmt/check，未跑 test | 低：本机有 Rust 工具链 |
| `npm audit` 依赖漏洞扫描 | 仅 CI | 低：本地直接跑 |
| `npm run build` 前端构建 | 仅 CI | 低：本地直接跑 |
| 浏览器 E2E（Playwright 实跑） | CI 跑，本地只做 e2e lint | 中：本机已有 playwright 受控浏览器惯例，需要稳定 fixture 环境 |
| Windows NSIS 桌面打包 | 仅 CI（13 分钟） | **不可本地化**：本机无 Windows 环境，保留 CI 低频手动触发 |

## 三、对标：同行怎么做

### 把门禁和合并放本地，是大厂内部主流（不是异端）

1. **Google（Piper/Critique/Tricorder）**：本地 presubmit 检查通过才能提交，
   提交即合入主线（没有 PR 环节），CI 是事后异步验证，挂了由"树关门"机制
   禁止继续提交直至修复。**提交粒度极细、频率极高，全靠本地门禁兜底。**
2. **Meta（Sandcastle/SapFix）**：本地 arc lint/arc unit → 直接提交 → 异步
   远端验证 → 失败自动 revert bot 回滚。同样是"本地门禁前置 + 远端事后兜底"。
3. **共同点**：大厂不信任的从来不是开发者的机器，而是"未经检查的变更"。
   只要门禁足够强且不可绕过，合并发生在哪里（本地/队列/远端）只是工程选择。

### 开源界选择远端 CI，是因为信任模型不同

4. **Chromium Commit Queue / Rust bors / GitHub Merge Queue**：PR 审查与
   CI 验证解耦，机器人单点合并，主线永远绿。存在的根本原因是**开源项目
   不信任贡献者的机器**，必须在平台控制的干净环境验证。这个前提对我们
   不成立——所有提交者都是自己的机器、自己的 AI 会话。
5. **SQLite（Fossil）/ PostgreSQL（邮件补丁）**：低频集成、本地验证充分、
   集中单点提交。历史上最稳的两种协作模式，节奏都远低于 GitHub Flow。

### 与我们处境最像的参照

6. **AI agent 驱动开发的团队（2025-2026 兴起）**：多 agent 并行开发普遍
   收敛到"本地验证闭环 + 低频对外同步"，因为 agent 的高频 API 模式触发
   平台风控已是公认问题（GitHub 2024-2025 批量封禁疑似 bot 账号）。
   我们的"多 AI 会话并行开发同一仓库"正是这个形态。

**对标结论：单人 + 多 AI 并行 + 已有等价本地门禁，走"本地合并 + 低频推送"
与 Google/Meta 内部模型同构，有充分先例；开源式 PR 门禁反而是错配。**

## 四、候选方案对比

| 方案 | 风控收益 | 工程成本 | 主要代价 | 判定 |
| --- | --- | --- | --- | --- |
| **A. 本地门禁 + 本地合并 + 低频 push main** | ★★★★★ 远端写操作降一个数量级，纯 git 协议 | 中：补 4 项门禁缺口 + 1 个集成脚本 | 纪律从平台强制降为脚本强制；main 保护放宽 | **推荐** |
| B. self-hosted runner（已有半成品） | ★★ 执行负载本地化，但 PR/push/轮询的 API 频率不降 | 低：脚本已备好 | 不解决封号根因 | 过渡可选 |
| C. 自建 Gitea/Forgejo 主远端 + GitHub 低频镜像 | ★★★★ GitHub 只见低频正常流量 | 中高：多维护一个服务 | 双远端一致性心智负担 | 备份增强项 |
| D. 维持现状 + 降自动化特征 | ★★ | 低 | 高频问题仍在，额度照烧 | 不够 |

**推荐组合：A 为主干 + C 的备份思想（每日 `git bundle`，可选 Gitea 镜像）+
D 中的协议纪律（永久停用 Git Data API push，gh api 轮询最小化）。**

附带收益：私有仓库 GitHub Actions 有免费分钟数限额（约 2000 分钟/月），
四分片 pytest + cargo + E2E 一轮全量就要几十分钟，当前模式配额随时烧穿；
本地化后这个隐患消失，也不再吃 Actions 排队时间。

## 五、落地设计（针对本仓库）

### 5.1 门禁补齐（一次脚本工作）

新增 `npm run check:full` = `check:sharded` + `cargo test` + `npm audit` +
`npm run build` + 浏览器 E2E。即"CI 有什么，本地就有什么"。

### 5.2 集成脚本（纪律的执行者）

新增 `scripts/local-integrate.sh`，逻辑固定：

```
1. 核验工作区干净（或按参数自动提交）
2. 跑 check:full（全绿才继续，任何一步失败即中止并保留现场）
3. git checkout main && git merge --no-ff <feature>（merge commit 注明
   门禁证据：各步骤耗时与通过状态）
4. 回到 feature 分支或按参数清理
```

原则：**门禁不过就合不进去，脚本不给跳过开关**；绕过只能手动操作，
而手动操作会在 git 历史里留下无门禁记录的 merge commit，可审计。

### 5.3 推送策略

- main：每日 2-4 次批量推送（正常人类节奏），推送前 `git fetch && rebase
  --ff-only` 检查远端是否前进；
- feature 分支：默认不推送，仅里程碑/需要跨机器时推；
- **永久停用 Git Data API push 兜底**；gh api 仅用于读操作且降频；
- 账号解封后首月保持保守频率，观察是否再次触发风控。

### 5.4 分支保护与 CI 调整

- main 的 required status checks 放宽（单人项目 + 本地门禁记录已足够；
  若保留保护，用 admin 直推并在 merge commit 里带门禁证据）；
- ci.yml 保留为"事后验证"：push main 时触发，hosted runner 跑轻量检查
  （lint 级），重负载 pytest 交给本地；或直接改为手动触发；
- windows-nsis / desktop-build 保留 workflow_dispatch 手动触发（发版时用）。

### 5.5 备份（低频推送的补偿）

- 每日 `git bundle create backup.bundle --all` 到另一物理位置（cron 自动化）；
- 可选：内网/同机 Docker 起 Gitea 作为第二远端，`git push --mirror` 低频同步，
  同时给 GitHub 留一个灾备副本。

### 5.6 多会话协调（关键运营规则）

- 指定**单一"集成者"会话**独占"跑 check:full + 合并 main + 推送"的权力
  （沿用现有"会话角色由用户指派"惯例）；
- 其他会话只交付 feature 分支 + 自己跑受影响专项测试；
- 这同时解决了并行会话本地 main 各自前进导致的推送冲突问题。

## 六、风险清单（如实）

| 风险 | 概率 | 缓解 |
| --- | --- | --- |
| 门禁被人为绕过（脚本强制弱于平台强制） | 中 | 集成脚本无跳过开关 + merge commit 门禁证据可审计 + AGENTS.md 写入约定 |
| macOS arm64 与 Linux 环境差异 | 低 | PG/pytest 已容器化；ruff/mypy/biome 跨平台一致；关注 cargo 与文件路径大小写 |
| Windows 打包无本地等价 | 确定 | 保留 CI workflow_dispatch 手动触发，仅发版时用 |
| 低频推送期间本机故障 → 丢失窗口拉长 | 低 | 每日 git bundle + 可选 Gitea 第二远端 |
| 多会话推送冲突 | 中 | 集成者单点合并推送 |
| 浏览器 E2E 本地不稳定（flaky） | 中 | 已知 flaky 用例重跑机制沿用现有惯例；E2E 可作为 check:full 的最后一步 |
| GitHub 二次风控 | 低 | 纯 git 协议 + 低频 + 无 API 滥用后，正常使用不会触发 |

## 七、待拍板问题

1. 集成者角色由哪个会话担任（建议：用户手动指定的当日值守会话）？
2. main 分支保护是"放宽"还是"保留 + admin 直推"？
3. 是否要起 Gitea 第二远端（建议先 git bundle 起步，确有需要再上 Gitea）？
4. GitHub 账号申诉期间，各会话的开发节奏是否照旧（建议照旧，本地合并
   照常做，推送积压到解封后批量执行——本地 main 是集成主干，GitHub 降级
   为备份出口）。
