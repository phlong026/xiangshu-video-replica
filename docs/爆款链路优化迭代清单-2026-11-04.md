# 爆款链路优化迭代清单（2026-11-04）

> 来源：2026-11-03 爆款链路全链路审计遗留问题（第三部分 1-5 主项 + B/C 组杂项），
> 经用户拍板纳入下一迭代。本清单是需求文档，不是排期承诺；实现时按仓库纪律
> 逐项立项（独立 worktree + feature 分支 + Codex 评审 + 门禁）。
> 同日已拍板并落地/关闭的事项见文末「已关闭项」。

## 定位说明

本清单五个主项都是**计费公平性与生命周期管理**问题：不阻塞当前功能，
但长期运行会积累客服对账成本与用户可感知的不公平。优先级按「用户可感知
不公平 > 平台成本暴露 > 工程一致性」排列。

## 主项（下一迭代范围，顺序即优先级）

### N1. 共享文案缓存归档清理器（P1）

**背景**：`viral_script_cache` 零清理、零 TTL，无限增长；`viral_routes.py:1181`
提取记录接口文档承诺「缓存被归档清理后 text 回 null」但清理器从未实现，
文档与实现脱节。

**目标**：缓存条目随媒体归档生命周期收敛，提取记录的过期语义落地。

**方案要点**：
- worker 增加定期扫掠：`viral_script_cache` JOIN `viral_media_preparations`，
  对「文案所凭归档已被回收/失效」的条目把 `result_json` 置 NULL（保留行与
  updated_at，交付侧校验语义不变）；
- 清理判定复用 `_credential_archive_is_current`（kind 对应归档 URI 比对），
  不引入新真源；清理动作写 `audit_logs`（`viral_script_cache.reap`）；
- TTL 参数进 settings，默认关闭待运营开启（灰度）。

**涉及**：`server/app/generation_worker.py`、`server/app/script_from_audio.py`、settings 迁移。

**验收**：归档失效后扫掠把正文置 NULL；提取记录接口回 `text=null`；
归档完好时扫掠不动；TTL 关闭时零行为。全部为 PG 用例。

**估计**：2-3 天。风险中（涉及交付语义，S 级评审）。

### N2. 生产者豁免与任务行解耦（P1）

**背景**：`viral_copy_producer_wallet`（viral_routes.py:1086）靠
`producer_task_id → script_from_audio_tasks` 行存活判定生产者豁免；任务行
被人工清理/重绑（script_from_audio.py:431-443/853-857）后，转写者本人会被
按非生产者收费。

**目标**：生产者豁免不再依赖任务行存活。

**方案要点**：`viral_script_cache` 加 `producer_wallet_id` 冗余列（迁移 +
回填既有行）；绑定/写入时同步写入；豁免判定优先读冗余列，任务行缺失时
回退现逻辑（兼容期双读）。

**涉及**：迁移、`script_from_audio.py`（绑定写入点）、`viral_routes.py`（豁免判定）。

**验收**：任务行删除后生产者 claim 仍免费；回填迁移幂等；双读兼容期行为不变。

**估计**：1-2 天。风险中（S 级：豁免判定变更）。

### N3. 付费转写缓存落空补偿（P2）

**背景**：完成阶段缓存写入条件 `producer_task_id=本任务 AND result_json IS NULL`
在绑定被改动后落空——生产者付了全价 ASR 但正文没进共享缓存，后来者会为
同一视频再付一次全价，无补偿。

**目标**：落空可观测、可补偿；后来者不再重复付全价。

**方案要点**：
- 完成阶段检测写入行数=0 且 viral_source 非空时写 `audit_logs`
  （`viral_script_cache.write_miss`，附 producer/钱包/时长），供客服补偿通道；
- 入队侧确认 `_lock_script_cache` 历史回溯对落空场景可达，不可达处补触发条件。

**涉及**：`script_from_audio.py`；无迁移。

**验收**：人为清绑后完成转写：落空事件落审计；下一请求者经历史重绑命中缓存不付 ASR。

**估计**：1 天。风险低。

### N4. 等待者 ASR 预留释放与生产者联动（P2）

**背景**（2026-11-04 按 Codex 收尾评审更正）：任务自身已 `FAILED` /
`SUBMISSION_UNCERTAIN` 的 ASR 计费单，现有对账器**已经直接释放**
（usage_billing.py:643），无须超时窗口；真正的缺口是**等待者**任务停留在
`PENDING` 且不再被 worker 推进（如生产者卡 UNCERTAIN 人工门禁、等待者租约
过期后未再拾起）时，对账器只检查等待者自身状态、不关联生产者，预留被
无限冻结。

**目标**：等待者预留不因生产者卡单而无限冻结；释放与人工恢复的冲突路径
语义明确。

**方案要点**：
- 核心是定义「等待者 ↔ 生产者」的关联判据（经 viral_script_cache 的
  producer_task_id / 同 (platform, video_id) 等待链），对账器据此把
  「生产者已 UNCERTAIN 超阈值、等待者仍 PENDING 超阈值」的计费单释放
  （阈值进 settings，默认 30 分钟，对齐 viral_search 口径）；
- **边界**：`finish_operation` 只支持相同结果重放（usage_billing.py:350）——
  已按失败释放、人工又确认成功的补偿**不能**依赖它，需要独立补偿台账
  （与 N5 的管理端处置动作联合设计）；
- 顺带补「双请求并发降级」PG 回归（Codex 闭环确认 #1 指出的验证缺口）。

**涉及**：`usage_billing.py`、`script_from_audio.py`（关联判据）、settings。

**验收**：生产者 UNCERTAIN 超阈值、等待者 PENDING 超阈值 → 等待者预留被
释放且有审计；生产者恢复推进后等待者照常命中缓存零结算；释放后人工确认
成功的补偿路径有台账、不重复结算。

**估计**：2-3 天。风险中（S 级：对账器变更）。

### N5. 改写 SUBMISSION_UNCERTAIN 出口（P1）

**背景**：enqueue 只复活 `FAILED+retryable`（script_rewrite.py:497-551），
UNCERTAIN 同键 replay 原样返回；客户端对 UNCERTAIN 不清幂等键
（scriptRewrite.ts:139-154）；无管理端解冻工具。用户不改一个字就永远重试
不出去（费已退，功能卡死）。

**目标**：UNCERTAIN 有出口，运营可处置。

**方案要点**：
- 任务侧：UNCERTAIN 超阈值（默认 24 小时，进 settings）后同键提交自动重开
  新一轮计费（对齐 /videos/source 的轮次语义），重开写审计；
- 管理端：复用 oral/first_frame 解冻工具先例，给 script_rewrite 加「人工确认
  失败/成功」处置动作（与 N4 冲突路径一并设计）。

**涉及**：`script_rewrite.py`、管理端路由、客户端幂等键策略微调
（UNCERTAIN 超时后允许清键重试）。

**验收**：UNCERTAIN 超 24h 同键重试能重开任务并正常扣费；管理端处置后
客户端可继续；处置动作全部落审计。

**估计**：2 天。风险中（S 级：计费轮次语义）。

## 杂项（与主项同迭代顺手清，或单独小批）

- M1 `local_video_extract_audio` 加 ffmpeg 超时（Rust `Command` 等待无上限，
  挂死即横幅永久挂起；建议 120s + 进度事件）；
- M2 `/videos/source` 客户端幂等键复用（api.ts:8756 默认 `createRequestKey`
  每次新随机，连点下载重复计费；与既有注释宣称的「同键复用轮次」对齐）；
- M3 转写完成时草稿已切来源：补 FIX-11 式通知（当前静默丢弃，费已花、
  正文在缓存，用户无感知）；
- M4 桌面缓存状态持久化或状态机自愈（`viral_cache.rs` statuses 纯内存，
  重启后 queued 假活轮询 300s；建议 status 查询时对「queued 且无活动任务」
  直接判 failed）；
- M5 提取/改写上限对齐：文案提取无时长上限、改写限 20000 字符——至少在
  文案工坊 UI 标注长文改写会截断；
- M6 `ConfirmedRewriteResponseError` 注释与实际计费语义（客户全额退费、
  仅 attempt 层记供应商成本）对齐，写进对账文档。
