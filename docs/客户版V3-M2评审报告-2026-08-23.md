## 1. 结论

M2 交付的激活码主链质量整体扎实：六表 schema 将一账户一码、slot 互斥、单会话、CHARGE 防重全部下沉为数据库约束并以真实 PG 断言锁定；首次激活的 7 类写入在单事务内全有或全无，100 并发是真实多连接 barrier 测试而非模拟；AEAD 信封的 AAD 绑定、密钥版本化、purge 与 029 CHECK 耦合自洽；T15 的单语句 UPSERT 共享预算设计正确且 PR #46 两条修复被测试钉死。静态门禁与迁移链实机演练全部通过（§2）。

阶段不能直接通过，原因集中在 T12 的审计与红线承载：

1. **造码/建批次的 reason 在持久层蒸发**（H1）：ACT-04 出口门明文要求"actor、reason、幂等键、request id 和审计齐全"，发放/暂停/恢复/作废/下载均持久化 reason，唯独铸造环节（批次创建零事件、生成事件不写 reason、导出事件连 request_id 也不写）审计链在源头断开。
2. **PRICE-01 红线无任何机制承载**（H2）："PRICE-01 决议未冻结前不得生成对外销售批次"只存在于文档登记；批次创建不校验面值与内部基础价关系，`026` 价格下限 CHECK 对激活码订单恒真（base=charged=面值快照）。任一 admin writer 今天即可创建"面值 1 分、额度 100 万"的可售批次并发放，客户侧激活即按该快照入账。

两条均不阻塞 T16+ 开发，但 H2 必须在任何管理端可操作面（T32）或对外发码之前关闭。

## 3. HIGH — 阻断项

### H1. 造码与建批次两个最高风险写路径的 reason 校验后被丢弃（审计链源头断开）

**位置**：`server/app/admin_activation_routes.py:238`（`idempotency_key, _reason = _require_write_contract(request, body)`）、批次创建 `:340-380`、生成 `:428-484`；关联 `server/app/activation_code_service.py:491-496`

- `_write_with_idempotency` 将 reason 解包为 `_reason` 后不再使用；批次创建无任何事件行，`generate_batch_codes` 的 GENERATED 事件不写 reason（reason 列已存在，`027:407`），`create_batch_export` 的 EXPORTED 事件只写 actor（连 request_id 也不写）。
- PR #43 评审曾把"下载 reason 被丢弃"定为 P1 并修复（现 `activation_code_service.py:537-549` 持久化 `download_reason`/`download_request_id`），但同类的铸造环节完全未覆盖——"这批码为什么造、依据什么单据"在持久层不可追溯，只能靠事后推断。
- ACT-04 出口门"actor、reason、幂等键、request id 和审计齐全"对铸造环节不成立。

**修复方案**：`generate_batch_codes` 已接收 request_id，同时接收 reason 写入 GENERATED 事件 reason 列；EXPORTED 事件补 request_id；批次创建补批次级审计事件（走追加式修正，遵守 append-only 规则）。

### H2. PRICE-01"不得生成对外销售批次"无任何代码/配置承载，价格下限对激活码订单形同虚设

**位置**：`server/app/admin_activation_routes.py:308-361`（`_validate_batch_payload` 仅校验正数与未来时间，不读 `runtime_settings.internal_base_unit_price_fen`）；`server/app/activation_code_routes.py:472-496`（base=charged=面值，`026_customer_security_and_billing.py:78-80` 的 `charged >= base` 恒真）

- 任务清单 T12 行与 §12.8 PRICE-01 的 No-Go 条款（"客户销售价与内部基础价关系未冻结前，不得生成对外销售批次"）目前唯一防线是 `docs/evidence/T12-EVIDENCE.md:86-88` 的流程登记。
- 影响敞口：当前无客户流量、管理端未对外，实际风险为持有 ASX1 writer 凭据的 operator 误操作；但一旦 T32 管理端页面上线，"面值 1 分、额度 100 万"批次一键可造，客户侧激活即按该快照入账。
- 属于 M0-H1 同类问题（红线只存在于文案）：要么给机制，要么显式记录风险接受，不得维持现状。

**修复方案（二选一）**：批次创建增加配置级 kill-switch（如 `VIDEO_REPLICA_ALLOW_ACTIVATION_BATCH_CREATION`，默认关）；或批次创建时对面值与 `internal_base_unit_price_fen` 做显式关系校验。在 PRICE-01 决议冻结前保持拒绝。

## 5. LOW（按主题归并，源条目可追溯至各子评审）

- **重放编排两份复制**：`_probe_replayable_response`（`activation_code_routes.py:178-237`）与事务内权威重放（`:771-827`）近似复制且已有一处分叉痕迹（probe 不显式看 `purged_at`）；T17/T19/T22 复用引擎时大概率三度复制。建议把"尝试重放"抽成引擎级函数返回结构化失败原因。

## 7. 做得对的部分（不建议返工）

- **M0-C1 无复发**：025–032 全部新迁移统一"PG-only 早退 + `postgresql_where`"模式，SQLite 车道不建激活码表并由路由 fail-closed 503。
- **不变量全部下沉数据库**：一账户一码（部分唯一索引 + 激活事实三重 UNIQUE）、slot `WHERE status='BOUND'` 互斥、fingerprint 部分唯一、`user_id` 主键=单会话、epoch 单调触发器实际安装并有降 epoch 测试、CHARGE 双重防重（idempotency_key 全局唯一 + charge_order 部分唯一）——并用真实 PG16 fixture 断言 `CheckViolation`/`UniqueViolation`/`RaiseException`，不靠应用自律。
- **ACT-06 是真证据**：专用迁移 PG 库 + 100 线程单 barrier + 逐表断言恰一份事实 + 钱包余额核对；同键并发恢复、同指纹跨码、业务失败释放键、用户名碰撞保存点重试四类竞态各有用例。
- **密钥卫生**：Crockford base32 28×5=140 bit 熵、CSPRNG、错误信息只含变量名与字节数；原始幂等键仅 SHA-256 摘要入库；device/session token 为 `token_urlsafe(32)` 且只存 keyed HMAC 摘要；明文码/凭据不入库、不入快照、不入日志均有扫描测试锁定。
- **AEAD 细节**：12 字节随机 nonce、AAD 绑定 `operation:scope:key_digest` 防跨行重放（有错 AAD 测试）；密钥版本化（V1 兼容裸名、最高版本密封、退役版本窗内 503 fail-closed）；purge 一条 UPDATE 清三列并记 `purged_at`，与 029 三态耦合 CHECK 自洽，无清掉活窗口的可能。
- **T15 设计正确性**：单语句 UPSERT 把新桶/重置/递增压进一条 `INSERT … ON CONFLICT … RETURNING`（桶主键为串行化点，多实例共享预算）；replay 零预算预检四关全过才短路（request_hash 匹配 + 密文存在 + 窗口未过 + AEAD 可验证），预算算术测试用剩余预算精确证伪"replay 消耗预算"；blocked-IP 停止铸造的短路 + 直接数 `activate:code|%` 行数的锁定测试。
- **跨任务衔接**：T13 的 activation_code 订单形状与 T08 的 026 全部 8 条 CHECK 精确兼容；T14 引擎泛化（`operation/scope/key_digest`）无 T13 泄漏，为 T17/T19/T22 复用就绪。
