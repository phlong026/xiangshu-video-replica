## 一、背景与目标

拆解链路（参考视频 → 结构化分镜/复刻提示词 → 确定性编译 → 生成）存在三类问题：

1. **稳定性**：拆解偶发报错/空返回，截断、安全拦截、空结果混为同一错误文案，用户重试徒劳。
2. **准确率**：motion 枚举归类、SHOT_CUT/ACTION_BEAT 边界判断偶有偏差；拆解提示词缺 few-shot 正例与观察依据前置。
3. **时长覆盖**：15–30 秒主链路与 4–180 秒长视频链路需在模型换代后保持稳定。

### T14 优化器与视频策略门控（v2 新增，评审 #3 的闭环）
- `ApilioGemini` 构造参数新增 `video_call_policy`（默认关闭）：截止预算、有界重试、token 回退**仅在视频工厂启用**；

### T2 finish_reason 先于正文可用性判定（v2 重写，评审 #2）
`_complete_once` 重排判定顺序：
1. 解析 `finish_reason`（小写化后包含式匹配）与 `usage`（**白名单字段读取**：`prompt_tokens/completion_tokens/total_tokens` 的数值型校验，禁止整字典复制）；
2. reason 含 `length` → **无论 content 是否存在一律判失败**（丢弃半截 body）：reason=`finish_reason_length`、retryable=False；
3. reason 含 `filter`/`safety`/`recitation`/`prohibited` → 一律判失败（丢弃 body）：reason=`finish_reason_content_filter`、retryable=False；
4. 其余 → 按 content 可用性走既有路径（空/非字符串 → 「空结果」retryable=True）；
5. 响应缺 `finish_reason` 字段（历史/异常信封）→ 保守走第 4 步，不抛新异常类型。

### T3 元数据落点区分成功与失败（v2 重写，评审 #7/#10）
- **成功**：`provider_response_ref.raw` 白名单扩展 `finish_reason` + `usage`（数值字段）；
- **失败**：任务行 `upstream_diagnostic` 增补 `finish_reason` 与实际尝试模型（与既有 http_status/failure_phase/reason 并列）；长视频失败路径同样增补；
- 优化器不纳入本期统计范围（明确记录该边界）；
- **T7b（对外中性化）**：`analysis_routes.py:1448-1455` 版本 payload 序列化时把 `provider` 字段映射为中性值（内部存储不变），客户端读取字段名保持兼容。

### T4 截止时间预算制（v2 重写，评审 #1/#5）
- 每次发起 provider 调用前校验剩余任务租约：`已耗时 + 本次超时 + 落库缓冲 > 租约剩余` 则停止发起新请求；
- 单次任务尝试的 provider 调用总数上限 4 次；执行顺序固定：**重试（同模型）→ 换备选模型 → token 回退（随请求内嵌，不计独立次数）**；
- 自动重试类别按 D5；换模型的 429/下线判定维持既有 `_should_try_fallback` 语义；
- 幂等依据改为：任务行锁 + owner/attempt 校验（`analysis_routes.py:1094`），并在测试中覆盖「租约过期后迟到结果被丢弃」「旧 attempt 重复完成被拒」。

### T5 max_tokens 三入口统一 + 精确回退（v2 修订，评审 #8）
- 三个视频入口统一：`analyze_with_context`（528）、`analyze_replica_prompt`（573）改为 `_analysis_max_tokens(duration_seconds)`；**基础 `analyze()`（458）补齐同一函数**；
- 公式 `min(32000, 16000 + int(duration_seconds)*800)`（20 秒即封顶；封顶合理性由 T0 实测 usage 支撑，数字记内部系统）；
- **优化器的 10000 不动**（其回退逻辑不经过 T5）；
- token 回退：仅视频请求、仅当原预算 >16000、仅当 400 原因明确指向输出上限；区分输出超限/输入超限/无关 400；最多一次；补「已是 16000 不回退」「回退后仍失败」「换模型后预算继承」测试。

### T6 超时与租约（v2 重写，评审 #1/#4）
- 主链路：单次超时 240s 起步，T0 定标；预算由 T4 的截止检查兜底（重试/换道不再可能突破租约）；

### Phase 1 验收标准（v2 按评审 #18 补成测试合同）
1. **分类矩阵**：`length`+非空截断 JSON → 失败且 body 不可达下游；`content_filter`+非空正文 → 失败；`stop`+空 content → retryable；缺失 content/message、非法 reason 类型、无 finish_reason 字段 → 保守分支；合法历史响应（无新字段）成功路径不回归。
2. **预算与序列**：虚拟时钟断言请求序列、全局次数 ≤4、截止前停止发起新请求、租约过期迟到结果丢弃、旧 attempt 重复完成被拒；429 → 重试/换道顺序与既有语义一致，`ref.model` 记录实际产出模型。
3. **max_tokens**：4s/19s/20s/30s/180s 边界（封顶临界）、基础入口补齐、优化器 10000 不变、无关 400 不触发回退、回退后仍失败路径。

5. **中性文案**：新增/改写日志与对外文案无供应商名；对外 ref 序列化 `provider` 为中性值且客户端字段兼容。

### C. Phase 0 实测结论摘要（2026-11-12，原始记录在内部系统）

方法：直连 provider，六支素材（15s×2 / 30s / 60s / 180s×2）× 双模型，共 4 轮 48 次调用。
结论（仅结论级，不含原始数据）：

1. **一次通过率**：`gemini-4-carbon` 18/18（100%）；`gemini-3.8-flash` 16/18——两次失败均为 180s 长视频上网关侧断连（~332s/570s），短素材无失败。
2. **耗时**：4-carbon 7–58s（多数 7–21s，与素材时长弱相关）；3.8-flash 8–208s，波动剧烈（同一素材跨轮可差 10 倍）。
3. **输出规模**：4-carbon completion 仅 ~2.2–2.4k tokens，远低于 16000 预算底；`finish_reason` 全程 `stop`，无截断——T5 动态预算余量充裕，T6 的 240s 主链路超时充足。
4. **网关缺陷（新发现，阻塞 4-carbon 上线）**：响应体存在周期性换行注入（`\r\n` 被插入键名/数字内部）。4-carbon 路线 18/18 全中，3.8-flash 仅 1/18；若不处理，4-carbon 在生产的 `json.loads` 会 100% 失败——**T15 为切 4-carbon 的硬前置**。生产兜底方案：`_complete_once` 解析失败时对原始 body 去 `\r\n` 重解析一次，成功则记日志留痕（转义 `\\n` 不受影响，安全性已论证）。
5. **网关缓存行为**：同一素材两模型在 15s 素材上返回过逐字节一致的输出（疑似跨模型缓存/同源兜底），30s 素材正常分化；不影响正确性，重分析同素材可能命中缓存。
6. **Phase 2 lint 实战命中**：3.8-flash 长视频 2 次缺时长要素（`REPLICA_DURATION_MISSING` 软警告生效，未丢结果）；4-carbon 0 次。
7. **质量待人工真值**：30s 快切素材上 4-carbon 判 6 段（切镜 5）vs 3.8-flash 判 13–14 段（切镜 12–13）——需人工看片定真值后再评价「过度锚定候选线索」问题。
8. **安全**：测试用 API key 仅在会话内使用、本地已删除；因已进入聊天记录，**建议轮换**。
