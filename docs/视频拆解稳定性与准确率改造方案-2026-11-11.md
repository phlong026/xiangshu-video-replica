# 视频拆解稳定性与准确率改造方案（2026-11-11）

> 状态：方案定稿（Phase 3 已拍板不立项），待 Codex 评审后进入实施。
> 关联调研：Gemini 官方视频理解 prompt 与市面拆解方法论调研（2026-11-11 会话，结论存项目记忆）。
> 本文档编号 T1–T13 仅在本方案内使用，与仓库其他任务清单无关。

## 一、背景与目标

拆解链路（参考视频 → 结构化分镜/复刻提示词 → 确定性编译 → 生成）存在三类问题：

1. **稳定性**：拆解偶发报错/空返回，失败原因无法分类（截断、安全拦截、空结果混为同一个错误文案），用户重试徒劳，排障靠猜。
2. **准确率**：motion 枚举归类、SHOT_CUT/ACTION_BEAT 边界判断偶有偏差；拆解提示词缺 few-shot 正例与推理前置。
3. **时长覆盖**：15–30 秒主链路与 4–180 秒长视频链路均需在模型换代后保持稳定。

**目标**：
- 失败可分类、部分可自动恢复；用户看到的错误文案与真实根因一致。
- 拆解枚举遵循率与边界判断质量可度量、可复测。
- 模型切换到新一代后，两条拆解链路（分镜拆解 + 长视频复刻提示词）行为一致、可回滚。

## 五、Phase 1 — 稳定性与模型切换（一个变更集，A 级评审）

### T1 模型默认值切换
`server/app/analysis.py:50-55`：`APILIO_ANALYSIS_MODEL = "gemini-4-carbon"`；`APILIO_ANALYSIS_FALLBACK_MODELS = ("gemini-3.8-flash",)`。注释更新：选型依据（D1）、设置页即时回滚路径、保留 2026-09-20 preview 名下线事故的教训（任何默认槽位不用 preview 名）。设置页覆盖能力（`analysis_model` / `analysis_model_fallbacks`）不变，仍是第一道运维手段。

### T2 finish_reason 与 usage 解析（本期核心）
`server/app/analysis.py` `_complete_once`：
- 解析 `choices[0].finish_reason`（小写化后包含式匹配，网关映射不规范时保守兜底）与 `usage`；
- content 为空/非字符串时按 reason 分流，全部归入 `RESPONSE_FAILURE_PHASE`，用 `upstream_diagnostic.reason` 区分：
  - 含 `length` →「拆解输出超出长度上限被截断」`retryable=False`，reason=`finish_reason_length`；
  - 含 `filter` / `safety` / `recitation` / `prohibited` →「该视频内容被上游安全策略拦截，无法拆解」`retryable=False`，reason=`finish_reason_content_filter`；
  - 其余（含 `stop` 但 content 空、reason 缺失）→ 维持现状文案「返回了空结果」，`retryable=True`。
- 历史兼容：响应缺 `finish_reason` 字段时按「未识别」走保守分支，不抛新异常类型。

### T3 provider_response_ref 扩展
`server/app/analysis.py:665-669`：`raw` 增加 `finish_reason` 与 `usage`（保持既有 provider/model/response_id 不动）。下游失败统计与对账以此为原料；`analysis_version_payload` 无需改动（ref 原样落库）。

### T4 传输层有界重试
`server/app/analysis.py` `_complete` 外层新增重试 helper：
- 触发条件：`AnalysisProviderFailed.retryable=True`（429/5xx/网络类）；
- 上限 2 次额外尝试，退避 2s/8s（叠加既有 `FAILOVER_RETRY_WAIT_SECONDS` 语义：换模型前的礼貌停顿保留）；
- `finish_reason_length` / `finish_reason_content_filter` 永不重试；
- 每次重试经 `recorded_urlopen` 留调用日志（含 external_call_model 标注），杜绝静默重复付费；
- 幂等依据：计费在入队侧（units=1，用户不受影响）；结果落库有 `create_or_recover_analysis_version` 并发保护。

### T5 max_tokens 动态化
`server/app/analysis.py:528,573`：硬编码 16000 抽为 `_analysis_max_tokens(duration_seconds)`，公式 `min(32000, 16000 + int(duration_seconds) * 800)`（Phase 0 定标后允许调整常量）；两处调用点（分镜拆解、长视频）统一走该函数。兜底：上游 400 且原因提及 max/output token 上限时，自动回退 16000 重试一次（该次记日志）。

### T6 超时与租约约束
- 主链路 transport 默认 240s 不动，Phase 0 实测 4-carbon p95 接近 240s 时才上调，硬约束：**主模型单次超时 × 2 + 换道停顿 ≤ 10 分钟任务租约**；
- 长视频链路 `replica_prompt.py:64` 默认 900s → 按 Phase 0 实测定标（预期上调至 1200s，25 分钟租约内单次调用安全），env `VIDEO_REPLICA_REPLICA_PROMPT_TIMEOUT_SECONDS` 覆盖能力不变。

### T7 失败文案分流（用户可见）
`server/app/analysis_routes.py` 失败卡片文案按 `upstream_diagnostic.reason` 分流：截断 →「视频过长导致拆解输出截断，请稍后重试」；安全拦截 →「该视频内容被上游安全策略拦截，无法拆解」（明确不提示重试）。文案保持中性，不出现供应商名（仓库红线）。

### Phase 1 验收标准（可测条目）
1. 单元测试：`finish_reason="length"` → `AnalysisProviderFailed` 且 `retryable=False`、reason=`finish_reason_length`；`"content_filter"` 同理；`"stop"` + 空 content → retryable；响应无 finish_reason 字段 → 保守分支不抛新异常。
2. 单元测试：retryable 失败重试 2 次后仍失败 → 最终失败附「已尝试 N 次」；不可重试失败零重试；429 → 重试耗尽后按既有逻辑切换备选模型，`ref.model` 记录实际产出模型。
3. 单元测试：`_analysis_max_tokens` 边界（4s/30s/180s/cap）；400 提及 token 上限时回退 16000 的路径。
4. 兼容：FakeGemini 全链路行为不变；`provider_response_ref` 新字段缺失的历史版本解析不炸。
5. 门禁：`uv run ruff check . && uv run ruff format --check . && uv run mypy app` 全绿；受影响专项 pytest 全绿；分片清单覆盖断言通过（新增测试文件后 `python scripts/ci/build-test-shards.py --shards 4`）。
6. 收尾：`npm run check:static`；合入走 `scripts/local-integrate.sh`（merge-queue 语义）；评审档位 A 级（对外错误文案与模型默认值变更；不碰资金/迁移，未达 S 级），评审证据写入 merge commit message。

## 六、Phase 2 — 准确率（独立变更集，B/A 级评审）

### T8 analysis.txt few-shot 出参示例
`server/app/prompt_rules/analysis.txt` 追加「输出示例」节：最小完整出参 JSON（`schema_version` + `analysis` 含 2 个时间段 + `generation_prompt` 固定值），覆盖 1 个 `SHOT_CUT` + 1 个 `ACTION_BEAT`、motion 六字段完整填写、`[听不清]` 与跨段台词拆分的用法。示例控制在 ~40 行内，避免显著推高每单 token 成本。

### T9 枚举判断前置依据
`analysis.txt` 第五节追加：「motion 各枚举值必须在段内文本先描述观察到的运动过程，再落枚举；boundary_reason 说明分段依据」——官方 reasoning-before-score 模式的提示词版（chat 通道无法控制 thinking 预算的等效手段）。

### T10 长视频出参 lint
`server/app/analysis.py` `parse_replica_prompt_payload` 增加确定性校验（宽松校验哲学不变，只加三条硬规则）：
- `replica_prompt` 命中禁词（「复刻」「原片」「源视频」）→ `AnalysisProviderFailed`（提示重新拆解）；
- 文本须包含媒体信息中的画幅与时长数值（缺失时降级为可接受但记 warning 落库，不丢付费结果——与「唯一必须可靠的是那段提示词本身」的既有取舍对齐，禁词是硬拒绝、要素缺失是软警告）；
- 长度上界（如 8000 字）超出按软警告处理。

### T11 legacy 缺 motion 用户可见化
`server/app/h3_prompts.py` `compile_replica_final_text`：`legacy_without_motion` 由仅记日志升级为返回值携带（或在调用方注入）issues 条目（code=`SHOT_MOTION_MISSING`），状态置 `NEEDS_REVIEW`，前端提示「第 N 镜缺运动信息，建议重新拆解」。注意保持函数纯度：issues 作为返回值的一部分而非副作用。

### T12 Phase 0 复测验收
提示词变更合入后，重跑 Phase 0 三支视频：Pydantic 一次通过率 3/3；motion 枚举无一越界；边界判断与人工核对一致（SHOT_CUT 数与 FFmpeg 候选吻合度不低于切换前基线）。

### Phase 2 验收标准
1. 单元测试：禁词命中硬拒绝；要素缺失软警告落库不丢结果；few-shot 示例节不破坏提示词文件读取与占位符替换（现有 analysis.txt 相关测试全绿）。
2. 单元测试：含 legacy 镜头的 shot_payload 编译 → 结果 issues 含 `SHOT_MOTION_MISSING` 且状态 `NEEDS_REVIEW`；新 motion 镜头无此条。
3. 门禁同 Phase 1 第 5-6 条；T12 复测记录留档于本文档附录。
