## 1. 结论

M0 的工程质量在静态维度上是达标的：`ruff` / `ruff format` / `mypy --strict` 零告警，603 个测试在本地 PG fixture 就绪时全绿，已提交证据日志无凭据泄漏，T06 抓到的四个方言守卫和一个 Alembic 事务缺陷都是真问题真修复。

但阶段不能通过，原因有两类：

1. **一个生产级阻断缺陷**：`uq_wallet_transactions_terminal_round` 在 PostgreSQL 上退化为全表唯一索引，导致任何生成任务都无法结算或释放预扣额度（第 2 节，已在真实 PG 上复现）。
2. **四个工作包被标记 `[x]`，但出口门实际未满足**：DB-01 的 CI fixture 不存在、DB-03 的 API/Worker 无法真正跑 PG、DB-02 的清单漏掉了导致缺陷 C1 的整个风险类别、DB-04 缺少 schema diff 证据（第 3 节）。

按 `docs/客户版任务清单-V3.md` §0 的规则（"任务完成不等于生产完成"）与 §12 的 No-Go 条款，这四项应退回 `[~]` 或修订出口门文案，不能维持现状。

## 3. CRITICAL — 阻断项

### C1. PostgreSQL 上钱包结算被唯一索引直接拒绝，全部任务无法结算

**位置**：`server/migrations/versions/022_internal_billing.py:198-204`

```python
op.create_index(
    "uq_wallet_transactions_terminal_round",
    "wallet_transactions",
    ["task_id", "billing_round"],
    unique=True,
    sqlite_where=sa.text("type IN ('SETTLE', 'RELEASE')"),   # ← 缺 postgresql_where
)
```

T06 补齐了 5 处 `postgresql_where`，**第 6 处漏了**。PostgreSQL 方言会静默忽略 `sqlite_where`，该索引因此退化为对全表生效的唯一索引。

**实机复现**（空库 `alembic upgrade head` 之后）：

```
uq_wallet_transactions_reserve_round  ... USING btree (task_id, billing_round) WHERE (type = 'RESERVE'::text)
uq_wallet_transactions_terminal_round ... USING btree (task_id, billing_round)          ← 无 WHERE 子句

✅ RESERVE(task_id='task1', billing_round=1) 插入成功
❌ SETTLE(task_id='task1', billing_round=1) 被拒绝
   -> psycopg.errors.UniqueViolation: duplicate key value violates unique constraint
      "uq_wallet_transactions_terminal_round"
```

**影响**：`server/app/internal_billing.py` 正是按 `(task_id, billing_round)` 先写 RESERVE、再写 SETTLE/RELEASE。在 PostgreSQL 上**没有任何一个生成任务能完成结算或释放**，预扣额度将永久卡在 reserved 状态，钱包账实永久不平。这是 M1 之后所有账务功能的地基缺陷。

**为什么自测没发现**：

- `server/tests/test_postgres_migrations.py:201` 的 `expected_partial` 只枚举 5 个索引，恰好与被修好的那 5 个一一对应，第 6 个不在断言集合内；
- DB-04 演练全程只查 schema，从不插入业务行，行为级冲突不可见；
- T06 提交信息自述"5 个 sqlite_where 部分唯一索引"，计数本身即错误。

**修复方案**：

1. 新增 Alembic revision 补 `postgresql_where=sa.text("type IN ('SETTLE', 'RELEASE')")`。**不得修改已发布的 022**——DB-04 的 No-Go 明确禁止篡改已发布 revision，只能追加修复。
2. 将 `expected_partial` 补足为 6 项，并增加一条断言：任何带 `sqlite_where` 的 `create_index` 必须同时带 `postgresql_where`（防止同类漏项再发生）。
3. 增加行级回归测试：RESERVE → SETTLE 同 `(task_id, billing_round)` 必须成功；SETTLE → SETTLE 重复必须被拒绝。

## 4. HIGH — 出口门未满足却已标记完成

### H1. DB-03 / T05：Worker 与 API 实际都无法运行在 PostgreSQL 上

- `server/app/generation_worker.py:126-135`：PG 模式下打一条 ready 日志即 `return`，任务循环完全不进入。更严重的是**进程 exit 0**——在 systemd / supervisor 下这是"正常退出"，不会触发 `Restart=on-failure`，属于静默 fail-open，与 T05 自身的 fail-closed 设计目标相悖。
- `server/app/bootstrap.py:48-58`：PG 模式下跳过 `bootstrap_runtime()`，凭据解密自检和本地密钥持久化都不执行。
- `server/app/auth.py:32`：每个 API 请求仍读 `VIDEO_REPLICA_DB_PATH` 并返回 `sqlite3.Connection`；`server/app/main.py` 对 `db_pg` 零引用。**没有任何 API 路由存在 PG 路径。**
- `server/app/db.py` 未被 T05/T06 改动（最近一次变更是无关提交 `f30273e`）。T05 交付的是新增并行模块 `db_pg.py`，不是"重构 DB 入口"。

DB-03 的完成证据要求是"API、Worker、测试均可使用 PG；连接回收/超时可观测"，当前只有"测试可以"，且可观测性未实现（见 M1）。

**处理建议（二选一，不得维持现状）**：
- 将 T05 / DB-03 退回 `[~]`；或
- 修订出口门文案为"PG 运行时基座就绪，业务接入见 T24/T25"，同步更新任务清单 §1/§12.1，并**先修掉 Worker 静默 exit 0**（PG 模式下应显式 `SystemExit(非 0)` 或阻塞待命，不能伪装成正常退出）。

### H2. DB-01 / T03：CI fixture 根本不存在，全部 PG 测试在 CI 静默跳过

`.github/workflows/ci.yml` 中 `quality-linux` 无 `services: postgres`，全文无 `TEST_POSTGRESQL_URL`。`T04-SQLITE-INVENTORY.md` 第 528-531 行写了 CI 片段，但从未落地到 workflow。

后果：`test_postgres_migrations.py` 与 `test_db_pg.py` 的 `pytest.mark.skipif` 在 CI 上全部命中，**静默 skip 不报错**。提交信息中的"603 全量回归绿"只在本地 fixture 运行时成立；CI 实际执行的是 ~580 绿 + PG 全跳过。C1 这类缺陷即使断言写对了，在 CI 上也拦不住。

DB-01 原文是"建立 PostgreSQL 16 本地与 **CI** fixture……CI 可重复运行"，标 `[x]` 不成立。

**这一项应在进入 M1 之前完成**——否则 M1 的全部 PG 工作都没有回归保护。

### H3. `alembic.ini` 仍硬编码 SQLite，运维路径打不到 PG

`server/alembic.ini:5` → `sqlalchemy.url = sqlite:///data/app.db`，`server/migrations/env.py` 不读取任何 DSN 环境变量。T06 仅在测试内用 `config.set_main_option()` 覆盖。

运维按常规执行 `alembic upgrade head` 依然写入 SQLite 文件。"PG 空库 upgrade head 通过"目前只在测试夹具内成立，不是可交付的部署路径。

**修复**：`env.py` 增加 `VIDEO_REPLICA_DATABASE_URL` 优先级解析（复用 `db_pg.resolve_database_config()`），并在部署手册中固化命令。

### H4. DB-02 / T04：清单漏掉了 C1 的整个风险类别

`T04-SQLITE-INVENTORY.md` 的 "Alembic Migration Analysis" 节只列了四项（batch_alter_table / AUTOINCREMENT / 内联 FK / DEFAULT CURRENT_TIMESTAMP），**完全没有 `sqlite_where` 部分索引**——而这正是 T06 踩的坑、C1 的根因。

同节写"`012`、`017`、`022` + 13 others"，没有行号，直接违反 DB-02 自身的证据要求（"文件、**行号**、替代方式和风险等级清单"）与 No-Go 条款（"清单漏项时不得估算迁移完成度"）。

另外第 490 行路线图仍推荐 "Refactor db.py to use **asyncpg** + connection pool"，与冻结规格 §8.1（psycopg3 + psycopg_pool only）和 T05 实际实现直接冲突。

**修复**：T04 增补一节"Alembic 方言参数清单"，逐行列出全部 `sqlite_*` kwargs 及其 PG 对应项与风险等级；把 batch_alter_table 的"+ 13 others"展开为带行号的完整表；将 asyncpg 建议改为 psycopg3。

## 7. 做得对的部分（不建议返工）

- **`env.py` 隐式事务提交缺陷的定位与修复**：不显式 `commit()` 会让 Alembic 复用 autobegin 的"外部事务"，整条升级链在连接关闭时被回滚。这是个真实且不易发现的问题，定位准确。
- **四个方言守卫全部站得住**：009 的 FK detach / re-attach（PG 强制执行 SQLite 忽略的外键）、014 的 `rowid` → `ctid`、`fk_external_call_logs_*` 的 63 字节标识符上限、`alembic_version` 版本表宽度。
- **`test_pg_transaction_serializable_write_conflict`**：真实开两条池连接制造 SQLSTATE 40001，不是 mock，是这批测试中质量最高的一个，为后续 SES/ACT 并发不变量打好了样板。
- **fail-closed 矩阵**覆盖了"PG URL + 遗留 `VIDEO_REPLICA_DB_PATH`"这种含糊配置并拒绝启动，比常见实现更严格。
- **T04 对 32 vs 33 模块口径差异做了显式对账**（第 546 行），没有掩盖数字分歧。
- 静态检查全绿；`docs/evidence/t02/` 已提交日志经扫描无凭据泄漏。
