# 短视频复刻桌面端：共享对话需求对比与范围决议

> 对比日期：2026-08-15
> 对话来源：[视频分析与生成系统](https://chatgpt.com/share/6a7fc46a-e710-83ec-85d2-c62b7cc5fd3f)
> 本地范围：当前工作区的产品文档、客户端、服务端、测试和验收记录
> 用途：解释需求来源、解决范围冲突；不替代唯一主规范
> 最终主规范：`docs/短视频复刻桌面端开发说明.md`
> 唯一执行清单：`docs/短视频复刻桌面端-V1.3后续开发任务清单.md`

---

## 1. 结论

共享对话确定的目标不是一个“把现有 Skill 套上界面”的工具，而是一个完整的 **AI 视频复刻工作站**：

> 人物身份建立 → 角色版本创建 → 多视角资产生成与审核 → 视频逆向分析 → 起始帧选择 → 人物置换首帧 → H3 Prompt 编译 → MiniMax H3 生成 → 预览、归档和导出。

当前仓库已经完成了大量服务端基础能力和本地 FakeProvider 契约，但存在两个结构性缺口：

1. **人物库只会消费已有参考图，不能生产人物资产包。** 当前 `characters` 以名称和 `reference_asset_ids` 为核心，没有“真人身份—角色人设—角色版本—多视角资产—审核发布”模型。
2. **桌面端尚未把后端能力串成员工可操作的纵向闭环。** 当前可完成项目创建、视频上传和拆解编辑，也能按 Batch ID 查看进度；人物、脚本、Prompt、批次创建、结果预览下载等主要入口仍未在同一工作台贯通。

因此当前状态应表述为：

> **后端生产链路核心已部分本地验证；人物资产生产和桌面端完整闭环未完成；真实 Provider 与 Windows 发布验收未通过。**

不能把“接口存在”“单元测试通过”“FakeProvider 通过”直接写成“V1.0/V1.3 已交付”。

当前整体上限不是 `READY_FOR_INTERNAL_RELEASE`。具体状态以 V1.3 后续开发任务清单为准。

## 3. 共享对话中的最终业务需求

### 3.1 产品定位

- 产品名：AI 视频复刻工作站（AI Video Replication Studio）。
- 目标：保留参考视频的镜头语言、动作逻辑、构图和节奏，将主体替换为企业已授权人物，并生成可追溯的新视频。
- P0 不是自动剪辑平台，不做社交平台发布、支付、会员、团队协作和运营分析。

### 3.2 人物资产系统

共享对话把“人物”定义为长期资产，而不是一组临时文件路径：

~~~text
真人身份 Person Identity
  └── 角色人设 Character Persona
        └── 角色版本 Character Version
              └── 多视角资产 Character Assets
                    └── 审核记录 Character Asset Reviews
~~~

必须支持：

- 上传一张清晰真人源照片；
- 保存肖像授权和有效期；
- 同一真人创建不同职业、服装和场景的人设；
- 生成正面、左右 45°、左右侧面、半身和全身等多视角资产；
- 单张审核、驳回和重生成；
- 角色版本整体发布、冻结、归档和回滚；
- 历史视频继续引用当时被冻结的角色版本；
- 视频复刻时根据起始帧人物朝向和景别自动选择身体参考图与脸部参考图；
- 所有源图、生成图和元数据进入企业对象存储。

### 3.3 三段 Prompt 流水线

共享对话要求把三个不同目的的 Prompt 分开：

1. Gemini 视频分析 Prompt：产出标准化 `video_analysis`。
2. 图片编辑 Prompt：用原始起始帧和人物参考资产生成人物置换首帧。
3. H3 Prompt Compiler：把标准化视频分析转换为符合 H3 输入约束的最终 Prompt。

Gemini 的自然语言结果不得直接透传给 H3。H3 Prompt 必须经过结构化编译、规则过滤、长度/时长/模式校验，并保存草稿、最终文本、版本和哈希。

### 3.4 资产和追溯

- COS 为默认企业资产中心，OSS 作为可切换实现。
- 数据库保存 `bucket/object_key` 等稳定引用，不长期保存签名 URL。
- 需要保留原视频、原始模型响应、标准化分析、起始帧候选、选定起始帧、人物参考选择、首帧候选、Prompt 快照、H3 任务、最终 MP4、成本、错误和审核记录。

### 3.5 桌面端闭环

员工应能在桌面端完成：

> 创建或选择已发布角色 → 新建项目 → 上传参考视频 → 审核镜头卡 → 选择角色版本 → 选择起始帧 → 生成人物置换首帧并确认 → 确认口播稿 → 编辑并锁定 H3 Prompt → 设置单项目候选数量 → 生成 → 预览、下载和重生成。

## 5. 冲突与最终裁决

### 5.1 Electron 与 Tauri

共享对话最初推荐 Electron；当前仓库已经采用 Tauri 2 + React + TypeScript，并已有自动拉起和 NSIS 配置。

**裁决：保留 Tauri，不进行技术栈重写。** Electron 只是早期建议，不是业务硬需求。

### 5.2 PostgreSQL 与 SQLite

共享对话早期建议 PostgreSQL；V1.2 已明确内部单机 P0 使用 SQLite，并实现 WAL、外键、超时、迁移、备份和恢复。

**裁决：P0 保留 SQLite。** 多节点和高并发出现真实需求后再单独迁移，不提前引入双数据库。

### 5.3 COS 单一存储与 COS/OSS 双适配

共享对话要求 COS 作为资产中心；当前规范增加 OSS 可切换能力。

**裁决：COS 仍是默认和正式验收对象，OSS 作为同一 StorageAdapter 的可选实现。** 业务对象不能依赖某一家签名 URL 格式。

### 5.4 单次生成与动态数量

共享 V1.0 暂缓“批量生产”，V1.2 要求员工输入 quantity。

**裁决：P0 支持一个项目、同一输入快照下生成 N 个候选；不支持跨项目批处理、模板批量套用或无人值守规模化生产。** 两者不再混用“批量”一词。

### 5.5 人物参考图与人物资产系统

V1.2 的 `Character + reference_asset_ids` 能支撑“使用已经准备好的参考图”，但不能满足共享对话中的“从一张真人照片生产多视角角色包”。

**裁决：V1.3 把人物资产生产恢复为 P0。** 现有 `characters` API 作为兼容层迁移，不重写首帧生成和项目历史。

### 5.6 Prompt 模板管理范围

共享对话要求管理 Gemini、图片编辑和 H3 三类模板；当前系统主要保存项目级 Prompt 结果。

**裁决：P0 必须保存实际使用的模板类型、版本、内容哈希和快照；管理员可视化编辑模板放到 P1。** P0 先解决可追溯性，不引入复杂 CMS。

### 5.7 H3 取消和回调

已有真实样本记录说明当前 METASO 通道不支持取消和回调。

**裁决：不把取消/回调列为代码缺陷。** P0 使用轮询；UI 的“取消”只允许取消尚未提交的本地任务，已提交任务明确提示无法撤回供应商调用。

## 6. 最终 P0 范围

### 6.1 必须完成

1. 内部桌面端身份、RBAC 和五入口导航。
2. 人物身份、角色人设、角色版本和多视角人物资产生产。
3. 人物源图质量检查、肖像授权、资产审核、单张重生成、发布和历史冻结。
4. COS 默认存储、短期访问 URL、稳定对象 Key 和追溯记录。
5. 参考视频上传、预检、抽帧、Gemini 结构化拆解和镜头卡编辑。
6. 原始首帧留档、候选起始帧、自动评分和人工确认。
7. 根据人物朝向/景别选择已发布角色资产，并允许人工改选。
8. GPT Image 2 / Nano Banana 人物置换首帧、多候选和人工确认。
9. 原稿/自定义稿、镜头匹配、H3 Prompt 编译、编辑、保存、锁定和快照。
10. 单项目动态 quantity、独立 H3 任务、阶段进度、失败/不确定状态和安全重试。
11. 成片自动归档、原生音轨检查、预览、下载、质检和再次生成。
12. FakeProvider 桌面 E2E、真实 Provider Gate、Windows 实机 Gate 和 10–20 项试跑。

### 6.2 P0 明确不做

- 跨项目批量生产和无人值守规模化生成；
- 自动剪辑、逐镜头分别生成后拼接；
- 独立 TTS、声音克隆、混音、音轨替换和口型同步；
- 文生视频和 H3 多对象参考；
- 自动发布到抖音、视频号等平台；
- 对外注册、支付、会员和计费系统；
- LoRA/身份适配器训练；
- 管理员可视化 Prompt 模板 CMS；
- 未经授权的人脸、人物或声音复刻。

## 8. 决策记录（ADR）

### Decision

以现有 V1.2 技术架构为基线发布 V1.3 最终主规范，恢复共享对话中缺失的人物资产生产域，并把桌面端纵向闭环、真实 Provider 和 Windows 实机设为独立门禁。

### Drivers

1. 共享对话明确把人物身份一致性和人物资产管理视为产品核心壁垒。
2. 当前仓库已有大量可复用后端能力，重写技术栈会增加风险而不会解决主要业务缺口。
3. 当前文档将“代码存在、FakeProvider、真实接口和发布”混在同一完成度描述中，容易形成错误交付判断。

### Alternatives considered

- 只给现有工作台补人物库页面：无法生产多视角资产，不能满足需求。
- 重新按共享对话的 Electron/PostgreSQL 架构开发：会丢弃当前已实现能力，成本高且没有业务收益。
- 把人物资产生产放到 P1：V1 无法完成“从真人照片到复刻视频”的自洽闭环。

### Why chosen

增量扩展人物域，同时复用现有分析、存储、首帧、Prompt 和 H3 代码，是最短且可验证的路径。

### Consequences

- 需要新增可逆数据库迁移和兼容旧 `characters` 数据的转换策略；
- 需要选择并真实验收一个多视角图片生成 Provider；
- 桌面端工作量从“补页面”升级为“完成全纵向工作台”；
- V1.3 在人物资产 Gate 通过前不能宣称 V1 完整交付。

### Follow-ups

- 以 `docs/短视频复刻桌面端开发说明.md` 作为唯一需求源；
- 以 `docs/短视频复刻桌面端-V1.3后续开发任务清单.md` 作为唯一状态源；
- 原 V1.2 任务计划和旧剩余清单仅作历史参考，不再更新完成度。
