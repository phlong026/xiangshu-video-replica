## 1. 结论

当前内部 P0 代码健康，但客户版 V3 仍不具备 merge-ready 或 production-ready 条件。激活码、客户身份、两设备、单在线 session、PostgreSQL、公平队列和客户前端尚未实现；真实 ZPay/COS/Provider、多实例和灰度也没有形成同一发布 SHA 的证据。

根据确定性门禁规则，Code Reviewer 为 `REQUEST CHANGES`，Architect 为 `BLOCK`，因此最终只能是 `REQUEST CHANGES`。这个结论不否定内部 P0 的本地能力，只阻止把当前实现宣称为完整客户版。

独立 Code Reviewer 运行 `npm run check` 通过，覆盖 secret scan、前端 323 tests、Tauri `cargo check`、Ruff/format/Mypy 和服务端 582 tests。该结果证明当前内部 P0 在本地检查下健康，证据层级最高仍是 `LOCALLY_VERIFIED`；没有运行真实 ZPay/COS/Provider、PG HA、双 API/四 Worker或 Windows 签名实机灰度。

## 4. HIGH Findings

### H-01：生产数据真源仍是 SQLite

**证据**

- `server/app/db.py:13-23` 固定返回 `sqlite3.Connection` 并开启 WAL；
- `server/app/db.py:42-52` Alembic URL 固定为 SQLite；
- 本轮扫描到 33 个 `server/app` 模块直接依赖 `sqlite3`；
- `server/migrations/versions/022_internal_billing.py:135-200` 的部分唯一索引仍使用 `sqlite_where`。

**影响**

无法证明多 API 下的一码一人、首充唯一、两设备槽、单 session、epoch fencing、公平队列和 PG HA。只修改新激活码模块不会消除旧业务路径的 SQLite 事务语义。

**最小修复**

先关闭 `DB-01` 至 `DB-08`：PG fixture、运行时连接/事务、001-head 迁移、SQLite 导入对账、账务约束和生产 fail-closed。禁止 SQLite/PG 双写。

### H-02：客户身份、设备凭据和 session fencing 不存在

**证据**

- `server/app/auth.py:52-80` 只支持内部 Bearer 或桌面/dev identity；
- `server/app/auth.py:99-110` 查询的是 `internal_access_tokens`；
- `server/app/generation_routes.py:203` 等业务写路由仍依赖 `AuthenticatedUser`，没有 `device_id/session_id/epoch/lease` 事务内复查。

**影响**

即使新增激活接口，旧设备仍可能在被切换后继续写项目、上传、任务或充值；只在中间件检查会产生通过认证后、提交事务前的竞态窗口。

**最小修复**

完成 `DEV-01` 至 `SES-05`，并逐写路由添加“中间件初验 + 业务事务内 fencing”的竞态测试。

### H-03：没有公网客户 API 装配边界

**证据**

- `server/app/main.py:76-97` 全局拒绝非 loopback 请求；
- `server/app/main.py:112-127` 未挂载 activation/device/session/customer router；
- 当前 CORS 仅允许本地开发和 Tauri origin。

**影响**

客户 API 当前不可用；直接删除 loopback 中间件又会把内部控制面暴露到公网。内部 P0 与客户云端不能靠隐式环境变量共用同一安全边界。

**最小修复**

显式拆分内部本机入口、客户入口和管理入口的 app assembly、路由、CORS/Host/可信代理与认证策略，并增加生产启动阻断测试。

### H-04：激活首充和后台调账不符合现有账务约束

**证据**

- `server/migrations/versions/022_internal_billing.py:98-103` 只允许 `provider='zpay'`、`pricing_scope='INTERNAL'`；
- `server/app/recharge_routes.py:61-134` 只创建 ZPay 充值单；
- 现有 `wallet_transactions` 具备 CHARGE/RESERVE/SETTLE/RELEASE 底座，但没有 activation/admin_adjustment 来源合同。

**影响**

首次激活无法在数据库约束内创建合法 PAID order/CHARGE；若绕过现有表直接加余额，会破坏追加式账本、幂等和对账。

**最小修复**

完成 `DB-07`、`ACT-05`、`BILL-01/02`，按来源建立条件约束、唯一 idempotency key 和逐笔重算测试；禁止直接 UPDATE 余额。

### H-05：任务调度是全局 FIFO，不是客户公平队列

**证据**

- `server/app/generation.py:3519` 使用 `BEGIN IMMEDIATE`；
- `server/app/generation.py:3521-3528` 每次领取先统计全局活跃任务；
- `server/app/generation.py:3546-3565` 按全局 `created_at, id` 领取队首。

**影响**

单个大客户可长期占满队列；多 Worker 缺少 PG 行锁语义；在任务量增长时，全局计数和队首扫描会成为锁竞争热点。

**最小修复**

先关闭 `QUE-01` ADR，再实现 `QUE-02/03` 的用户轮转、`FOR UPDATE SKIP LOCKED`、用户/Provider 两层并发和不确定提交保护，最后用 `QUE-04` 压测定索引。

### H-06：客户前端和桌面边界仍是内部 P0

**证据**

- `client/src/App.tsx:64-81` 调用 `setInternalAccessToken()`；
- `client/src/App.tsx:193-201` 展示“内部访问令牌”；
- `client/src-tauri/src/lib.rs:24-80` 自动探测并启动本地 FastAPI sidecar。

**影响**

没有首次激活、第二设备、冲突切换、heartbeat、安全凭据持久化；客户云版本若继续自动拉起本地业务后端，会形成身份和数据双真源。

**最小修复**

完成 `FE-01` 至 `FE-05`、`DESK-01/02`：Web 使用安全 cookie，桌面使用 Keychain/DPAPI，客户云构建与内部 sidecar 构建显式分离。

### H-07：管理端无法证明真实操作人

**证据**

- `server/app/control_auth.py:17-47` 把一个代理 token 固定映射到 `CONTROL_ADMIN_USER_ID`；
- `client/src/AdminApp.tsx:22-28` 只有账号钱包、充值订单和支付价格三个页签。

**影响**

发码、作废、解绑、强制下线和调账都不能追溯真实 operator；共享管理员会破坏审计和最小权限。

**最小修复**

完成 `DB-08`、`ACT-04`、`DEV-03`、`ADM-01/02`，建立 per-operator session、CSRF、admin/auditor RBAC、reason、二次确认和 request id。

## 5. MEDIUM Findings

### M-01：客户生产缺 Provider/COS fail-closed

`server/app/analysis_routes.py:56-75` 和 `first_frame_routes.py:65-88` 在未保存配置时回退 Fake；`media_routes.py:121-129` 未配置 COS 时回退本地存储。该行为适合内部演示，但客户生产可能把配置缺失误报为业务成功。

关闭 `EXT-01`：只有显式开发/测试 profile 允许 Fake/local，客户生产缺配置应启动失败或返回稳定 503。

### M-02：人物生成失败可能被占位图掩盖

`server/app/simple_character.py:1608-1649` 在 Provider 缺失、失败或返回不可用图片时生成 `local_placeholder`；`simple_character.py:1402-1478` 还会把生成的视图写成已批准资产。`character_image_generation.py:1131-1138` 的独立人物 Provider 当前也只有 Fake 实现。

关闭 `CORE-03`、`EXT-04`：客户真实链必须明确标记来源，Provider 失败不能把占位图计为真实生成成功、收费成功或人工审核通过。

### M-03：现有真实组件证据没有形成发布联合证据

历史记录显示 Apilio Gemini 和 COS 有组件级真实样本，但 H3、GPT Image 2、Nano Banana、人物 Provider、完整 COS archive/copy、ZPay 联合链仍不完整，且不是同一发布 SHA。

关闭 `EXT-03` 至 `EXT-06`、`COS-01`、`BILL-03`，只把同一候选版本、同一环境的联合竖切标为 `REAL_CHAIN_VERIFIED`。

## 6. LOW Findings

### L-01：核心文件过大，后续改动容易扩大回归面

`server/app/generation.py` 约 4,941 行，`client/src/api.ts` 约 2,507 行，`AdminApp.tsx` 约 513 行。当前不建议先做大重构；在公平队列、customer/control API 和管理页出现真实边界时做最小提取，并保持 Provider 状态机和账务语义不变。

### L-02：内部 P0 与客户 V3 的配置语义需要显式命名

当前多个模块通过“是否有配置”决定 Fake/真实、本地/云端。建议用明确 deployment profile 和启动校验代替分散推断，但不要引入新配置框架。

## 7. 性能专项结论

| 检查项 | 结论 |
| --- | --- |
| N+1 查询 | 本轮重点路径未确认新的典型 N+1；客户页尚未实现，后续需在真实列表 API 复核 |
| 无界列表 | 当前 control/wallet/recharge 主列表已有 limit/offset；导出上限 5,000，客户新页面必须继续服务端分页 |
| O(n²) | 未在本轮关键路径确认阻断性 O(n²)；公平队列尚未实现，不能提前断言复杂度达标 |
| 队列热路径 | 当前全局 COUNT + FIFO + SQLite 写锁是明确风险，必须由 PG EXPLAIN/锁等待证据裁决 |
| 前端渲染 | 客户页面尚未实现；管理端继续扩展单组件会增加全量状态刷新风险，应按真实页面边界拆分 |
| 外部调用 | 已有部分 timeout/error 处理；真实 Provider 失败、限流、提交不确定仍需联合验收 |

## 8. 架构评审结论

Architect 状态为 `BLOCK`，理由如下：

1. 当前架构真源是内部单机 P0，目标架构是真正的客户多实例系统，两者安全和事务假设不同；
2. PostgreSQL 是激活、设备、session、账务和公平队列的共同前置，不能把这些功能先建在 SQLite 后再迁移；
3. 内部本地 sidecar 与客户云端必须显式分产品边界，但应复用同一项目/素材/生成/账务域，不能复制整套业务逻辑；
4. Provider/COS/ZPay 的历史组件证据不能拼接成发布联合证据；
5. 在 `DB -> ACT -> DEV/SES -> CORE/QUE -> STAGING -> REAL -> GRAY` 关键路径完成前，不得批准客户上线。

## 9. 证据、推断与未知项

**Evidence**

- 当前源码确实使用 SQLite、内部身份、全局 FIFO、内部 token 前端和本地 sidecar；
- 当前检查通过 323 个前端测试和 582 个服务端测试；
- 客户 activation/device/session 路由和模块当前不存在；
- V3 任务和测试规格尚未有完成证据。

**Inference**

- 只实现激活码会在 PG、session fencing、客户前端和真实链路处继续阻塞；
- 若保留分散的自动 Fake/local 回退，生产误判成功的风险较高；
- 若先做 UI 再定事务模型，会产生明显返工。

**Unknown**

- 真实服务器、PG HA、COS 权限、ZPay 商户、Provider 控制台的当前外部配置；
- Windows 签名证书和实机环境；
- 真实客户负载、Provider 成本和失败率。

这些未知项需要外部环境和人工授权，不能由本地代码评审判定通过。
