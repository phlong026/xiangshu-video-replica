## 7. 两个核心问题的结论

### 7.1 合并执行环境：本地还是远程？

**两者分工使用——本地是"冲突解决与预检环境"，远程是"正式验证与合并环境"：**

- **本地负责**：rebase/merge 解冲突、`scripts/pg-fixture.sh start` + `npm run check` 全量门禁预检。先把问题挡在推送前，避免反复触发远程 CI（全量门禁单轮 20–30 分钟）。
- **远程负责**：PR 触发三门禁 CI + 代码评审 + squash merge。本地测试**不能替代** CI——Windows Tauri 构建、secret 扫描、npm audit 等只在 CI 执行（R7）。
- **铁律**：任何情况下不直接 push main（R1）；不合并 backup 分支；本地 main 与 origin/main squash 后分叉属预期，用 reset 对齐（R10）。

### 7.2 提交流程规范：是否必须走 PR + CI？

**必须，无例外。** 这不是可选项而是仓库硬约束（R1–R4）：

- main 仅接受 PR + squash merge，三门禁全绿是合并前置条件；
- 评审线程须逐条 resolve（R4）；
- chore 微改动同样走 PR（PR#93/#94 即现行实践）；
- 本地 main 的 110 提交收编也必须走 PR（PR#26 为直接先例）；
- 本报告全部操作不涉及需人工授权的动作（R9）；如后续收编内容触发授权项，另行取得所有者授权。

## 8. 风险清单与注意事项

1. **全量 pytest 并发禁令（R5）**：多 worktree 同时跑门禁必须串行；曾发生并行会话停 fixture 导致 9 个连接错误假性失败（C5 证据提交中已记录）。
2. **并发代理冲突**：人物库收口 worktree 有 31 个未提交文件，可能属于其他活跃代理会话。任何清理/合并操作前，先确认该会话已完成（用 lsof/mtime 观察 or 与所有者确认）。曾发生并发代理互踩 CI 与文件修改的教训。
3. **push 前提交核对**：`git log origin/<分支>..HEAD --oneline` 必须且仅是本任务提交；squash 后外来提交不可逆进入 main（PR#39 教训，已写入 AGENTS.md）。
4. **PR#96 base 修复是前置条件**：不修 base，它对 codex/frontend-v1.4 永远 CONFLICTING。
5. **backup 分支严禁合并**：133 提交落后，合入等于把 61/58 个文件回退到 9 月 2 日前状态。
6. **squash 收编的历史代价**：110 提交的明细历史在 main 上压缩为 1 个提交。缓解：第 0 步打归档 tag。
7. **在制分支变基方式**：收编 main 后，基于旧本地 main 的分支只能用 `rebase --onto` 或 merge-into-fresh-branch 模式（§6 第 9 步），严禁直接 `rebase origin/main`。

9. **PR#94 超时根因**：exit code 124 为命令超时（Rust/Tauri 编译段），非测试断言失败；优先重跑而非改代码。
