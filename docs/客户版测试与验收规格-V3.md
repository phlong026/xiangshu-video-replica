## 2. 单元测试

### 2.1 激活码

- CSPRNG 生成的码具有至少 128 bit 熵，格式校验和掩码稳定；
- 数据库、日志、异常和审计无明文；
- 客户 `username` 由服务端随机生成，不包含激活码片段、手机号或可枚举序号；唯一冲突重试，激活幂等重放返回同一个用户；
- 金额、单价和条数只用整数；快照计算精确；
- GENERATED/ISSUED/ACTIVE/SUSPENDED/REVOKED/EXPIRED 转移合法，非法转移拒绝；
- ACTIVE 后重复设备操作不再次计算或增加余额；
- 同一用户第二个码统一返回 `USER_ALREADY_ACTIVATED`。

### 2.2 两设备槽

- slot 只允许 1 或 2；第三槽由模型和数据库同时拒绝；
- 同一设备摘要重试不重复占槽；
- 槽位和 fingerprint 唯一性只约束当前 `BOUND` 且未撤销行；解绑后槽位可复用，历史行完整保留；
- 相同设备指纹/凭据不能同时绑定不同客户用户；测试结论只覆盖该指纹/凭据，不把客户端摘要宣称为不可伪造的物理设备身份；
- 第二设备绑定不产生充值单或钱包流水；
- 解绑在线设备先撤销 session；迟到设备 token 不可恢复绑定；
- 配对请求一次性、过期、批准人和候选设备摘要校验正确。

### 2.3 Session 状态机

- 无会话、同设备重试、其他设备冲突、显式切换、logout、超时状态均有确定结果；
- session epoch 只增不减；旧 epoch 永不恢复；
- heartbeat 30 秒、lease 90 秒使用数据库时间计算；
- 旧 session 的 logout/heartbeat 不改变新 session；
- 设备撤销、用户暂停、码暂停后 session 立即无效。

### 2.4 账务与任务

- 首充生成一个 PAID activation_code order 和一个 CHARGE；
- ZPay 后续充值进入同一钱包且不改变设备/session；
- 任务仍按用户 RESERVE/SETTLE/RELEASE；
- 切换设备不取消、不克隆、不重新扣费任务。

## 3. PostgreSQL 集成测试

### 3.1 首次激活原子性

对同一 ISSUED 码发起 100 个并发事务：

- 恰好一个成功；
- 一个 user、wallet、activation、slot 1、recharge order、CHARGE 和 session state；
- 其余返回稳定业务错误；
- 任一步注入异常全部回滚；
- 提交后响应丢失，以同幂等键恢复同一设备/session 响应，不重复入账。
- 同一激活幂等键恢复同一个 `user_id/username`，不得因用户名碰撞重试或响应恢复创建第二用户。

### 3.2 一人一码

- 一个已激活用户提交另一个 ISSUED 码：拒绝且两个码、钱包、设备均保持原状；
- 两个 API 并发尝试把不同码绑定同一用户：唯一约束保证恰好一个关系；
- 已暂停、已作废码不能通过换设备或重试绕开状态；
- 管理员不能把已激活码换绑另一用户。

### 3.3 两设备

- 两个候选设备并发争夺 slot 2：恰好一个成功；
- 第三设备在两个槽占用时始终拒绝；
- 解绑 slot 2 后一个新设备可占用 slot 2，历史记录仍可审计；
- PostgreSQL 中存在针对当前绑定的槽位和 fingerprint 部分唯一索引，不存在会阻断历史保留后槽位复用的无条件 `(code_id, slot_no)` 唯一约束；
- 第二设备绑定前要求有效批准或管理员核验；伪造批准拒绝。
- 第二设备 enroll 已提交但响应丢失后，同一幂等键恢复同一 `device_id`、slot 和设备凭据，不新增绑定、不重新占槽；同键不同请求返回 409。

### 3.4 单在线与 fencing

- 设备 A 在线时，设备 B 在两个 API 节点发起 100 个普通登录，全部 409，当前 session 仍为 A；
- 同一设备携带当前有效 session token 重新登录只续租，不换 token、不增 epoch；同一设备丢失 session token 后以设备凭据恢复时恰好递增一次 epoch，旧 token 和旧 epoch 迟到写入均失败；
- A/B 同时从无会话状态登录，数据库最终只有一个 current device；
- B 显式切换：同一事务递增 epoch 并改为 B；A 下一次请求/heartbeat 401；
- A 的迟到 logout 不清除 B；A 的迟到 heartbeat 不延长 B 也不复活 A；
- A 写请求先通过中间件，B 随后切换，A 在业务事务重新校验 epoch 时失败且无业务写入；
- 停止 heartbeat，数据库时间越过 90 秒后 B 可登录；旧 A heartbeat 仍失败；
- 主库切换或 API 重启不产生双 session。
- 登录成功但响应丢失后，同一幂等键恢复同一 token/session epoch；不新增 session event，不再次递增 epoch；同键不同请求返回 409。
- 显式切换成功但响应丢失后，同一幂等键恢复切换结果；A 保持失效、B 获得原已提交会话，不执行第二次切换。
- 恢复窗内的设备/session 响应仅以 AEAD 密文保存；恢复窗后密文清除，结果引用和审计不含凭据明文。
- 恢复窗配置按客户端最坏重试时长验证；密文清理延迟和清理失败触发指标与告警。

## 4. API 与浏览器 E2E

### 4.1 首次使用

1. 输入有效主激活码和设备名；
2. 服务端提交后显示面值和到账条数；
3. 自动进入工作台并显示设备 1/2、当前在线；
4. 创建项目和任务，钱包冻结一条；
5. 成片归档后结算；
6. 退出后 session 立即释放。

### 4.2 第二设备

1. 第二设备输入同一码并发起配对；
2. 第一设备批准；
3. 第二设备显示已绑定但第一设备在线；
4. 普通登录看到冲突，不进入工作台；
5. 显式切换并二次确认；
6. 第二设备进入工作台并看到同一钱包、项目和任务；
7. 第一设备收到会话失效提示并回到登录页。

### 4.3 设备恢复

- 第一设备不可用时，管理员按发放记录批准第二设备；
- 两槽已满时必须先审计化解绑；
- 第三设备不能仅凭激活码挤掉现有设备；
- 被解绑设备的所有凭据和 session 均失效。

### 4.4 后续充值

- 已激活用户不能输入第二个主激活码；
- ZPay 支付后同一钱包增加条数；
- 激活码、两个设备槽、当前 session 和用户并发不改变；
- 支付回调重复/乱序仍只入账一次。

## 5. 公平队列和多 Worker

- A 用户排队 1,000 个任务，B 100 个，C 10 个；三者都有额度时每轮都获得机会；
- 任一用户运行中任务不超过默认 1；两设备不增加用户并发；
- A/B 设备切换前后，排队顺序和任务 owner 不改变；
- 四个 Worker `FOR UPDATE SKIP LOCKED` 领取无重复、无全局队首阻塞；
- Worker 崩溃后的租约恢复不重复 Provider 提交或钱包结算；
- 10,000 排队任务保存 `EXPLAIN (ANALYZE, BUFFERS)`、锁等待和连接池等待证据。

## 6. 安全测试

- 激活码枚举、错误、过期、已激活返回近似响应与限流；
- 码、设备 token、session token 不进入日志、Sentry、CSV、数据库 dump 或 LocalStorage；
- 第二设备绑定必须绑定候选设备摘要，批准不可转用；
- 设备指纹重装/伪造测试被风险控制和审计捕获；验收材料不得把客户端指纹描述为绝对物理设备证明；
- CSRF、CORS、Host、Forwarded Header、cookie 属性、IDOR 和跨用户 404；
- session fixation、epoch 回退、token 重放、切换竞态、旧设备迟到写入；
- 管理员解绑、强制下线、暂停码要求真实 actor、原因、二次确认和幂等键；
- 密钥轮换保留必要旧 key 验证窗，不使现有设备随机掉线；
- 依赖审计、密钥扫描和认证/账务/并发专项 Code Review 全绿。

## 7. 数据迁移

- PostgreSQL 16 空库 upgrade head；存量 SQLite 导入 PG；禁止双写；
- 旧 users、wallets、orders、transactions、projects、tasks、assets 主键集合一致；
- 每个钱包可由流水重算一致，PAID 无 CHARGE 和 CHARGE 无 PAID 都为 0；
- activation_code provider/price scope/price snapshots 的合法与非法形状由 PG check constraints 验证；
- code/user/session/order/CHARGE 唯一约束及当前设备槽位/fingerprint 部分唯一索引真实存在；
- 客户生产配置 SQLite 或本机持久资产时 fail-closed；
- 迁移期间停止新写入，导入/对账/切换/回滚窗口有演练记录。

## 8. 性能、HA 与可观测性

### 8.1 建议容量基线

- 10,000 客户用户、10,000 ACTIVE 主激活码、20,000 绑定设备；
- 10,000 排队任务、100,000 历史任务；
- 100 并发普通 API p95 < 300 ms；
- 登录/heartbeat 100 并发 p95 < 300 ms；
- 100 个同一码激活竞态 2 秒内收敛为一个事实；
- 队列领取 p95 < 200 ms，锁等待 p95 < 50 ms。

最终阈值在目标服务器规格冻结后定标。

### 8.2 故障演练

- 杀死任一 API，LB 继续服务且单在线不失效；
- 杀死 Worker，租约恢复且不重复付费；
- PostgreSQL 主备切换后逐笔核对 100 个已确认 activation/order/CHARGE/session epoch；
- COS/Provider/ZPay 临时失败保持原幂等键和状态机；
- 建议数据库 RTO <= 5 分钟，已确认资金事务目标 RPO=0；达不到必须显式降级。

### 8.3 指标与告警

- 激活成功/失败/并发冲突/一码一人唯一约束阻断；
- 设备槽占用、绑定失败、配对等待、解绑；
- 当前在线数、登录冲突、显式切换、heartbeat 延迟、租约超时、旧 epoch 阻断；
- 每用户队列长度、最大等待、运行数、Provider 槽位；
- 钱包不一致、PAID 无 CHARGE、CHARGE 无来源；
- PG 连接、锁等待、慢查询、复制延迟、备份/PITR；
- P1：重复入账、双在线、旧设备成功迟到写入、跨用户访问、账本不一致。

## 9. 发布门

### Gate A：代码与 PostgreSQL

单元、PG 集成、迁移、前后端静态/构建、安全扫描全绿。

### Gate B：类生产多实例

双 API、四 Worker、PG HA、私有 COS、LB 下完成激活/双设备/单在线/切换/公平/故障测试。

### Gate C：真实外部链路

经授权执行一个真实激活码首充、最低额 ZPay、COS put/head/get/delete、Provider 成功/失败/提交不确定；证据绑定同一发布 SHA。

### Gate D：灰度

先完成支持平台的签名客户构建和实机安装/升级/卸载验证，再执行内部账号 -> 10 个客户码 -> 100 个客户码。连续观察无错账、双在线、旧会话写入、跨用户泄漏和严重饥饿后才扩大；未签名 Windows 包只能用于 `UNSIGNED_INTERNAL_TEST`，不能进入客户灰度。

## 10. 完成定义

只有用户确认的五项业务口径实现，所有自动化与类生产门通过，签名客户构建完成实机验证，真实链路验收、灰度、回滚、备份恢复、告警和值班均有证据，才可称为“完整客户版正式开放”。
