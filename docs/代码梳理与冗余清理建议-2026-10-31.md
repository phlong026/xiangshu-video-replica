## 一、业务全景

产品定位：**AI 短视频复刻生产工作台**——上传参考视频，AI 拆解分镜，生成同结构的新视频，按条计费。

主链路（一句话版本）：

```
参考视频/爆款链接 → AI 拆解分镜 → 人物库 + 首帧 → Prompt 与批次编排
      → 视频生成（异步队列） → 成片直链交付 → 钱包按条结算
```

### 1.1 三层结构

| 层 | 技术栈 | 职责 |
| --- | --- | --- |
| 桌面端 `client/src-tauri` | Tauri 2 / Rust | 只做系统能力：分段下载、ffmpeg 抽帧、视频号本地解密、发布账号。**不启动本地业务后端** |
| 界面 `client/src` | React 19 + Vite | 客户工作台 + 管理控制台共用一份构建，两个入口（`main.tsx` / `admin-main.tsx`） |
| 服务端 `server/app` | FastAPI + psycopg3（同步） | 全部业务逻辑、异步 Worker、计费。生产库唯一真源 PostgreSQL 16 |

### 2.2 B 类：业务逻辑上的双轨并存（风险最高，需业务确认）

#### ① 人物域存在两套并存的创建流程 —— **高**

- **旧轨**：`characters.py:97 create_character` 直接写 `characters` 表，再经 `sync_legacy_character_domain`(`characters.py:389`) 向新表回写镜像。
- **新轨**：`simple_character.py:479 create_simple_character` 直接写 `person_identities` / `character_personas` / `character_versions`，**不经过** `characters` 表。
- **关键证据**：前端全仓只调用了 1 个人物端点——`api.ts:3742` 的 `GET /api/characters?project_id=`（只读）。
  而 `character_routes.py:152/196/225/243` 暴露的 `POST/PATCH/DELETE/PUT /characters` **没有任何客户端调用**。
- **数据可见性断裂（已逐条核实）**：
  - `characters.py:42 list_characters` 的 SQL 是 `SELECT ... FROM characters`（`:60`）。
  - 全仓库只有 `characters.py:118` 和 `:196` 会写 `characters` 表（INSERT / UPDATE）。
  - `simple_character.py` **完全不碰** `characters` 表（全文仅 2 处出现该词，均非 SQL 写入）。
  - 结论：新轨创建的人物**不会**出现在前端唯一在用的列表接口里；旧轨的四个写接口则是"活的但无人调用"。
- **建议**：确认业务上是否已完全切到新轨。若是，下线 `characters` 的写路由并移除 `sync_legacy_character_domain`；若否，需明确两轨的数据同步口径——目前是单向镜像，容易出脏数据。

#### ② 计费有两套并行实现 —— **高**

- `usage_billing.py:39 accept_operation` 与 `internal_billing.py:166 reserve_internal_billing` 各自写 `wallet_transactions`。
- `internal_billing.py:396/595/828` 三处 INSERT 几乎相同。
- `billing_evidence.py:74-87` 只能靠 `service` 字段分支来兼容两条链路。
- `usage_billing.py:495 record_attempt` 与 `discount_service.py:83/178` **只被测试调用**，真实折扣走 `billing_catalog.py:168 merge_customer_discount`。
- 这是钱相关的代码，两套并存意味着对账口径有两份真源，属于最高风险项。

## 三、不建议动的"受控重复"

避免误伤，以下重复是**有意为之**，不要清理：

1. **`styles.css` 与 `customer/customer-access.css` 的 31 条相同规则**：`customer-access.css:4-6` 注明由 `styles.css` 拆出，客户制品不打包 `styles.css`（`RootApp.tsx:2-4`）。这是构建产物隔离的需要。
2. **`publishers/vendor/` 下的第三方库**（抖音/视频号发布，约 6,600 行）：是 vendored 第三方代码，有 `VENDOR-NOTES.md` 说明，不应按内部代码标准去重。
3. **`client/src/generated/api.ts`**：OpenAPI 自动生成，不手改。
4. **Alembic 迁移的 175 个文件**：即使有 `005_remove_provider_result_url` → `008_provider_result_url` 这种语义反复，也属"已发布迁移不可篡改"的红线范围，**只能追加**。
5. **`FirstFrameSelection.tsx` 与 `SourceFrameSelection.tsx`**：经逐行比对是不同职责（AI 生成首帧 vs 视频抽帧），不是重复。只有 25 行选中状态机可抽 hook。
6. **`deploy/` 的 `api-1/api-2`、`worker-1..4`**：同构副本，多实例部署的正常写法。

## 四、建议的清理顺序

分四批，每批独立可验证，避免一次性大改。

**第 1 批｜零风险，纯删除（约 3,200 行）**
删 2.1 节 A 类全部文件及其对应测试。跑 `npm run check:static` 验证。预期零业务影响。

**第 2 批｜修一致性缺陷**
先修 `formatStatus` 的 `PENDING` 文案冲突（用户可见），再合并 `apiBaseUrl` / `requestControl` 两份重复实现。这批改完对用户有直接价值。

**第 3 批｜抽公共函数（去重，不改行为）**
`_admin_to_current_user`、`is_customer_production`、`formatFen`、`errorMessage`、JPEG 尺寸解析。纯重构，靠现有测试兜底。

**第 4 批｜需业务确认后才能动**
① 人物域双轨是否下线旧轨；② 计费两套实现是否收敛；③ SQLite 通道是否整体下线；④ `generation.py` 拆分。

**不建议现在做的**：`generation.py` 拆 5 个模块、`api.ts` 拆分——收益是长期可维护性，但改动面极大，且当前没有覆盖足够的集成测试兜底。建议等前面三批稳定后再规划。
