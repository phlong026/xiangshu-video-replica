# 短视频复刻桌面端 V1.2 开发任务计划

> 计划版本：V1.2
> 制定日期：2026-08-13
> 当前状态：待开发执行
> 适用范围：内部员工使用的 Windows 桌面端 P0
> 唯一需求来源：短视频复刻桌面端开发任务书 V1.2
> 计划原则：若本计划与主任务书冲突，以主任务书为准

## 1. 开发目标

完成以下可运行闭环：

> 上传参考视频 → Gemini 拆解 → 编辑镜头卡片 → 选择人物 → 生成人物置换首帧 → 编辑口播稿与 H3 Prompt → 输入生成数量 N → 创建 N 个 H3 任务 → 查看批次进度条和单任务阶段 → 逐个获得并归档带 H3 原生音轨的 MP4

P0 固定技术边界：

- 桌面端：Tauri 2 + React + TypeScript；
- 业务服务：FastAPI；
- 数据库：SQLite；
- 对象存储：腾讯 COS 默认、阿里 OSS 可切换；
- 视频拆解：Apilio Gemini 3.1 Pro Preview；
- 首帧绘图：Apilio GPT Image 2 / Nano Banana Pro 2K；
- 视频生成：METASO MiniMax H3 图生视频；
- 音频：只使用 H3 成片原生音轨；
- 不实现文生视频、多对象参考、TTS、声音克隆、混音或口型同步；
- 生成数量由员工输入，受管理员安全上限控制；
- P0 采用轮询显示任务进度，不引入 WebSocket/SSE。

## 2. 执行原则

1. 先完成 Provider 与安全门禁，再进入真实 H3 闭环。
2. 新功能先写失败测试，再实现到测试通过。
3. 每个开发增量都必须保持程序可运行、数据库可迁移、已有测试通过。
4. Provider 调用必须有 FakeProvider，自动化测试不依赖真实付费模型。
5. 所有外部调用必须有超时、错误映射、脱敏日志和有限重试。
6. 不在客户端保存第三方密钥。
7. 不猜测 METASO 查询接口。
8. SQLite 只部署在服务端本机磁盘，使用 WAL 和短事务。
9. 不显示供应商未提供的虚假生成百分比。
10. 一次提交 N 个视频意味着 N 次独立付费 H3 调用。

## 5. 阶段 G0：开发前门禁

### G0-01 METASO H3 接口闭环

任务：

- 取得正式任务查询接口说明；
- 确认成功响应的状态和结果 URL；
- 确认是否支持取消或回调；
- 保存脱敏后的请求/响应样本；
- 验证 H3 I2V 返回 MP4 是否包含可播放原生音轨。

验收：

- createImageToVideo 和 queryTask 的真实字段均有证据；
- 不使用官网控制台专用下载 URL；
- 不存在猜测接口；
- 可完成“创建 → 查询 → 下载 → 归档”最小链路。

阻断规则：

- G0-01 未通过时，只能开发 FakeH3Provider；
- 真实 H3 查询适配器不得标记完成。

### G0-02 Apilio 模型门禁

任务：

- 验证 gemini-3.1-pro-preview；
- 验证 gpt-image-2；
- 验证 nano-banana-pro-2k；
- 验证 Gemini 视频 URL 输入；
- 验证 Gemini json_schema，不支持时确认 json_object 降级；
- 验证两种图片模型的重复 image 多图字段；
- 验证 Nano Banana 的 9:16 与 2K。

验收：

- 每个启用模型都有脱敏成功样本；
- 模型别名写入 Provider 契约测试；
- 不允许静默切换模型。

### G0-03 安全门禁

任务：

- 吊销已经暴露的 METASO 密钥；
- 创建新密钥并只放入服务端密钥存储；
- 确认 COS/OSS 使用私有桶；
- 确认内部员工登录来源和角色映射；
- 定义真实模型测试预算。

验收：

- 仓库、日志、截图和数据库中没有完整密钥；
- employee、admin、auditor 三类角色已确认；
- 真实测试有预算和负责人。

### A1-02 SQLite 基础

任务：

- 接入 SQLite；
- 配置 WAL、foreign_keys 和 busy_timeout；
- 建立 Alembic；
- 创建用户、项目、资产、版本、批次、任务、外部调用和审计表；

- 备份恢复后任务、版本和审计数量一致。

完成标准：

- data/app.db 在本机磁盘创建；
- Worker 重启可以恢复未完成任务；
- 每日备份任务可运行；

### C4-01 进度聚合 API

任务：

- 聚合 total_count、terminal_count 和 progress_percent；
- 聚合各状态数量；
- 批次状态；
- 单任务阶段和耗时；
- 结果完成后立即返回；
- 失败重试后的进度重新计算。

计算规则：

- FAILED、CANCELLED 计入 terminal_count；
- SUCCEEDED 且 ARCHIVED 计入 terminal_count；
- SUBMISSION_UNCERTAIN、ARCHIVE_FAILED 和进行中任务不计入；
- progress_percent=floor(terminal_count/total_count×100)。

测试先行：

- 全部等待；
- 部分完成；
- 全部成功；
- 成功与失败混合；
- SUBMISSION_UNCERTAIN；
- ARCHIVE_FAILED；
- 完成后重试导致进度重新计算；
- Worker 重启后聚合结果一致。

完成标准：

- GET /generation-batches/{id} 返回稳定进度契约；
- 客户端无需自行推测状态。

估算：3–4 人日。

## 15. 首个开发迭代建议

第一迭代只做：

1. G0 外部门禁；
2. A1 工程骨架；
3. SQLite 表、迁移、租约和备份；
4. FakeProvider；
5. 一个最小项目创建页；

第一迭代完成后，员工应能：

> 创建项目 → 输入生成数量 N → 创建 N 个假任务 → 看见任务从等待、运行到完成 → 关闭并重开软件后继续看到正确进度
